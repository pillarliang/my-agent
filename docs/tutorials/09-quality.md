# Quality：观测发生了什么，验证是否做对

## 1. 分开三个问题

**观测**帮助理解系统做了什么、时间花在哪里，**运行验证**检查本次结果是否满足指定条件，**评测**则通过一组任务比较版本与基线。三者需要配合，但回答的问题不同。

完整日志能解释过程，结果是否正确仍需检查产物；单个案例通过也只说明该条件与样本，需要更多任务才能判断整体质量。

## 2. MVP 的观测

SQLite 事件保存 Run、Step、调用 ID、工具名与结果码，`--trace` 将相同元数据实时写入 stderr，完整消息另行保存。这样可以按事件快速定位边界，再按需查看正文。

当前事件没有正式的 Span 身份、父子树与持续时间指标。后续可以增加 `EventSink` 或 `TraceSink` 适配器，把导出实现与 Loop 分开。

## 3. 三种观测方案

### JSONL 或 SQLite 事件

JSONL 或 SQLite 依赖少、便于本地检查，适合学习与单机应用；需要跨任务聚合、告警和可视化时，还要增加相应查询和展示能力。

### OpenTelemetry

OpenTelemetry 用 Trace 表示执行链、Span 表示模型或工具调用，便于关联服务、队列和 Worker。接入时需要同时控制属性大小、采样和敏感数据。

[GenAI 语义约定入口](https://opentelemetry.io/docs/specs/semconv/gen-ai/)持续演进，集成时应固定版本并验证字段映射，避免上游变化影响诊断与分析。

### 专用 Agent 观测平台

专用平台通常提供 Prompt、调用树、评测与数据集界面，可以减少界面开发，同时增加供应商和数据治理依赖。通过导出适配器接入，可以保留本地事件与平台之间的边界。

## 4. 运行验证的选择

文件存在、Schema、编译、测试与数值结果适合确定性检查；表达质量和相关性可以使用模型裁判；需求判断或高后果交付则常需要人工评审。应按任务能够取得的实际证据选择方式。

优先检查实际产物，开放式内容再引入模型裁判，并准备独立标准与校准样本。即使换一个模型，裁判也可能与执行模型共享盲点。

`FileContainsVerifier` 只检查前 8000 个字符，旧文件也可能通过。因此当前主结果只显示“已通过指定检查”，并保存目标、预期文字、读取结果与哈希。工具证据和模型说明分别展示；要证明本次写入，还需关联调用回执、产物版本和最终内容，详见[结果与验收说明](../13-results-and-evidence.md)。

## 5. 三层测试不要混用

### 代码测试

参数、路径、文件、上下文和存储可以直接用本地输入与真实资源测试，无需模型。例如，向执行器提交重复 JSON 键，检查是否拒绝；这类测试位于 `tests/`，不模拟模型响应。

### 协议契约测试

模型与协议集成测试使用真实 SDK 和服务端点，检查实际工具调用、结果关联、用量与错误。认证失败使用无效凭证访问真实接口，输出截断使用真实输出额度触发；无法稳定重现的异常会列入覆盖限制。

### 真实模型评测

真实评测固定任务、工作区与验收条件，记录成功、工具使用、用量、耗时和失败类型，观察 Prompt、工具说明与模型决策的效果。重要比较应重复运行并报告样本数，以反映非确定性波动。

## 6. 运行本项目评测

默认评测使用 DashScope `qwen3.8-flash`，调用与 Web、CLI 相同的 `AgentService`：

```sh
uv run python scripts/evaluate.py
```

脚本读取 `evals/cases.json`，在独立临时目录中运行三个真实任务，每例最多 8 次模型请求。模型名来自配置，所有调用会产生实际 API 用量。评测 OpenAI 时，在配置凭证后加入 `--provider openai`。

若只检查本地组件，可运行 `uv run pytest -m "not live"`；这会排除真实模型案例，直接测试文件、参数和存储，不会提供替代模型。

输出包含每例的验收、状态、Steps、已知用量和耗时，临时目录与原始数据库随后删除。如果需要长期比较原始轨迹，可以在下一阶段增加显式输出目录与模型配置快照。

## 7. 怎样比较优化

比较时一次改变一个主要因素，例如 Context 策略，并固定模型、任务、工具版本与评测器。质量、约束违反、用量、耗时和人工修正量应一起观察，才能解释收益与代价。

费用应分开计算输入、输出、缓存与额外工具费用；缺失用量报告为未知，避免用零或统一单价掩盖不确定性。

## 8. 动手练习

练习增加一份包含恶意指令的普通资料，检查是否出现未授权文件；再加入旧文件已经满足 contains 的案例，检验报告能否准确说明检查器的局限。

**验收条件：** 报告分别说明控制流、权限与任务质量，并给出各自证据，使你能够定位一次失败究竟发生在哪一层。

评测报告中的 `passed` 表示该案例的外部评测条件通过，`run_outcome` 则保留运行时结论。例如，读取案例可以由评测脚本核对正确标记，但没有配置运行时检查器的 Run 仍是未验证。两者各有检查范围，不能相互替代。
