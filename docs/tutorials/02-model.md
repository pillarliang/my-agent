# Model：把供应商协议留在适配器

## 1. 输入与输出

Model 接收 `Context`、请求超时和单次输出额度，返回统一的 `Reply`，或抛出公开 `ModelError`。Runner 只依赖这个协议，因此接入供应商时主要修改适配器与装配代码。

## 2. MVP 的两个真实模型适配器

`OpenAIModel` 使用 Responses API，将用户消息、完整模型输出项和函数结果转换为 API 输入。本地 SQLite 与 Context Builder 决定实际发送内容，不依赖服务端 `previous_response_id` 管理历史。

`DashScopeModel` 使用 OpenAI 兼容的 Chat Completions 协议，读取独立的 Key 与端点，并转换统一消息。当前默认模型 `qwen3.8-flash` 已通过真实工具调用验证，详见 [DashScope 教程](../12-dashscope.md)。

OpenAI Responses 适配器设置 `store=False` 并请求加密推理续接材料；DashScope 适配器使用非思考模式，不保存 `reasoning_content`。这是两种协议各自的处理方式，供应商数据政策仍由服务与账户条款决定。

## 3. 为什么必须保存完整输出项

一次响应可能包含文字、函数调用和续接材料。如果只保留 `output_text`，会丢掉调用；即使重建了函数调用，也可能遗漏推理模型继续执行需要的协议项。

OpenAI Responses 适配器将完整输出项存入 `provider_items`，下次按原顺序回传，再追加函数结果。核心不显示或解释私有推理，只保留协议需要的完整材料。

[OpenAI 函数调用文档](https://developers.openai.com/api/docs/guides/function-calling)说明了调用结果关联与推理项续接要求。协议测试会检查加密续接项和 `call_id` 的保留。

## 4. 三种适配方式

### 方案 A：供应商原生 SDK

原生 SDK 能直接暴露函数调用、响应状态与用量字段，代价是需要理解各供应商格式。本项目的 OpenAI 适配器采用这种方式。

### 方案 B：兼容统一接口

兼容 API 或代理可减少多模型试验中的接口差异，DashScope 就通过 OpenAI SDK 调用兼容的 Chat Completions 端点。不过，工具调用、并行参数、推理模式与错误字段仍需逐项验证。

### 方案 C：更严格的中立协议

中立协议为文字、调用、结果和能力定义共同类型，把供应商特有材料放入不透明字段，并拒绝后端不支持的能力。它适合长期维护多个后端，但会增加协议设计与兼容检查成本。

MVP 已通过 `Reply`、`ToolCall` 与 `provider_items` 实现了中立协议的简化版本，并用会话绑定防止不同模型或端点误用历史。后续可以先增加能力声明，再决定是否需要更完整的协议。

## 5. 流式响应是另一个状态机

流式响应可以提前显示文字，但参数可能分段到达，因此还需要独立的组装状态机。响应完成且完整参数通过校验后，适配器才能将调用交给执行器。

建议新增一个适配器内部累积器。

```text
response started
  -> 收集文字增量
  -> 按 item_id 累积函数参数
  -> 收到 completed
  -> 校验完整 JSON
  -> 返回 Reply
```

断流时应保存诊断并将响应标为不完整，已经收到的部分文字或 JSON 不能作为执行未完成调用的依据。

## 6. 错误与重试

MVP 关闭 SDK 自动重试，将网络、限流和认证错误映射为公开模型错误；不完整响应、拒答或不支持的输出也会结束 Run。先建立可观察的失败语义，再增加分类重试：

- 认证失败：直接停止，要求修正配置。
- 限流或暂时服务错误：按 Retry-After 或带抖动退避，有限重试。
- 上下文超限：修正输入，不能原样无限重发。
- 协议错误：保留诊断，不静默切换成文字解析。

重试可能计费，次数与时间应进入总预算。模型请求与工具副作用重试需要分别设计，后者还必须确认动作是否已经发生。

## 7. 动手练习

练习新增一个真实后端适配器，或为现有适配器增加流式组装。当前已有 DashScope 和 OpenAI 两个适配器；改变模型名只需要配置，新增协议能力则通过真实调用验证，并记录尚未触发的异常。

**验收条件：** 同一 Runner 能通过新后端完成读文件循环，测试覆盖完整调用、错误参数、拒答和不完整响应；流式实现还应覆盖断流。Runner 中不应出现供应商名称分支。
