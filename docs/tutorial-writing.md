# 教程补充与写作规范

本规范适用于所有模块的通用教程、阶段实践和代码说明，贡献者与代码助手均应遵循。

教程的第一宗旨是：**让读者用最低的认知成本，快速抓住核心本质与实现逻辑。**

## 核心优化原则（必须严格执行）

1. **拒绝翻译腔与生硬造词（自然、直击痛点）**
   - 严禁使用不符合中文母语直觉的别扭表达（例如把“多轮对话”说成“用户再次开口时”，把“保存历史记录”说成“留下交互材料”）。
   - 标题和正文必须直白、自然，直接点明“要解决什么问题”。

2. **交互与场景列表化（高信息密度）**
   - 凡是涉及“用户与模型的对话”、“多步操作流程”或“状态变化”，严禁写成一整段啰嗦的流水账文字。
   - 必须拆解为结构化的列表（如：`* **用户**：...`、`* **模型**：...`、`* *（系统动作）*`），让读者一眼看清复现路径。

3. **目标与标准直白化（拒绝公文/教条感）**
   - 将生硬拗口的“本轮完成标准”、“验收条件”等表述，统一转化为符合直觉的 **“期望达到的效果”**。
   - 采用 `**短语核心点**：一句话具体表现` 的列表形式呈现，做到边界清晰、一目了然。

4. **彻底剔除无关噪音（章节解耦、独立可读）**
   - 删除所有与当前小节核心主题无关的解释、跨章节的包袱或未出现的铺垫（例如：在讲“会话保存”时，突然去解释“不需要先做某文件读取实验”、“不需要准备某某 txt 文件”）。
   - 确保每一小节职责单一，读者无需依赖外部上下文就能完全看懂本节为什么出发、要解决什么问题。

### 参考示例（严格对齐此修改力度与行文风格）

#### 【修改前（反面教材）】

> 1. 起点：用户再次开口时，需要记住什么
> 先考虑一段不调用工具的对话。用户说：“这段对话里，请叫我星河。”助手回答：“好的，星河。”退出程序，再打开并追问：“我刚才让你怎么称呼我？”如果新请求只有这句追问，模型就没有依据知道“刚才”说了什么。
> 这里要解决两个需求：人能查到已经发生的交互；模型在后续提问时能得到相关历史。只让模型生成回答，还不能满足这两个需求。程序需要留下交互材料，并能在需要时找到它们。
> 本轮完成标准：第一问和回答在退出后仍可查询；同一会话的追问实际带入前面的消息；新建会话不会混入另一段对话；查询记录不请求模型，也不执行工具。
> 理解这一节只需知道：程序接收用户问题，向模型提交消息，取得响应，有时会执行模型提出的工具调用。无需先完成文件读取实验，也无需准备 notes.txt。业务文件的读取是可选工具行为；保存和加载会话自己的记录，是本节新增的职责。

#### 【修改后（标准范本）】

> ### 1. 问题起点：如何让程序记住聊过的内容？
>
> 默认情况下，无论是模型接口还是单次运行的程序，都是“无状态”的。考虑以下场景：
>
> * **用户**：“这段对话里，请叫我星河。”
> * **模型**：“好的，星河。”
> * *（退出程序，重新打开）*
> * **用户**：“我刚才让你怎么称呼我？”
>
> 如果此时只把最后这句话发给模型，模型没有任何前文依据，根本不知道“刚才”发生了什么。
>
> 要解决这个问题，系统必须满足两个核心诉求：
> 1. **给模型提供上下文**：同一会话后续提问时，自动带入前面的历史消息。
> 2. **供用户回溯历史**：程序退出重进后，依然能查到已经发生过的对话。
>
> 因此，程序不能只做“传话筒”，还必须负责**将对话记录持久化保存，并在需要时按会话加载**。
>
> **期望达到的效果：**
> * **记录可持久化**：退出程序后再打开，之前的问答记录依然可以查询。
> * **上下文自动延续**：在同一会话中追问时，程序会自动把历史消息一并传给模型。
> * **会话相互隔离**：新建会话时，绝不会混入其他会话的历史消息。
> * **查询不消耗算力**：仅查看历史记录时，直接读取本地存储，不请求模型。

## 读者与目标

面向第一次从零实现 Agent 的读者。先让读者理解问题、职责与选择，再沿源码完成一个可运行、可验证的小版本。

从 `examples/00_plain_loop.py` 逐步扩展。每次只落实当前阶段所需，区分设计参考、当前已实现与后续扩展。

## 原理比较与 MVP 实践的分工

模块教程帮助读者理解不同 Agent 怎样解决同一问题；阶段教程带读者实现当前所需的一个最小版本。了解多个方案与实现多个方案是两件事。

**模块原理按同一维度比较参考实现。** 优先结合 pi、Codex 等 Agent 的固定版本源码，沿一个贯穿的例子说明：

- 要解决的共同问题与必须保证的行为。
- 各自的术语含义、职责划分和数据结构；名称相同不代表含义相同。
- 谁产生数据，谁执行动作，怎样更新、保存、查询和重新用于模型输入。
- 方案适合什么需求、带来什么成本；哪些能力当前可以暂不采用。

引用具体源码位置，并区分源码事实与本教程的归纳。比较应围绕本模块的问题，不为凑出差异列举无关功能；参考实现相同时也如实说明。比较之后明确本项目当前选择与理由，不把参考项目的全部能力变成练习清单。

**阶段实践按依赖顺序交付 MVP（最小可用版本）。** 每个模块先确定最小职责、输入输出、与现有 Loop 的接入点和完成标准，只实现一种足以支撑当前闭环的方案。达到完成标准后推进下一模块，先将选定的核心模块串成可验证的端到端 Agent；整体跑通后，再按真实任务暴露的问题优化单个模块。

MVP 必须保留必要的权限检查、真实回执和明确的错误传播。会阻塞闭环、破坏正确性或权限约束的问题及时修复；不影响首版闭环的性能、复杂查询、分支、并发、恢复和扩展机制列为后续优化，并说明什么需求会触发它们。“整体搭建完成”以选定的核心范围为准，不要求先实现所有可选能力。

## 必须分清的三层内容

- **设计原则**：模块解决什么问题，承担什么职责，必须保证哪些行为。更换实现后，这些要求仍应成立。
- **可选实现方案**：有哪些相关选择，各自适合什么情况、带来什么成本。方案是选择，不是必须全部实现的功能清单。
- **当前代码实现**：本项目选了哪种方案、为什么选择、怎样接入、如何运行和验证。类名、配置字段、具体调用位置属于这一层。

例如 Policy 的原则是“被拒绝的动作不能执行”。规则用条件分支、配置匹配还是独立服务判断，是实现选择；本项目在 ToolRegistry 中调用 Policy，则是当前代码的接法。不能把这三层写成同一件事。

比较方案时先分清所比较的问题。Policy 中“怎样得到动作”与“怎样判断规则”是两个选择；注册时声明权限和用条件分支判断规则可以组合，不是互相替代的方案。沙箱约束执行环境，也不能当作权限判断的另一种写法。

每个模块都要说明与相关模块的交互：谁提供配置、谁发起调用、传递哪些数据、谁作决定或真正执行，以及失败怎样返回。直接调用与经 Runner 转交的数据分开说明，不能只列邻接模块名称；也不要求为尚未实现的职责提前创建类或接口。

当前选择须标明对应阶段和采用的方案组合。尚未实现的模块明确写“未选择／未实现”，将示意图与练习标为后续设计；已有会话记录、事件或工具注册基础，不等于已经具备长期记忆、独立观测或动态插件系统。

## 章节分工

- **模块通用教程**：讲问题、职责、设计原则、核心抽象、黑盒交互，再比较相关实现方案与取舍。
- **阶段教程**：说明问题起点、期望达到的效果、当前选定方案与理由、初始化和调用过程、源码入口与运行验证方式。
- **系统职责地图**：展示模块分工和当前进度，与学习阶段分开。状态必须与源码一致。

通用教程以稳定职责为主，不从当前类名、配置或函数签名开始。当前实现只作简短标注并链接到阶段实践；代码阅读顺序和实验命令集中放在阶段教程。

阶段教程开头直接切入本轮要解决的问题与**期望达到的效果**，再说明当前为什么选择这个实现。命令行参数、文件大小和平台限制放在运行或边界说明中。

通用使用与固定实验分开。用户描述任务即可；实验文件名、资料和验证条件由实验配置，不把它们写进通用 Agent 的职责，也不要在正文中插入与当前主题无关的跨章节免责解释。

## 讲解顺序

通用模块按以下顺序组织：

1. **问题与原则**：是什么、为什么需要、有什么用，缺少它会发生什么，必须保证什么。
2. **核心抽象与黑盒交互**：先用普通话解释输入、输出与职责，再按需命名。图中标明谁发起、谁决定、谁执行，以及失败如何返回。
3. **可选方案与取舍**：选择与当前问题相关的少量方案，说清适用情况与成本。不为凑齐分类列出无关机制，也不把别的方案一概写成错误。
4. **当前选择与实践入口**：明确标注“本项目当前选择”，简述理由并链接到阶段教程；未实现方案不能写成已有能力。

阶段实践按以下顺序组织：

1. **问题起点与期望达到的效果**：用结构化场景点明痛点，以 `**短语核心点**：一句话具体表现` 列出期望达到的效果。
2. **选定方案与理由**：引用通用原则，说明当前选法及其范围，不暗示这是唯一正确实现。
3. **初始化、调用与源码**：沿一次完整调用阅读。区分创建对象时传入的配置，与运行时交换的请求、动作和回执。
4. **运行与验证**：给出可执行命令、观察位置和预期结果，覆盖成功与有代表性的失败。

阶段的“初始化、调用与源码”应让读者找到当前代码的调用流程，以及函数与类之间的关系；按源码区分函数、类与协议，不把职责名称画成不存在的类。有数据库时，在对应阶段说明表的用途、字段、主外键、关联与关键约束，并链接建表源码。图和表配合具体任务解释保存时机与设计理由，详细约束可折叠，不复制整段实现。

通用图表达职责与数据方向，不要求某个具体类或文件存在。展示当前类名、方法或执行位置的图，须标注“当前实现”，放到对应实践中。两个图可以使用同一个例子，但不要混淆它们的用途。

## 内容与表达

- 正文直接解释问题、原理、数据关系、实现取舍和具体操作。不写“讲解顺序采用……”“本页讲……、另一页讲……”等编排说明，不复述写作要求、对话过程或修改计划；用标题和内容本身体现结构。链接应指向具体知识或操作，而不是用来宣告页面分工。
- 实现状态在必要位置简短标注一次，不反复插入“当前仅……”“尚未实现……”等提醒。技术限制、示例假设和失败条件放在对应问题处说明。
- 使用简洁中文和具体例子，先解释含义，再引入名称；不直接堆类名和字段。
- 专业术语采用通用译名；没有自然、准确的中文表达时保留英文并解释含义，不硬造译词。普通要求直接说“之前提出的要求”，避免“旧约束失去可见性”这类生硬表达。
- 通读标题、正文、表格、图注和 SVG 中的文字，保持同一概念的说法一致。缩写和专业术语首次出现时解释具体含义；不要用“身份”“边界”“治理”等抽象词代替实际的 ID、执行步骤或处理动作。
- 用一个贯穿的例子说明“谁提交什么、谁怎样回答、谁真正去做”。同一例子的文件名保持一致。
- 新术语用一句普通话说明作用；不能用另一个抽象术语解释它。
- 原理保留必要的动机与数据关系，代码细节链接源码；不能只剩源码链接，也不长段复述源码。
- 实现只在源码维护。教程不复制已有函数，不用伪代码、职责表或字段表代替讲解；简短接口用法可用于解释如何接入。
- 不写旧版本迁移过程或反复比较历史实现。替代方案写成设计选择，当前选择和未实现范围写清楚。
- 区分参数合法、动作获准、执行成功和成果正确。模型文字不能代替真实回执与实际文件检查。
- 精简重复。复杂但非起步必需的方案放到折叠区，不能用未来蓝图压过当前学习主线。

## 本项目当前实践约定

这些是当前版本的选择，不作为所有 Agent 或其他模块必须采用的设计原则。

- 阶段 2 用“允许新建、禁止覆盖”验证 Policy，确认拒绝后原文件未变。当前代码实现到阶段 4；阶段 3 从纯对话推导会话与记录，不引入 Context 管理、独立成果验收模块或固定报告实验。
- 阶段 3 为“会话与记录”，阶段 4 为“上下文管理与预算”，阶段 5 为“用 Memory 跨会话复用项目知识”；阶段 6–8 分别为长任务机制、安全恢复、入口与扩展。阶段 3 从问题推导设计并对照现有源码；阶段 4 已实现按完整任务裁剪、必需历史保护与每次请求前预算检查；计量与 SDK 共用编码，以 UTF-8 字节数保守估算，不冒充精确 Token 数。不能把持久存储写成预算管理的必需依赖。
- 阶段 3 与阶段 4 正文分别维护在 `stages/stage-3.html`、`stages/stage-4.html`，左侧目录分别列出；原 3A / 3B 页面只保留旧地址跳转。移动章节后同步直接链接，并保留旧锚点跳转。
- 当前工具是普通函数，注册时用数据声明所需权限和路径参数名；共享代码生成 ActionRequest，注册表统一调用 Policy 后才执行。教程须解释“需要权限”不等于“已经获准”。
- 工作目录和 Policy 在创建注册表时由应用传入；运行时 Runner 提交 ToolCall、接收 ToolResult。初始化依赖与消息协议分开说明。
- 阶段 3 先用独立的纯对话说明需要记录什么，再推导顺序、会话归属、任务结束状态、保存与查询，最后接入 Loop；工具调用作为可选扩展，不依赖前面读取固定文件的实验。先解释需求，再引入 Session + 用户任务 Turn + 有序记录，不预设三张表，也不从最终字段倒推需求。会话保存与查询已实现，运行命令必须对照源码。保留历史不意味着自动恢复中断任务。
- 新增或修改其他模块时也按三层组织。选用不同实现时，更新当前选择与阶段说明，不把具体实现抬升成通用原则。

## 文件与维护方式

教程总目录是 [tutorial.html](tutorial.html)。阶段正文直接维护在 `stages/`，模块原理在 `modules/`，扩展导读在 `guides/`，参考资料在 `reference/`；每章只有一个正文来源，通过相对链接互相引用，不在总目录复制整章。

共享样式和交互维护在 `assets/tutorial.css` 与 `assets/tutorial.js`；复用图示各自维护为 `assets/diagrams/` 下的 SVG，章节专用简图也可直接写入 HTML。正文与图源分开存储，但阅读时图、解释和练习仍放在一起。页面可直接用浏览器打开，不增加文档构建流水线。

编辑时先定位并读取有关章节，只有修改样式、交互或图示时才读取对应资源；避免将全书正文和图源一次塞入工具输出。目录搜索匹配章节标题，不跨页加载全文；新增章节时同步各页目录。总目录的旧锚点兼容由 `assets/legacy-links.js` 维护。

[README](../README.md) 保留入口、阅读导航和运行方式。本文件维护写作规范，具体模块原理放回教程。Harness 职责地图中的模块范围和状态以源码为准。

## 提交前检查

- 删除不能帮助理解原理、比较实现或完成操作的句子；正文不复述讲解计划、章节分工和写作规范。
- 暂时忽略类名和函数名，读者仍能说清模块解决的问题与必须保证的行为。
- 通用原则、可选方案、当前选择分别标明；读者能指出哪些可以替换，哪些要求不能丢失。
- 参考 Agent 按共同问题比较实现原理，有对应源码依据；未采用方案没有被写成当前实现任务。
- 当前阶段只要求完成可接入整体闭环的模块 MVP；局部优化与可选能力明确列为后续，不阻止进入下一模块。
- 当前选择有理由、有源码依据；当前图示与接口名称对应代码，未实现方案有明确标注。
- 初始化与运行时调用分开说明；不能把配置包装或检查所在文件当成必需协议。
- 阶段命令可复制执行，预期结果包含真实回执或文件的观察方式。未运行的实验不得写成已验证。
- 区分本地文件与协议检查、真实模型表现。真实 API 调用须说明用量；不以固定协议响应证明模型能力。
- 检查 HTML 结构、锚点、源码链接和 SVG 引用。
