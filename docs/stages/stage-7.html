阶段 7：按需求增加入口、扩展与编排

在单 Agent 核心闭环稳定运行的基础上，按实际业务场景选择性接入 Web 入口、能力扩展（Skills / Hooks / MCP）或多 Agent 编排。

1. 应用入口：让 CLI 与 HTTP 共用执行核心

1.1 现有 CLI 入口与后续扩展接入位置

当前入口为命令行 main()：负责接收参数、调用 run_task() 推进 run_agent()，或直接查询会话记录（见阶段 3）。

1.2 新增 HTTP 入口的调用流程

  1. 请求校验与会话定位：HTTP 接口接收任务描述与可选会话 ID；未指定 ID 时新建会话，指定 ID 时核对工作目录与权限配置。
  2. 执行与查询分离：提交任务走 run_task()（耗时任务可交由后台或队列执行并立即返回任务 ID）；历史查询直接调用只读记录接口，绝不触发模型或工具。
  3. 实时进度观察：通过 SSE 或轮询读取已提交的执行进度；客户端断开观察连接不等于取消后台正在运行的任务。
  4. 按需挂载扩展或编排：外部工具通过适配器统一返回 ToolResult；Hooks 在固定生命周期节点触发；子 Agent 编排则显式管理父子任务 ID、权限边界与结果汇合。

1.3 扩展所需的状态数据

引入异步 Web 入口或多 Agent 编排时，再按需补充后台任务状态、事件游标、取消标记或父子任务关联字段（注：仓库中的 serve_tutorial.py 仅用于本地预览静态教程网页，不提供 Agent 运行 API）。

1.4 入口设计核心原则

无论通过 CLI 还是 Web 提交任务，底层都应复用同一套应用服务、权限规则与会话记录；任务提交、只读查询与进度观察三条路径职责分明。

2. 能力扩展：Skills、Hooks 与 MCP

  • Skills（方法复用）：将特定领域的任务流程整理为按需加载的指导文档，减少常驻系统指令体积。
  • Hooks（生命周期拦截）：在模型请求前后或工具调用前后注入观测、审计或参数检查逻辑。
  • MCP（外部工具接入）：通过标准协议连接外部工具服务，转换为内部统一的 ToolSpec 与 ToolResult，并继续受 Policy 與预算约束。

3. 多 Agent 编排：Graph 与子任务委派

  • 显式工作流（Graph）：适合步骤固定、包含确定性检查或人工审批节点的业务流程。
  • 子 Agent 委派（Subagents）：将大量搜索或独立评审工作交给拥有独立上下文窗口与受限权限的子 Agent，主 Agent 仅接收结构化结论与证据引用。

4. 期望达到的效果

  • 多入口行为一致：CLI 与 Web 入口共用同一套权限控制与执行逻辑，查询与断线重连不会误触发重复执行。
  • 扩展受控不越权：接入的 Skills、Hooks 或 MCP 工具严格遵守主程序的 Policy 权限与输入预算限制。
  • 编排收益可量化：引入多 Agent 或扩展机制后，能与单 Agent 基线对比质量、Token 消耗、耗时与协调开销，证明新增复杂度物有所值。
