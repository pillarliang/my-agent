阶段 3：会话与记录

1. 问题起点：如何让程序记住聊过的内容？

默认情况下，无论是模型接口还是单次运行的程序，都是“无状态”的。考虑以下场景：

  • 用户：“这段对话里，请叫我星河。”
  • 模型：“好的，星河。”
  • （退出程序，重新打开）
  • 用户：“我刚才让你怎么称呼我？”

如果此时只把最后这句话发给模型，模型没有任何前文依据，根本不知道“刚才”发生了什么。

要解决这个问题，系统必须满足两个核心诉求：

  1. 给模型提供上下文：同一会话后续提问时，自动带入前面的历史消息。
  2. 供用户回溯历史：程序退出重进后，依然能查到已经发生过的对话。

因此，程序不能只做“传话筒”，还必须负责将对话记录持久化保存，并在需要时按会话加载。

期望达到的效果：

  • 记录可持久化：退出程序后再打开，之前的问答记录依然可以查询。
  • 上下文自动延续：在同一会话中追问时，程序会自动把历史消息一并传给模型。
  • 会话相互隔离：新建会话时，绝不会混入其他会话的历史消息。
  • 查询不消耗算力：仅查看历史记录时，直接读取本地存储，不请求模型、也不执行工具。

2. 需要保存哪些对话数据？

要完整还原一段对话，不能只记用户的问题（否则查不到当时的回答），也不能只记最后答案（否则丢了最初的前提要求）。起步至少需要按顺序保存以下内容：

  • 用户输入（TextMessage）：记录每次提问的原始文本与角色。
  • 模型完整响应（ModelResponse）：不仅包含回答文字，还包含工具调用请求、停止原因、Token 用量及协议续接数据（continuation data），不能简单压成一个纯文本字符串。
  • 严格的先后顺序：先说“请叫我星河”再说“改叫我小河”，颠倒后结果完全不同。时间戳仅作参考，必须用递增序号保证顺序确定。

包含工具调用的对话还需要存什么？

当对话中触发了工具调用时，交互过程会变成多步：

  • 用户：“当前工作目录有哪些文件？”
  • 模型：发起 list_files 工具调用（包含工具名、参数与 call_id）。
  • （工具在本地执行，返回真实文件列表或失败原因）
  • 模型：根据工具回执给出最终回答。

为了核对“模型打算做什么”与“工具实际执行了什么”，还必须原样保存真实工具回执（ToolResult），并通过 call_id 与对应的工具调用关联。权限拒绝或执行报错也是真实发生的结果，必须如实记录，绝不能用模型口头回答的“已成功”代替真实回执。具体数据结构见模型契约与工具契约。

3. 如何归组多次提问并判断任务是否结束？

仅有消息列表还不够，系统还需要通过两层边界来组织记录：

  • 会话（Session）——隔离不同对话：如果把所有提问混在同一条历史里，新话题就会被旧对话干扰。因此为每段连续对话分配唯一标识（session_id），同一 ID 追加并读取同一份记录，新建会话则从空白历史开始。
  • 单次任务（Turn）——标记一次提问的起止状态：考虑程序运行到一半意外退出的场景——用户问题已落盘，但模型还没回答。下次重开时，不能因为文件里有几条记录就误以为上次提问已经完成。因此将“从接收一次用户提问，到完成回答或报错停止”的过程定义为一个 Turn。

每个 Turn 显式记录开始与结束状态：

  • completed（正常完成）：本次提问的消息与工具调用链已完整闭合（注：若工具被 Policy 拒绝，模型如实告知用户并结束回答，对话过程本身依然完整，状态同样记为 completed）。
  • failed（执行失败）：执行途中发生异常并中止。
  • 未结束（仅有开始、无结束记录）：进程中途中断，留存记录供排查，但不会混入后续模型上下文。

本项目当前选择：Session + 用户任务 Turn + 有序记录。这一结构直接满足对话隔离、消息归组和未完成任务识别的需求，无需额外引入 Run、Step 或独立事件表。

其他 Agent 的命名是否一样

不一定。pi 的 turn 接近一次助手响应及其工具结果，Codex 的 turn 接近一次用户任务。本项目采用后者的尺度。固定版本源码中的术语对照说明了区别；名称相同不代表数据范围相同。

4. 持久化格式：为什么选择单会话 JSONL 文件？

进程退出后内存数据会清空，因此必须将记录写入持久化存储。本项目当前选择“一个会话对应一个 JSONL 文件”（默认路径为 .learn-agent/sessions/<session_id>.jsonl），每行一个 JSON 对象，新记录直接追加到文件末尾。相比一开始就引入数据库，纯文本 JSONL 零外部依赖、方便直接打开核对顺序与内容；待后续遇到海量会话筛选或并发写入需求时，再演进到 SQLite。

JSONL 文件的记录结构

  • 首行文件头（SessionHeader）：记录格式版本、session_id、绑定工作目录 workspace 与创建时间。绑定工作目录是为了防止续接会话时误切到另一个目录环境。
  • 后续有序条目（Record）：每行通过 seq 固定递增顺序，turn_id 标记所属任务，time 记录时间，type 区分三类条目：
    • turn_started：标记一次用户提问开始。
    • message：在 payload 中用 kind（user / assistant / tool_result）和 value 保存完整消息或回执。
    • turn_finished：记录任务结束状态（completed / failed）及失败原因。
一条用户消息的包装示例
{
  "seq": 2,
  "turn_id": "T1",
  "type": "message",
  "time": "2026-10-25T01:00:00Z",
  "payload": {
    "kind": "user",
    "value": {"role": "user", "content": "这段对话里，请叫我星河。"}
  }
}

T1 只是便于阅读的代号，实际任务 ID 由程序生成。会话 ID 位于首行文件头，不在每条记录里重复。

系统指令（System Prompt）、模型连接、工具注册表和 Policy 属于当次运行的初始化配置，每次请求模型时动态组装，不重复写入用户历史消息中。

5. 写入时机与异常处理

如果等到最终回答生成后才一次性保存，中途一旦出错就会丢失已发生的交互过程。因此程序采用边执行边追加写入（flush）的策略：

  1. 任务启动时：立即写入 turn_started 与用户输入消息。
  2. 模型返回时：先将完整 ModelResponse 写入文件，再检查停止原因（即便遇到拒答或截断，原始响应也已留存供排查，但不会继续执行其中的工具调用）。
  3. 工具执行后：将真实 ToolResult 写入文件。
  4. 任务结束时：正常完成写入 completed；捕获到异常时写入 failed 及报错信息，再将原异常继续抛出。

可靠性与边界约束：

  • 单写者独占锁：每个会话文件通过文件锁限制同一时刻只有一个写入者，避免多进程追加导致序号交错。
  • 损坏立即报错：读取时若发现未知版本、序号断层或末尾残行，直接抛出明确错误，绝不静默降级为空历史。
  • 非事务边界：进程被强杀（如 SIGKILL）时可能来不及写入结束条目，此时该 Turn 保持“未结束”状态；本地文件动作与日志追加也不在同一事务内，断电等极端情况下需在恢复阶段核对外部状态。

6. 读取路径：如何支撑历史查询与多轮续接？

保存下来的 JSONL 文件服务于两条不同的读取路径：

  • 供用户查看历史：会话列表只需读取每个文件的首行文件头和修改时间，无需加载全部消息；查看单会话详情时，校验版本与序号后原样返回全部记录（包括失败和未结束的任务片段），全程不请求模型、也不重新执行工具。
  • 供模型续接上下文：按顺序筛选出状态为 completed 且消息链完整的任务，还原为模型可接收的消息列表。失败或未结束的任务片段仅留存供人工排查，不混入模型后续输入；若某任务标记为 completed 却缺失配对的工具回执或最终回答，则直接报告文件损坏。

完整复现路径：“请叫我星河”的两轮对话

  1. 第一轮提问（新建会话 S1，创建任务 T1）：
    • 发给模型的输入：[系统指令, 用户："这段对话里，请叫我星河。"]
    • 追加写入文件：T1 开始 → 用户消息 → 助手响应 → T1 正常结束。
  2. 退出重开并追问（指定会话 S1，创建任务 T2）：
    • （系统动作：定位 S1 文件，校验版本与工作目录，提取已完成的 T1 消息）
    • 发给模型的输入：[系统指令, 第一问, 第一答, 本次追问："我刚才让你怎么称呼我？"]（共 4 项输入）。
  3. 取得第二轮回答并结束：
    • 追加写入文件：T2 开始 → 本次追问 → 助手第二答 → T2 正常结束（T1 的历史仅在请求模型时读取引用，不会重复写入文件）。

两轮问答结束后，会话文件内共有 1 个文件头和 8 条记录（其中 4 条是消息记录）。查询会话详情会展示全部 8 条记录，而第二轮发给模型的是筛选还原后的 4 项上下文输入——磁盘记录格式、查询展示视图与模型请求输入各司其职，不能把文件每一行原封不动直接丢给模型。

同理，加载历史中的工具回执只是把过去发生过的观察结果放回上下文，不会重新调用工具；若用户再次询问当前目录状态，模型仍会发起新的工具调用。当历史消息不断累积、接近上下文窗口上限时，则进入阶段 4：上下文管理与预算。

7. 源码实现：将 SessionLog 接入 Agent Loop

会话的保存、查询与历史重建统一封装在 session.py 中；Loop 继续专注推进当前任务，在关键节点调用会话接口记录数据。

沿一次调用对照源码

  1. 入口分流（main()）：区分查询与执行。若是查询命令，直接调用 read_session() 或 list_sessions() 打印结果并返回；若是执行任务，则新建或打开指定 SessionLog，传入工作目录与 Policy。
  2. 环境核对（run_task()）：核对会话绑定的工作目录与当前配置一致，随后创建 ToolRegistry 和 LLMService，调用 run_agent()，并在退出时关闭模型连接。
  3. 加载历史与启动任务（run_agent()）：先调用 session.history_turns() 取出已完成的历史任务块；再调用 start_turn() 记录本次任务开始与用户提问，避免重复加载本次问题。history() 保留平铺消息的查询接口；请求前的预算筛选见阶段 4。
  4. 记录模型响应与工具回执：每次 model.invoke() 返回后，先调用 append_message() 保存完整响应；若需执行工具，经 tools.execute() 完成校验、授权与执行后，再调用 append_message() 保存真实回执。
  5. 记录任务结论（SessionLog）：拿到有效最终回答后调用 finish_turn()，校验消息链完整后写入 completed 并更新内存可用历史；若中途抛出异常，则写入 failed 及原因后继续向外抛出。

阅读源码时，建议先看 SessionHeader / Record 的数据结构，再看 start_turn()、append_message()、finish_turn() 的写入逻辑，最后看 _history() 如何筛选并还原已完成任务。Session / State 模块原理对比了本项目与 pi、Codex 源码的实现取舍。

8. 运行与验证

在项目根目录执行以下命令（前两条会请求真实模型并产生 API 用量，需按 README 配置环境变量）：

uv run python -m learn_agent "这段对话里，请叫我星河。"
uv run python -m learn_agent --session <第一条输出的会话ID> "我刚才让你怎么称呼我？"

再执行本地只读查询命令（不请求模型、不执行工具、无需配置模型密钥）：

uv run python -m learn_agent --list-sessions
uv run python -m learn_agent --show-session <同一个会话ID>

运行本地自动化测试（使用本机固定协议响应与临时文件，不请求外部模型）：

uv run pytest tests/test_session.py
uv run python scripts/check_docs.py

期望达到的效果

  • 记录可往返还原：写入一问一答并正常结束后，关闭再重开会话，读取出的消息字段与原内容完全一致。
  • 追问自动带入历史：同一会话第二次提问时，实际发给模型的请求按顺序包含 [system, user, assistant, user]；新建会话则从空历史开始，互不混入（见 test_session.py）。
  • 查询零副作用：执行 --list-sessions 与 --show-session 时，不创建模型连接、不调用任何工具，且原会话文件内容不会增加。
  • 工具调用链完整关联：包含工具调用的对话能完整保存模型调用请求、call_id、真实回执与最终回答；续接历史时直接复用已有记录，不会重复执行旧工具。
  • 失败与损坏边界清晰：模型报错、工具拒绝或未结束任务都会留存可查询的记录，但失败或未结束的任务绝不会混入后续模型上下文；遇到未知版本、序号断层或末尾残行时明确报错停止。
