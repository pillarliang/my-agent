阶段 0：跑通独立的最小 Agent Loop

打开 examples/00_plain_loop.py，从 run_agent() 开始看。

1. 一次循环

模型根据本次请求里的 messages 了解任务进展。工具在本地执行后，程序要把真实结果写回消息链；下一次请求时，模型才能据此继续判断。

2. 阅读循环

打开 00_plain_loop.py，定位 run_agent()。

阅读时先抓住两个分支：模型提出工具调用，就执行并带着结果继续；没有工具调用且有非空文字，就返回说明。请求次数上限保证循环能够停止。

assistant.tool_calls[].id 与 tool.tool_call_id 表示同一次调用。先记录模型提出的调用，再记录对应回执（工具实际返回的内容或错误），下一次请求才能知道每个结果属于哪个动作。

2.1 当前函数与 SDK 类的关系

本阶段所有业务逻辑都在 00_plain_loop.py。main()、run_agent()、execute_tool() 和 read_file() 都是普通函数；没有自定义 Runner、ModelAdapter 或工具类。OpenAI 是 SDK 提供的客户端类，消息是 API 格式的字典。

2.2 从启动到返回的实际顺序

  1. main() 加载配置，创建 SDK 客户端，把任务、模型名和工作目录传给 run_agent()。
  2. run_agent() 创建含 system 和 user 的 messages，直接调用 client.chat.completions.create()。
  3. 检查停止原因、拒答和工具调用类型。正常响应以 assistant 字典加入内存；如果没有工具调用，非空文字作为最终答案返回。
  4. 有工具调用时，execute_tool() 检查工具名、JSON 和 path，再调用 read_file() 读取真实文件。预期读取失败变成失败回执，程序错误继续向外抛出。
  5. Runner 把回执序列化为 tool 消息，通过 tool_call_id 关联调用，加入下一轮请求。达到次数上限仍没有最终回答则报错；退出时关闭 SDK 客户端。

2.3 数据放在哪里

TOOLS 是内存中的工具声明列表，messages 是一次运行的消息列表。notes.txt 是被读取的资料文件。本示例不导入 learn_agent，也不创建 SQLite 表；退出后消息列表不会保留。持久记录的字段与表关系在 阶段 3A 引入。

3. 安装、配置与运行

需要 Python 3.12 或更新版本与 uv；在项目根目录执行。按 .env.example 配置有效的 DashScope Key、匹配的 HTTPS 端点和可用模型。已有环境变量优先，已有 .env 可以复用。

项目根目录执行
uv sync --locked
uv run python examples/00_plain_loop.py

运行会请求真实模型并产生用量。默认最多四次请求，关闭 SDK 自动重试。模型会看到读取到的资料；示例工作区只放可用于本次学习的文件。

4. 阅读工具实现

在同一文件中，按 execute_tool() → read_file() 的调用顺序阅读。

工具参数来自模型，属于外部输入，因此在 execute_tool() 入口校验。read_file() 专注文件读取与资源范围，这样可以单独测试，也方便以后复用。

文件不存在等预期失败也作为回执交给模型，给它修正请求的机会。模型请求失败或响应未正常结束时，循环则停止；不能把失败改写成成功或空内容。

5. 通过实验理解完整循环

  1. 读取 notes.txt，观察第一次调用、真实文本回执和下一轮输入。
  2. 请求不存在的文件，观察失败也能成为模型反馈。
  3. 在本地测试越界路径、非 UTF-8 或过大文件，观察工具拒绝结果。
  4. 让本地协议响应持续请求工具，验证 max_steps 会停止循环。
不请求外部模型的本地检查
uv run pytest
uv run ruff check learn_agent examples scripts tests
uv run mypy
uv run python scripts/check_docs.py

本地测试使用实际 SDK 和本机 HTTP 服务检查消息协议，工具读取真实临时文件。它验证程序行为，不证明真实模型一定会选择正确工具。真实模型表现需单独运行示例观察。

6. 完成条件

你能指出哪行发送模型请求、哪行实际读取文件、哪行把结果送回去，并能解释正常回答、读取失败与请求次数耗尽，就完成阶段 0。
