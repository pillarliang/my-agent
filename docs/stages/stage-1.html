阶段 1：拆分单文件，定义模块接口

在阶段 0 的单文件脚本里，循环控制、SDK 协议转换和文件读取混写在一起——每新增一个工具就要改一次 if/else 分发，切换模型服务也要改动主循环。本阶段将单文件拆分为三个职责单一的模块：Tools 负责工具注册与执行，Model 负责模型通信与协议转换，Runner 负责推进循环。

1. Tools：定义工具，统一注册与执行

通用原理见 Tools 模块教程。在当前实现中，ToolDefinition 保存工具名、功能说明、参数模型、执行函数与权限声明；ToolRegistry 按名称查找工具，统一完成参数校验、权限检查（阶段 2 展开）、函数执行与回执封装。当前默认注册 list_files、read_file、search_text 和 write_file 四个工具。

  1. 工具接口契约（contracts.py）：定义 ToolDefinition、ToolSpec、ToolCall、ToolResult 与 ToolExecutor 协议。
  2. 工具注册表（registry.py）：负责工具注册、Schema 生成、参数校验、统一权限检查与异常转换。
  3. 本地文件工具（filesystem.py）：各个工具均为普通函数，共用工作目录路径与资源检查。

所有工具在当前进程内同步执行：非法参数和预期的文件操作失败统一包装为 ToolResult 回执返回给模型；重复注册或代码 Bug 则直接抛出异常。

展开当前工具执行流程

如何新增工具：只需编写一个普通 Python 函数，定义参数模型、所需权限和路径参数名，再调用 register() 注册即可，无需修改 registry.py 或 Runner。

2. Model：统一请求与回复，隔离 SDK 协议

通用原理见 Model 模块教程。当前由 LLMService.invoke() 接收统一的 ModelRequest，返回 ModelResponse 或抛出 ModelError。API Key、Base URL 与 SDK 客户端生命周期均由服务内部管理，并通过 OpenAIChatModel 适配 Chat Completions 协议。

  1. 模型接口契约（contracts.py）：定义 Model 协议、ModelRequest、ModelResponse 与内部消息类型。
  2. 模型服务（service.py）：LLMService 在初始化时读取配置并创建 SDK 客户端，通过 invoke() 转发请求，通过 close() 释放连接。
  3. 协议适配器（openai_chat.py）：负责将内部消息编码为 SDK 格式、发起网络请求、解码响应并转换异常。

每次模型响应除了保留文本、工具调用 ID、停止原因和 Token 用量外，还会原样保留 continuation data（模型服务要求在下一轮请求中继续携带的协议数据，如推理项），并在下一轮请求时由适配器自动编码带回。遇到输出截断、拒答、协议错误或连接失败时，直接抛出错误停止循环。

3. Runner：通过统一接口串联模型与工具

从入口 main() 到 run_task()，应用层按顺序完成组装：接收用户任务 → 配置工作目录 workspace 与权限 policy → 创建 ToolRegistry 与 LLMService → 调用 run_agent() → 在 finally 中关闭模型连接并返回结果。

进入 run_agent() 后，Runner 自身不再耦合任何 SDK 字段或具体工具函数，只按固定步骤推进循环：

  1. 请求模型：读取工具注册表的 specs，连同当前消息序列组装为 ModelRequest，调用 model.invoke()。
  2. 保存并检查响应：将完整的 ModelResponse 加入消息序列，确认响应正常结束。
  3. 分发工具调用：若响应包含 ToolCall，逐个交由 tools.execute() 执行，将返回的 ToolResult 追加到消息序列，继续下一轮模型请求。
  4. 返回最终结果：若无工具调用且回答非空，则返回包含最终回答与工具回执列表的 RunResult；若达到步数上限仍未结束，则报错停止。

模块间的黑盒契约详见 Runner ↔ Tools 与 Runner ↔ Model。

3.1 对照源码看函数、类与协议

main()、run_task() 和 run_agent() 是函数；LLMService 持有 SDK 客户端与 OpenAIChatModel 适配器；ToolRegistry 持有按名称索引的 ToolDefinition；Model 与 ToolExecutor 则是 Runner 依赖的接口协议（Protocol）。

3.2 沿一次 read_file 调用追踪完整链路

  1. 组装注册表与模型服务：run_task() 创建 ToolRegistry(DEFAULT_TOOLS, workspace, policy)（根据参数模型生成工具 Schema）与 LLMService，一并传给 run_agent()。
  2. 编码并请求模型：Runner 构造 ModelRequest 调用 LLMService.invoke()，内部委托 OpenAIChatModel.invoke() 完成消息编码、SDK 调用与响应解码，返回 ModelResponse。
  3. 校验并执行工具：Runner 将 ToolCall 交给 ToolRegistry.execute()。注册表完成参数校验与 Policy 权限检查后，调用 read_file() 读取文件，将结果封装为 ToolResult 返回。
  4. 进入下一轮并收尾：完整模型响应与工具回执进入下一轮请求；得出最终回答后返回 RunResult，并在 finally 块中关闭模型服务连接。

3.3 运行期数据保存在哪里

工具定义、参数对象与网络连接均保存在内存中；单次任务的消息序列维护在 Runner 内存列表里（跨进程持久化保存见阶段 3）。

4. 运行与验证

项目根目录执行 · 沿用 .env 配置，会请求真实模型
uv sync --locked
uv run python -m learn_agent "在资料中找到验收标记，告诉我来源和行号"

期望达到的效果

  • 模块解耦可扩展：新增工具只需编写普通函数并调用 register()，无需修改 registry.py 和 Runner；替换模型协议适配器也无需改动任何工具实现。
  • 调用与协议数据完整传递：工具回执通过 call_id 精确关联，模型完整响应与 continuation 协议数据自动带入下一轮请求。
  • 错误边界严格分流：预期的工具执行失败作为回执反馈给模型；模型输出截断、拒答或网络请求失败则立即停止，绝不误触发工具执行。

在本地执行 uv run pytest，对应单元测试见 test_tools.py 与 test_models.py。
