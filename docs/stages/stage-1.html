阶段 1：拆分单文件，定义模块接口

把单文件循环拆成三个职责：Tools 执行工具，Model 请求模型，Runner 控制循环。本阶段已将 Tools 和 Model 拆成独立模块，下面按当前代码说明它们如何接入 Runner。

1. Tools：定义工具，统一注册与执行

原理与接口见 Tools 通用教程。ToolDefinition 保存工具名、用途、参数模型、执行函数和权限声明；ToolRegistry 按名称找到注册项，统一校验、询问 Policy、执行并返回回执。当前注册 list_files、read_file、search_text 和 write_file。

  1. 工具接口定义：先读 ToolDefinition、ToolSpec、ToolCall、ToolResult 与 ToolExecutor。
  2. 注册表：看注册、声明生成、参数校验与异常转换；其中统一权限检查见阶段 2。
  3. 文件工具：各工具使用相同定义方式，共用资源访问检查。

执行在当前进程内。非法参数和预期执行失败返回回执，注册错误和程序错误向外抛出。

展开当前工具执行流程

增加工具：编写普通函数，指定参数模型、所需权限和路径参数名，再调用 register()。不修改 registry.py 或 Runner。

2. Model：统一请求与回复，隔离 SDK 协议

原理与接口见 Model 通用教程。当前由 LLMService.invoke() 接收 ModelRequest，返回 ModelResponse 或抛出 ModelError。服务内部管理 API Key、Base URL 和 SDK client，并使用 OpenAIChatModel 适配现有 DashScope 调用。

  1. 模型接口定义：先读 Model 接口、请求、回复与消息类型。
  2. 模型服务：LLMService 在构造时读取配置并创建 client，invoke() 发起请求，close() 释放连接。
  3. 协议适配器：看消息编码、SDK 请求、响应解码与错误转换。
  4. 跟着一次工具调用，观察回复中的文字、调用 ID、停止原因和 continuation 数据如何被保存，再用于下一轮请求。

第一版支持一次性返回文本和函数工具调用，记录供应商报告的用量。每次请求只有一次网络尝试；截断、拒绝、协议错误与连接错误都明确停止。路由、熔断与降级后续迭代。

这里的 continuation data 指模型服务要求在后续请求中继续携带的协议数据，例如响应中的推理项；需要按该服务的协议保存和传递。

3. Runner：通过接口连接两个系统

从 main() 顺着读：接收任务 → 设置工作区和权限 → 调用 run_task() → 展示结果。工作目录 workspace 与权限 policy 作为两个参数传入。

run_task() 用提前写好的 DEFAULT_TOOLS、工作目录 workspace 和权限 policy 创建 ToolRegistry，再创建 LLMService、调用 Runner，运行后关闭模型连接。它只返回 Runner 的运行结果。Key、Base URL、鉴权和 SDK client 都由模型服务内部管理。进入 run_agent() 后，Runner 只做：

  1. 读取工具的 specs，连同消息历史提交给 model.invoke()。
  2. 保存整份 ModelResponse，检查是否正常完成。
  3. 有工具调用时提交给 tools.execute()，将 ToolResult 追加到历史，再请求模型。
  4. 没有工具调用时返回 RunResult，包含模型说明与本次回执；请求次数耗尽则停止。

模块间的交互分别见 Runner ↔ Tools 与 Runner ↔ Model。SDK 消息编码由 Model 适配器负责，Runner 不解释 continuation 数据。

3.1 对照源码看函数、类与数据对象

main()、run_task() 和 run_agent() 是函数。LLMService 持有 SDK 客户端和 OpenAIChatModel 适配器；ToolRegistry 持有按名称组织的 ToolDefinition，每个注册项保存普通函数及参数类。Model 与 ToolExecutor 是 Runner 使用的协议，表示需要哪些方法，不要求具体实现继承某个共同父类。

3.2 沿一次 read_file 调用追踪

  1. run_task() 创建 ToolRegistry(DEFAULT_TOOLS, workspace, policy)。注册表保存注册项，specs 根据参数类生成模型可见的工具声明；此时不读取资料。
  2. 应用创建 LLMService，服务内部创建 SDK 客户端和适配器，再把服务和注册表交给 run_agent()。
  3. Runner 生成 ModelRequest。LLMService.invoke() 转给 OpenAIChatModel.invoke()；适配器通过 _encode_message() 编码消息，调用 SDK，再通过 _decode() 得到 ModelResponse。
  4. Runner 检查响应，逐个把 ToolCall 交给 ToolRegistry.execute()。注册表解析和校验参数，生成动作、询问 Policy，获准后才调用注册项中的 read_file()，并将返回值包装为 ToolResult。
  5. 完整模型回复与工具回执进入下一轮消息。最终无工具调用且有非空回答时返回 RunResult；应用在 finally 中关闭模型连接。模型错误、注册错误和未声明的程序异常向外抛出。

3.3 当前入口已有的记录功能怎样理解

Tools 与 Model 没有各自的数据库表，工具注册项、参数对象和连接都在内存中。当前 CLI 只运行一个独立任务，messages 保存本次交互；持久记录与历史读取见阶段 3A 的待实现设计。

4. 运行与验收

项目根目录执行 · 沿用 .env 配置，会请求真实模型
uv sync --locked
uv run python -m learn_agent "在资料中找到验收标记，告诉我来源和行号"

验收

  • 新增普通函数只需注册，registry.py 和 Runner 都无需修改；替换模型适配器无需修改工具实现。
  • 工具结果通过调用 ID 关联，完整回复和后续请求所需的协议数据一起进入下一轮。
  • 预期工具失败可反馈；模型截断、拒绝或请求失败不会触发工具。

本地执行 uv run pytest，检查见 test_tools.py 与 test_models.py。固定协议响应验证工具与消息如何连接；真实模型会选择哪些工具，需要运行后观察。
