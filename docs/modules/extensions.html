模块原理与方案

Extensions：接入 Skills、Hooks 和外部工具

1. 问题起点：为什么不同的扩展机制不能混成同一种“插件函数”？

当系统需要扩展能力时，常见的五种机制职责截然不同：

  • Skill（技能方法）：提供特定任务的步骤指南与参考资料，按需加载到模型输入（Context）中。
  • Hook（生命周期回调）：在运行开始、工具调用前后等固定节点触发观测或拦截逻辑。
  • Middleware（中间件）：包裹模型请求或工具调用，用于统一转换输入、处理重试或记录日志。
  • MCP（Model Context Protocol）：通过标准协议连接外部工具服务、资源与 Prompt 模板。
  • Plugin（插件包）：将上述 Skills、Hooks 和工具声明打包，统一管理版本、校验与分发。

核心安全边界：发现或加载扩展，绝不等于自动授予执行权限。

2. 模块协作：各类扩展分别接入哪个核心模块？

  • Skills → Context Manager：方法说明与参考资料交给 Context Manager 按需选入本轮输入，不直接执行其中引用的脚本。
  • Hooks / Middleware → Runner：生命周期回调注册到 Runner 的指定步骤；若回调改写了工具参数，必须重新经过参数校验与 Policy 授权。
  • MCP 外部工具 → Tools：由 Tools 适配为内部统一的 ToolSpec，执行前同样必须通过 Policy 权限检查。
  • 失败隔离策略：普通观测类回调失败可按约定降级告警；但用于拦截危险动作的控制类回调一旦失败，必须拒绝执行动作（Fail-closed）。

3. Skills 的 3 种加载方案对比

A. 全量正文常驻

  • 做法：启动时读取所有 Skill 全文，每轮都拼入系统指令。
  • 适用场景：方法极少、极短且固定的系统；一旦方法库增长，会严重挤占上下文窗口并引发规则冲突。

B. 元数据发现 + 正文按需加载（推荐基线）

  • 做法：平时只加载各 Skill 的名称与简短描述（Metadata）；当匹配当前任务或由用户/模型显式激活时，才在长度限制内读取正文（参考 Agent Skills 规范）。
  • 适用场景：中小型方法库，既大幅节省常驻 Token，又能清晰记录本轮激活了哪个版本的 Skill。

C. 检索驱动的方法库

  • 做法：针对大型方法库，先按任务检索候选 Skill，再核对适用条件、版本与依赖后加载。
  • 适用场景：海量领域技能库；需额外维护检索索引，并防止高度相似的方法给出矛盾指令。

4. Hooks 与中间件的 3 种实现方式

A. 进程内函数回调

  • 做法：在 run.start、model.before、tool.before、tool.after 等节点直接调用进程内注册的 Python 函数。
  • 优缺点：类型清晰、延迟极低，适合可信内置逻辑；但与主程序共享内存与权限，回调阻塞会直接卡住主循环。

B. 进程外事件协议（子进程 Hook）

  • 做法：通过 stdin 传入事件 JSON，stdout 返回控制决定，stderr 输出诊断日志，配合超时与退出码管理。
  • 优缺点：语言无关、进程隔离、易于强制超时终止；适合接入外部检查脚本。

C. 包裹调用的中间件（Middleware）

  • 做法：按洋葱模型（外层前处理 → 内层前处理 → 实际调用 → 内层后处理 → 外层后处理）包裹模型或工具调用。
  • 注意事项：执行顺序直接决定结果——例如若把重试中间件包在非幂等写工具外层，会导致重复写入；若先计算 Token 预算再由内层中间件注入工具定义，会导致预算漏算。
扩展机制 适用场景 核心收益 主要实现代价
进程内回调 可信、轻量的内部事件处理 简单直接、零序列化开销 共享内存与权限，异常易波及主进程
进程外 Hook 外部语言脚本、需独立超时控制 进程隔离、易于限制输出与超时 需维护 JSON 协议、退出码与子进程清理
中间件（Middleware） 跨调用复用的转换、日志与控制 解耦横切关注点 多层嵌套时调用顺序与副作用排查复杂

5. MCP 外部工具应该接在哪里？

MCP：通过工具适配器接入统一执行管线（当前尚未接入）

  • 统一适配为内部契约：连接 MCP Server 发现工具后，将其转换为内部统一的 ToolSpec，并在同一次 Run 中锁定版本（参考 MCP 2025-11-25 架构）。
  • 复用校验与授权管线：模型发起的 MCP 工具调用，依然必须经过注册表的参数校验、Policy 权限检查、大小限制与错误分流；外部服务声称自己“只读”不能替代宿主的 Policy 授权。
  • 连接生命周期管理：本地 stdio 子进程需限制传入的环境变量并负责进程回收；远程 HTTP 服务需管理鉴权、超时与断连报错。

6. 开源与工业界实现对照

  • Deep Agents（源码核对）：SkillsMiddleware 将方法发现与请求注入分离，在 graph.py 中按固定顺序装配中间件栈。
  • Claude Code（官方文档）：Hooks 说明明确定义了工具调用前后等触发点，以及每个事件允许返回的有限控制决策。
  • pi（源码核对）：agent-session.ts 在上下文压缩前后提供明确的单步扩展回调，避免插件随意替换整个核心状态机。
  • AgentScope Java（官方文档）：Skill 装配支持从工作区与仓库加载技能资料，将资料读取与运行组件配置解耦。

7. Plugin 插件包如何封装与升级？

当需要同时分发 Skills、Hooks 和工具声明时，可用带清单文件（Manifest）的目录结构封装：

  • 安装校验：检查路径是否越界、内容哈希是否匹配、宿主接口版本是否兼容。
  • 运行期锁定版本：同一次 Run 执行期间固定使用同一插件版本，升级后从下一次 Run 生效，防止中途切换导致前后回执不一致。

8. 本项目当前实现与未实现范围

  • 已实现（截至阶段 3：显式函数注册）：通过 ToolRegistry.register() 显式注册本地 Python 函数并声明权限需求（如 examples/count_lines.py，详见阶段 1）。
  • 未实现（留待阶段 8 按需扩展）：Skill 目录扫描与按需注入、Hook 回调协议、Middleware 栈、MCP 客户端接入以及 Plugin 包管理。

期望达到的效果：

  • 未激活正文零注入：默认只加载 Skill 元数据，未激活的 Skill 正文绝不占用模型上下文预算。
  • 加载不自动执行脚本：读取 Skill 正文时严格检查路径越界与大小上限，且绝不自动执行正文中提及的外部脚本。
  • MCP 异常可受控降级：当本地只读 MCP 服务断连、Schema 变更或返回超大结果时，适配器能准确拦截并转为结构化错误回执。
  • 权限边界不被绕过：任何扩展（Skill、Hook 或 MCP）都无法绕过 Policy 执行未授权的写操作。
