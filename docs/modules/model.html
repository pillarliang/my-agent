模块原理与方案

Model：适配模型服务与通信协议

1. Model 是什么，为什么单独做一个模块

Model 模块负责和模型服务通信：把任务和已有对话发给模型，再把模型的回答交回来。

请求模型需要处理地址、密钥和服务要求的数据格式。如果把这些全写进 Runner，循环就会和某一家模型服务绑在一起。单独做一个模块，Runner 就可以专心决定什么时候请求模型、什么时候执行工具。

两个核心抽象

  • 统一调用接口：Runner 总用同一种方式发送请求、取得回答。本项目由 LLMService.invoke() 提供。
  • 协议适配器：把项目自己的请求和回答，转换成模型服务要求的数据格式。更换模型服务时，主要修改这一层。

密钥、服务地址和连接也由 Model 内部管理。请求回来后，如果模型要求执行工具，仍由 Runner 安排执行。

2. Runner 怎样使用 Model

输入选择和协议通信是两件事。当前 Runner 提供本次任务的完整消息，Model 只编码和发送请求。未来的 Context Manager 负责输入选择；Model 不自行查询记录或删除历史。工具定义只提供说明，本地函数仍由工具系统执行。

以“读取 notes.txt”为例：Runner 先把任务、已有对话和可用工具告诉 Model；Model 请求远端模型，可能带回“请调用 read_file”的回答。Runner 执行后，把实际读到的内容放进下一次请求。

  • 发给模型的材料（ModelRequest）：任务和对话、可用工具说明，以及这次最多生成多少内容。
  • 模型的回答（ModelResponse）：回答文字，或者要求执行的工具调用；也可能同时有两者。
  • 请求失败（ModelError）：例如连不上服务，或回答无法按约定读取。当前 Runner 遇到这种错误会停止。

Runner 通过 LLMService.invoke() 完成一次请求。它保存整份回答，执行工具后再继续请求。

输出经 Runner 回到相关模块。Model 提出的工具调用交给 Tools 校验、授权和执行；真实回执经 Runner 进入下一轮 Context。请求、响应与回执由 Runner 交给 State 保存。Model 报告的用量可以供后续预算分析与观测使用，但请求后的用量不能代替请求前的输入检查。

初始化时应用选择模型服务与连接配置；运行时交换请求、响应和错误。超时或协议错误返回 Runner，是否重试应有明确策略；单次模型适配器不应悄悄接管整个任务生命周期。

读源码时再看：回答里还保存了什么

回答还可能带有生成停止原因、Token 用量，以及下一次请求需要原样带回的供应商数据。这些数据由适配器解释，Runner 保存后继续传递。

这里的 continuation data 指模型服务要求在后续请求中继续携带的协议数据，例如响应中的推理项；需要按该服务的协议保存和传递。

如果回答被截断或被服务拒绝，当前循环会停止，避免执行没有生成完整的工具调用。工具参数仍由工具系统解析和检查。

展开编码、请求与解码管线

工具参数保留原始 JSON，由工具系统解析和校验。模型适配器负责协议格式，工具系统负责资源访问与权限检查。

按需查阅：协议差异、适配方案、流式与重试

3. 协议之间有什么差异

Chat Completions 通常按消息表示交互：Assistant 的工具调用列表与后面的工具结果通过 ID 关联。Responses 按输出项表示文字、调用和其他协议材料；函数结果通过 call_id 关联。

阿里云函数调用说明展示应用接收调用、执行函数、追加结果并再次请求的流程。OpenAI 函数调用说明另外解释了如何在后续请求中保留推理项并加入函数结果。只抽取最终文字，会丢掉执行工具所需的信息；只重建调用，也可能丢掉后续请求需要的其他协议数据。

将“兼容 OpenAI”理解为需要验证的协议范围，而不是全部特性承诺。模型、地域、端点与模式都可能影响并行调用、推理过程相关数据和参数支持。升级时应重新执行真实服务的接口测试。

4. 有哪些适配方案：分别决定三件事

应用内部怎样表示一次请求

直接使用供应商的请求和响应对象，需要的转换代码少、独有字段容易保留，适合单一后端的短程序；采用项目内部统一的请求与响应格式，再由适配器转换，能让 Runner 与供应商协议分开，代价是维护字段转换，并正确保留后续请求需要的协议数据。能力协商是可再增加的机制，用来声明图片、流式或计数等支持范围，并不是统一的内部接口天然具备的能力。

适配器怎样连接模型服务

原生协议适配器能保留供应商特性，但多后端需要分别维护；直接调用兼容端点可以复用 SDK，但仍需核对兼容范围；经模型网关可以集中鉴权、路由和限流，但增加中间层、运维和字段转换风险。三者都可以位于同一个内部接口后面。

谁负责工具循环与会话

本地 Runner 控制循环时，模型调用只完成一次请求。完整 Agent SDK 或托管运行时可以承接更多执行与会话工作，但这时接入的是整个 Agent 运行服务，需要重新约定历史、授权、工具、重试与恢复的归属；这不是简单更换模型地址。

当前组合：统一的内部请求／响应格式＋一个 Chat Completions 适配器＋直接连接兼容端点＋本地 Runner。尚无能力协商、自建网关、其他协议适配器或托管循环。不同层的选择可以组合，不应把它们排成只能四选一的方案。

5. 真实项目可以怎样借鉴

pi，源码核对。 agent-loop.ts 在上下文变换后执行 convertToLlm，再调用模型流接口。可借鉴的是将“选择哪些信息”和“编码成哪个协议”放在两个位置；这样换供应商不必重写历史选择算法。

Deep Agents，源码核对。 graph.py 将模型、能力后端和中间件装配到运行图。可借鉴的是让装配层选择实现，而不是让核心循环到处判断当前使用哪一家供应商。

OpenAI 提供的不同接口。 Agent 开发入口区分模型 API、SDK 与托管 Agents API。它们都能参与构建 Agent，但应用获得的控制权不同；选型时先确定要学习单次协议还是复用整段运行时。

6. 流式响应为什么是另一套状态机

流式接口可能逐段返回文字、工具名、参数片段和最终状态。实现时按每个响应项的 ID 收集逐步返回的内容，只有在调用完整并通过校验后，才允许执行。网络断开时残缺的参数不是可以执行的 JSON。

用户可见的文字流可以提前显示；工具调用必须完整接收并通过校验后才能执行。工具进度事件与模型 Token 增量也是两种流：后续 Web 可以用 SSE 传递运行事件，这并不意味着模型已经流式生成。参见应用入口计划。

7. 错误、重试与切换模型

输入无效、权限错误和上下文超限不能原样无限重试。限流或临时故障可在等待后重试，并限制重试次数，但要记录尝试次数并消耗同一预算。流式断开后还需识别是否已经执行工具，避免整段任务重跑产生重复效果。

切换模型也不是只改名称：新模型可能有更小窗口、不同协议和不兼容的 continuation 数据。应使用可用于新模型的消息记录重新构建请求，并检查预算；不能把另一供应商的加密 continuation 数据直接放进新请求。用量缺失报告未知，不记为零。

8. 本项目当前选择与未实现范围

截至阶段 2：沿用阶段 1 定义的统一内部接口与单一 Chat Completions 适配器。LLMService 管理凭证、连接与关闭，当前配置连接 DashScope 兼容端点，支持文本和函数工具；Runner 保留本地执行权。这样可以先验证一次完整工具调用与结果反馈，同时隔离协议与循环。初始化与协议细节见阶段 1。

当前 Runner 直接构造 ModelRequest，不保存会话或请求日志。continuation 用于同一协议、端点和模型的后续请求；记录设计见阶段 3A，Context 管理尚未接入。

未实现：能力协商、Responses 适配器、流式输出、自动重试、多模型路由、熔断和降级。当前 SDK 自动重试被关闭；上文有关重试和切换的讨论是设计参考。统一内部接口不代表任意供应商都可不经适配直接替换。

9. 动手练习与验收

顺着适配器阅读编码、请求和解码过程，再看模型接口行为检查。观察工具调用与模型服务返回的协议数据如何进入下一次请求，以及截断、拒绝和 HTTP 错误如何停止循环。

模型服务检查验证配置优先级、缺失配置、重复调用与关闭行为；服务关闭后再次调用会报错。新增协议实现同一个 Model 接口，Runner 与工具实现无需修改；真实供应商行为单独运行验证。
