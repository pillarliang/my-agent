模块原理与方案

Interfaces：让不同用户入口共用执行流程

1. 实现原理：提交、执行和观察分开

Web 与 CLI 的入口结构

通用目标示意：CLI 与 Web 可以共用应用服务；当前仅有 CLI，图中的 HTTP / WebRuns 尚未实现。

同一个生成报告的请求，无论来自命令行还是浏览器，都应经过相同配置、权限和执行流程。前端不需要理解模型协议，CLI 也不应复制另一个 Agent Loop。

应用服务接收业务数据，例如会话 ID 和问题，而不是 HTTP Request 或 DOM 对象。存储中的 Run ID 用来关联执行、历史和进度，页面显示什么不能用来判断任务是否实际完成，应以保存的执行记录为准。

2. 与相关模块怎样交互

以“读取 notes.txt”为例，入口收集问题并展示结果，应用服务选定工作目录、工具能力和权限配置，再交给 Runner。Runner 控制执行，记录层保存事实。入口无需识别模型协议，也不能仅凭前端按钮决定工具权限。

执行和查询是两条路径：提交任务会启动运行；查询只读取已经保存的记录，不再次调用模型或工具。错误沿发起调用的路径返回，展示层应区分“请求未被接受”“运行失败”和“查询失败”，不能将缺少结果显示为成功。

初始化和运行时分开：初始化时选择组件与配置；运行时传递任务、ID、结果和错误。改用后台队列后，需要另行确定谁负责运行任务；入口仍应如实展示已保存的执行记录。

3. 执行服务有哪些方案

这里比较谁负责运行任务、提交者是否等待。当前采用 A：CLI 同步等待；B、C、D 均是未接入的可选方向。进度怎样传输是下一节的另一项选择。

A. 请求内同步执行

接口一直等待 Runner 返回，适合 CLI 和耗时很短的调用，实现简单、错误直接。代价是请求等待时间限制了任务能运行多久，页面断开后也难以清楚表达执行状态。

B. 进程内后台执行

接口先返回任务 ID，程序在当前进程中管理后台任务，查询和进度接口独立工作。它适合本地 Web MVP，代码少，也能避免模型网络等待阻塞 HTTP 事件循环。

不足是 Web 进程退出时，后台任务也会停止，线程里的阻塞工作也不能仅靠取消异步 Task 就可靠停止。FastAPI 并发说明有助于理解异步 HTTP 处理与同步阻塞工作的区别；仍需由应用明确哪个组件负责启动、等待和停止任务。

C. 持久队列与独立 Worker

先把提交的任务保存到存储中，由 Worker 领取并运行，前端继续按任务 ID 查询。它适合长任务、服务重启和独立扩容。

还需要处理重复投递、租约、任务状态、取消请求的传递，以及外部操作的结果核对。队列保证受理或再次投递，并不自动保证每个工具只执行一次，参见 State。

D. 外部 Agent 运行服务

Web 或 CLI 调用完整运行服务，接收它返回的任务 ID 与事件。它减少自建调度，但需要明确会话、权限、历史和生成结果由谁管理，避免同时维护两套冲突状态。

这是部署与控制权方向的选择，不必为了拥有 Web UI 就引入它。

4. 进度协议怎样选择

Web 进度、补读与历史查询

未来 SSE 方案示意，尚未实现；观察与 Run 执行分别进行。

方案 工作方式 适用情况 主要代价
HTTP 轮询 周期查询状态或增量 低频状态、简单客户端 间隔与重复查询
POST + SSE + GET 提交、单向事件、最终查询 聊天与工具进度 长连接、游标和补读
WebSocket 双向消息通道 高频控制与交互 消息协议、重连和连接状态

MDN SSE 说明定义单向事件、事件 ID 和重连行为。如果后续 Web 入口主要接收进度，可以选择 SSE；提交任务、取消或审批可以另用普通 POST。这是候选方案，当前项目没有 HTTP / SSE 服务。

进度传输与模型流式生成不同。阶段 3 保存模型请求、响应、工具回执和运行结束等事件，并打印终端进度；没有工具开始事件、实时推送或逐 Token 展示。轮询适合低频更新，SSE 适合单向推送，WebSocket 适合持续双向交互，后两者需要连接与重连管理。模型流式还需修改 Model 适配器。

5. 真实系统怎样组织入口

AgentScope Java，指定版本的官方文档。 架构说明区分直接调用、当前请求内流式事件，以及持久会话任务操作。可借鉴的是让不同入口复用模型、工具与中间件配置，同时明确谁安排执行。

pi，指定版本的官方文档。 RPC 接口通过结构化命令与事件将运行核心接入其他界面。可以借鉴“不同协议适配器共用同一个执行核心”的组织方式；RPC 不是必须使用 HTTP 或浏览器的接口。

6. 断线、历史与重复提交

每个事件使用固定 ID，客户端保存已读位置；重新连接后补读遗漏事件，再按事件 ID 去重。持久历史负责重建页面，实时事件负责显示后续变化；只保存前端聊天数组，无法可靠应对刷新和跨入口读取。

用户点击发送后网络中断，可能不知道任务是否已经受理。后续可以增加客户端请求 ID，由服务做提交去重；仅仅重发 HTTP POST 可能启动第二次任务。这个请求 ID 与模型工具调用 ID 不同。

页面关闭、请求断开、用户取消和进程退出也应分别定义。取消的接口应返回受理状态，最终停止要由执行端确认；UI 不应在发出取消请求后立即伪装所有工具已经停止。

7. 本项目当前选择与未实现范围

截至阶段 2：同步 CLI。任务经 run_task() 进入 Runner，返回 RunResult；应用创建并关闭模型连接。当前没有会话存储或历史查询入口。

运行前由入口设置工作目录与 Policy，工具清单由应用配置决定；模型按任务选择调用。每次启动独立处理一个任务，命令见阶段 1；会话查询留作阶段 3A。

未实现：Web、后台任务、队列、SSE、WebSocket、请求去重和用户取消协议。它们属于阶段 6 的可选扩展，不要求为了增加另一种展示方式而全部建设。

8. 后续练习：Web 入口与任务控制

需要 Web 时，先让 CLI 与 HTTP 共用同一个应用服务，分别验证任务提交、只读查询和进度查看；再依据等待时长选择同步、后台或队列执行。查询和刷新页面不能启动另一次运行。

若增加重连、提交去重或取消，分别检查缺失进度能补读、使用同一请求 ID 重复提交时，不会再次启动任务，以及取消后确实收到执行端停止确认。保存真实状态与未解决错误，不能仅凭前端连接关闭就标记任务结束。
