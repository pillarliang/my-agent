模块原理与方案

Tools：执行模型提出的工具调用

本章解析工具系统的核心抽象、模块间协作与扩展方案；具体代码接入见阶段 1，权限拦截见阶段 2。

1. 问题起点：模型如何通过 Tools 与外部环境交互？

大模型本身只能接收文本并输出文本，无法直接读取本地文件或操作外部系统。当任务需要访问外部资源时，交互流程如下：

  • 用户：“帮我看看工作区里有哪些文件，并读取笔记内容。”
  • 模型：先发起 list_files 工具调用；收到文件列表回执后，再发起 read_file(path="notes.txt") 调用。
  • （系统动作：工具系统在本地打开文件，将真实文本内容或报错信息封装为回执返回给 Runner）

两个核心内部抽象

  • 工具定义（ToolDefinition）：将普通 Python 函数与工具名称、功能说明、参数校验模型及所需权限绑定在一起（模型只能看到生成的说明 Schema，接触不到底层 Python 函数）。
  • 工具注册表（ToolRegistry）：按名称管理所有已注册工具，收到调用后统一完成查找、参数校验、动作识别、Policy 授权与函数执行。

工具系统与 Runner 的黑盒交互

Runner 无需关心每个工具内部如何实现，只通过三个标准数据对象与工具系统交互：

  • 工具声明（ToolSpec）：Runner 读取 tools.specs，获取供模型阅读的工具名称、用途说明与参数 JSON Schema。
  • 调用请求（ToolCall）：模型发起调用时，Runner 将包含调用 ID、工具名与原始参数字符串的 ToolCall 传给 tools.execute(call)。
  • 真实回执（ToolResult）：工具系统返回带有原 call_id 的执行结果（含文件内容、权限拒绝或执行错误），供 Runner 关联回下一轮模型请求。

2. 与相关模块的协作边界

  • 初始化期配置（Application → Tools）：应用启动时将工具定义列表、工作目录 workspace 与权限规则 Policy 注入 ToolRegistry。
  • 请求期声明传递（Tools → Runner → Model）：Runner 读取公开的 ToolSpec 列表并交由 Model 编码发送给模型；底层函数引用与安全规则留在本地。
  • 执行期权限拦截（Tools ↔ Policy）：收到模型调用后，Tools 先校验参数并结合目标文件状态生成 ActionRequest（如区分 create 与 overwrite），经 Policy 批准后才真正执行底层函数。
  • 结果持久化与错误分流（Tools → Runner → State）：参数错误、权限拒绝和预期的文件读取失败均封装为带 call_id 的 ToolResult，由 Runner 写入会话记录并带入下一轮；未捕获的代码 Bug 则直接抛出异常停止运行。

实现方案的三个正交维度：工具粒度（专用结构化工具／通用命令工具／聚合业务工具）、执行位置（进程内函数／独立 Worker／远程沙箱）与调度方式（串行／并行／异步长任务）。本项目当前采用专用结构化文件工具 + 进程内函数 + 串行执行，其余扩展方案见下方折叠区。

3. 工具应负责多大范围的操作

A. 专用结构化工具

例如 read_file(path, offset, limit) 和 write_file(path, content)，每个工具有少量明确参数。实现可以准确限制路径、大小和作用，模型也更容易理解返回值。

它适合学习和操作范围明确的业务。代价是需要维护较多工具，组合能力取决于提供的操作；工具数量增大后还要处理 Schema 占用和发现问题。

B. 通用能力工具

例如 Shell、SQL 或代码执行，一个接口可以表达很多操作。它灵活、工具表短，也方便复用现有 CLI；代价是难以从任意字符串识别真实资源和副作用，超时、进程清理和隔离也更复杂。

通用工具适合已有执行环境和资源访问限制的场景。不能仅通过检查命令前缀就认为执行环境已足够安全，子进程和间接调用也会产生效果。执行隔离见 Policy。

C. 完整业务操作工具

例如 generate_monthly_report(source_ids, template_version)，内部完成取数、生成和登记。它减少模型需要协调的步骤，并用程序直接检查业务中必须满足的条件。

代价是复用范围窄、接口版本与业务耦合。内部如果继续调用模型或外部服务，也必须把用量、错误、部分效果和检查范围返回给上层，不能只返回一句“已完成”。

粒度 模型承担什么 便于控制什么 主要限制
专用结构化工具 组合小动作 参数、路径和结果范围 工具与 Schema 增长
通用工具 生成命令或程序 灵活表达复杂操作 难以判断命令会修改什么，也难以隔离执行
完整业务操作工具 选择业务动作 业务要求和事务范围 灵活性与业务耦合

Anthropic 工具设计实践讨论名称、说明和返回内容对决策的影响。它们应作为任务评测变量；“工具越少越好”和“越专用越好”都需要具体任务证据。

4. 执行放在哪里

进程内函数依赖少、延迟低，适合可信、耗时和输出大小可控的小工具；但阻塞、崩溃和主进程共享权限是明显限制。

独立 Worker 进程通过结构化协议执行，方便限制输出和强制终止。它需要进程监督和资源清理；单独启动进程并没有自动隔离主机文件和网络。

远程服务或沙箱后端通过 RPC 提交动作，返回任务 ID 和回执，适合更强隔离与独立扩容。它引入认证、网络故障、版本兼容和无法确认结果等问题，需要与状态记录和恢复机制一起设计。

工具 API 与执行后端可以分开。例如同一个 read_file 访问本地工作区、受限容器或远程逻辑文件系统；Runner 继续使用同一 ToolCall，后端负责真实资源映射。

5. 真实实现怎样做

Deep Agents，源码核对。 FilesystemMiddleware 提供模型可调用的文件工具，并通过后端协议访问存储；wrap_tool_call 在工具返回结果时处理超大内容。BackendProtocol 区分文件能力与执行能力。可借鉴的是分别处理工具定义、工具结果和实际执行后端。

pi，源码核对。 agent-loop.ts 根据执行设置和工具的串行要求选择串行或并行批次。可借鉴的是让执行策略由程序决定，不能因为模型一次返回多个调用就自动并行执行所有会修改外部资源的操作。

MCP，协议文档。 架构规范把外部能力放在服务器、连接放在客户端、授权和聚合放在宿主。MCP 可以统一发现与调用，但业务幂等、核对操作结果和访问范围仍需应用定义，详见扩展教程。

6. 串行、并行和长任务怎样选择

互不依赖的只读操作适合受限并发；同一文件的“读 → 改 → 检查”有依赖，应保持顺序。并行写入不同路径也可能共享索引或全局状态，因此仅比较文件名不足以判断独立性。

工具元数据可以增加 effect_class、并发分组、超时和是否可查询回执。调度器据此限制并发；这些元数据必须由可信实现提供，不能直接把外部服务器自报的“只读”当成授权证明。

长任务宜返回 job_id，再通过事件或间隔查询获取后续进度。返回任务 ID 只表示已受理，不能视为产物已完成。

7. 执行结果、幂等与结果未知时的处理

考虑外部创建报告的调用：服务已经创建资源，但返回前网络断开。程序只知道结果未知，不能简单按失败重试。正确设计需要先保存逻辑调用 ID，执行时使用稳定幂等键，随后查询回执或真实资源。

后续接入远程工具时，再增加逻辑调用 ID、每次尝试的 ID、操作成功或结果未知的状态，以及外部系统的记录。当前没有实现这套远程协议。

同一逻辑调用的重试复用幂等键；用户有意再次执行的新动作应分配新的 ID。只按参数哈希对所有调用去重，会误拦用户有意重复执行的操作。更完整的恢复设计见 State。

8. 大段结果与精确编辑

大结果应带总量、预览范围、截断标记和补读引用。Context 可以选择少发一些内容，但完整回执仍应有位置可查；模型不应把预览当成全量结果。

下一阶段的编辑工具可要求 expected_sha256 和必须匹配的原文片段，写入前重读并比较版本，发现外部修改就拒绝。它能减少因原始内容过时而覆盖他人新改动的情况，却不自动解决所有跨进程竞态；需要结合原子替换、锁或隔离工作区。

9. 本项目当前选择与未实现范围

  • 本项目当前选择：采用 专用结构化文件工具 + 进程内普通函数 + 串行执行，默认注册 list_files、read_file、search_text 和 write_file。
  • 尚未实现（按需扩展）：通用 Shell / SQL 执行器、MCP 外部工具接入、独立 Worker 进程、沙箱隔离、并行工具调度与远程幂等重试。

Tools 与 Policy 的衔接流程

  1. 注册时声明权限：工具注册时通过数据字段声明所需权限（read / write / list）和路径参数名（如 path_parameter="path"），无需传入自定义权限回调。
  2. 执行前生成动作：ToolRegistry 根据权限声明、已校验参数与目标文件状态生成 ActionRequest（写入操作会自动区分 create 与 overwrite），统一调用 Policy.evaluate()。
  3. 按决定放行或拦截：获得许可才调用实际工具函数；被拒绝则直接返回 policy_denied 回执，底层函数不会运行（详见 Policy 教程 与 阶段 2）。

10. 动手练习与期望达到的效果

以新增统计文件行数的工具 count_lines 为例，由于它需要读取文件，注册时直接声明 permission="read" 与 path_parameter="path"：

tools.register(
    count_lines, ReadFileArguments,
    permission="read", path_parameter="path",
)

在项目根目录运行完整示例 count_lines.py（不调用模型）：

uv run python -m examples.count_lines

期望达到的效果：

  • 零侵入扩展：新增工具只需编写普通函数并调用 register()，无需修改 registry.py 或 Runner（见 test_tools.py）。
  • 权限检查自动生效：开启读取权限时正常返回行数（3 行）；关闭读取权限时自动被 ToolRegistry 拦截并返回 policy_denied 回执。
