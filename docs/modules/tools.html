模块原理与方案

Tools：执行模型提出的工具调用

本章讲工具系统的核心抽象、与 Loop 的接口和内部机制；注册与调用见阶段 1，文件新建权限的检查见阶段 2。

1. Tools 是什么，怎样和 Runner 配合

工具是程序实际做事的代码。例如模型想知道 notes.txt 的内容，只能提出“读取这个文件”的要求；工具才会真正打开文件，把内容或失败原因交回来。

用户不知道文件名时，模型可以先调用 list_files 查看工作目录，再决定读取哪个文件。工具系统保存每个工具的说明和实现，收到调用后按名称找到对应工具。

两个核心抽象

  • 工具定义（ToolDefinition）：把普通执行函数与名称、用途、参数模型、权限声明对应起来。模型只看到工具说明，不会取得 Python 函数。
  • 工具注册表（ToolRegistry）：保存这些定义，收到调用后按名字找到工具，检查参数、识别动作、询问 Policy，允许才执行。

工具系统与 Runner 的黑盒交互

仍然看读取文件：工具系统先告诉 Runner“有 read_file，可以传入文件路径”；模型提出读取 notes.txt 后，Runner 把这次调用交给工具系统，工具系统实际读取并交回结果。

  • 工具说明（ToolSpec）：告诉模型工具能做什么、需要哪些参数。Schema 是程序可读取的参数格式要求。
  • 调用要求（ToolCall）：例如调用 read_file，参数是路径 notes.txt。
  • 执行结果（ToolResult）：例如实际文件内容，或“文件不存在”。结果保留调用编号，Runner 才知道它对应哪次要求。

在代码中，Runner 读取 specs 取得说明，通过 execute(call) 提交调用。它不需要逐个了解工具内部的写法。增加写文件工具后，执行前的权限检查见 Policy。

2. 与相关模块怎样交互

初始化时注册能力，运行时提交动作。应用把工具实现、工作目录与 Policy 交给工具系统；Runner 取得公开工具定义，交给 Context Manager 计入输入，再由 Model 编码给模型。实现函数、连接和权限规则并不因此发送给模型。

以保存 summary.txt 为例：模型提出调用，Runner 转交原始参数；Tools 解析参数、确认实际操作的文件和新建／覆盖动作，再向 Policy 请求决定。获准后才执行文件操作。参数错误、权限拒绝和预期执行失败返回带原调用 ID 的回执；程序错误明确上报，不能伪装成一次普通工具失败。

执行后，Runner 把真实回执交给 State 保存，再进入下一轮 Context。裁剪只影响下次发送的输入，不改写原始回执；记录写入失败也不能证明文件操作未发生。工具成功说明操作完成，成果是否满足任务仍需另行检查。

方案分三项选择：工具粒度（专用／通用／业务）、执行位置（进程内／Worker／远程）与调度方式（串行／并行／后台任务）。当前选择专用文件工具、进程内函数、串行调用；其他组合的成本见下方展开说明。

3. 工具应负责多大范围的操作

A. 专用结构化工具

例如 read_file(path, offset, limit) 和 write_file(path, content)，每个工具有少量明确参数。实现可以准确限制路径、大小和作用，模型也更容易理解返回值。

它适合学习和操作范围明确的业务。代价是需要维护较多工具，组合能力取决于提供的操作；工具数量增大后还要处理 Schema 占用和发现问题。

B. 通用能力工具

例如 Shell、SQL 或代码执行，一个接口可以表达很多操作。它灵活、工具表短，也方便复用现有 CLI；代价是难以从任意字符串识别真实资源和副作用，超时、进程清理和隔离也更复杂。

通用工具适合已有执行环境和资源访问限制的场景。不能仅通过检查命令前缀就认为执行环境已足够安全，子进程和间接调用也会产生效果。执行隔离见 Policy。

C. 完整业务操作工具

例如 generate_monthly_report(source_ids, template_version)，内部完成取数、生成和登记。它减少模型需要协调的步骤，并用程序直接检查业务中必须满足的条件。

代价是复用范围窄、接口版本与业务耦合。内部如果继续调用模型或外部服务，也必须把用量、错误、部分效果和检查范围返回给上层，不能只返回一句“已完成”。

粒度 模型承担什么 便于控制什么 主要限制
专用结构化工具 组合小动作 参数、路径和结果范围 工具与 Schema 增长
通用工具 生成命令或程序 灵活表达复杂操作 难以判断命令会修改什么，也难以隔离执行
完整业务操作工具 选择业务动作 业务要求和事务范围 灵活性与业务耦合

Anthropic 工具设计实践讨论名称、说明和返回内容对决策的影响。它们应作为任务评测变量；“工具越少越好”和“越专用越好”都需要具体任务证据。

4. 执行放在哪里

进程内函数依赖少、延迟低，适合可信、耗时和输出大小可控的小工具；但阻塞、崩溃和主进程共享权限是明显限制。

独立 Worker 进程通过结构化协议执行，方便限制输出和强制终止。它需要进程监督和资源清理；单独启动进程并没有自动隔离主机文件和网络。

远程服务或沙箱后端通过 RPC 提交动作，返回任务 ID 和回执，适合更强隔离与独立扩容。它引入认证、网络故障、版本兼容和无法确认结果等问题，需要与状态记录和恢复机制一起设计。

工具 API 与执行后端可以分开。例如同一个 read_file 访问本地工作区、受限容器或远程逻辑文件系统；Runner 继续使用同一 ToolCall，后端负责真实资源映射。

5. 真实实现怎样做

Deep Agents，源码核对。 FilesystemMiddleware 提供模型可调用的文件工具，并通过后端协议访问存储；wrap_tool_call 在工具返回结果时处理超大内容。BackendProtocol 区分文件能力与执行能力。可借鉴的是分别处理工具定义、工具结果和实际执行后端。

pi，源码核对。 agent-loop.ts 根据执行设置和工具的串行要求选择串行或并行批次。可借鉴的是让执行策略由程序决定，不能因为模型一次返回多个调用就自动并行执行所有会修改外部资源的操作。

MCP，协议文档。 架构规范把外部能力放在服务器、连接放在客户端、授权和聚合放在宿主。MCP 可以统一发现与调用，但业务幂等、核对操作结果和访问范围仍需应用定义，详见扩展教程。

6. 串行、并行和长任务怎样选择

互不依赖的只读操作适合受限并发；同一文件的“读 → 改 → 检查”有依赖，应保持顺序。并行写入不同路径也可能共享索引或全局状态，因此仅比较文件名不足以判断独立性。

工具元数据可以增加 effect_class、并发分组、超时和是否可查询回执。调度器据此限制并发；这些元数据必须由可信实现提供，不能直接把外部服务器自报的“只读”当成授权证明。

长任务宜返回 job_id，再通过事件或间隔查询获取后续进度。返回任务 ID 只表示已受理，不能视为产物已完成。

7. 执行结果、幂等与结果未知时的处理

考虑外部创建报告的调用：服务已经创建资源，但返回前网络断开。程序只知道结果未知，不能简单按失败重试。正确设计需要先保存逻辑调用 ID，执行时使用稳定幂等键，随后查询回执或真实资源。

后续接入远程工具时，再增加逻辑调用 ID、每次尝试的 ID、操作成功或结果未知的状态，以及外部系统的记录。当前没有实现这套远程协议。

同一逻辑调用的重试复用幂等键；用户有意再次执行的新动作应分配新的 ID。只按参数哈希对所有调用去重，会误拦用户有意重复执行的操作。更完整的恢复设计见 State。

8. 大段结果与精确编辑

大结果应带总量、预览范围、截断标记和补读引用。Context 可以选择少发一些内容，但完整回执仍应有位置可查；模型不应把预览当成全量结果。

下一阶段的编辑工具可要求 expected_sha256 和必须匹配的原文片段，写入前重读并比较版本，发现外部修改就拒绝。它能减少因原始内容过时而覆盖他人新改动的情况，却不自动解决所有跨进程竞态；需要结合原子替换、锁或隔离工作区。

9. 本项目当前选择与未实现范围

截至阶段 3A：专用结构化文件工具＋进程内普通函数＋串行执行。默认注册列目录、读取、搜索和写入，注册项提供参数模型和权限声明。这样可以直接检查参数、真实文件和回执，而无需先建设 Worker 或远程协议。

阶段 3A 增加会话与执行记录，步骤中保存实际请求；工具执行契约延续阶段 1 和阶段 2。尚无 Shell／SQL 通用执行、MCP、独立 Worker、沙箱、并发工具调度、后台任务、幂等重试或版本化精确编辑；未来方案不代表当前文件工具具备这些能力。

Tools 怎样询问 Policy

注册时用数据声明需要 read、write 或 list 权限，不传权限判断函数。比如 read + path_parameter="path" 表示“读取本次调用中 path 指定的文件”。

注册表先根据权限声明和本次参数生成动作与目标（ActionRequest），再统一调用 Policy.evaluate()。读取与搜索对应 read；写入先识别 create 或 overwrite。

Policy 返回允许或拒绝及原因（PolicyDecision）。允许才调用注册的执行函数；拒绝直接返回 policy_denied，执行函数不会运行。完整协议与黑盒图见 Policy 教程。

所有注册的工具共用这一处权限检查，执行函数不需要手动调用授权。注册与回执见阶段 1；统一权限检查见阶段 2。

10. 动手练习

count_lines 需要读取文件，因此注册时直接声明 read，并说明路径来自调用参数 path：

tools.register(
    count_lines, ReadFileArguments,
    permission="read", path_parameter="path",
)

permission 表示工具需要什么权限；path_parameter 是参数名，不是固定文件名。声明需求不等于获得授权，Policy 仍可拒绝。

完整例子见 count_lines.py。运行后先得到 3 行，再看到禁止读取的回执；不请求模型：

uv run python -m examples.count_lines

接入测试还验证它能通过 Runner 完成模型请求、工具执行与结果反馈，无需修改注册表。
