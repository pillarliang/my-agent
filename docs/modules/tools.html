模块原理与方案

Tools：执行模型提出的工具调用

本章解析工具系统的核心抽象、模块间协作与扩展方案；具体代码接入见阶段 1，权限拦截见阶段 2。

1. 问题起点：模型如何通过 Tools 与外部环境交互？

大模型本身只能接收文本并输出文本，无法直接读取本地文件或操作外部系统。当任务需要访问外部资源时，交互流程如下：

  • 用户：“帮我看看工作区里有哪些文件，并读取笔记内容。”
  • 模型：先发起 list_files 工具调用；收到文件列表回执后，再发起 read_file(path="notes.txt") 调用。
  • （系统动作：工具系统在本地打开文件，将真实文本内容或报错信息封装为回执返回给 Runner）

两个核心内部抽象

  • 工具定义（ToolDefinition）：将普通 Python 函数与工具名称、功能说明、参数校验模型及所需权限绑定在一起（模型只能看到生成的说明 Schema，接触不到底层 Python 函数）。
  • 工具注册表（ToolRegistry）：按名称管理所有已注册工具，收到调用后统一完成查找、参数校验、动作识别、Policy 授权与函数执行。

工具系统与 Runner 的黑盒交互

Runner 无需关心每个工具内部如何实现，只通过三个标准数据对象与工具系统交互：

  • 工具声明（ToolSpec）：Runner 读取 tools.specs，获取供模型阅读的工具名称、用途说明与参数 JSON Schema。
  • 调用请求（ToolCall）：模型发起调用时，Runner 将包含调用 ID、工具名与原始参数字符串的 ToolCall 传给 tools.execute(call)。
  • 真实回执（ToolResult）：工具系统返回带有原 call_id 的执行结果（含文件内容、权限拒绝或执行错误），供 Runner 关联回下一轮模型请求。

2. 与相关模块的协作边界

  • 初始化期配置（Application → Tools）：应用启动时将工具定义列表、工作目录 workspace 与权限规则 Policy 注入 ToolRegistry。
  • 请求期声明传递（Tools → Runner → Model）：Runner 读取公开的 ToolSpec 列表并交由 Model 编码发送给模型；底层函数引用与安全规则留在本地。
  • 执行期权限拦截（Tools ↔ Policy）：收到模型调用后，Tools 先校验参数并结合目标文件状态生成 ActionRequest（如区分 create 与 overwrite），经 Policy 批准后才真正执行底层函数。
  • 结果持久化与错误分流（Tools → Runner → State）：参数错误、权限拒绝和预期的文件读取失败均封装为带 call_id 的 ToolResult，由 Runner 写入会话记录并带入下一轮；未捕获的代码 Bug 则直接抛出异常停止运行。

实现方案的三个正交维度：工具粒度（专用结构化工具／通用命令工具／聚合业务工具）、执行位置（进程内函数／独立 Worker／远程沙箱）与调度方式（串行／并行／异步长任务）。本项目当前采用专用结构化文件工具 + 进程内函数 + 串行执行，其余扩展方案见下方折叠区。

4. 执行放在哪里：开箱即用的沙箱（Sandbox）技术选型

为什么生产环境中不能只用“进程内普通函数”？

在原型开发时，让 Agent 直接在主进程中执行 Python 函数最简单。但一旦引入 Shell 执行、网络请求或代码运行，进程内方案面临三大致命缺陷：

  • 主进程崩溃扩散：工具发生内存溢出、死循环或底层段错误（Segfault）时，会导致整个 Agent 挂掉。
  • 宿主环境破坏风险：模型生成的危险命令（如误删系统文件、篡改环境变量）会直接破坏宿主机。
  • 资源与网络失控：无法对单次工具执行限制 CPU 核心、内存上限与网络访问范围。

4 种执行后端的演进层次

  • 进程内函数（In-Process）：零序列化开销、延迟最低（<1ms），适合可信、无副作用且耗时极短的本地辅助计算。
  • 独立 Worker 子进程：通过管道或 RPC 通信，能独立设置超时、捕获崩溃；但单独起子进程并不自动隔离宿主文件与网络。
  • 容器沙箱（Docker / Podman）：基于 Linux 命名空间（Namespaces）与控制组（cgroups），适合本地开发与企业私有云部署。
  • 微虚拟机沙箱（MicroVM，如 Firecracker）：硬件级虚拟化强隔离，冷启动达毫秒级，是多租户云端沙箱的黄金标准。

5. 工具集成平台与标准协议：Composio 与 MCP

从“手写 Tool 函数”到“生态化接入”的核心痛点：

在实际业务中，让 Agent 接入外部系统（如 GitHub、Slack、Jira、Salesforce、Gmail）时，最繁琐的往往不是编写工具的 JSON Schema，而是：

  • 复杂的认证管理：每个 SaaS 都有不同的 OAuth2 授权回调、Token 自动刷新和密钥安全存储。
  • 海量接口维护成本：第三方 API 版本升级、参数变更会导致自定义 Tool 频繁失效。
  • 生态割裂：为某个框架写的工具难以直接复用到其他 Agent 项目中。

解决方案 A：Composio（开箱即用的企业级 SaaS 工具平台）

Composio (composio.dev) 是目前业界最成熟的 Agent 工具托管与集成平台：

  • 全托管身份认证：内置处理 200+ 主流应用（GitHub、Slack、Jira、Notion、Gmail、Salesforce 等）的用户 OAuth2 授权、Token 刷新与多租户权限隔离。
  • 即插即用 SDK：一行代码直接将第三方服务的读写操作转化为标准工具对象，原生支持 LangChain、LlamaIndex、OpenAI SDK 等。
  • 原生支持 MCP 桥接：Composio 可以直接将其托管的所有应用工具一键发布为标准的 MCP Server，无需修改宿主架构即可消费。

解决方案 B：MCP（Model Context Protocol，开放标准协议）

MCP (modelcontextprotocol.io) 由 Anthropic 提出，旨在成为 AI 工具领域的“LSP（Language Server Protocol）”：

  • Client-Host-Server 架构：Agent Harness 充当 Host/Client，外部数据源与服务充当独立的 MCP Server。通过基于 JSON-RPC 的标准协议交换工具定义（tools/list）与调用回执（tools/call）。
  • 丰富的成熟社区生态：官方与开源社区已维护大量现成的 MCP Server，包括数据库查询（Postgres、SQLite）、代码仓库（GitHub、Git）、浏览器自动化（Puppeteer）与本地文件服务。
  • 宿主统一适配：Harness 的 ToolRegistry 只需通过一个 MCPClient 驱动层，就能动态发现并加载远端 MCP Server 暴露的所有工具，将其适配为内部统一的 ToolSpec。
集成方案 谁负责认证与 API 维护 通信方式 主要优势 主要代价 / 限制

Composio 平台 Composio 托管服务 HTTPS API / 本地 SDK / MCP 桥接 开箱即用 200+ SaaS，彻底省去 OAuth 维护成本 依赖外部商业服务，需网络出网与凭据托管信任

6. 工具应负责多大范围的操作（粒度设计）

A. 专用结构化工具

例如 read_file(path, offset, limit) 和 write_file(path, content)，每个工具有少量明确参数。实现可以准确限制路径、大小和作用，模型也更容易理解返回值。

它适合学习和操作范围明确的业务。代价是需要维护较多工具，组合能力取决于提供的操作；工具数量增大后还要处理 Schema 占用和发现问题。

B. 通用能力工具

例如 Shell、SQL 或代码执行，一个接口可以表达很多操作。它灵活、工具表短，也方便复用现有 CLI；代价是难以从任意字符串识别真实资源和副作用，超时、进程清理和隔离也更复杂。

通用工具适合已有执行环境和资源访问限制的场景。不能仅通过检查命令前缀就认为执行环境已足够安全，子进程和间接调用也会产生效果。执行隔离见 Policy。

C. 完整业务操作工具

例如 generate_monthly_report(source_ids, template_version)，内部完成取数、生成和登记。它减少模型需要协调的步骤，并用程序直接检查业务中必须满足的条件。

代价是复用范围窄、接口版本与业务耦合。内部如果继续调用模型或外部服务，也必须把用量、错误、部分效果和检查范围返回给上层，不能只返回一句“已完成”。

粒度 模型承担什么 便于控制什么 主要限制
专用结构化工具 组合小动作 参数、路径和结果范围 工具与 Schema 增长
通用工具 生成命令或程序 灵活表达复杂操作 难以判断命令会修改什么，也难以隔离执行
完整业务操作工具 选择业务动作 业务要求和事务范围 灵活性与业务耦合

Anthropic 工具设计实践讨论名称、说明和返回内容对决策的影响。它们应作为任务评测变量；“工具越少越好”和“越专用越好”都需要具体任务证据。

7. 调度控制、幂等性与大结果处理

A. 串行、并行与长任务

互不依赖的只读操作适合受限并发；同一文件的“读 → 改 → 检查”有依赖，应保持顺序。并行写入不同路径也可能共享索引或全局状态，因此仅比较文件名不足以判断独立性。

工具元数据可以增加 effect_class、并发分组、超时和是否可查询回执。调度器据此限制并发；这些元数据必须由可信实现提供，不能直接把外部服务器自报的“只读”当成授权证明。耗时较长的异步任务宜返回 job_id，再通过事件通知或轮询回执推进，不能让整个 Agent 循环长时间同步阻塞。

B. 幂等性与结果未知时的重试

考虑外部创建报告或提交工单的调用：服务已经创建资源，但返回前因网络抖动中断。程序只知道结果未知，不能简单按失败直接重试。正确设计需要为每次逻辑调用分配稳定幂等键（Idempotency Key），并在重试前主动查询外部系统回执或资源状态。

C. 大段结果截断与精确代码编辑

工具输出不可预知地过大时，必须支持截断、总量提示与溢出转存（详见阶段 6）。在代码修改场景下，生产级 Agent（如 Claude Code、Cursor）普遍弃用“整文件全量重写”，转而采用带行号定位或原文本锚点的精确 Patch 替换工具，既能大幅节省 Token 预算，又大幅降低外部文件被意外截断覆盖的风险。

8. 本项目当前选择与生产级演进路径

  • 本项目当前选择（学习 MVP）：采用 专用结构化文件工具 + 进程内普通函数 + 串行执行，默认注册 list_files、read_file、search_text 和 write_file。

    选择理由：避免在一开始引入 Docker、微虚拟机或复杂的 OAuth 凭据，让读者用最低认知成本彻底跑通 ToolSpec 注册、模型参数校验与 ToolResult 回执的闭环流程。

  • 向生产级演进路径（开箱即用平滑升级）：
    • 升级执行环境为沙箱：上层 ToolRegistry 与 Runner 契约完全保持不变；仅需将底层写入或命令执行函数对接为 E2B（sandbox.filesystem.write）或本地 Docker 容器，即可瞬间具备高隔离安全性。
    • 接入海量 SaaS 或外部工具：利用通用 MCP 客户端（或 Composio 的 MCP 导出服务），将外部服务声明动态载入 ToolRegistry，实现零代码维护扩展。

Tools 与 Policy 的衔接流程

  1. 注册时声明权限：工具注册时通过数据字段声明所需权限（read / write / list）和路径参数名（如 path_parameter="path"），无需传入自定义权限回调。
  2. 执行前生成动作：ToolRegistry 根据权限声明、已校验参数与目标文件状态生成 ActionRequest（写入操作会自动区分 create 与 overwrite），统一调用 Policy.evaluate()。
  3. 按决定放行或拦截：获得许可才调用实际工具函数；被拒绝则直接返回 policy_denied 回执，底层函数不会运行（详见 Policy 教程 与 阶段 2）。

9. 动手练习与期望达到的效果

以新增统计文件行数的工具 count_lines 为例，由于它需要读取文件，注册时直接声明 permission="read" 与 path_parameter="path"：

tools.register(
    count_lines, ReadFileArguments,
    permission="read", path_parameter="path",
)

在项目根目录运行完整示例 count_lines.py（不调用模型）：

uv run python -m examples.count_lines

期望达到的效果：

  • 零侵入扩展：新增工具只需编写普通函数并调用 register()，无需修改 registry.py 或 Runner（见 test_tools.py）。
  • 权限检查自动生效：开启读取权限时正常返回行数（3 行）；关闭读取权限时自动被 ToolRegistry 拦截并返回 policy_denied 回执。
