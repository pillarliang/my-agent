Memory：选择跨会话保留的知识

1. 问题起点：新会话需要知道什么？

  • 用户（会话 A）：“这个项目使用 uv，Python 命令请使用 uv run。”
  • 模型：“好的。”
  • （结束会话 A，新建会话 B）
  • 用户（会话 B）：“怎样运行测试？”

新会话没有前面的消息，模型就缺少项目约定。Memory 的作用是把值得复用的知识单独保存，在后续任务需要时重新提供给模型。它不是修改模型参数，也不是把所有会话历史都放进请求。

  • 值得保留：已确认的项目事实、长期偏好和经过验证的经验，例如“项目使用 uv”。
  • 需要重新核对：当前测试结果、临时报错和文件某一行的内容；这些信息随时间或代码变化，不能当作一直成立的事实。

2. Session、Memory 与 Context 怎样配合？

  • Session 保存发生过什么：按会话保存问题、回答与工具回执，供查询或续接对话。
  • Memory 保存值得复用什么：保存选定的事实或偏好，说明来自哪里、适用于哪个项目或用户。
  • Context 决定本次发送什么：把本次问题、选中的历史和适用记忆组装成模型输入，并检查完整请求的预算。

一次使用记忆的任务可以分为以下步骤：

  1. 应用确定范围：根据当前工作区或用户配置，指定可读取的记忆来源。
  2. Memory 读取资料：返回内容及其来源；条目多时，也可以先查找与任务相关的条目。
  3. Context 检查输入：将记忆与其他输入一起计量，再决定是否能够发送。
  4. 模型参考资料回答：需要操作文件时提出工具调用，执行仍经过 Tools 与 Policy。

记忆可以由用户直接维护，也可以从会话记录中提取。因此 Session 能提供写入来源，但 Memory 不必依赖自动扫描历史。模型提出的候选与用户已经确认的事实要分清；记忆中的“允许覆盖文件”也不能替代实际权限检查。

没有记忆与读取失败是两种结果：前者可以正常继续，后者应按应用约定明确处理，不能悄悄当成“没有记忆”。

3. Memory 存在哪里？（四种常见存储位置）

设计 Memory 时，首先要明确“什么内容值得存”以及“存在哪里”：

  • 存什么内容：只存跨会话反复使用的项目事实与偏好（如依赖工具、代码规范）和经过验证的排障经验（现象、原因与解法）。如果某套操作已经成为固定执行流程，则适合整理成 Skill。

按系统复杂度从低到高，Memory 常见有四种存放位置：

A. 单份项目或全局 Markdown 文件（如 <workspace>/MEMORY.md、AGENTS.md）

直接存放在项目工作区根目录（仅对当前项目生效）或用户全局配置目录（如 ~/.agent/MEMORY.md，对当前用户的所有项目生效）。纯文本最容易打开查看、手动修改和纳入版本控制；适合条目不多、以核心项目约定为主的阶段。

B. 索引文件 + 分主题 Markdown 文件（如 MEMORY.md + memories/*.md）

主文件只存放简短目录与一句话摘要，详细的模块说明或排障记录拆分到独立主题文件中。适合知识按主题明显分块、单文件已经过长的场景。

C. 结构化数据库表（如 SQLite memories 表）

将每条记忆存为数据库记录（包含 id、适用范围 scope、正文 content、来源 source、状态 status、更新时间 updated_at 等字段）。适合需要按项目/状态精确过滤、保留更正轨迹或由程序并发写入的场景。

D. 向量索引或混合检索库（如 SQLite FTS + Embedding 向量库）

在结构化条目之上额外建立关键词倒排索引与语义向量索引。适合记忆条目非常多、用户提问用词与原文字面差异较大的场景，但会引入向量计算与检索评测成本。

4. 什么时候、怎么增删改查（CRUD）？

明确了存在哪里之后，还要定下什么时候触发、由谁执行“增、查、改、删”。注意区分“存在哪里（存储介质）”与“谁来写（人工 vs 模型工具 vs 后台提取）”是两个正交的选择：

增（Create：什么时候写入、谁来写？）

  • 方式 1：用户手动编辑文件（最简单可靠）：当用户确认一条长期约定（如“本项目用 uv run”）时，直接打开 MEMORY.md 写入。注意：在普通对话里模型口头回答“好的，我记住了”只会留在当前 SessionLog，不会自动写入记忆文件。
  • 方式 2：模型在对话中调用记忆工具写入：用户明确要求“请记住这条规则”时，模型发起 memory_write 或文件写入工具调用，经 Policy 权限检查或用户确认后落盘。
  • 方式 3：会话结束后后台自动提炼：任务或会话结束时，后台流程扫描 SessionLog，提炼出值得复用的事实写入记忆库。省去人工整理，但必须额外防范“把模型猜错的结论当成事实写入”以及重复写入问题。

查（Read / Query：什么时候读取、怎么放进模型请求？）

  • 方式 1：每次任务启动时全量读取（适合短文件）：run_task() 启动时直接读取当前工作区的 MEMORY.md 全文，交给 Context 组装成参考资料消息放进 ModelRequest。优点是稳定直接、无需模型先调工具找文件；代价是每次请求都要占用这部分输入预算。
  • 方式 2：每次请求前按关键词或向量检索（适合数据库 / 向量库）：在 Context 组装请求前，先按当前项目范围过滤，再用本次用户问题检索最相关的 Top-K 条记忆放入请求。
  • 方式 3：模型按需调用工具读取（适合索引 + 主题文件）：任务启动时只向模型提供简短目录索引；当模型判断需要某个主题的细节时，再主动调用读取或检索工具拉取正文。

改（Update：约定变化时怎么更新、新旧冲突听谁的？）

  • 文件方案：直接修改 MEMORY.md 中的对应内容。为避免同一次多步任务执行中途上下文突然变化，任务执行期间应锁定启动时读取的快照，修改后的内容在下一次任务启动时生效。
  • 数据库与索引方案：按条目 id 更新正文并同步刷新检索索引；若需保留历史审计，可将旧条目标记为 superseded（已替代）并插入新条目。
  • 新旧冲突优先级：当旧会话历史（SessionLog）里残留着旧做法，而当前读取的 Memory 已更新为新约定时，系统指令必须明确优先级：本次用户明确要求 > 当前读取的 Memory > 历史对话中的旧默认约定。

删（Delete / Forget：什么时候删除、删除的边界在哪？）

  • 文件方案：删掉 MEMORY.md 中的过期段落，或直接清空、删除文件；下一次任务启动时便不再注入该内容。
  • 数据库与自动提炼方案：将条目标记为 deleted 并同步从检索索引中移除；若开启了后台自动提炼，还必须阻止后台从旧 SessionLog 里把同一内容再次提取回来。
  • 删除的边界：删除 Memory 的作用是停止在后续任务中自动加载该知识，但它不会自动抹掉旧会话 SessionLog 里已经发生过的历史问答。

5. 源码比较：pi 与 Deep Agents 怎样加载项目知识？

两者都能从文件提供持续可用的项目背景。pi 将相关文件称为项目上下文；Deep Agents 使用 MemoryMiddleware。这里比较的是文件怎样进入模型输入，不能据此推断它们都具备自动提取或结构化记忆库。

pi：从目录发现上下文文件

  1. 初始化与数据：资源加载器根据 cwd 和 agentDir 查找上下文文件，保存 path 与 content；包含全局来源与目录层级来源。
  2. 调用与输入：buildSystemPrompt() 接收已加载的上下文文件，将路径与正文放进系统提示词的项目上下文部分。
  3. 读取与失败：loadContextFileFromDir() 读取文件，遇到读取异常会输出警告；这是一种实现选择，应用也可以选择明确失败。

固定版本依据：resource-loader.ts 的文件发现与读取、system-prompt.ts 的输入组装，提交 9d2ec7f。

Deep Agents：显式配置文件来源

  1. 初始化与数据：创建 MemoryMiddleware 时传入 backend 与 sources；文件内容以路径为键保存在 memory_contents。
  2. 调用与输入：before_agent() 在状态尚未包含记忆时下载来源文件；默认情况下，模型调用包装器经 modify_request() 将格式化的记忆加入系统消息。
  3. 读取与失败：文件不存在时跳过；其他下载错误抛出异常。已有 memory_contents 时不会在这个钩子里重新加载，更新何时可见取决于状态如何刷新。

固定版本依据：初始化参数、before_agent()、请求组装与调用，提交 97f856d。

本教程的归纳：目录发现便于继承项目约定，但需要解释加载范围与顺序；显式来源便于控制读哪些文件，但需要管理配置与刷新时机。两者的文件内容都需要进入模型输入才能生效，保存文件本身还不够。

6. 什么时候才需要结构化条目？

一份人工维护的短文件，可以用文件路径标明来源，用工作区限制适用范围。需要逐条更正、查询或自动整理时，再增加条目结构。

自动提取与结构化存储需要补充的信息
  • 来源：记录对应会话、任务或原始资料的位置，方便核对。
  • 适用范围：明确属于哪个用户或项目，查询时先限制范围。
  • 有效状态：区分正在使用、被更正和已删除的内容，避免查询返回旧值。
  • 确认依据：区分用户明确提供的事实与模型候选；模型不能替用户生成确认记录。

只有需要保留更正过程时，才增加版本关联；只有知识具有明确有效期时，才增加过期时间。这些字段服务于具体行为，不是 Memory 的统一格式。

7. 更正与遗忘时的三个核心边界

无论采用文件还是数据库方案，处理知识的更正与遗忘时，都必须把清三个关键边界：

  • 单次任务内锁定不可变快照：多步任务执行中途如果允许底层记忆文件被随时改动，会导致第 1 步和第 2 步发给模型的项目约定不一致，引发推理混乱。因此，修改后的记忆只能在下一次任务生效，当前任务必须锁定启动时读取的快照。
  • 冲突消解遵循三层优先级：当新旧约定发生冲突时，不能靠运气让模型猜，系统指令必须声明规则：本次用户明确要求 > 当前读取的 Memory 默认约定 > 会话历史中的旧默认记录。
  • 区分“停止注入”与“物理抹除”：删除 Memory 的本质是停止在后续任务中作为背景资料自动加载。它不能、也不应该自动去重写或篡改过去已保存在 SessionLog 里的真实问答历史。

8. 本项目当前选择：一份人工维护的项目文件

阶段 0–4 已实现会话保存、续接与上下文预算；Memory 尚未实现。阶段 5 已选择工作区根目录的 MEMORY.md：由用户编辑，每次任务开始时读取，路径与正文一起进入预算检查，同一任务使用同一份内容。

选择它是因为少量项目约定可以直接检查，不需要先解决提取准确率与检索质量。初始化位置、现有源码入口和拟议调用流程见 阶段 5：怎样接入现有闭环。

9. 期望达到的效果

  • 跨会话复用：新会话获得当前项目的已保存知识，而无需加载其他会话的全部历史。
  • 范围与来源明确：能查明读取的是哪个项目的哪份资料。
  • 更正及时生效：修改或删除记忆后，新任务不再从记忆来源加载旧内容。
  • 预算和权限有效：记忆计入输入预算，工具执行仍由 Policy 决定。

具体检查步骤见 阶段 5：实现后怎样验证。
