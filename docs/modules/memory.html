Memory：选择跨会话保留的知识

1. 问题起点：新会话需要知道什么？

  • 用户（会话 A）：“这个项目使用 uv，Python 命令请使用 uv run。”
  • 模型：“好的。”
  • （结束会话 A，新建会话 B）
  • 用户（会话 B）：“怎样运行测试？”

新会话没有前面的消息，模型就缺少项目约定。Memory 的作用是把值得复用的知识单独保存，在后续任务需要时重新提供给模型。它不是修改模型参数，也不是把所有会话历史都放进请求。

  • 值得保留：已确认的项目事实、长期偏好和经过验证的经验，例如“项目使用 uv”。
  • 需要重新核对：测试结果、临时报错和文件具体行内容会随代码变动而失效，不能视为恒定事实，引用或排查时必须重新核实最新状态。

2. Session、Memory 与 Context 怎样配合？

  • Session 保存发生过什么：按会话保存问题、回答与工具回执，供查询或续接对话。
  • Memory 保存值得复用什么：保存选定的事实或偏好，说明来自哪里、适用于哪个项目或用户。
  • Context 决定本次发送什么：把本次问题、选中的历史和适用记忆组装成模型输入，并检查完整请求的预算。

一次使用记忆的任务可以分为以下步骤：

  1. 应用确定范围：根据当前工作区或用户配置，指定可读取的记忆来源。
  2. Memory 读取资料：返回内容及其来源；条目多时，也可以先查找与任务相关的条目。
  3. Context 检查输入：将记忆与其他输入一起计量，再决定是否能够发送。
  4. 模型参考资料回答：需要操作文件时提出工具调用，执行仍经过 Tools 与 Policy。

记忆可以由用户直接维护，也可以从会话记录中提取。因此 Session 能提供写入来源，但 Memory 不必依赖自动扫描历史。模型提出的候选与用户已经确认的事实要分清；记忆中的“允许覆盖文件”也不能替代实际权限检查。

没有记忆与读取失败是两种结果：前者可以正常继续，后者应按应用约定明确处理，严禁在代码中用 try...except Exception: return None 悄悄当成“没有记忆”：

  • 没有记忆（预期内的空状态）：未创建 MEMORY.md（捕获 FileNotFoundError）或正文仅含空白。此时解析函数返回 None，流程正常推进，本次请求不注入记忆消息。
  • 读取失败（非预期的系统异常）：文件存在但无访问权限（PermissionError）、编码损坏（UnicodeDecodeError）、软链接指向工作区外部（越界）或目标是目录。若静默吞掉异常，会导致关键项目规范悄然失效，引发模型盲目操作。工程上应按约定显式处理：
    • 强一致模式（本项目采用）：在发出第 1 步模型请求前直接抛出异常中断执行（Fail-Fast），强制用户修正损坏的配置文件后再运行；
    • 容错辅助模式（如 pi）：若记忆仅作参考，可捕获异常并在控制台/日志中显式输出 Warning 告警并标记运行降级，绝不装作无事发生。

3. Memory 的存储介质与数据结构（从纯文本到多维命名空间）

设计 Memory 时，首先要划分“存什么内容”以及“采用什么数据结构和存储介质”：

  • 存什么内容（核心原则）：只存跨会话反复使用的项目事实与规范（如依赖管理工具、编码约束）和经过验证的排障经验（现象、原因与解法）。临时报错、单行代码或瞬时测试结果应在需要时通过工具重新核对，不属于持久记忆；固定的多步执行流程则适合打包成 Skill。

按系统复杂度从低到高，业界常见的存储形态与数据结构分为四类：

A. 单份 Markdown 纯文本（如 <workspace>/MEMORY.md、CLAUDE.md）

直接存放在项目工作区根目录（仅对当前项目生效）或用户全局配置目录（如 ~/.agent/MEMORY.md）。纯文本天然具备极高的可读性，便于开发者直接查看修改，并能直接纳入 Git 进行代码审查（PR）。适合规则条目较少、以核心项目约定为主的阶段。

B. 目录索引 + 分主题 Markdown 文件（如 MEMORY.md + memories/*.md）

主文件只保留精简的目录与一句话摘要，详细的模块规范或故障案例拆分到独立主题文件中。适合知识按模块或主题明显分块、单文件已经过长导致阅读困难的场景。

C. 结构化关系表与层次化命名空间（如 SQLite memories 表、LangGraph BaseStore）

将每条知识保存为包含完整元数据的结构化条目。适合多租户系统、多项目隔离，或需要程序并发读写、保留更正审计轨迹的场景。一个标准的结构化条目通常包含以下元数据：

  • 来源（Source）：记录产生该知识的原始会话 ID、用户任务或文档链接，便于后续追溯和人工核实。
  • 适用范围（Scope）：明确知识属于全局用户、组织团队还是特定项目，在读取和检索时作为硬性过滤条件。
  • 有效状态（Status）：标记当前为有效（active）、已废弃（superseded）还是已删除（deleted），避免检索出过期规则。
  • 确认依据（Confirmation）：区分是由用户明确声明的事实，还是模型生成的候选建议；未经人类确认的模型猜测不能作为硬规则生效。

D. 向量索引或混合检索库（如 SQLite FTS + Embedding 向量库）

在结构化条目之上额外建立关键词倒排索引与语义向量索引。适合条目极多、用户提问用词与记忆原文字面差异较大的场景，但会引入向量计算、分块嵌入和检索评测的额外工程成本。

4. 核心机制：写路径（维护/提炼）与读路径（检索/注入）

明确了数据结构后，必须定下 Memory 的两条核心流水线：知识如何沉淀落盘（写路径）与知识如何进入模型输入（读路径）。注意：“存在哪里”与“谁来读写”是正交的工程选择。

4.1 写路径（Write Pipeline）：知识如何沉淀落盘？

知识写入可以由人工主导，也可以由模型或后台流程辅助。无论底层是 Markdown 还是数据库，写入都可以归纳为三条通道：

  • 通道 A：人工直接录入与命令维护（最稳健，零幻觉）：用户确认一条长期约定后，直接编辑 MEMORY.md 或在终端输入 /memory 命令。注意：普通对话中模型口头回答“好的，我记住了”只会追加在 SessionLog 中，绝不自动篡改物理记忆文件。
  • 通道 B：对话中模型主动调用工具（即时响应，受权限约束）：用户明确要求“请记住这条规范”时，模型发起 memory_write 工具调用；该动作必须经由 Policy 权限检查或人工弹窗确认后方可落盘。
  • 通道 C：会话后离线反思提炼（高自动化，须去噪去重）：任务或会话结束后，后台异步 Reflection 任务扫描 SessionLog，提炼出值得复用的事实批量写入。该通道不阻塞在线交互，但必须增加防幻觉校验，防止把模型的临时猜测沉淀为永久事实。
  • 统一写入治理关卡：所有通道在落盘前均须完成三件事：绑定作用域（Scope）防止越界；去噪核查剔除瞬时报错；冲突替代若新旧约定矛盾，更新正文并标记旧条目为 superseded。

4.2 读路径（Read Pipeline）：知识如何进入模型输入？

知识保存后，必须在恰当的时机组装到模型请求中才能真正生效。常见的读取注入方式同样有三条通道：

  • 通道 1：任务启动时全量加载（短规则首选，零延迟，非 RAG）：run_task() 启动时自动读取当前工作区的 MEMORY.md 全文，由 Context Manager 组装为系统参考消息。优点是稳定直接、模型无需先调工具找文件；代价是每次请求都要消耗固定输入预算，仅适合几十行以内的项目约定。
  • 通道 2：每次请求前动态检索（经典被动 RAG，海量条目首选）：
    • 技术本质：本质就是经典的 RAG（检索增强生成，Pre-retrieval RAG） 模式在记忆系统中的落地。
    • 执行机制：在组装每步请求前，外围框架先按租户或项目范围硬过滤，再用当前用户问题做关键词（FTS/BM25）或向量相似度（Embedding Top-K）计算，仅提取最相关的几条记忆切片拼入 Prompt。
    • 交互特征：模型被动接收，无感知。外部系统在请求发出前静默完成检索与组装，模型不需要先调用工具，适合多租户背景、条目海量且单条规则相对独立的知识库场景。
  • 通道 3：运行期模型按需查阅（渐进式披露 + Agentic RAG，大文档首选）：
    • 技术本质：将 “渐进式披露（Progressive Disclosure）” 的信息分层策略与 “基于工具的主动式检索（Agentic RAG）” 相结合。
    • 执行机制：
      • 第一层（轻量路标，渐进披露）：初始输入绝不塞入海量正文，仅提供简短的主题目录或索引大纲（如列出有哪些可用规则模块），以极低的 Token 成本让模型“知道系统里存在什么”。
      • 第二层（按需检索，工具召回）：模型在多步执行中遇到专业问题时，自主发起工具调用——若查阅某模块正文调用 read_memory(topic)（定向抽取）；若在长文档中找细节，则自主提炼精准搜索词调用 search_memory(query)（触发底层的全文或向量召回）。
    • 交互特征：模型主动驱动，支持多跳。由模型根据当前任务上下文判断“查不查、去哪查、搜什么词”，甚至在结果不符时换词重搜。适合体系复杂、单篇篇幅巨大的架构指南与业务文档。

4.3 读写协同的三大工程铁律

  • 铁律一：单次任务内锁定不可变快照：多步任务执行中途如果允许底层记忆文件被随时改动，会导致第 1 步与第 2 步模型看到的项目约定不一致，引发严重的推理混乱。因此，修改后的记忆只能在下一次任务生效，当前任务内部必须锁定启动时读取的内存快照。
  • 铁律二：三层冲突消解优先级：当新旧约定发生冲突时，不能让模型凭运气猜测，系统指令必须声明明确的裁决准则：本次用户明确要求 > 当前读取的 Memory 默认约定 > 历史对话中的旧记录。
  • 铁律三：停止注入 vs 物理抹除：删除 Memory 的本质是停止在后续任务中作为背景资料自动加载。它绝不能、也不应该去重写或篡改过去已保存在 SessionLog 里的真实对话与工具审计历史。

5. 主流 Agent 的 Memory 架构全景与源码方案对比

在不同类型的 Agent 系统中，由于交互目标、执行环境和记忆生命周期不同，Memory 的设计呈现出截然不同的架构流派。以下结合固定开源源码与官方机制，系统拆解业界最具代表性的五大方案：

5.1 方案一：文件约定与层级目录发现（pi / Claude Code / Cursor）

这是代码开发类 Agent 最主流、最轻量的方案。其核心逻辑是：不依赖任何外部数据库，直接将纯文本文件作为知识载体，利用操作系统的目录树结构实现规则的层级继承与自动发现。

  • 数据载体与多层作用域：
    • 全局用户级（User-Level）：存放在用户根目录（如 ~/.claude/CLAUDE.md 或 ~/.pi/agent/），记录跨所有项目的通用偏好（如“使用中文回答”、“默认使用 TypeScript 严格模式”）。
    • 项目仓库级（Project-Level）：存放在工作区根目录（如 CLAUDE.md、AGENT.md、.cursorrules），记录当前代码库的构建工具、测试命令与架构约束。
    • 子目录与路径级（Path-Level）：存放在特定模块目录（如 .claude/rules/*.md 或 .cursor/rules/*.mdc），通过 glob 路径规则仅在编辑特定文件时动态激活。
  • 读取与加载机制（以 pi 源码为例）：

    在 pi 源码中，resource-loader.ts 的 DefaultResourceLoader 实现了目录递归扫描：

    1. 向上递归发现：从当前工作区 cwd 出发向上遍历父目录，结合全局 agentDir，查找所有上下文文件并读取为 { path, content } 对象。读取异常时记录警告而不中断主流程。
    2. 组装系统提示词：在 system-prompt.ts 中，buildSystemPrompt() 遍历已加载的上下文文件，将文件路径与正文格式化为系统提示词中的 projectContext 独立段落。
  • 工程实践（以 Claude Code 为例）：

    Claude Code 通过 CLAUDE.md 体系实现了灵活的记忆管理：支持开发者通过终端命令 /memory 实时查看和人工编辑生效的记忆列表；在较新版本中，还支持模型在识别到明确的项目约定后，提炼出单条事实供用户确认后存入 .claude/ 记忆目录。

  • 架构取舍与适用场景：
    • 优势：高透明度、零外部依赖；纯文本天然支持通过 Git 进行版本控制、差异比对与代码审查（PR），非常契合团队工程协作。
    • 局限与代价：缺乏动态语义检索能力。当规范文件体积庞大时，每次请求全量拼入系统提示词会大量挤占模型的输入 Token 预算。

5.2 方案二：中间件切入与存储抽象解耦（Deep Agents）

在个人电脑上运行 Agent（如本地开发中的 Cursor、Claude Code）时，硬盘是永久持久化的，直接读取 ~/.claude/CLAUDE.md 极其自然。但当 Agent 部署到云原生、多租户或容器化沙箱环境时，底层运行逻辑发生了根本变化：

  • 为什么云端节点“无法假定本地存在固定物理文件”？
    • 容器随生随灭（节点无状态）：在云端或沙箱中，运行 Agent 的 Docker 容器或 Pod 往往是临时的。任务一执行完毕，容器连同其本地硬盘就会被直接销毁重置，存放在本地磁盘上的记忆文件彻底丢失。
    • 多节点请求漂移：用户上一秒发起的请求在 A 容器执行，下一秒追问可能被网关调度分发到了 B 容器。B 容器根本访问不到 A 容器的本地文件系统。
    • 多租户隔离与安全：同一台服务器可能先后承载不同企业客户的任务，如果直接把记忆当作明文文件保存在本地，极易造成数据混淆或跨租户安全泄漏。
  • 核心破局思路：计算与存储彻底解耦：

    执行节点只负责纯粹的流程调度与计算（即“无状态 Runner”），而记忆数据必须存放在远端独立的中心化存储中（如 Redis、PostgreSQL、S3 等云端对象存储）。Deep Agents 展现了将记忆抽象为独立中间件并解耦底层存储后端的标准架构：

  • 核心抽象与生命周期钩子：

    Deep Agents 在 memory.py 中定义了 MemoryMiddleware，通过框架提供的中间件机制切入 Agent 生命周期：

    1. 显式来源声明：创建中间件时传入待读取的来源路径列表 sources 和底层存储后端 backend（可以是本地目录、内存 Mock，或 S3 等远程对象存储）。
    2. 前置拉取（before_agent）：在 before_agent(state) 钩子中，中间件检查当前 Agent State；若尚未加载记忆，则通过 backend.read() 异步拉取 sources 中的全部内容，写入 State 中的 memory_contents 字典。
    3. 请求注入（modify_request）：在 modify_request(request, state) 中，中间件将格式化后的 memory_contents 拼接到 SystemMessage 发给模型。
  • 架构取舍与适用场景：
    • 优势：存储后端可插拔，运行时与物理宿主环境彻底解耦；多租户权限可由后端统一审计，非常适合无服务器（Serverless）或分布式 Agent。
    • 局限与代价：来源必须在 Agent 启动前由配置或外部调用方显式指定，无法在执行中根据文件系统的目录结构自发嗅探或动态扩展。

5.3 方案三：类操作系统分层内存与模型自管理（MemGPT / Letta）

在需要超长周期、无限对话的个人助手或虚拟伴侣场景中，上下文窗口即使达到数百万 Token 也无法承受长年累月的原始交互。MemGPT（现为 Letta）率先提出了借鉴现代计算机操作系统分层存储架构（Hierarchical Memory）的经典方案，并把记忆的增删改查完全交由模型自主驱动。

  • 三层存储体系（类比计算机体系结构）：
    1. 工作上下文（Working Context / 内存 RAM）：留在当前上下文窗口内的核心提示区。其中专门划出一块核心记忆区（Core Memory），分为 persona（Agent 的人设准则与长期使命）和 human（用户的关键画像与硬性偏好）。这部分内容在每一步请求中都全量可见，容量严格受限。
    2. 回想存储（Recall Storage / 二级缓存）：按时间顺序追加保存的完整对话事件与历史交互记录，支持按时间窗口或全文关键词搜索。
    3. 归档存储（Archival Storage / 外存磁盘）：由外部数据库（通常为向量数据库）持久化存储的海量事实知识库，容量理论上无上限。
  • 模型自管理工具（Agent-Driven Tools）：

    不同于系统静默组装，MemGPT 将记忆的维护赋予模型一组显式的内置工具：

    • core_memory_append(name, content) / core_memory_replace(name, old_content, new_content)：模型在对话中察觉到用户的新事实时，主动发起工具调用更新自己的 human 或 persona 区块。
    • archival_memory_insert(content)：模型主动把复杂背景、文档总结或重要推导沉淀到长期向量库中。
    • archival_memory_search(query, page)：当当前工作内存缺乏某领域知识时，模型主动发起语义检索工具调用，从归档库中翻查历史资料。
  • 架构取舍与适用场景：
    • 优势：突破上下文窗口物理上限，赋予 Agent 跨越数月甚至数年的“自主成长”能力，适合终身学习助手与沉浸式 NPC。
    • 局限与代价：严重依赖模型的自反思与决策准确性。在实际工程中，模型容易产生“记忆幻觉”、误将废话频繁存入 Core Memory 挤占宝贵空间，或在不需要的时候频繁调用检索工具增加延迟与成本。

5.4 方案四：多租户命名空间与语义检索键值库（LangGraph / LangChain Long-Term Memory）

在企业级应用中，Agent 往往需要同时服务数千名用户、处理跨多个团队的项目知识，因此多租户隔离、权限归属与混合检索能力成为首要考量。LangGraph 的 Long-Term Memory 体系提供了工业级的抽象实现。

  • 核心抽象与数据模型（BaseStore）：

    LangGraph 引入了跨会话持久化的 BaseStore（底层可对接 Postgres、Redis 等存储），采用层级化的 (namespace, key, value) 三元组组织数据：

    • 命名空间隔离（Namespace）：通过元组实现多维作用域路由。例如：
      • 个人偏好：("users", user_id, "profile")
      • 团队规范：("orgs", org_id, "teams", team_id, "rules")
      • 任务文档：("projects", project_id, "docs")
    • 键值读写与向量混合检索：支持 store.get(namespace, key) 精确获取，更支持 store.search(namespace, query="...", limit=K) 在指定命名空间下直接调用向量模型进行 Top-K 语义检索。
  • 双通道写入管道（Two-Lane Writing）：
    • 实时通道（In-Loop Tool）：对话过程中，Agent 可以直接调用记忆更新工具，经业务校验后写入指定命名空间。
    • 异步反思通道（Offline Reflection Node）：会话结束后，系统在后台启动一个独立的反思 Agent（Reflection Node）。该节点扫描本次对话的 SessionLog，提取出有价值的新事实、合并冲突偏好后调用 store.put() 批量落库，完全不增加用户在线问答的等待耗时。
  • 架构取舍与适用场景：
    • 优势：租户隔离边界清晰，权限管控严格；既能精确读取关键配置，又能模糊匹配非结构化经验，非常适合企业级 SaaS 平台。
    • 局限与代价：架构非常重，必须依赖外部数据库、Embedding 服务与后台反思调度任务，初始搭建与运维成本高。

5.5 方案五：事件驱动事实沉淀与用户可控画像（OpenAI ChatGPT / Codex / AgentScope Java）

为了让普通用户无需理解文件格式或命名空间，面向消费者的通用助手多采用由大模型自动提炼事实（Fact List），并配合前端可视化面板供用户审计与管理的方案。

  • 机制与交互流程：
    1. 隐式提炼与事件触发：用户在对话中透露出持久特征（如“我平时在 macOS 上用 zsh，写 Python 优先使用 3.12”），服务端模型在推理输出时附带一个结构化的 Memory Update Event。
    2. 前端感知与审计面板：界面给出轻量级提示（如“已更新记忆”）。用户随时可在设置中打开“个人记忆管理面板”，查看所有已保存的单条事实条目，并支持单条编辑或彻底删除。
    3. 上下文选择性注入（按需拼装系统提示）：

      用户沉淀的事实条目日积月累可能有几十甚至上百条（如“养了一只猫”、“喜欢简洁代码”、“技术栈是 Python 3.12”）。若每次提问都不加筛选地全部塞入，既浪费 Token 预算，又会分散模型的注意力。因此系统在组装输入时执行“按需筛选 + 紧凑注入”：

      • 筛选策略（相关性 vs 全量）：
        • 海量条目时（按问题相关性筛选）：当用户问代码时，后台先做语义检索，仅挑出与编程相关的偏好；宠物或生活偏好被自动过滤（这正是 4.2 节通道 2 动态检索的典型体现）；
        • 条目较少时（全部有效事实）：若用户累计沉淀的事实只有十几条，直接打包全部尚未被删除或替代的有效偏好。
      • 紧凑格式化呈现：将选中的事实从数据库中取出，拼装为最省 Token 的纯文本条目清单，作为系统指令（System Prompt）的一部分发送给模型： 
        [已知用户偏好与背景约定]
- 用户偏好使用 Python 3.12，函数必须包含类型标注
- 代码风格要求精简，不输出多余的寒暄与废话
      • 无感生效：模型带着这组定制事实生成回答，用户会感觉模型“懂我的习惯”，且全程模型无需调用任何检索工具。
    4. AgentScope Java 的实践：在 AgentScope Java memory.md 中，系统专门设计了 LongTermMemory 接口与压缩整理流程，明确区分了“完整的执行历史（Session Log）”与“经提炼后的长期记忆条目（LongTermMemory）”。
  • 架构取舍与适用场景：
    • 优势：对终端用户极度友好，无需学习任何特定命令或维护格式；用户可直观审查和纠错。
    • 局限与代价：自动提炼容易将短期上下文（如“我这周在度假”）误判为永久偏好；当新旧偏好冲突时，若缺乏人工干预，系统容易在多条相互矛盾的记忆间摇摆。

7. 期望达到的效果

  • 跨会话复用：新会话获得当前项目的已保存知识，而无需加载其他会话的全部历史。
  • 范围与来源明确：能查明读取的是哪个项目的哪份资料。
  • 更正及时生效：修改或删除记忆后，新任务不再从记忆来源加载旧内容。
  • 预算和权限有效：记忆计入输入预算，工具执行仍由 Policy 决定。

具体检查步骤见 阶段 5：怎样验证。
