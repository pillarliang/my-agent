Memory：选择跨会话保留的知识

1. 问题起点：新会话需要知道什么？

  • 用户（会话 A）：“这个项目使用 uv，Python 命令请使用 uv run。”
  • 模型：“好的。”
  • （结束会话 A，新建会话 B）
  • 用户（会话 B）：“怎样运行测试？”

新会话没有前面的消息，模型就缺少项目约定。Memory 的作用是把值得复用的知识单独保存，在后续任务需要时重新提供给模型。它不是修改模型参数，也不是把所有会话历史都放进请求。

  • 值得保留：已确认的项目事实、长期偏好和经过验证的经验，例如“项目使用 uv”。
  • 需要重新核对：当前测试结果、临时报错和文件某一行的内容；这些信息随时间或代码变化，不能当作一直成立的事实。

2. Session、Memory 与 Context 怎样配合？

  • Session 保存发生过什么：按会话保存问题、回答与工具回执，供查询或续接对话。
  • Memory 保存值得复用什么：保存选定的事实或偏好，说明来自哪里、适用于哪个项目或用户。
  • Context 决定本次发送什么：把本次问题、选中的历史和适用记忆组装成模型输入，并检查完整请求的预算。

一次使用记忆的任务可以分为以下步骤：

  1. 应用确定范围：根据当前工作区或用户配置，指定可读取的记忆来源。
  2. Memory 读取资料：返回内容及其来源；条目多时，也可以先查找与任务相关的条目。
  3. Context 检查输入：将记忆与其他输入一起计量，再决定是否能够发送。
  4. 模型参考资料回答：需要操作文件时提出工具调用，执行仍经过 Tools 与 Policy。

记忆可以由用户直接维护，也可以从会话记录中提取。因此 Session 能提供写入来源，但 Memory 不必依赖自动扫描历史。模型提出的候选与用户已经确认的事实要分清；记忆中的“允许覆盖文件”也不能替代实际权限检查。

没有记忆与读取失败是两种结果：前者可以正常继续，后者应按应用约定明确处理，不能悄悄当成“没有记忆”。

3. 先分清：记什么、谁来写？

  • 项目事实与偏好：如依赖管理方式、报告格式；适合在相关任务中反复使用。
  • 经验记录：如一次排障的现象、原因与解决办法；应保留当时的环境和依据，供类似问题参考。
  • 固定操作方法：如每次发布要执行的步骤；当它已经成为可重复执行的流程，可以整理成 Skill。

这些内容都可以先由人写入文件。“有没有长期记忆”和“会不会自动提取记忆”是两回事。自动提取节省整理时间，但增加核对事实、处理冲突和防止错误写入的成本。

4. 怎样保存和读取？

A. 一份短文件，按任务读取全文

用户把知识写进 Markdown 文件，程序在任务开始时读取。内容少时最容易理解和检查，也能直接编辑、更正与删除；代价是每次请求都要承担全文的输入成本。

B. 索引文件加主题文件，按需补读

启动时只加载简短目录，需要某个主题时再读正文。适合知识已经分成多个主题的情况；需要解决索引与正文同步，以及没有读到相关正文时怎样处理。

C. 数据库条目，按项目和关键词查询

用 SQLite 等数据库保存条目，按项目、状态和关键词筛选。适合需要精确查询、更正记录或并发写入的情况；代价是维护表结构和查询逻辑。

D. 向量或混合检索

把文本转换为向量，查找含义相近的候选，也可以结合关键词查询。适合条目多、提问用词变化大的情况；需要额外的向量生成、索引维护与检索效果评测。只能在当前用户有权访问的范围内查询，含义相近也不代表事实仍然有效。

这些是存储和读取方式，可以逐步组合；自动提取则决定谁生成写入内容，不是另一种存储介质。

5. 源码比较：pi 与 Deep Agents 怎样加载项目知识？

两者都能从文件提供持续可用的项目背景。pi 将相关文件称为项目上下文；Deep Agents 使用 MemoryMiddleware。这里比较的是文件怎样进入模型输入，不能据此推断它们都具备自动提取或结构化记忆库。

pi：从目录发现上下文文件

  1. 初始化与数据：资源加载器根据 cwd 和 agentDir 查找上下文文件，保存 path 与 content；包含全局来源与目录层级来源。
  2. 调用与输入：buildSystemPrompt() 接收已加载的上下文文件，将路径与正文放进系统提示词的项目上下文部分。
  3. 读取与失败：loadContextFileFromDir() 读取文件，遇到读取异常会输出警告；这是一种实现选择，应用也可以选择明确失败。

固定版本依据：resource-loader.ts 的文件发现与读取、system-prompt.ts 的输入组装，提交 9d2ec7f。

Deep Agents：显式配置文件来源

  1. 初始化与数据：创建 MemoryMiddleware 时传入 backend 与 sources；文件内容以路径为键保存在 memory_contents。
  2. 调用与输入：before_agent() 在状态尚未包含记忆时下载来源文件；默认情况下，模型调用包装器经 modify_request() 将格式化的记忆加入系统消息。
  3. 读取与失败：文件不存在时跳过；其他下载错误抛出异常。已有 memory_contents 时不会在这个钩子里重新加载，更新何时可见取决于状态如何刷新。

固定版本依据：初始化参数、before_agent()、请求组装与调用，提交 97f856d。

本教程的归纳：目录发现便于继承项目约定，但需要解释加载范围与顺序；显式来源便于控制读哪些文件，但需要管理配置与刷新时机。两者的文件内容都需要进入模型输入才能生效，保存文件本身还不够。

6. 什么时候才需要结构化条目？

一份人工维护的短文件，可以用文件路径标明来源，用工作区限制适用范围。需要逐条更正、查询或自动整理时，再增加条目结构。

自动提取与结构化存储需要补充的信息
  • 来源：记录对应会话、任务或原始资料的位置，方便核对。
  • 适用范围：明确属于哪个用户或项目，查询时先限制范围。
  • 有效状态：区分正在使用、被更正和已删除的内容，避免查询返回旧值。
  • 确认依据：区分用户明确提供的事实与模型候选；模型不能替用户生成确认记录。

只有需要保留更正过程时，才增加版本关联；只有知识具有明确有效期时，才增加过期时间。这些字段服务于具体行为，不是 Memory 的统一格式。

7. 怎样更正和遗忘？

  • 人工文件方案：直接修改或删除正文，下次读取时使用新内容。若缓存了旧内容，需要同步刷新缓存。
  • 条目与索引方案：更正或删除正式条目时，同步更新查询状态和检索索引，避免旧值继续被返回。
  • 自动提取方案：删除后还要阻止后台流程从旧对话中重新提取同一内容。

删除记忆不等于删除历史：旧问答可能仍在 Session 中，已发送给模型的内容也无法撤回。说明遗忘效果时，要明确指的是“不再从记忆来源自动加载”，还是还要另外删除历史和其他副本。

8. 本项目当前选择：一份人工维护的项目文件

阶段 0–4 已实现会话保存、续接与上下文预算；Memory 尚未实现。阶段 5 已选择工作区根目录的 MEMORY.md：由用户编辑，每次任务开始时读取，路径与正文一起进入预算检查，同一任务使用同一份内容。

选择它是因为少量项目约定可以直接检查，不需要先解决提取准确率与检索质量。初始化位置、现有源码入口和拟议调用流程见 阶段 5：怎样接入现有闭环。

9. 期望达到的效果

  • 跨会话复用：新会话获得当前项目的已保存知识，而无需加载其他会话的全部历史。
  • 范围与来源明确：能查明读取的是哪个项目的哪份资料。
  • 更正及时生效：修改或删除记忆后，新任务不再从记忆来源加载旧内容。
  • 预算和权限有效：记忆计入输入预算，工具执行仍由 Policy 决定。

具体检查步骤见 阶段 5：实现后怎样验证。
