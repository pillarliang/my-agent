模块原理与方案

Memory：选择跨会话保留的知识

1. 实现原理：写入和读取是两个流程

报告任务结束后，可以复用的知识可能是“这个项目使用 uv”和“用户偏好报告列出来源”。“本次测试失败”则与产物版本和时刻相关，不宜直接保存为永远有效的项目事实。

Memory：受控写入、读取与遗忘

后续能力 · 阶段 3 已有会话记录，尚未实现跨会话长期记忆。

写入流程判断“是否值得记住”；读取流程判断“现在是否适用”。即使自动提取质量很好，后续仍要处理过期、冲突和撤销。相似度只帮助寻找候选，不证明内容真实、有效或获准使用。

2. 与相关模块怎样交互

State 提供原始记录，Memory 管理可复用条目，Context 选择本次材料。例如用户明确提出“以后报告都附来源”：记忆写入入口接收这条偏好和适用范围，或从 State 取得带记录 ID 的原始消息；核对来源、冲突与确认条件后才提交条目。模型可以辅助提取候选，但生成候选不等于事实已经确认。

开始新任务时，应用或 Context 向 Memory 提供任务线索和可访问范围；Memory 返回带来源、版本和有效状态的候选，Context Manager 再根据输入预算选择要发送的内容。检索无命中、记忆已过期和服务查询失败是不同结果，不应都显示成“没有记忆”。

若让模型通过工具写入记忆，写入仍经 Tools 和 Policy 授权；记忆内容不能扩大权限。当前 Policy 只处理文件操作权限；未来若按用户或项目管理记忆条目，还需要定义条目访问权限。保存会话和提炼长期知识可以独立建设。

3. 先区分知识类型和存储方案

知识可以分成事实与偏好、经验案例、可复用方法。前两类适合保存来源和适用条件；多步骤方法也可能更适合整理成 Skill。分类帮助确定生命周期，不要求为每类部署一个数据库。

文件、SQL 和向量索引则属于另一组选择：文件方便人工编辑，SQL 方便字段格式与关联关系的检查，向量索引方便按含义查找内容。它们可以组合，不是知识类型，也不是固定的技术升级阶梯。

4. 有哪些实现方案

以下是可以组合的设计方向，当前均未接入长期记忆。A–C 主要比较保存与检索方式；D 比较写入自动化程度。也可以由用户确认后写入 SQL，或用文件保存正文再建立向量索引，不必把自动提取与向量检索绑定。

A. 用户维护的文件记忆

用短索引列出主题，正文放在 Markdown 文件中；每个 Run 只加载相关概览，再按需读取正文。写入由用户维护或由显式操作触发。

它容易审阅、版本控制和迁移，适合单用户学习系统。代价是冲突合并、作用域和删除规则需要约定；每次都加载全部记忆文件，仍会导致输入越来越长。

B. 结构化条目加关键词检索

用 SQLite 保存 ID、类型、作用域、来源、版本和状态，再按关键词、项目和时间检索。正文可以在数据库或文件中，检索索引由程序维护。

它便于更正、撤销和审计，精确术语和项目名也容易命中；代价是查询与 Schema 设计，同一意思换种说法时可能检索不到。如果先验证结构化偏好与更正，可以从 SQL 条件开始，再按需要增加全文检索（FTS）；它只是候选方案，当前没有实现。

C. 向量或混合检索

为条目生成 Embedding，按含义检索，再与关键词、时效和类型过滤组合，必要时重排。它适合知识量大、相同意思有多种表达的检索问题。

新增成本包括模型用量、索引版本、重建和质量评测。权限过滤不能只在拿到前几条结果后做，否则既可能漏掉有权内容，也会把越权数据带入后续处理。原文、来源和条目状态仍应在正式存储中维护。

D. 自动提取与后台整理

任务结束时或压缩前，从交互提取候选，再合并、去重和确认。有的系统直接更新记忆文件，有的先保存日记或观察，再定期整理。

它减少人工维护，但可能把模型猜测写成事实、把一次性要求写成长期偏好，或在用户更正后写回旧值。应记录提取器版本和来源范围，先允许查看与拒绝候选，再逐步提高自动写入比例。

方案 适合什么 收益 主要问题
文件索引与正文 少量、人工可审查知识 透明、易迁移 合并和范围管理
SQL 条目与关键词 需要版本、更正与隔离 行为可解释 难以找到意思相近但用词不同的内容
混合检索 资料多、同一意思有多种表达 更容易找到相关内容 索引与评测成本
自动整理 人工维护困难 减少重复整理 错写、冲突和遗忘失效

自动整理是写入策略，混合检索是读取策略。两者可以分别引入，不能因为增加向量数据库就宣称获得了完整记忆系统。

5. 不同实现怎样做

Claude Code，官方文档。 记忆说明区分用户维护的规则文件和自动记忆；自动记忆使用有大小限制的 MEMORY.md 索引，主题文件按需读取。可借鉴的是“短索引常驻、细节按需”，以及让用户能查看和修改保存内容；它不证明记忆会始终正确。

Deep Agents，源码核对。 MemoryMiddleware 在 before_agent 加载配置来源，在请求修改阶段把记忆片段加入 System 消息；已经存在于状态中的内容不会无条件重读。官方记忆文档说明通过后端配置用户或 Agent 作用域。可借鉴的是加载与存储分离；引入本项目时要自行明确哪些文件可作为指令，哪些只能作为参考资料。

AgentScope Java，指定版本的官方文档。 Memory 设计使用按日追加的记录和合并后的长期文件，区分事实提取、合并与会话摘要；长期内容作为参考材料进入 Context。它展示了“先积累、后整理”的写入流程，也会产生额外模型调用与维护工作。

LangChain，官方文档。 长期记忆 Store 用 namespace 和 key 管理条目，并支持范围内查找。可借鉴的是先确定用户、项目等作用域，再决定用哪种索引。namespace 的构造与访问校验仍是应用责任。

这些做法不同，尤其是记忆进入 System 还是参考材料。教程不会把某个实现的默认信任方式视为所有系统必须遵循的规则。

7. 更正、遗忘和时效怎样实现

事实变化时，将旧条目标为被替代，再写入新版本；读取时只选有效条目。若存在冲突且没有明确更正依据，应保留不确定性，而不是任意挑一个更相似的结果。

遗忘至少涉及正式条目、检索索引和提取来源。只删除向量索引，后台仍可能从旧历史重新提取；只删除数据库，缓存或摘要还可能留有副本。可用撤销标记阻止被遗忘来源再次进入提取，但具体是否删除原始记录、备份和派生产物，需要明确操作范围。

时效由知识类型决定：当前构建状态很快失效，稳定偏好可以长期保留但允许覆盖。记忆中的“用户曾经批准发送”不能代替本次动作授权，权限始终由 Policy 判断。

8. 本项目当前选择与未实现范围

截至阶段 2：尚未选择或实现长期记忆方案。当前只有单次任务的内存消息，持久会话记录也待实现。State 的对话历史与 Memory 的跨会话知识各有用途；当前没有记忆提炼、检索或遗忘接口。

阶段 3 先验证“完整记录与本次输入分开”，见阶段实践。长期记忆作为后续阶段的可选方向，应先确定具体复用任务、访问范围、更正和删除要求，再选文件、结构化条目或检索方式；没有承诺必须实施某一种数据库。

9. 后续练习：跨会话复用与遗忘

在两个新会话中检验用户明确要求保存的同一项目的记忆，再用另一个项目验证范围隔离。更正后检查新版本生效，遗忘后检查条目、索引和后续提取均不再复用它；记忆内容也不能开启写权限。

引入自动化后，再统计候选准确率、错误内容写入正式记忆的比例、检索到过期内容的比例和遗忘后重新出现的比例。检索命中和实际任务检查结果一起报告，才能判断记忆是否帮助了系统。
