模块原理与方案

Recovery：中断检查点、异常容错与安全恢复

本章系统解析 Agent 在真实长任务与生产环境中的故障容错体系：从物理崩溃断点识别、运行时异常分级处理，到检查点（Checkpoint）设计与带副作用动作的幂等恢复机制。代码实践与测试注入见阶段 7：中断后怎样安全继续。

1. 问题起点：为什么保存了历史还不等于能安全恢复？

默认情况下，普通的 Agent 会话记录仅负责按顺序追加写入消息（如用户提问、模型响应、工具回执）。但在生产长任务中，进程可能因断电、OOM（内存耗尽）、超时或宿主机重启在中途突然死亡。考虑以下典型场景：

  • 用户：“帮我生成一份审计报告 audit.log，并调用支付接口完成服务续费。”
  • 模型：提出调用 write_file(path="audit.log", content="...")。
  • （系统动作：底层文件已在物理磁盘写入成功，或外部支付网关已成功扣款）
  • （意外中断：在程序将执行回执写入 JSONL 日志之前，物理机断电或进程因 OOM 突然被系统强杀）
  • （系统重启）

如果此时仅依据日志记录进行“无脑重放”，日志中只有“模型发起调用”而没有回执，系统会误以为动作从未执行过，从而再次发起写文件或再次调用扣费接口——导致磁盘文件被二次篡改破坏，或产生灾难性的重复扣款！

要实现安全恢复，系统必须将三类数据物理分离：

数据对象 存储内容 在恢复流程中的核心作用
会话记录（Transcript） 用户提问、模型完整回答与工具观察回执 证明对话中“说过什么、发生过什么”，供模型生成下一轮上下文与人工回溯排查。
执行检查点（Checkpoint） 当前任务停在哪个 Step、待确认动作标识与生命周期指针 记录“推进到了哪一步”，是崩溃重启后的定位锚点，防止重头盲目计算。
动作执行物证（Receipt / Evidence） 物理磁盘状态（时间戳、哈希）或外部 API 幂等状态查询回执 核对“动作是否在物理世界真实生效”，解决网络超时和日志缺失时的状态不确定性。

2. 核心辨析：崩溃切分断点 vs 运行时工具失败

在工程实现中，开发者极易将“工具执行报错”与“系统崩溃断点”混为一谈。它们是两个完全正交的维度：

比较维度 生命周期崩溃断点（Crash Cut Points） 运行时工具失败（Runtime Failures）
物理现象 进程突然死亡（断电、OOM、SIGKILL），内存数据全丢。 进程完好存活，执行遇到预期或未预期的报错。
能否捕获 无法被代码内的 try...except 捕获。 可被 Harness 捕获并打包为结构化 ToolResult。
发生位置 发生在 Harness 生命周期与外部世界的交界边缘。 发生在工具函数逻辑内部或模型协议解析层。
恢复手段 冷启动恢复：加载独立 Checkpoint，探查物证后继续。 热循环自愈：直接将错误回执喂回给模型，由模型在下一步自主修正。

生命周期中的四大崩溃注入断点

测试与验证容错能力时，应在以下四个关键临界点注入崩溃中断：

  1. 动作派发前中断：模型已返回调用意图，但 Harness 尚未调用底层函数。（恢复策略：重新做 Policy 权限检查后安全重做）
  2. 动作执行中／返回前中断：底层写文件或网络请求正在进行，进程突然死亡。（恢复策略：外部状态未知，必须先探查磁盘/网络凭据，绝不盲目重试）
  3. 收到结果但未落盘前中断：底层操作已成功，ToolResult 已在内存，但在追加写入会话文件前崩溃。（恢复策略：依据幂等键和物证核实，直接补齐回执，跳过工具执行）
  4. 结果落盘后、下一轮模型请求前中断：工具回执已安全持久化，但尚未发送给模型。（恢复策略：直接加载已有完整上下文，推进下一轮模型推理）

3. 模型 Tool Call 失败的处理机制：什么时候让模型重试？

当模型发出的工具调用出现问题时，绝不是简单无脑地让模型一次次重试。系统应根据错误性质分层处置：

A. 模型可自愈错误（喂回错误回执，触发自主纠错）

  • 参数格式错误（Schema Validation Error）：模型漏掉了必填参数，或将数值传成了字符串。
  • 工具名不存在（Unknown Tool）：模型幻觉编造了一个系统未注册的工具名。
  • 受控业务失败（Domain Error）：要读取的文件不存在、目标目录为空等。
  • 处理方式：Harness 捕获异常，将其包装为带真实报错信息的 ToolResult(is_error=True, content="...")，作为 Observation 传给模型。模型会在下一轮根据错误提示修正参数或调整策略。

B. 权限拦截错误（Policy Denied，明确阻断）

  • 场景：模型尝试覆盖已被保护的文件，或试图越权访问工作区外的目录。
  • 处理方式：Policy 判定拒绝后，直接生成安全拦截回执。模型收到“已被安全策略拒绝”的客观事实，应当向用户说明或寻求新路径，而非重复暴力请求。

C. 基础设施级临时故障（框架层退避重试，不惊动模型）

  • 场景：调用外部模型接口或第三方 API 时遇到网络偶发丢包、429 限流或 503 临时不可用。
  • 处理方式：由底层客户端或 Tool 内部使用指数退避（Exponential Backoff with Jitter）自动重试 2~3 次。这类故障是物理链路问题，不需要浪费模型 Token 去让模型重新思考。

D. 连续死循环与无进展（断路器熔断，人工介入 HITL）

  • 场景：模型产生思维僵局，连续 3 次传入完全相同的错误参数或陷入死循环。
  • 处理方式：触发 Loop 断路器（Circuit Breaker），强制将任务置为 paused_for_human（暂停等待人工确认），避免无限消耗模型算力和费用。

4. 恢复中断任务的执行步骤（底层机理推导）

在设计恢复流程时，必须严格执行以下四步标准化管线：

  1. 独立恢复入口（Resumed Run）：

    恢复操作必须通过专用的 resume_task(run_id) 入口执行，不与接收新提问的 run_task(prompt) 混用。严禁为了“图省事”直接在数据库中把未完成的任务强行改成 completed——这会导致日志中出现无回执的悬空 ToolCall，破坏大模型协议上下文的完整性。

  2. 判断动作状态（严格区分四态）：

    扫描 Checkpoint 中所有未闭合的工具调用，严禁只有二元的“成功/失败”：

    • completed（已确认完成）：工具回执完备，直接复用已有结果，跳过工具执行。
    • not_dispatched（尚未派发）：底层操作确认从未发生，可重新发起执行。
    • running（后台异步执行中）：与外部任务句柄重新挂接并等待完成。
    • unknown（结果未知）：极度危险状态。系统必须暂停自动执行，先触发“物证探查器（Evidence Probe）”核实外部状态；若无法确认，坚决挂起转交人工介入（Human-in-the-Loop）。
  3. 重新校验 Policy 权限（动态安全审查）：

    即使在中断前该动作已被 Policy 批准，在恢复重试时必须按当前最新的 Policy 重新做一次权限检查。因为在系统崩溃到恢复的这段时间里，用户可能修改了权限配置（如撤销了写权限），绝不能以历史批准记录绕过当下的安全防线。

  4. 持久化恢复进度与幂等绑定（Invocation 与 Attempt）：

    为每次逻辑调用（Invocation）分配全局唯一的幂等键（idempotency_key），并将每次物理重试记录为独立的尝试（Attempt）。恢复探查或重新执行成功后，先将回执写入磁盘 Checkpoint，再拉起模型继续推进循环。

5. 会话记录外需要补充哪些状态？（样本数据结构与场景案例）

如果系统只保存普通的聊天记录（[{"role": "user", ...}, {"role": "assistant", ...}]），一旦崩溃就无法知道工具执行到底处在哪个临界点。因此，可靠 Harness 必须在对话文件外，独立维护一份任务运行检查点记录（Run Checkpoint）。

5.2 场景演练对比：两类故障的差异化恢复路径

故障场景 崩溃发生点与状态判定 恢复引擎的实际执行动作
场景 A：带副作用的写操作在执行中崩溃 * 动作：write_file
* 状态：unknown
* 崩溃点：动作执行中／返回前 		1. 恢复命令读取 Checkpoint，发现 inv_write_report_01 状态为 unknown。
2. 阻止自动重写，触发 filesystem_stat 探查器核对文件存在性与哈希。
3. 确认文件内容与模型要求一致（证明崩溃前已落盘），直接合成成功回执写入会话。
4. 恢复状态标记为 completed，不消耗额外写算力，直接推进下一轮模型请求。
场景 B：只读操作在派发前崩溃 * 动作：read_file
* 状态：not_dispatched
* 崩溃点：动作派发前 		1. 恢复命令扫描到只读动作未执行。
2. 提交当前生效的 Policy 重新审查读取权限。
3. 审查获准后，发起第 2 次 Attempt 执行真实读取。
4. 将最新读取回执保存为 Observation，恢复模型循环。

6. 业界主流 Agent 容错与恢复方案对比

各开源项目和工业框架在处理“中断与恢复”时，根据其架构形态形成了不同的代表性模式：

方案 / 框架 核心容错机制 检查点粒度 中断与人工介入（HITL） 适用场景与主要代价
LangGraph 基于图节点的 Checkpointer（Memory / Sqlite / Postgres）。 Node 级别：每经过一个节点自动存盘一个版本快照。 原生支持在节点前/后调用 interrupt() 挂起，外部传参通过 resume() 恢复。 适合复杂状态图编排；但状态快照较大，需仔细设计持久化字段的序列化。
OpenAI Assistants API 基于服务端的 Run 状态机（queued → in_progress → requires_action）。 RunStep 级别：每个 ToolCall 和 Message 派生独立步骤。 模型提出 ToolCall 时 Run 进入 requires_action 挂起，客户端提交回执后恢复。 标准 SaaS 云端状态；强依赖外部托管，无法掌控底层执行细粒度断点。
Temporal / Durable Execution 工作流事件溯源（Event Sourcing）与 Activity 幂等执行。 Activity 级别：每个外部动作绑定唯一 Token，历史自动重放。 原生支持长期休眠、定时器唤醒与人工审批信号（Signal）。 工业级可靠性最高；但要求工作流代码必须保持确定性（Deterministic），改造成本高。
pi / Codex 单线程 Rollout Reconstruction 与 Turn 完整性重建。 Turn 级别：按递增序号维护消息链，未闭合调用补齐空回执。 通过只读检查历史回放重建模型上下文，遇到破损断行安全丢弃末尾。 极简高效，单机无外部重型依赖；但对多步骤外部副作用需依赖人工探查补全。

7. 期望达到的效果

  • 断点位置精准还原：系统重启后能明确识别任务夭折在生命周期哪个断点，绝不从头盲目重新请求模型。
  • 未知状态零盲目重试：对于结果未知的有副作用动作，必须探查物理物证或暂停等待人工确认，杜绝重复写入或重复扣费。
  • 已完成步骤零算力浪费：已成功落盘的回执在恢复时直接复用，不重复调用工具或模型。
  • 安全规则动态一致：恢复重新执行任何动作时，严格遵循当前环境生效的 Policy，不因历史记录豁免安全检查。
  • 运行时异常自愈闭环：参数校验错误和业务异常以 Observation 形式喂回模型，模型在预算范围内自主修正，连续死循环时及时熔断。
