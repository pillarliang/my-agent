Context Manager：组织本次发给模型的内容

1. 问题起点：Context 管理的对象是什么？

在长任务中，历史消息与外部资料会快速膨胀。考虑以下多步场景：

  • 用户：“读取项目资料，生成包含来源和 UTC 时间的报告，先不要发布。”
  • （经过多轮读取、修改和检查，累计了数十条消息与大段日志）
  • 用户：“继续完成报告。”

此时，模型仍然需要知道整体目标、关键约束（如“先不要发布”）、已确认的信息、当前文件状态和下一步计划：

  • 全量重发：很容易超出模型上下文窗口限制，且无关日志会稀释关键信息。
  • 随意删减：如果简单截断早期消息，很可能把第 1 轮“先不要发布”的约束一起删掉。

Context Manager（或 Context Builder）的核心职责，就是根据带来源标记的历史记录与参考资料，按预算筛选并组装本轮实际发给模型的输入内容。它既不是简单拼接聊天记录，也不负责替用户授予工具执行权限。

数据对象 保存什么 谁维护 是否每轮全部发送
Transcript 原始请求、模型输出、工具调用与回执 执行记录层（State） 否
Task State 当前目标、已确认约束、待办、检查状态 应用与状态层 只发送本轮需要的部分
Artifacts 文件、日志和其他真实产物 工具与产物存储 通常发送引用和摘要片段
Memory 跨会话可复用的知识与偏好 记忆管理模块 按用户、项目等作用域筛选
Context 本轮指令、消息、参考资料和工具定义 Context Manager 是（即为本轮请求输入）

不同来源的内容进入模型时必须保留来源标记与信任边界：应用配置的系统指令、用户要求、读取文件中的普通文本，绝不能因为最终都拼成字符串就被当成同等优先级的指令；历史记录里保存的旧授权，也不能改变当前执行器的权限判定。

2. 模块协作：谁发起、谁决定、谁执行？

在一次模型请求前后，各模块的协作流程如下：

  • Runner 发起输入构建：传入当前问题、系统指令、已保存的历史消息与工具回执、可用参考资料以及 Token 预算。
  • State 与 Tools 提供候选数据：记录层提供历史消息，工具系统提供工具定义（Schema）和已产生的回执。
  • Context Manager 做出筛选决定：决定哪些内容进入本轮请求，并返回组装好的输入与来源清单。
  • Runner 调用 Model 与 Tools：拿到构建好的输入后请求 Model；模型返回工具调用后交由 Tools 与 Policy 校验执行，拿到真实回执并保存后进入下一轮。

异常与边界处理：

  • 预算不足无法构建时：Context Manager 返回明确原因，由 Runner 决定停止或切换策略，绝不能悄悄丢掉必需约束后继续请求。
  • 职责严格解耦：选中某段文件内容不等于授予其指令权限；历史记录中的旧授权也不代表本次动作获准。
  • 数据传入方式：既可以由 Runner 先取好历史传给构建器（依赖少、易测试），也可以让构建器通过只读接口按需加载（适合多数据源系统）。

当前代码状态：尚未接入独立的 Context Manager。目前 Runner 直接加载同一会话的已完成历史并追加当前消息，详细演进计划见阶段 4。

3. 内部流程：如何组装一次模型输入？

下图展示了从收集候选数据到预算复核的完整流程（当前代码仅实现历史读取，尚未实现筛选与预算复核）：

三个核心实现原则：

  • 按轮重整，按源刷新：每次调用模型前重新整理输入，不同数据源可按各自的周期刷新。
  • 原始记录与模型输入分离：压缩或裁剪只影响“本次发给模型的视图（Context）”，不能覆盖或删除数据库中的完整历史记录（Transcript）。
  • 全量预算核算：预算必须同时覆盖系统指令、历史消息、参考资料、工具 Schema、协议开销以及模型输出预留，不能只统计用户问题字数。
  • 构建过程只读无副作用：构建上下文时只能做只读查询，不能顺便触发外部写操作；选择清单应保留在程序侧，便于排查“模型这一轮到底看见了什么、省略了什么”。

4. 核心方案对比：7 种上下文管理策略

A. 全量历史拼接：最直接的对照基线

  • 做法：按时间顺序发送全部历史交互，附上系统指令和工具定义。
  • 适用场景：短任务，或作为排查“模型是否因缺失信息而出错”的对照基线。
  • 代价與局限：输入随轮次线性增长；且无关历史过多时，即便信息在窗口内，模型仍可能漏掉早期提出的要求。

B. 按完整交互块裁剪：低成本限制输入增长

  • 做法：将消息划分为完整交互块（至少包含一次模型调用及其全部工具回执），保留近期块与当前请求，从最旧的块开始整块移除；绝不能只按“最后 N 条消息”居中切断调用与回执。
  • 适用场景：短对话、彼此独立的任务。
  • 代价与局限：无需额外调用模型生成摘要、行为确定；但早期提出的要求和证据会随旧块一起被移出，持续修改同一产物的任务需额外维护结构化任务状态。

C. 大段工具结果另存（Offloading）：优先消除大体积噪音

  • 做法：将长日志或大文件内容保存在产物存储中，消息里只保留执行状态、首尾预览、文件引用和分页补读方式；已写入文件的大段参数也可从后续请求中精简（原始记录仍保留）。
  • 适用场景：工具频繁返回长日志、长文档或大段代码的任务。
  • 代价与局限：无需模型概括，能保留精确路径与错误码；但必须提供可靠的补读路径（直接截断且无法补读会永久丢失细节），并记录内容哈希或版本以防文件被修改。

D. 历史摘要 + 近期原文：长任务的状态压缩

  • 做法：将较早的完整交互块交由模型生成摘要（包含目标、已确认约束、关键事实与来源、失败尝试、待办与产物引用），与“结构化任务状态 + 近期原文块 + 当前参考资料”重新组装成输入。
  • 适用场景：多步骤、长链路演进的复杂任务。
  • 代价与局限：需要额外的模型调用与版本管理；连续多次摘要会累积信息失真，因此关键约束与检查结果应优先从结构化状态读取，且摘要失败时必须有保守回退策略（不能静默使用空摘要）。

E. 按需检索与渐进加载：减少初始装入量

  • 做法：初始只提供目录、标题、工具名称或简短描述，当任务需要时再通过关键词（如 SQLite FTS）、向量或混合检索拉取正文片段。
  • 适用场景：候选参考资料或扩展方法极多，但单轮只需要其中很小一部分。
  • 代价与局限：无法替代过程状态（不知道刚才试过什么、目标为何改变）；检索可能漏掉资料或命中越权内容，必须在检索和读取原文两个阶段都做权限校验。

F. 独立子任务隔离：避免主上下文被探索过程撑爆

  • 做法：把边界明确的搜索或评审交给独立子 Agent，只传入目标、约束和证据要求；主 Agent 仅接收最终结论与来源引用，无需装入子任务的全部中间探索过程。
  • 适用场景：需要大量文件搜索、试错或独立评审的子问题。
  • 代价与局限：增加额外调用与交接核验成本；若采用复制父 Agent 完整历史的 fork 模式，子任务本身仍有较高的初始输入成本（详见 Orchestration）。

G. 供应商原生压缩：托管协议状态

  • 做法：调用模型 API 提供的原生压缩接口，由服务端返回供后续请求续接的不透明协议数据。
  • 适用场景：深度绑定单一供应商 API、希望减少自建摘要逻辑的场景。
  • 代价与局限：压缩结果通常不可读、不可编辑，且无法跨模型供应商迁移；若需跨供应商切换，仍需在本地保存原始记录与结构化任务状态。

5. 方案横向对比与组合关系

机制 主要解决什么问题 新增成本 典型失败风险 如何组合使用
完整块裁剪 历史消息不断增长 少量分块与选择逻辑 丢失早期提出的要求 与结构化任务状态、检索组合
大段结果另存 单次工具结果或参数过大 产物存储与分页补读接口 引用失效、预览漏掉关键错误 通常作为摘要前的第一步清洗
历史摘要 长任务产生大量过程记录 额外模型调用、摘要版本管理 关键细节失真、多次压缩偏离原意 与近期原文、原文补读组合
检索与渐进加载 候选参考资料和工具定义过多 索引维护、多轮检索往返 漏检相关资料、命中过期或越权内容 与过程摘要互补，解决不同问题
子任务隔离 中间探索过程过多 任务委派、结果核验与额外调用 交接信息遗漏、子任务错误传播 子任务内部同样需要 Context 管理
原生压缩 协议续接数据与输入持续增长 服务端用量、供应商强耦合 状态不透明、跨模型不兼容 需配合本地原始记录与产物存储
前缀缓存 重复前缀的计算开销与首字延迟 需保持前缀稳定、统计命中率 前缀变动导致缓存未命中 只降成本与延迟，不减少上下文占用长度

注意区分“前缀缓存”与“上下文裁剪”：前缀缓存命中可以降低重复计算费用和延迟，但所有内容依然占用模型的有效上下文窗口，绝不能用缓存替代输入预算检查。

6. 开源与工业界 Harness 实践对照

pi：分离“上下文整理”与“模型协议转换”

  • 实现机制（源码核对）：agent-loop.ts 先运行 transformContext 整理消息，再经 convertToLlm 转为供应商协议格式。compaction.ts 根据窗口上限和预留额度判断是否压缩，寻找可安全切分的完整交互边界，保存摘要与 retainedTail；context.ts 再据此重建本轮输入。
  • 可借鉴点：将原始记录、上下文转换点和模型协议编码解耦，既保留完整审计记录，又能灵活调整本轮输入。

Deep Agents：用中间件协同“大结果另存”与“历史摘要”

  • 实现机制（源码核对）：filesystem.py 在工具返回边界拦截大结果并另存；summarization.py 在 wrap_model_call 中应用已有摘要事件、精简旧参数并按阈值触发摘要（参考官方文档）。
  • 可借鉴点：在工具结果边界和模型请求边界分别控制体积；但在学习阶段建议先写成显式函数，避免中间件顺序过早复杂化。

AgentScope Java Harness：显式分配預算与配对裁剪

  • 实现机制（文档与源码核对）：Context 文档区分稳定指令、历史、任务状态与参考资料；CompactionMiddleware 与 ConversationCompactor 在请求前按规则裁剪并生成摘要，严格保持工具调用与回执成对出现。
  • 可借鉴点：数据源、任务状态、历史预算与完整执行日志（Session Log）职责分明。

Claude Code 与 Codex / OpenAI Responses：按需加载与分层清理

  • Claude Code（官方文档）：运行机制采用“常驻规则简短、Skills 按需加载、子任务独立窗口”，并在接近上限时先清理旧工具输出再生成摘要。
  • Codex 与 Responses（官方文档）：Codex 配置参考公开了自动压缩阈值；Responses 压缩文档提供服务端原生压缩，返回供后续请求续接的不透明数据。

7. 场景推演：不同策略在同一个长任务中的表现

假设一个 30 轮的长任务经历了以下节点：

  • 第 1 轮（用户）：“报告必须使用 UTC 时间，且完成前先不要发布。”
  • 第 10 轮（工具）：读取了 50 页构建日志。
  • 第 20 轮（用户）：“把报告表格改成三列格式。”
  • 第 30 轮（用户）：“继续完成报告。”

不同单点策略与组合策略的效果对比如下：

  • 仅按块裁剪：保留了第 20 轮的新格式，但丢掉了第 1 轮的 UTC 时间要求（需靠结构化任务状态补回）。
  • 仅做历史摘要：可能把“先不要发布”错误概括成“准备发布”（需靠保留关键约束原文和独立 Policy 授权兜底）。
  • 仅另存大段结果：成功移走了第 10 轮的 50 页日志正文，但无法压缩 30 轮的对话过程。
  • 仅做资料检索：能找到相关项目文档，但不知道用户在第 20 轮改过表格格式。
  • 组合策略：用任务状态锁定“UTC 时间、不发布、三列格式”等核心约束，将第 10 轮长日志另存为引用，对早期探索过程做摘要，按需补读原文细节。

8. 本项目演进顺序

当前状态（阶段 3）：已实现会话保存与历史加载，Runner 直接将同一会话的已完成历史与本轮消息构造成 ModelRequest，尚未引入输入计量、裁剪、摘要或检索。

后续在阶段 4 与阶段 5 中，将按“先计量预算 → 再按完整交互块裁剪 → 最后按真实失败引入另存、摘要或检索”的顺序逐步演进。

9. 期望达到的效果（后续实现验收）

在后续阶段接入 Context Manager 时，建议先实现纯选择函数（输入完整记录块，输出保留、摘要与省略清单），再用固定长任务样本验证。

期望达到的效果：

  • 原始记录零破坏：无论怎样裁剪或摘要，数据库中的完整历史记录（Transcript）始终保持原样。
  • 调用回执严格配对：裁剪后的输入中，每一次工具调用（ToolCall）都与对应的工具回执（ToolResult）成对出现，不产生孤立消息。
  • 核心约束不丢失：对话早期提出的格式要求和用户中途的更正，在压缩后依然保留在模型输入中。
  • 引用可回溯原文：被另存的大段日志或文件保留准确的来源 ID 与补读路径，摘要消耗的 Token 计入总用量。
  • 评价兼顾质量与成本：不仅统计节省的 Token 数，同时核对最终产物是否通过检查、额外调用次数与压缩失败率。
