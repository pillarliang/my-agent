Context Manager：组织本次发给模型的内容

1. 问题起点与设计原则：为什么“保存了历史”不等于“每次全发给模型”？

在多轮对话或长任务中，历史消息与工具返回结果会快速膨胀。考虑以下多步场景：

  • 用户（第 1 轮）：“帮我写一份活动通知，用中文，时间统一写 UTC，定稿前先不要覆盖原文件。”
  • （中间经历多轮文件读取、长日志排查与草稿调整，累积了数十条历史消息）
  • 用户（当前轮）：“沿用前面的时间规则，把通知缩成两句。”

此时，系统如果直接把持久化存储里的记录原样拼给模型，会立刻遇到两个问题：

  • 全量重发会撑爆窗口并稀释重点：早已作废的草稿和大段工具输出会反复占用模型上下文窗口（Context Window），不仅拉高耗时与费用，还会触发输入超限报错，或把第 1 轮的“UTC 时间”要求淹没在噪音中。
  • 盲目截断会丢失约束或破坏协议：如果简单截取“最近 K 条消息”，既可能把第 1 轮的核心要求删掉，又可能把一次工具调用（ToolCall）和它的执行回执（ToolResult）从中间切断，直接触发模型接口协议报错。

因此，“存储层保存了多少历史（State / Transcript）”与“本次请求实际发给模型多少内容（Context）”必须拆成两个独立职责。Context Manager（上下文管理器）专门负责：在每次调用模型前，根据输入预算从候选历史、当前任务消息、参考资料与工具定义中筛选并组装本轮请求。

数据对象 保存什么内容 由谁维护 是否每轮全量发给模型
执行记录（Transcript / SessionLog） 按严格顺序落盘的用户提问、模型完整响应、工具调用与真实回执 会话与状态层（State） 否（作为完整审计与恢复依据保留在存储中）
结构化任务状态（Task State） 当前目标、已确认约束（如 UTC 规则）、待办与检查状态 应用或任务状态层 只发送当前生效的部分
外部产物（Artifacts） 工作区文件、长日志等真实数据产物 文件系统与产物存储 按需发送引用路径、摘要预览或相关片段
长期记忆（Memory） 跨会话复用的项目事实与用户偏好 记忆模块（Memory） 按用户、项目等作用域筛选注入
本轮上下文（Context） 本次请求实际发送的系统指令、入选消息、参考片段与工具定义 Context Manager 是（直接构成单次 ModelRequest）

无论后续采用整块裁剪、结果另存还是历史摘要，Context Manager 都必须保证四条设计底线：

  • 原始记录与模型输入分离（只读无副作用）：筛选、裁剪或压缩只生成“本次发给模型的输入视图”，绝不覆盖或删除会话存储中的完整历史记录。
  • 调用与回执严格配对（协议完整性）：筛选后的消息序列中，每个 ToolCall 都必须与对应的 ToolResult 成对出现，绝不产生孤立的调用或回执。
  • 全量编码口径核算预算：预算计算必须同时覆盖系统指令、入选历史、当前任务消息、工具 Schema、协议续接数据（continuation），并为模型回答预留输出空间（max_output_tokens）。
  • 严守来源角色与权限边界：不同来源的数据进入上下文时必须保持原始角色（绝不把文件内容或旧消息提权为系统指令），历史中的旧授权也不改变当前 Policy 的权限判断；若仅必需内容就已超出预算，必须在请求模型前明确报错停止，绝不静默丢弃必需约束。

2. 黑盒交互与调用时机：谁发起、谁决定、谁执行？

在运行循环中，Context Manager 作为纯逻辑决策模块接入在 Runner 每次调用 Model.invoke() 之前，与周边模块交换两项核心数据：

  • 输入（候选材料与预算配置）：系统指令、长期记忆（Memory 快照与项目规则）、按任务归组的候选历史块（State）、当前任务已产生的提问／响应／回执、可用工具定义（Tools Schema）以及输入 Token 预算。
  • 输出（本轮请求视图或超限错误）：在预算内组装好的消息序列与选择决策清单（记录保留了哪些块、注入了哪些记忆、省略或压缩了哪些块、最终计量体积）；若仅固定必需内容已超出预算，则返回明确的无法构建原因。

注意调用时机：不是只在收到用户提问时筛选一次，而是循环内每发起一次模型请求前都要重新复核。因为同一任务内部第 1 步调用工具读取文件后，返回的大段回执会立刻增大第 2 步请求模型的输入体积。

3. 核心机制拆解：开源 Harness 如何解决三个共同问题？

要把候选数据安全地变成单次模型请求，所有 Agent Harness 都必须依次解决三个具体问题：在哪里转换视图、怎样核算预算、从哪里安全切分。

问题一：持久化记录如何转换成模型请求视图？

  • pi（三步显式流水线）：将“存储记录 → 上下文消息 → 供应商协议”严格拆成三层。session/context.ts 中的 buildSessionContext 先从 JSONL 条目树重建当前分支的消息；进入 agent-loop.ts 的 streamAssistantResponse 后，先调用 transformContext 在 Agent 消息层完成筛选或注入，最后调用 convertToLlm 编码为具体供应商的请求格式。
  • Codex（Rollout 重建与运行期上下文）：RolloutRecorder 将完整交互追加写入 JSONL；续接或请求时，由 model_context.rs（load_latest_model_context）与 rollout_reconstruction.rs 根据回滚或压缩标记提取有效 ResponseItem 序列。
  • Deep Agents 与 AgentScope Java（请求前中间件拦截）：Deep Agents 在 summarization.py 的 wrap_model_call 中拦截模型调用并替换过长历史；AgentScope Java 在 CompactionMiddleware.java 中于请求前检查预算并调用压缩器。

问题二：如何计量体积并判断何时触发裁剪或压缩？

“只保留最近 5 轮对话”无法防止超限——单次读取大文件的回执就可能占满整个窗口。可靠的实现必须按 Token 口径核算，并为模型回答预留输出额度：

可用输入预算 = 模型上下文窗口 (contextWindow) - 最大输出预留 (reserveTokens / max_output_tokens) - 安全余量

  • pi（窗口减去预留额度）：compaction.ts 中的 shouldCompact(contextTokens, contextWindow, settings) 判断当前上下文 Token 是否超过 contextWindow - settings.reserveTokens，提前为本轮生成留出空间。
  • Deep Agents（按模型窗口比例自动计算阈值）：summarization.py 中的 compute_summarization_defaults 根据模型最大窗口自动设定触发压缩的 Token 阈值与尾部保留额度。
  • Codex（可配置压缩阈值）：在配置参考中公开上下文窗口与自动触发压缩的 Token 阈值。

问题三：从哪里下刀才不会切断工具调用与回执配对？

模型协议要求助手发出的每个 ToolCall 后面必须紧跟对应 call_id 的 ToolResult。如果按消息条数从中间一刀切断，留下一半回执或孤立调用，模型接口会直接拒绝请求：

  • pi（findCutPoint 避开工具回执边界）：compaction.ts 从最新消息往前累计保留尾部（keepRecentTokens），在寻找切分点 findCutPoint 时明确规定切分起点绝不能是 toolResult 消息，必须对齐到完整的交互边界，将切分点之后的尾部作为 retainedTail 原样保留。
  • AgentScope Java（成对裁剪校验）：ConversationCompactor.java 在清理旧工具结果与压缩历史时，显式检查并保证工具调用与回执成对保留或成对移除。
  • 本项目阶段 4 MVP（以已完成的完整 Turn 为最小裁剪单元）：直接复用阶段 3 已校验闭合的用户任务边界（Turn）。一个已完成的 Turn 完整包含“用户提问 → 全部工具调用与回执 → 最终回答”，按整块 Turn 保留或省略，天然不会拆散任何一组 call_id。

4. 可选方案对比：超出预算后的 7 种处理策略与演进脉络

在上下文工程中，这 7 种策略并不是彼此孤立的功能清单，而是一条由真实业务痛点驱动的阶梯式演进脉络：前一种方案暴露出的致命缺陷，往往正是后一种方案被发明的根本原因：

A. 全量拼接 ──(线性超限)──> B. 确定性分块裁剪
                             ├─(单步大回执撑爆)──> C. 大输出另存与预览
                             └─(多步长链失忆)────> D. 历史摘要与折叠
                                                       └─(静态资料挤占/探索试错噪音)──> E. 按需检索 ──> F. 子任务隔离 ──> G. 服务端原生加速

A. 全量历史拼接（对照基线）

  • 做法：按时间顺序发送全部已完成历史与当前消息，附上系统指令和工具定义（最基础的基线行为）。
  • 适用场景：轮次少、工具输出短的简单对话，或作为排查“模型出错是否因为裁剪丢了信息”的对照基线。
  • 代价与局限（线性膨胀与单步炸裂）：输入体积随轮次与工具调用线性膨胀；只要遇到一个上千行的大日志文件或超过 10 轮交互，就会瞬间打爆模型上下文上限（如 8k/32k 限制），直接触发 ContextWindowExceeded 报错停止。
  • 演进方向：不能任由消息无约束堆积，必须引入确定性输入预算与切分边界，直接催生了 B. 按完整交互块确定性裁剪。

B. 按完整交互块确定性裁剪（阶段 4 MVP 首选）

  • 做法：锁定系统指令、显式标记的必需历史与当前任务消息，将其余已完成的历史任务（Turn）作为可选块；超出预算时从最旧的可选 Turn 开始整块省略，直到满足预算。
  • 适用场景：多轮日常问答、阶段性独立任务，以及构建长任务机制前的基础预算防线。
  • 收益：零额外模型调用、结果完全确定、块内交互原文 100% 保真，且以完整 Turn 为单位裁剪天然保证 ToolCall 与 ToolResult 不被切断。
  • 代价与局限（长任务中的两大确定性死穴）：单纯按完整块硬裁剪，在面对真实复杂长任务时会暴露出两类致命失效，这直接构成了引入方案 C 与方案 D 的根本原因：
    • 死穴一：工具单次吐出巨量数据（单步撑爆当前轮）：
      • 用户：“分析 access.log 中最近的 5 个 500 报错根因。”
      • 模型：调用 read_file(path="access.log")。
      • （系统执行：日志文件有 10MB、20 万行文本，单条 ToolResult 估算超过 80,000 Token）
      • 失效表现：撑爆预算的是当前轮内正在生成的单个工具回执。此时即便把所有历史 Turn 全部裁光（哪怕历史被裁为 0 条），仅“当前用户提问 + 系统指令 + 单条超大回执”就已经突破预算上限，任务在单步内直接报错崩溃。
      • 演进方向：必须在工具回执进入模型前进行物理拦截与外置暂存，直接催生了 C. 大段工具结果另存与首尾预览（Offloading）。
    • 死穴二：多步执行后硬裁剪导致目标遗忘（长链失忆与任务跑偏）：
      • 用户：“重构 auth 鉴权模块。必须严格兼容旧版 JWT 格式，最后输出重构文件清单。”
      • （模型连续执行了 16 轮文件检索、修改与单元测试）
      • （触发整块硬裁剪：前 8 轮交互被全量丢弃）
      • 模型：“重构已完成。”（完全忘记了必须兼容旧版 JWT 格式的核心约束，也没有输出文件清单）
      • 失效表现：为了给不断增长的后续动作腾出空间，最早期包含用户全局目标、核心约束与验收标准的消息被粗暴移出上下文。模型在长链路后期彻底“失忆”并出现不可控跑偏。
      • 演进方向：不能对历史交互做全盘抛弃，而应将中间探查过程提炼折叠，同时将全局硬约束纳入保护区，直接催生了 D. 历史摘要 + 近期原文（Compaction / Summarization）。

C. 大段工具结果另存与首尾预览（Offloading / Staging）

  • 做法：专门解决上述“死穴一（单步超大回执）”。在工具执行完毕向 Runner 返回时检查回执体积；若超过安全阈值（例如 3,000 字符或 1KB），自动将完整内容写入磁盘暂存文件（如 .learn_agent/artifacts/tool_xxx.txt）。发给模型的 ToolResult 仅保留【前 500 字符预览】+【后 500 字符预览】，并附带完整文件磁盘路径、大小元数据与定向分页补读指令（如 read_file(path=..., offset=..., limit=...)）。后续轮次中，落盘的大段参数也可同样替换为简短引用。
  • 适用场景：频繁读取长文档、大代码文件、构建日志或批量检索结果的任务。
  • 收益与优势：无需额外调用模型即可大幅削减单步体积膨胀，保证单次模型请求绝不突破窗口上限。
  • 代价与局限（首尾盲区与多轮无效化）：
    • 盲区一：关键信息落入首尾之外（信息黑盒）：若日志的中间第 10 万行才是关键报错堆栈，首尾预览完全覆盖不到，模型只能通过额外的分页读取工具反复试探，大幅增加网络往返与思考步数。
    • 局限二：无法阻止多轮对话本身的累积：另存机制只在工具返回超大体积时触发；如果对话持续数十轮，每次工具调用哪怕只返回 100 字符，对话消息历史依然会累加撑爆窗口。
  • 演进方向：大结果另存必须与 D. 历史摘要 配合使用；针对大文件检索，通常应推动向 E. 文本精准切片与按需检索（Grep / AST） 演进，避免一次性通读整文件。

D. 历史摘要 + 近期原文（Compaction / Summarization）

  • 做法：专门解决上述“死穴二（多步长链失忆）”。当已完成任务块累计占用超过上下文预算水位线（例如占用达总预算的 50% 或 75%）时，在安全切分点（如 findCutPoint 避开 toolResult 边界）触发压缩。将中间多轮“尝试、报错、探查、修正”的冗长工具交互折叠为一条结构化事实摘要（提炼当前总目标、已确认约束、关键发现与结论、失败尝试和文件指针），与“近期原文块（retainedTail）+ 当前任务消息”拼装为本轮请求。
  • 绝对保护区（Inviolable Zones）与资料分离：
    • 保护核心指令与初衷：长任务摘要必须设立两道硬性保护底线：用户的首条原始自然语言 Prompt（包含目标方向、硬性约束与验收条件）以及最近一轮的交互原文（retainedTail）属于绝对受保区，绝不进行模糊折叠，确保模型始终不忘初衷。
    • 严禁外部静态大文件混入保护区：绝对保护区只保护用户的“提问指令”，绝不包含用户手动附带、勾选的大型外部静态资料或源码附件！若将动辄数千行的大文件直接内联并视为“不可裁剪的原始 Prompt”，系统在第 1 轮就会直接突破预算超限崩溃；即便第 1 轮勉强塞入，也会在后续数十轮中永久霸占 70%~80% 的宝贵窗口，导致整个任务因“窗口窒息”而瘫痪。用户选择的外部文件必须归入“参考资料与产物层（Artifacts）”，通过工作区路径引用由模型按需读取，或经由策略 E 进行动态切片检索，绝不享有永久常驻豁免权。
  • 适用场景：跨数十轮持续演进同一复杂产物、包含多步探索与试错的长任务。
  • 代价与局限（连续失真退化与静态资料挤占）：
    • 痛点一：连续递归压缩导致的细节失真（有损压缩退化）：当任务持续数十步、经历 3~4 次连续摘要后，早期的关键事实（如精确函数签名、端口号、正则表达式）极易在语言反复浓缩中被过度平滑或产生漂移，引发后续执行偏离。
    • 痛点二：外部静态规范常驻挤占动态窗口：摘要只能压缩“对话与工具历史”；但若项目包含数十份规范文档、API 手册或大量可用工具 Schema，这些静态参考在每轮请求中必须常驻，在对话发生前就吃掉了大半窗口。
  • 演进方向：静态资料绝不能全量常驻，必须根据当前提问动态拉取，直接催生了 E. 按需检索与渐进加载（Retrieval / Progressive Disclosure）。

E. 按需检索与渐进加载（Retrieval / Progressive Disclosure）

  • 做法：初始上下文只放入简短目录、文档标题或技能（Skills）摘要，运行中按当前问题通过关键词（如全文检索 FTS）或向量检索动态拉取相关片段。
  • 适用场景：项目参考资料、规范文档或扩展工具极多，但单轮只需用到其中极小一部分。
  • 收益与优势：将静态资料占用的常驻 Token 压缩到极低水平，把宝贵的窗口额度留给当前任务思考。
  • 代价与局限（检索漏检与主线程探索噪音）：
    • 痛点一：语义鸿沟与检索漏检（Retrieval Miss）：关键词或向量检索无法保证 100% 召回，若漏掉关键规范段落，模型会依据残缺背景盲目操作。
    • 痛点二：主线程试错探索过程污染主上下文：为了定位一个问题，Agent 在主循环中连续运行 20 次搜索、阅读 10 个无关代码片段，这些试错过程全塞在主线程上下文中，导致主上下文被大量检索垃圾噪音淹没，迅速耗尽窗口并分散模型注意力。
  • 演进方向：将大量冗长、充满试错噪音的专项探查工作剥离出主窗口，交由拥有独立上下文的子任务执行，主 Agent 只接收精炼结论，直接催生了 F. 独立子任务窗口隔离（Sub-agent Isolation）。

F. 独立子任务窗口隔离（Sub-agent Isolation）

  • 做法：将耗费大量步数的代码搜索、日志排查或独立评审委派给拥有独立上下文窗口的子 Agent；主 Agent 只接收子任务最终提炼的结论与证据引用（详见 Orchestration）。
  • 适用场景：探索过程长、中间噪音多，但最终结论简短的子问题（如“在整个仓库搜索所有使用了废弃 API 的位置”）。
  • 收益与优势：主任务上下文极其干净，主 Agent 的注意力聚焦于核心全局目标，彻底免受几十轮中间探索碎片干扰。
  • 代价与局限（上下文断层与协调开销）：
    • 痛点：信息孤岛与上下文断层（Context Disconnect）：子 Agent 拥有干净独立的上下文，但也意味着它看不到主任务隐式获知的全局背景与用户偏好。若任务派发提示词不够完备，子 Agent 会南辕北辙；若子 Agent 汇报结论过于简略，主 Agent 无法核验底层真实证据。同时，多 Agent 协调会显著拉高耗时与调用成本。
  • 演进方向：依赖严密的父子任务契约（明确的目标 Schema、证据要求与 Policy 权限继承，见编排模块）；特定模型生态中，服务商则尝试从底层提供 G. 供应商服务端原生压缩 来免去应用层设计复杂度的开销。

G. 供应商服务端原生压缩（Provider-Native Compaction）

  • 做法：调用模型服务商专有压缩端点（如 OpenAI Responses API 的 Compaction），由服务端返回不透明的压缩续接数据供下一轮传入。
  • 适用场景：固定使用单一模型服务商、希望免去自建摘要 Prompt 的场景。
  • 收益与优势：无需客户端编写切分与摘要逻辑，直接复用模型厂商训练有素的内部隐空间压缩。
  • 代价与局限（黑盒锁定与跨模型断裂）：
    • 痛点：状态黑盒不可读、跨供应商不可迁移：服务端返回的是加密或私有的不透明续接数据（continuation blob）。开发者无法审计究竟丢弃了哪些上下文，无法纠正幻觉，更无法在不同模型供应商之间切换复用。
  • 演进方向：原生压缩仅适合固定单一服务商的传输与显存加速；生产级系统的全局事实源（Source of Truth）必须始终锚定在本地由 State 与 Context Manager 统一管理的透明记录中。

7. 场景推演：不同策略在同一个长任务中的表现

回到开头的长任务场景，假设一次持续 30 轮的任务经历了以下四个关键节点：

  • 第 1 轮（用户）：“写一份活动通知，用中文，时间统一写 UTC，定稿前先不要覆盖原文件。”
  • 第 10 轮（工具回执）：读取了 50 页的往期活动记录与长日志。
  • 第 20 轮（用户）：“把通知末尾的日程改用三列表格呈现。”
  • 第 30 轮（用户）：“沿用前面的规则，继续完成最终版通知。”

不同策略在该场景下的真实效果对比：

  • 仅按完整块裁剪（不标记必需块）：完整保留了第 20 轮的三列表格要求和近期工具配对，但第 1 轮的“UTC 时间”因时间最早被整块移出；改进方式：支持显式标记必需历史块（如保留 T1）或提取结构化任务约束。
  • 仅做历史摘要：能把前 20 轮浓缩成一段话，但摘要模型可能漏掉“UTC 时间”或把“先不要覆盖原文件”误缩写为“准备写入原文件”（因此在保留关键要求原文的同时，写入动作仍须由独立 Policy 拦截兜底）。
  • 仅另存大段工具结果：消除了第 10 轮 50 页长日志占用的巨量体积，但无法阻止 30 轮对话消息本身的持续增长。
  • 仅做外部资料检索：能按关键词查到往期活动片段，但不知道用户在第 20 轮口头改过表格格式。
  • 分阶段组合演进：先在阶段 4 实现“预算计量 + 必需块保护 + 按完整 Turn 整块裁剪”守住窗口底线；在阶段 6针对长日志选择“大结果另存预览”，针对超长探索过程选择“历史摘要”。

8. 本项目当前选择与演进路线

  • 当前历史来源：SessionLog.history_turns() 从 JSONL 还原已完成的完整任务块；也可直接提供内存历史。原始历史与本次模型输入分开保存。
  • 当前已实现（阶段 4 MVP：上下文管理与预算）：选择 共用协议编码的离线体积估算 + 输出预留核算 + 必需内容保护 + 按完整用户任务（Turn）从旧到新确定性裁剪 + 每次 model.invoke() 前复核 + 返回裁剪决策清单。
    • 为什么首版选这一组合：复用阶段 3 已闭合的 Turn 边界即可 100% 保证 ToolCall 与 ToolResult 配对不断裂；纯函数逻辑无需额外消耗模型 Token 生成摘要，行为完全确定、易于在本地做精确手算与边界验证。
  • 计量范围：当前以输入 JSON 的 UTF-8 字节数保守估算 Token，不是供应商的精确计数。应用设置窗口额度与安全余量，可按模型替换计量器；具体配置见阶段 4。
  • 后续按需扩展：大段工具结果另存与分页补读、历史摘要压缩（Compaction）、按需资料检索（RAG）与跨会话长期记忆（Memory）。

9. 期望达到的效果

将 Context Manager 接入闭环后，期望达到的效果：

  • 原始记录零破坏：无论本轮请求省略了多少旧任务，SessionLog 文件或内存中的原始完整历史始终原样保留。
  • 调用回执严格配对：筛选后的本轮输入中，所有工具调用（ToolCall）与工具回执（ToolResult）均成对闭合，绝不触发协议配对错误。
  • 必需约束严格受保：系统指令、显式标记的必需历史（如第 1 轮的 UTC 要求）与当前正在执行的任务消息优先保留；若仅必需内容已超出预算，在请求模型前直接报错停止。
  • 循环内动态复核：同一任务内工具返回大段回执后，下一步请求模型前自动重新计量与筛选，防止循环中途撑爆窗口。
  • 取舍决策透明可查：每次构建均返回预算上限、保留块列表、省略块列表与最终计量值，一眼分清“是信息没发给模型，还是发了但模型没遵守”。
