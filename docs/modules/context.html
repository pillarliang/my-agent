Context Manager：组织本次发给模型的内容

1. Context 管理的对象是什么

假设用户要求：“读取项目资料，生成包含来源和 UTC 时间的报告，先不要发布。”经过多次读取、修改和检查后，模型需要继续知道目标、具体要求、已确认的信息、当前文件和下一步计划。直接重发全部历史容易超限；随意删除历史，又可能漏掉“先不要发布”这条要求。

Context Builder 根据有来源记录的消息和材料，组织本次发给模型的内容。它不只是拼接聊天消息，也不负责替用户授予执行权限。

对象 保存什么 谁维护 是否每轮全部发送
Transcript 原始请求、模型输出、工具调用与结果 执行记录层 否
Task State 当前目标、已确认要求、待办、检查状态 应用与状态层 只发送本次需要的部分
Artifacts 文件、日志和其他真实产物 工具与产物存储 通常发送引用和片段
Memory 跨任务可复用的知识 记忆管理模块 按用户、项目等适用范围选择
Context 本轮指令、消息、材料和工具定义 Context Builder 是

同一份内容进入模型时还要有来源标记。应用配置的指令、用户要求、读取文件中的文字，不能仅因为最后都变成字符串就被当成同等优先级的指令。记忆里保存的过去授权也不能改变执行器的当前授权。

2. 与哪些模块交互，谁发起、谁决定、谁执行

仍以“读取 notes.txt，再追问结论”为例。Runner 发起本次输入构建：它带来当前问题、应用指令、已保存的模型调用与工具结果、可用材料以及预算。记录层提供历史记录，工具系统提供能力说明和已产生的回执；Context Manager 决定哪些材料进入本次请求，并返回选择结果与来源清单。

Runner 取得输入后再请求 Model；Model 负责协议编码与模型通信。模型提出工具调用后，Runner 将其交给工具系统，Policy 决定动作能否执行，实际回执回到 Runner 并保存。下一轮再构建上下文。选中了某段文件内容，不等于给该内容授予指令权限；保留了过去的授权，也不代表本次动作获准。

无法构建满足要求的输入时：Context Manager 返回明确原因，Runner 决定停止或采用预先定义的其他策略，不能悄悄丢掉必需材料后继续请求。模型请求失败由 Model 报告；动作被拒绝由工具系统形成回执。三种失败分别由不同模块报告。

依赖可以怎样接：可以由 Runner 先取材料再传给构建器，也可以让构建器通过只读来源接口加载材料。前者依赖少、容易单独测试；后者适合来源很多的系统，但需要处理来源访问权限和读取失败。需要摘要时可另外调用模型服务，需要检索时可连接检索服务；这些是选用相应策略后才增加的协作，不是 Context Manager 的必需依赖。

当前尚未接入 Context Manager。阶段 3A 的 Runner 直接发送已完成任务的全部历史，并保存实际 ModelRequest。下图与方案比较属于通用设计；后续接入方式见阶段 3B。

3. 内部怎样构建一次输入

Context：本次输入与策略组合

通用处理流程，当前尚未实现；阶段 3A 只保存会话与执行记录。

这里有三个实现要点。第一，每次调用模型前重新整理输入，但不同来源可以有不同刷新周期。第二，原始记录和本次选出的输入应分开保存；压缩成功不应让审计记录一起消失。第三，预算必须覆盖工具 Schema、协议材料和输出预留，不能只数用户文字。

构建结果应能回答“模型这一轮看见哪些材料，哪些被省略，以及为什么”。这份选择清单与数据库中的完整历史是两份不同证据；清单可以留在程序侧查询，不要求发送给模型。

读取来源资料时应只读，且可以重复读取，不能在构建输入时顺便创建订单或发送消息。若需要执行新的文件读取，应由执行流程取得真实回执，再让构建器选择这些材料。

4. 有哪些实现方案

A. 完整历史：建立最直接的对照版本

实现时按时间顺序发送完整交互，另外附上稳定指令和工具定义。它几乎没有选择逻辑，适合短任务，也便于检查模型是否因缺少材料而失败。

这种方法保留了完整信息，代价是输入会持续增长。而且，即使信息已经放进输入，模型也不一定能正确使用。扩大窗口可以容纳更多历史，但无关内容仍会占用输入、增加费用，模型也仍可能漏掉对话前面提出的要求。它是对照基线，不是生产系统永远适用的默认方案。

B. 按完整交互块裁剪：限制增长速度

给消息分块，保留近期块、当前请求和未结束调用，再从最旧的可移除块开始裁剪。一个块至少要维护模型调用与全部对应结果；不能只按最后 N 条消息切片。

它不增加摘要模型成本，行为确定、容易定位遗漏。缺点是早先提出的要求和收集到的证据，可能随历史消息一起被移出本次输入，模型也就无法参考这些内容。适合短对话、彼此独立的任务；持续修改同一产物时，应额外维护当前目标和重要要求。后续也可以采用更保守的方案：整个正在执行的 Run 都不裁剪。

C. 工具结果另存与按规则精简输入：先处理重复的大内容

将长日志保存在产物存储中，消息只留状态、首尾预览、引用和补读方式。对于已保存到文件的写入内容，可以从后续请求中移除重复的大段参数；执行时的原始参数仍需保存。

这类策略不需要模型概括，通常比立即摘要更容易保持准确的路径、错误码和数值。但引用必须可以回读，文件可能被覆盖或删除，预览也可能漏掉关键错误。可以记录内容哈希、文件版本和读取时间，标明证据来自哪次读取。直接截断且不给补读路径，会永久丢失可用细节。

对上面的报告任务，可以把 50 页构建日志变成“测试失败、失败项摘要、完整日志引用”，而不是把用户的“不发布”也压缩掉。分页读取工具应限制返回量，否则刚另存的全部内容又会一次读回。

D. 摘要加近期原文：保存过程中的工作状态

选择一段较早的完整交互记录，调用模型生成摘要；保留近期原文和尚未结束的工具调用。重建输入时使用“任务状态 + 旧摘要 + 近期块 + 当前材料”。摘要可以包含目标、已确认的要求、事实和来源、失败尝试、待办、产物引用与不确定项。

由程序保存来源 ID、原始内容的范围及哈希值、摘要版本，以及生成摘要消耗的 Token 数。模型只生成内容，不能自行决定过去的哪些授权仍然有效。连续摘要还会累积信息损失，因此重要要求和实际检查结果最好能从结构化状态重新生成。

同步摘要会阻塞当前请求，生命周期简单；后台摘要可提前准备，减少等待，却要处理取消和过期。如果后台根据版本 10 生成摘要，而用户已在版本 11 修改要求，就不能直接覆盖新状态。先做同步并验证效果，再考虑带版本检查的后台生成。

摘要失败时要明确选择保留原来的输入内容、采取较保守裁剪，或停止；不能悄悄用空摘要继续。摘要中的“已完成”仍是模型生成的工作说明，真正验收应读取检查器与产物证据。

E. 按需检索与渐进加载：减少一开始装入的内容

先提供目录、标题、工具名称或方法描述，任务需要时再取正文。项目文件可先用路径、关键词或 SQLite FTS；表达变化较大的知识可以尝试向量检索；混合检索结合精确匹配、语义匹配与重排。

检索适合“资料很多，但本轮只需要很少一部分”。它无法替代过程摘要：当前目标为何改变、刚才试过什么，需要从任务状态和交互中取得。检索还可能漏掉相关资料、命中旧版本或读取超出用户或项目访问范围的内容；访问控制应在检索和取原文阶段都生效。

在报告任务中，先检索与报告主题相关的段落，再补读原文。将返回片段带上来源位置、版本和截断信息，最后检查能否找到所需证据、保留任务要求，不能只看输入减少了多少。

F. 独立子任务 Context：避免主过程积累全部探索

把边界明确的搜索或评审交给独立执行者，只把目标、必须遵守的要求和证据要求传给它，主过程接收结果与来源引用。这种方式通过分工，让主 Agent 只接收子任务的结果，无需接收全部执行过程。

收益是大量探索过程留在子任务中；代价是额外调用、遗漏交接信息和结果核验。通过 fork 复制父 Agent 全部历史的子任务仍有输入成本，不能一律宣称委派节省 Token。权限、文件系统、预算和消息上下文的隔离也是不同问题，详见多 Agent 编排教程。

G. 供应商原生压缩：保留后续请求需要的协议状态

部分模型 API 提供压缩接口，由服务返回供后续请求使用的协议项。其内容可能是不透明状态，不能按普通摘要解析、编辑，或直接带到另一个供应商继续。

它能减少应用自己设计摘要的工作，但会增加协议和供应商耦合；内容是否完整准确仍需通过任务评测检查。跨供应商迁移要保留可用于不同模型的任务记录、原始记录与产物引用。本项目目前没有启用这类压缩，兼容 Chat Completions 也不能证明某端点支持它。

5. 方案之间怎样比较

机制 主要解决什么 新增成本 典型失败 能否组合
完整块裁剪 历史记录不断增长 少量选择逻辑 模型可能收不到之前提出的要求 可与任务状态、检索组合
大段结果另存 单次结果或参数太大 存储与补读 引用失效、预览误导 通常可先于摘要
历史摘要 长任务产生大量过程记录 模型调用、版本管理 失真、多次压缩后偏离原意 与近期原文、原文回读组合
检索与渐进加载 候选资料和定义太多 索引、检索往返 漏掉相关资料、过期、越权 与摘要解决不同问题
子任务隔离 探索中间过程太多 委派、整合与额外调用 交接遗漏、错误传播 子任务内部也需 Context 管理
原生压缩 后续请求需要的协议数据和不断增长的输入 服务用量、供应商耦合 不透明、跨模型不兼容 与外部证据存储组合
前缀缓存 重复前缀的处理开销 供应商的使用限制与效果测量 缓存未命中 通常不会减少本次输入的总长度

前缀缓存和选择输入内容解决的是两个问题。缓存命中可能减少重复处理成本，但模型仍需在有效窗口内处理请求；不能用缓存替代预算检查。

6. 不同 Harness 实际怎样做

pi：分别处理会话记录整理与模型协议转换

源码核对，指定提交版本。 agent-loop.ts 先运行 transformContext，再经 convertToLlm 转成供应商消息。这样可以分别扩展上下文选择和协议编码。

Harness compaction.ts 根据上下文窗口和预留额度判断是否需要压缩，选择可以安全分开的完整交互记录，并处理一轮交互中较早部分过长的情况。压缩结果保存摘要与 retainedTail；会话处理代码根据最新压缩条目和后续消息重建输入。这样既保留了原始记录，也能单独调整发给模型的内容。

可以借鉴的是“小型循环 + 独立转换点 + 明确压缩状态”。引入本项目时，仍须检查摘要是否准确，并处理来源记录和失败情况，不能只复制一个压缩 Prompt。

Deep Agents：用中间件协调内容另存与摘要

源码核对，指定提交版本。 summarization.py 的 wrap_model_call 先应用已有摘要事件，再处理旧参数、重新计数并判断是否摘要；它将历史文本另存到存储后端，用摘要事件记录本次输入采用了哪份摘要。

filesystem.py 则在工具结果边界处理大内容。官方 Context 说明结合内容另存、摘要和原文读取。需要注意，源码中内容另存失败仍可能继续摘要并给出告警，因此“永远能回读全部原文”不能作为无条件保证。

可以借鉴的是“在处理模型请求与工具结果时，分别控制它们的内容大小”。代价是中间件顺序、后端可靠性和状态更新更复杂；本项目学习时宜先将这些步骤写成显式函数。

AgentScope Java Harness：先分配材料预算，再处理历史

官方文档与压缩源码核对，指定提交版本。 Context 文档区分稳定指令、历史、临时任务状态和参考资料。动态来源在每次准备模型请求时读取；每次应用调用时加载工作区材料。可选材料可按优先级省略，必需材料和工具定义也进入最终预算。

CompactionMiddleware 在模型请求前处理压缩；ConversationCompactor 负责按规则裁剪、生成摘要，并保持工具调用与结果配对。独立 Session Log 用于保留实际执行记录。

可以借鉴的是“材料来源、任务状态、历史预算和完整记录各有职责”。代价是组件更多，必须理解刷新周期和提交时机。这里的 Java Harness 配置不能套用到 AgentScope Python。

Claude Code：按需加载加分层清理

官方文档，未推断内部源码。 运行机制描述了先清理旧工具输出、必要时再摘要的行为，并说明 Skills 按需加载、子 Agent 使用自己的窗口。文档也明确早期细节可能丢失，不能把自动压缩理解为无损保存。

可以借鉴的是“常驻规则保持简短，具体材料按需读取，让子任务自行处理探索过程，只向主 Agent 返回所需结果”。这说明了产品公开的行为，不足以确定全部内部阈值、摘要算法或 Prompt。

Codex 与 Responses：分别观察 Harness 配置和 API 能力

官方文档。 Codex 配置参考公开了自动压缩阈值与模型窗口配置。Responses 压缩文档另外说明服务端阈值压缩和独立压缩调用，返回供后续请求使用、应用无法直接解读的压缩数据。

可借鉴的是把供应商的 continuation 数据留在适配器中，并给应用保留明确的预算和停止策略。这里没有证明所有 Codex 入口使用完全相同的路径，也没有把 API 能力视为当前 Learn Agent 已实现的能力。

Learn Agent：保留便于观察的最小版本

阶段 0 保留单次任务的内存循环；阶段 3A 加入持久会话并发送全部已完成历史。当前没有输入预算或裁剪，摘要和检索也尚未实现。

7. 同一个长任务会有什么差异

假设用户在第 1 轮要求报告使用 UTC 时间，第 10 轮读取大量日志，第 20 轮修改报告格式，然后在第 30 轮要求继续：

  • 仅裁剪可能保留第 20 轮格式，却失去第 1 轮时间要求。需要从已确认任务状态补回。
  • 仅摘要可能把“不要发布”概括成“准备发布”。需要保留来源、重要要求和独立授权检查。
  • 仅另存大段内容能移走日志正文，但无法概括目标变更。仍需历史或任务状态。
  • 仅检索可能找到相关文档，却不知道用户刚改过格式。仍需当前要求和过程信息。
  • 组合策略可以保留已确认的要求，将日志另存为文件，概括之前的执行过程，按需补读原文；仍要通过实际检查确认是否有效。

这些是用于比较机制的推演，不是上述产品实测结果。同一任务应固定模型、工具、文件快照与验收条件，再比较压缩前后的输入、结果与失败。

8. 本项目按什么顺序演进

本项目当前状态：仅实现会话与记录，Runner 直接构造 ModelRequest。Context 管理、输入计量、历史裁剪、摘要和检索均留待后续；本章方案不代表已有代码。学习计划见阶段 3B。

每次只增加当前需求所需的机制，用相同任务和可观察证据检查行为。

9. 后续练习与验收

先实现一个纯选择函数，输入真实记录中的完整块，输出保留、摘要和省略范围，原始记录保持不变。再接入真实模型生成摘要，使用同一组长任务比较扩展前的基线与新策略。

样本至少包含：对话前面提出的格式要求、用户更正、长日志、一次工具失败、文件被外部修改，以及未完成的工具调用。分别检查：重要要求是否保留、引用是否对应原文、调用是否配对、用量是否包含摘要请求、产物是否通过指定检查。

不要只报告“节省了多少 Token”。还要检查关键要求是否保留、证据是否正确、任务是否通过检查，并记录额外调用次数、总耗时和压缩失败率。没有运行的比较应保留为实验计划，不能写成优化已经生效。
