通用设计原则与可选方案 · 当前实现见阶段 2

Policy：在执行前检查操作权限

1. 问题起点：为什么执行工具前必须做权限检查？

一旦给 Agent 开放写文件、删文件或调用外部接口的工具，模型就可能因误解指令或受外部资料诱导而发起危险操作。考虑以下场景：

  • 用户：“把资料整理成摘要保存下来，不要动原来的资料文件。”
  • 模型：调用 write_file(path="notes.txt", content="...")，试图直接覆盖原有资料。
  • （系统拦截：在真正写入磁盘前，Policy 检查发现该操作属于“覆盖已有文件”，直接拒绝执行）

这就是 Policy（权限策略） 模块的核心职责：在工具真正产生副作用之前，根据安全规则（Rules）对本次动作作出许可决定（Decision）。无论后续如何替换具体实现，Policy 都必须保证四条底线：

  • 按真实动作而非字面工具名判断：必须识别出本次调用究竟是“新建文件（create）”还是“覆盖已有文件（overwrite）”，以及具体操作哪个目标路径。
  • 权限规则来源可信：只依据应用配置或经用户明确确认的授权作判断；模型生成的文字或读取到的外部文档内容绝不能自行授予权限。
  • 拒绝决定必须阻断执行：一旦返回拒绝，底层工具函数绝对不能运行，且默认遵循“未明确允许即为拒绝”。
  • 实际执行严格符合所获许可：获准“新建”后，若写入瞬间目标文件已存在，绝不能自动降级为“覆盖”。

2. 黑盒交互：输入动作请求，输出许可决定

以拦截覆盖文件为例，工具系统与 Policy 之间的黑盒交互只交换两项数据：

  • 输入（ActionRequest）：本次要执行的具体动作与目标资源，例如 ActionRequest(operation="overwrite", resource="summary.txt")。
  • 输出（PolicyDecision）：是否允许执行及原因说明，例如 PolicyDecision(allowed=False, reason="禁止覆盖已有文件")。

关键认知澄清：模型只给出意图与参数，物理状态由 Harness 检查决定

初学者极易产生一个误区：“是不是模型在 ToolCall 里把 operation 参数写成了 overwrite？”——绝对不是！模型只发起 write_file(path="summary.txt", content="...")，模型既不能也不应该决定操作是新建还是覆盖。真正的动作性质是由 Harness 系统前往物理磁盘执行 lstat() 探查后判定的：

  • 模型（LLM）：发出业务意图 write_file(path="summary.txt")，表达“我想向这个文件写入内容”。
  • 工具系统（Harness）：探查工作区物理磁盘。若文件不存在，包装为 ActionRequest(operation="create")；若文件已存在，包装为 ActionRequest(operation="overwrite")。
  • 策略模块（Policy）：根据当前安全规则裁决是否放行。默认规则下，overwrite 被判定为 allowed=False。
  • 安全拦截：底层物理写入被阻断，原文件完好无损，并向模型返回 policy_denied 回执。

在与周边模块协作时，职责边界如下（具体 Python 代码见阶段 2）：

  • 应用入口（Application）：在初始化工具注册表时注入权限规则与工作目录配置。
  • 工具系统（Tools）：在运行期校验参数并识别真实动作，统一调用 Policy；若被拒绝，生成 policy_denied 回执交回 Runner。
  • 上下文与状态（Context / State）：Context 只管理模型输入，State 只记录发生过的回执——历史记录中某次操作曾获准，绝不代表本轮新调用自动获准。

3. 核心机制解析与可选方案对比

实现 Policy 时，“如何从工具调用中提取动作”和“如何根据规则判断许可”是两个可以独立组合的设计维度：

维度一：如何从调用中识别动作？

  • 注册时声明权限元数据（本项目方案）：工具注册时声明所需权限类别（如 read / write）和路径参数名（如 path_parameter="path"），由底层共享代码自动去参数字典提取路径、结合真实文件系统状态自动生成 ActionRequest。适合多个工具复用同类权限的场景。
  • 工具提供自定义动作描述函数：由每个工具各自编写函数解析参数并描述动作。适合各工具资源形态差异极大的场景，但维护成本更高。

维度二：如何判断规则？

  • 代码条件分支（本项目方案）：在内存中通过配置开关（如 allow_create、allow_overwrite）与白名单集合（如 create_files）直接判断。规则简单直观，适合起步阶段。
  • 声明式规则配置：将允许／拒绝条件写成配置文件按优先级匹配。适合规则频繁变动的场景，需处理规则冲突与默认兜底。
  • 独立策略服务：由外部服务集中审批并返回决定。适合多应用共享企业级权限，但会引入网络调用与服务高可用成本。

具体案例：什么是“声明权限类别与路径参数名”？

看 WRITE_FILE 的注册定义（filesystem.py）：

WRITE_FILE = ToolDefinition(
    name="write_file",
    description="写入一个工作区文件...",
    arguments_model=WriteFileArguments,  # 参数模型，包含 path 和 content 两个字段
    function=write_file,                 # 底层写文件的普通函数
    permission="write",                  # 声明 1：权限类别为“写入意图”
    path_parameter="path",               # 声明 2：去参数中找名为 "path" 的字段提取目标路径
)

为什么要这样声明？因为模型在发起调用时，传过来的只是一个普通 JSON 参数字典（如 {"path": "summary.txt", "content": "..."}）。有了这两项元数据，底层通用函数 prepare_action() 就能全自动运行：

  • 根据 path_parameter="path"，自动提取出目标文件 summary.txt（避免每个工具重复编写解析逻辑）；
  • 根据 permission="write"，自动前往工作区磁盘调用 lstat() 探查物理文件是否存在；
  • 若文件不存在则生成 ActionRequest(operation="create")；若已存在则生成 ActionRequest(operation="overwrite")。

具体案例：什么是“注入权限规则”？

在命令行入口启动 Agent 时（__main__.py）：

# 1. 开发者决定本次运行的安全策略：允许新建，但禁止覆盖！
policy = Policy(
    allow_read=True,
    allow_create=True,
    allow_overwrite=False  # 默认禁止覆盖
)

# 2. 将 policy 和工作区路径作为参数传入工具注册表：
tools = ToolRegistry(
    definitions=[LIST_FILES, READ_FILE, WRITE_FILE],
    workspace=WORKSPACE,
    policy=policy  # <-- 这就是“注入权限规则”！
)

为什么叫“注入”？为什么不直接把写工具删掉来做只读？

“工具管能力，Policy 管开关”。通过外部注入 Policy 来管理权限，具有三个关键的工程优势：

  • 支持细粒度白名单：例如设置 Policy(allow_create=False, create_files=frozenset([Path("output/report.md")]))，能做到“全局只读，但特批允许生成一份专属报告”，这是直接删掉工具做不到的。
  • 具备因果感知与友好解释：模型如果调用了未授权工具，会收到结构化的 policy_denied 回执，能礼貌地向用户说明“该操作已被安全策略拦截”，而不是因找不到工具而困惑或产生幻觉。
  • 工具集统一，环境动态切换：同一套代码和工具列表，只需在初始化时注入不同的 Policy 实例，就能无缝切换“只读分析模式”、“代码生成沙箱模式”或“生产覆盖重构模式”。

完整的真实场景：端到端 5 步协同闭环

当一个外部配置了“禁止覆盖”策略的 Agent 面临覆盖写时，系统经历以下确定性的 5 步闭环：

  • 步骤 1（启动注入）：开发者在启动时创建 Policy(allow_create=True, allow_overwrite=False) 并注入 ToolRegistry。
  • 步骤 2（模型表达意图）：模型发出工具调用 write_file(path="summary.txt", content="报告...")，模型不决定也不含有 create 或 overwrite。
  • 步骤 3（系统探查物理状态）：ToolRegistry 依据 path_parameter="path" 提取路径，通过 lstat() 探查发现 summary.txt 在磁盘上已存在！系统客观判定这是覆盖写，组装出 ActionRequest(operation="overwrite", resource="summary.txt")。
  • 步骤 4（策略审查）：ToolRegistry 询问注入的 Policy，Policy 命中 allow_overwrite=False 规则，返回 PolicyDecision(allowed=False, reason="禁止覆盖已有文件")。
  • 步骤 5（安全拦截与回执）：ToolRegistry 放弃调用底层物理写函数，磁盘原文件毫发无损，并向模型返回带有拦截原因的 ToolResult(status="policy_denied")。

4. 本项目当前选择与未实现范围

  • 本项目当前选择：采用 注册时声明权限 + 共享函数识别动作 + 注册表统一拦截 + 内存条件分支判断（源码 walkthrough 与实验命令见阶段 2）。CLI 默认允许工作区内读取与新建文件，禁止覆盖已有文件。
  • 尚未实现（按需扩展）：声明式规则引擎、人工在线审批、短期受限授权凭据（Capability Token）以及操作系统级沙箱隔离。

5. 期望达到的效果

  • 合法操作正常执行：在工作目录内读取文件或新建不存在的文件时，Policy 返回允许并完成操作。
  • 违规覆盖零副作用拦截：尝试覆盖已有文件时，Policy 返回 policy_denied，底层写入函数不执行，原文件内容保持不变（见阶段 2 禁止覆盖实验）。
  • 并发竞态不降级：获准新建文件后，若写入前目标文件已被其他进程抢先创建，底层独占创建立即报错，绝不演变为覆盖写入。
按需了解：审批、受限授权与执行隔离（当前未实现）

6. 人工审批

需要人作决定时，可以暂停并展示具体动作、目标和参数。审批后执行前仍须确认动作未变、授权仍有效。它适合需要人工判断的操作，代价是等待状态、身份校验和恢复流程。

7. 执行隔离

Policy 判断是否批准动作；沙箱限制执行代码实际能访问什么。它们是不同职责。子进程本身不保证文件或网络隔离，操作系统限制、容器或虚拟机也需要按授权范围配置，不能替代业务权限判断。

8. 受限授权凭据

也可以由可信程序签发仅允许特定主体、动作、目标和有效期的凭据。它适合短期委托，代价是撤销、过期、并发使用和重试管理；不是给工具加一个“已批准”参数就能实现。

9. 不可信资料与进一步阅读

资料可能诱导模型提出越权动作。提示模型忽略恶意指令有帮助，但权限仍须由程序执行检查，不能让资料自行修改规则。更多源码与设计资料见方案依据；等待与恢复涉及的状态问题见 Session / State。
