模块原理与方案 · 依据 pi / Codex 源码

Session / State：管理会话与执行记录

1. 要解决什么问题，为什么需要记录

Agent Loop 能读 notes.txt 并回答，但只保存在内存中的消息会随程序退出而丢失。重新启动后问“刚才的验收标记是什么”，程序没有材料告诉模型“刚才”指什么；只留下最终回答，也无法核对读取的是哪个文件、工具是否失败。

本模块要补上三件事：将相关交互归入同一段对话；保留足够的消息与真实回执；在查看历史或再次提问时读取正确的材料。它不负责调用模型、执行工具或判断权限。保存一段对话也不自动具备任务恢复能力。

2. 先看一次交互，再决定怎样分层

用户先说“读取 notes.txt，告诉我验收标记”，Agent 请求模型、执行读取，再请求模型得到回答；用户随后追问“再说一次标记”。从这个过程可以分出三个尺度：

  1. 整段对话：关联两次提问、配置和历史，生命周期可以跨进程。
  2. 一次用户任务：从接受一个问题到回答、失败或中断；它可能请求模型多次。
  3. 具体内容与动作：用户输入、助手文字、工具调用、工具回执。每次模型请求是一次执行动作，不天然要求成为持久表中的一个层级。

3. 每个尺度要保留什么

会话元数据用于找到和解释整段对话：稳定 ID、记录格式版本、创建时间、工作目录；需要复现配置时再保留模型与指令信息。ID 用来关联，版本用来解释结构，工作目录用来确认历史观察属于哪个资源范围。

一次用户任务的数据用于分清“哪次问题产生了哪些结果”：任务标识、起止位置、完成／失败／中断结论及必要错误。可以用开始、结束条目表达，也可以更新数据库中的任务行；有这个概念不等于必须建表。

内容条目保留问题、模型响应、工具调用参数与真实回执。它们按确定顺序排列，并保留调用 ID，保证回执能找到对应调用。时间戳便于观察，单靠时间戳不足以保证顺序。

本次模型请求还包含系统指令、工具声明和输出限制。它是从当前材料组装出的输入；是否额外保存每次完整请求是调试选择，会重复占用历史空间。请求日志与会话消息不必使用同一种结构。

设计时逐项问：这份数据属于哪段对话或哪次任务？是谁产生的？重启后还需要吗？是原始材料还是根据原始材料计算出的视图？这些问题先于数据库表名。

4. Message 里面有什么：文本、调用与回执

Message（消息）表示交互内容，不能只存展示给人的一句话。以读取 notes.txt 为例，至少要区分用户输入、助手响应与工具回执；助手响应又可能包含文字、思考材料和工具调用。

pi：三类基础消息，内容由多个块组成

基础类型主要构成在读取例子中的意义
UserMessagerole=user；content 是文字或文本／图片块数组；timestamp。用户要求读取 notes.txt。
AssistantMessagerole=assistant；content 包含 TextContent、ThinkingContent、ToolCall；另有 api、provider、model、usage、stopReason、timestamp，失败时可有 errorMessage。一次响应可同时有解释文字和读取调用；不要只保存文字。
ToolResultMessagerole=toolResult；toolCallId、toolName、content、isError、timestamp，可带 details 与用量。程序读取文件后的真实结果，通过 toolCallId 对应助手调用。

ToolCall 内容块带 type=toolCall、id、name 和结构化 arguments；文本块带 type=text 与 text。系统指令单独在 AgentState.systemPrompt 中，不是这三类基础消息之一。这里列出文本与工具主线的字段，完整可选字段与扩展类型见pi 消息定义、AgentState / AgentMessage。

Codex：模型交互统一为 ResponseItem

与本例有关的分支主要内容应保留的关联
Messagerole、content 内容块，可带 id、status、phase。区分用户、助手及其他角色；phase 可表达输出阶段。
FunctionCallname、arguments、call_id，可带 namespace、id 与状态。arguments 是模型提供的调用参数；call_id 关联结果。
FunctionCallOutputcall_id 与 output，可带 id、状态。工具输出与原调用配对，不能只剩一段无来源文字。
Reasoning推理摘要、内容或加密续接材料，视供应商与响应而定。原生续接材料不一定能完整显示给用户，也不应被任意改写。

依据：Codex ResponseItem 与 ContentItem。这些是本例相关分支，源码还有自定义工具、搜索、图像等类型。对外的 ThreadItem 则整理为 UserMessage、AgentMessage、CommandExecution 等展示项，不能拿展示文本代替模型交互原始材料。

消息与记录包装分开。pi 的 SessionMessageEntry 在 message 外再放 type、id、parentId、timestamp；Codex 的 RolloutLine 包装 RolloutItem。它们解决保存与重建问题，不要求模型 API 接收同样的外层字段。

5. 怎么存，存在哪里：内存、原始记录与查询数据

内存保存“正在使用的状态”。当前消息、流式文本、正在执行的调用和临时错误会更新或清空；模型连接、取消信号等运行资源通常不能直接序列化。要持久保存什么，应由重启后的使用需求决定。

原始记录保存“以后仍需解释的材料”。JSONL 是一行一个 JSON 对象，适合按顺序追加和手工检查；SQLite 适合关联查询、事务与并发控制。还可以组合：正文在文件，索引在数据库。存储介质不决定消息类型，也不决定是否有实时事件。

pi：内存索引与一份会话 JSONL

SessionManager维护内存中的 fileEntries、byId 和当前 leafId；appendMessage 生成带 id、parentId 的条目。持久模式下会话文件位于用户的 pi sessions 目录。正常追加使用 JSONL；首次落盘有缓冲策略，不能把调用 appendMessage 简化成“立刻保证磁盘已有这一行”。

条目之间的 parentId 表达分支；当前叶子决定本轮采用哪条路径。会话文件头记录版本、ID、时间与 cwd。分支关系与消息内容可以放在同一个文件，不要求建立 Session、Run、Step 三张关系表。

Codex：rollout 正文、SQLite 元数据与分页查询

RolloutRecorder通过写入队列处理 JSONL 记录，提供 record_canonical_items、persist 与 flush。提交到队列和等待写入完成是不同节点；实现还支持缓冲与压缩，不能把每次函数返回都解释为断电后一定可恢复。

RolloutItem区分 SessionMeta、ResponseItem、TurnContext、Compacted、EventMsg 等记录。SQLite 线程数据保存可查询的元数据；历史查询代码还提供 Turn / Item 分页视图。因此“用了 JSONL”不等于“没有数据库”，“用了数据库”也不等于“所有材料都只存在一张消息表”。

起步选择看需求。单进程练习可先用内存加 JSONL；需要按工作区、标题、时间筛选大量会话时再加索引；需要多个执行者协调时另行设计写入协议。不要为了名字看起来完整，提前复制参考项目的全部存储设施。

6. 是否只有新增和查询：区分三种变化

持久历史可以采用追加与读取接口；内存状态、分支选择和查询索引还需要更新。

  • 内存状态会改。追加完整消息、替换流式消息、增加或移除待执行工具 ID、设置或清空错误，都属于更新。
  • 持久历史可以主要追加。任务完成时再追加结束条目，已有内容保持可追溯；也可以选用更新任务状态行的数据库方案。
  • 查询索引与管理信息会变。改名、归档、分支选择与删除策略另有接口，不能从“正文追加”推断“系统永远没有修改”。

pi 的getEntries / branch / appendSessionInfo将会话条目定义为追加式记录；branch 改变叶子选择，改名可追加会话信息条目。Codex 的元数据更新与归档是独立管理操作；回退或分支也需要明确的历史选择规则。

7. 查询其实有三条路径

  1. 找会话：根据 ID、目录、更新时间或标题找元数据，不必读取所有正文。pi 可扫描会话文件；Codex 的列表查询可结合 SQLite 与 rollout 元数据。
  2. 看过程：按会话定位记录，再按条目顺序或所选分支还原展示；保留错误与未完成片段，供人核对。读取不调用模型，也不重放工具。
  3. 为下一次模型请求构造历史：解释记录类型和分支，选取可用消息，处理压缩标记，再编码成模型协议。它不是“把整个日志文件发送给模型”。

pi 的getBranch / buildSessionContext从叶子沿 parentId 找到路径，再生成模型消息；自定义状态条目不一定进入上下文。随后Agent Loop执行上下文处理与模型协议转换。

Codex 分别提供list_threads、read_thread与load_latest_model_context。后者按历史模式加载所需 rollout 区段；重建代码解释消息、压缩及相关上下文材料。分页展示的结果不等于本次模型请求的全部输入。

首版可以先选择“只把正常结束的完整用户任务用于追问”。失败与未结束部分仍供详情查询。工具调用和回执要配对；遇到无法解释的版本或残缺结构，应报告问题，不能静默当作空历史。

8. 如何与 Agent Loop 配合，State 与 Event 在哪里

初始化时，入口确定会话与保存位置；Loop 仍使用已经配置好的模型和工具。运行时，入口提交新问题，Loop 加载可用历史组成工作消息，在模型或工具返回后保存内容，在本次任务结束时保存结论。存储失败返回调用方；存储层不替 Loop 决定下一步，也不执行工具。

State 是当前数据的视图。例如当前模型输入、活动任务状态、待执行调用。可以直接更新，也可以根据收到的事件更新；不要求名为 State 的模块、类或表。

Event 描述一次发生的变化，具体用途由实现决定。pi 的processEvents先用消息与工具事件更新内存状态，再通知订阅者；AgentSession在 message_end 等位置处理会话保存。Codex 的持久记录中也有 EventMsg，事件还可参与历史解释。因此不能把 event 一概理解成“只给外部系统通知”，也不能认为所有事件都要保存或都能送给模型。

Loop 可以直接调用保存函数记录消息与任务边界；当界面、存储和监控都需要响应同一次变化时，事件订阅可以减少 Loop 与这些接收方的直接依赖。

保留历史与恢复执行分开。重启后用历史开始新任务，属于对话续接；从中断处恢复旧任务，还需核对外部动作是否生效、结果是否已确认、当前权限是否仍允许。重建消息不能恢复原网络请求或撤销已修改的文件。中断恢复还需要这些执行信息。

9. 最小方案：一个会话文件与有序记录

Session + 用户任务 Turn + 有序记录可以支撑保存与追问：一个会话对应一份 JSONL，任务开始与结束条目划分每次提问，消息记录保留完整响应与工具回执。读取时按顺序还原已完成任务，交给下一次模型请求。单进程场景下可以直接检查文件；需要筛选大量会话时再加查询索引。
