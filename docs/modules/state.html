模块原理与方案 · 依据 pi / Codex 源码

Session / State：管理会话与执行记录

1. 问题起点：为什么多轮对话与问题排查离不开状态记录？

默认情况下，模型接口与单次运行的进程都是无状态的。考虑以下多轮对话场景：

  • 用户：“这段对话里，请叫我星河。”
  • 模型：“好的，星河。”
  • （退出程序，重新打开）
  • 用户：“我刚才让你怎么称呼我？”

如果没有把前面的对话持久化保存下来，重启后的程序就无法向模型提供上下文，用户也无从查证此前发生过的交互。因此，Session / State（会话与状态记录） 模块专门负责三件事：

  1. 按会话隔离与归组：将同一段连续对话归入同一个 Session，防止不同对话的历史互相串味。
  2. 完整保存交互记录：按严格顺序记录用户提问、模型完整响应与真实工具回执。
  3. 按场景提供读取视图：既支持用户离线查看完整历史，也能为下一轮模型请求还原可用上下文。

该模块只负责状态与记录的存取，不负责调用模型、执行工具或判断权限；单纯保存对话历史也不等于自动具备中断恢复能力。

2. 数据分层：从整段对话到单条消息

观察一段包含多轮追问与工具调用的交互，可以自然划分出三个数据层级：

  1. 整段会话（Session）：关联多次用户提问、工作目录配置与完整历史，生命周期跨越多次进程启动。
  2. 单次用户任务（Turn）：从接收一次用户提问开始，中间可能经历多轮模型请求与工具调用，直到得出最终回答、报错失败或意外中断。
  3. 具体交互条目（Message / Record）：用户输入、模型响应、工具调用与工具回执。单次模型请求只是循环内部的一步执行动作，无需为此单独建一张持久化表。

3. 每一层需要保存哪些核心数据？

  • 会话元数据（Session Metadata）：包含唯一会话 ID、记录格式版本、创建时间与绑定的工作目录。工作目录用于校验后续追问是否仍在同一资源环境内。
  • 单次任务边界（Turn Boundary）：包含任务 ID、起止位置、结束状态（completed / failed / 未结束）及错误信息，用于区分“已完成的历史”与“中途异常中断的残片”。
  • 有序内容条目（Ordered Messages）：按严格递增序号保存用户提问、模型完整响应、工具调用参数与真实回执，并通过 call_id 保持调用与回执一一配对（仅靠时间戳不足以保证顺序）。
  • 当次请求组装配置（非持久历史）：系统指令、工具 Schema 与输出上限属于每次调用模型时动态组装的请求配置，无需在每条历史消息中重复存储。

4. 消息结构对比：文本、工具调用与回执（pi vs Codex）

消息记录不能只存最终展示给用户的纯文本，还必须保留模型发起的工具调用、思考或协议续接数据，以及工具返回的真实回执。下面以调用目录列表工具的场景对比 pi 与 Codex 的消息结构：

pi：三类基础消息，内容由结构化块组成

基础类型主要构成在目录列表场景中的作用
UserMessagerole="user"；content 为纯文本或文本／图片块数组；带 timestamp。记录用户提问：“当前目录有哪些文件？”
AssistantMessagerole="assistant"；content 包含 TextContent、ThinkingContent、ToolCall；另含模型名、usage、stopReason 等元数据。单次响应可同时包含说明文本与工具调用请求，不能只截取纯文本。
ToolResultMessagerole="toolResult"；含 toolCallId、toolName、content、isError 等。保存列出目录后的真实回执，通过 toolCallId 关联对应的调用。

源码依据：pi 消息定义、AgentState / AgentMessage（系统指令保存在 AgentState.systemPrompt 中，不混入三类基础消息）。

Codex：模型交互统一表示为 ResponseItem

相关分支主要内容关键关联关系
Messagerole、content 内容块，可选带 id、status、phase。区分用户与助手角色，phase 标记输出阶段。
FunctionCallname、arguments、call_id。保存模型生成的原始调用参数，用 call_id 关联执行结果。
FunctionCallOutputcall_id 与 output。将工具真实输出与原调用配对。
Reasoning推理摘要、内容或加密续接数据（continuation data）。原样保留供后续请求使用，不可随意丢弃或篡改。

源码依据：Codex ResponseItem 与 ContentItem。

内层消息与外层记录包装分离：pi 的 SessionMessageEntry 在 message 外包裹 type、id、parentId、timestamp；Codex 的 RolloutLine 包裹 RolloutItem。外层字段服务于磁盘落盘与历史重建，发送给模型时则只提取还原后的内层消息。

5. 存储介质对比：内存、JSONL 与 SQLite

  • 内存状态（In-Memory）：保存当前正在运行的上下文消息、流式片段与网络连接，进程退出即释放。
  • JSONL 追加文件：每行一个 JSON 对象，天然契合按时间顺序追加的对话日志，零数据库依赖且便于直接打开排查。
  • SQLite 关系存储／索引：适合海量会话的多维筛选（按工作区、标题、时间分页查询）、事务更新与并发控制。

pi：内存树索引 + 单会话 JSONL 文件

SessionManager 在内存中维护 fileEntries、byId 和当前叶子节点 leafId，落盘采用单会话 JSONL 文件。首行记录版本、ID、时间与工作目录 cwd；后续条目通过 id 与 parentId 表达对话分支，无需建立多张关系表。

Codex：JSONL 正文（Rollout）+ SQLite 元数据索引

RolloutRecorder 将完整交互条目（RolloutItem）异步追加到 JSONL 文件，同时使用 SQLite 维护线程元数据，支持快速分页与检索（thread_history/read.rs）。

6. 状态变更方式：追加写入与元数据更新

  • 运行期内存状态——原地更新：追加新消息、拼接流式输出、记录待执行工具 ID 或更新错误状态。
  • 持久化对话历史——只追加不篡改（Append-Only）：新消息和任务结束状态依次追加到文件末尾，保留完整的审计轨迹。
  • 会话管理信息——按需更新：如会话重命名、归档或切换分支指针（见 pi 的 branch / appendSessionInfo 与 Codex 的 update_thread_metadata.rs、archive_thread.rs）。

7. 三条读取路径：会话列表、历史详情与上下文重建

  1. 查询会话列表：只读取文件头或索引元数据（ID、工作目录、更新时间），不加载全部对话正文（见 Codex list_threads.rs）。
  2. 查看单会话详情：按顺序还原整份会话记录（含失败报错和未完成片段），供开发者或用户回溯排查，全程不调用模型、不重放工具（见 Codex read_thread.rs）。
  3. 重建模型上下文：筛选出已完成且消息链闭合的历史记录，处理分支或压缩标记后还原为模型消息列表（见 pi buildSessionContext 与 Codex load_latest_model_context、rollout_reconstruction.rs）。

8. 与 Agent Loop 的协作边界：State、Event 与中断恢复

  • 初始化与运行期分工：初始化时由应用入口打开或新建会话；运行期由 Loop 先读取已完成历史组装请求，再在收到用户提问、模型响应、工具回执和任务结束时依次调用写入接口。
  • State（当前状态视图）与 Event（状态变化通知）：State 表示当前时刻的数据快照（如活动消息链、待执行工具），Event 表示一次状态变更（如 pi 的 processEvents 与 AgentSession）。单进程下 Loop 可直接调用保存函数，无需强制引入复杂的事件总线。
  • 多轮续接不等于中断恢复：在已完成历史之上发起新提问属于“多轮续接”；而从崩溃点继续未完成的任务属于“中断恢复”，后者还必须核对外部副作用是否已发生。

9. 本项目当前选择与期望达到的效果

本项目当前选择：采用 单会话 JSONL 文件 + 用户任务 Turn 边界 + 严格序号记录（完整推导与源码见阶段 3：会话与记录）。

期望达到的效果：

  • 完整保留交互链：按递增序号保存用户提问、完整 ModelResponse 与带 call_id 的真实 ToolResult。
  • 上下文干净续接：追问时自动加载同一会话内已正常完成（completed）的历史消息，自动过滤失败或未结束的任务残片。
  • 只读查询零副作用：列出或查看会话记录时直接解析本地 JSONL 文件，不请求模型、也不重新执行工具。
  • 损坏与冲突严密防护：通过单写者文件锁防止并发交错；遇到未知版本、序号断层或末尾残行时明确报错停止。
