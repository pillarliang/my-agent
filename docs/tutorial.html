逐步建成什么样的系统

按职责划分系统边界，先明确每个模块解决什么问题，再按阶段逐步落地代码：

  • 应用与行为配置
    • 用户入口、任务目标、系统指令与工具集配置已实现：CLI 命令行入口；模型连接配置由 LLMService 内部管理
  • Harness 核心
    • Loop / Runner：推进循环、控制步数上限、汇总运行结果。已实现：最小自主工具循环与最大步数限制
    • Model / LLMService：统一模型调用接口，隔离 SDK 协议与凭证管理。已实现：单端点非流式调用与协议转换
    • Context Manager：在预算内筛选并组装本轮发给模型的上下文。后续阶段（阶段 4）：尚未实现输入计量与裁剪
    • Tools：管理能力声明、参数校验、函数分发与真实回执。已实现：list_files、read_file、search_text 与受控 write_file
    • Policy：在工具执行前检查操作权限与资源边界。已实现：区分读取、新建与覆盖；默认允许新建、禁止覆盖
    • Session / State：持久化保存会话记录，支撑历史查询与多轮续接。已实现：单会话 JSONL 存储、Turn 边界、历史查询与上下文还原
    • Quality：运行过程观测与任务质量评测。已有终端进度输出与本地协议测试；独立评测模块待扩展
  • 按需求增加的能力
    • 长任务与知识复用：计划、历史摘要、资料检索、长期记忆。
    • 可靠执行与隔离：中断恢复、后台 Worker、执行沙箱。
    • 扩展与编排：Skills、MCP、Hooks、Graph 工作流、多 Agent 协作与 Web UI。
  • 外部资源
    • 模型服务、本地工作区、存储介质与外部 API。当前已接入：模型服务、本地工作区与 JSONL 会话文件

学习导航：阶段 2 已实现 Policy 权限拦截；阶段 3 从多轮对话痛点推导会话保存与续接；阶段 4 探讨长对话下的上下文预算与裁剪。

学习主线：从独立 Loop 逐步扩展

每个核心模块先交付可接入现有闭环、可独立验证的最小可用版本（MVP），先跑通端到端主线，再根据真实任务的痛点做局部演进。

阶段与模块职责图怎样对应
  1. 阶段 0 · 最小 Loop：单文件跑通“模型请求 → 工具执行 → 结果反馈”闭环。
  2. 阶段 1 · 模块拆分：拆出 Tools 与 Model 模块，Runner 通过统一协议接口调用。
  3. 阶段 2 · 权限控制：接入 Policy，在执行前拦截覆盖已有文件等危险动作。
  4. 阶段 3 · 会话与记录：将对话与工具记录持久化为 JSONL，支持历史查询与多轮追问。
  5. 阶段 4 · 上下文管理与预算：对话变长后，按预算筛选本次发给模型的上下文。
  6. 阶段 5 · 长任务机制：按瓶颈针对性引入结果预览、历史摘要、检索或长期记忆。
  7. 阶段 6 · 可靠执行：处理进程中断后的状态核对与安全恢复。
  8. 阶段 7 · 扩展与编排：按需接入 HTTP 入口、Skills、Hooks、MCP 与多 Agent 协作。
