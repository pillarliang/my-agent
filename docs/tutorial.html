阶段 0：闭合独立的最小 Agent Loop

打开 examples/00_plain_loop.py，从 run_agent() 开始看。

1. 一次循环

模型根据本次请求里的 messages 了解任务进展。工具在本地执行后，程序要把真实结果写回消息链；下一次请求时，模型才能据此继续判断。

2. 阅读循环

打开 00_plain_loop.py，定位 run_agent()。

阅读时先抓住两个分支：模型提出工具调用，就执行并带着结果继续；没有工具调用且有非空文字，就返回说明。请求次数上限保证循环能够停止。

assistant.tool_calls[].id 与 tool.tool_call_id 表示同一次调用。先记录模型提出的调用，再记录对应回执，下一次请求才能知道每个结果属于哪个动作。

3. 安装、配置与运行

需要 Python 3.12 或更新版本与 uv；在项目根目录执行。按 .env.example 配置有效的 DashScope Key、匹配的 HTTPS 端点和可用模型。已有环境变量优先，已有 .env 可以复用。

项目根目录执行
uv sync --locked
uv run python examples/00_plain_loop.py

运行会请求真实模型并产生用量。默认最多四次请求，关闭 SDK 自动重试。模型会看到读取到的资料；示例工作区只放可用于本次学习的文件。

4. 阅读工具实现

在同一文件中，沿 execute_tool() → read_file() 阅读。

工具参数来自模型，属于外部输入，因此在 execute_tool() 入口校验。read_file() 专注文件读取与资源范围，这样可以单独测试，也方便以后复用。

文件不存在等预期失败也作为回执交给模型，给它修正请求的机会。模型请求失败或响应未正常结束时，循环则停止；不能把失败改写成成功或空内容。

阶段 1：从单文件提取模块与契约

把单文件循环拆成三个职责：Tools 执行工具，Model 请求模型，Runner 控制循环。本阶段已完成两条模块边界，下面按当前代码说明实现顺序。

1. Tools：定义工具，统一注册与执行

原理与接口见Tools 通用教程。ToolDefinition 保存工具名、用途、参数模型、执行函数和权限声明；ToolRegistry 按名称找到注册项，统一校验、询问 Policy、执行并返回回执。当前注册 list_files、read_file、search_text 和 write_file。

  1. 工具契约：先读 ToolDefinition、ToolSpec、ToolCall、ToolResult 与 ToolExecutor。
  2. 注册表：看注册、声明生成、参数校验与异常转换；其中统一权限检查见阶段 2。
  3. 文件工具：各工具使用相同定义方式，共用资源访问检查。

执行在当前进程内。非法参数和预期执行失败返回回执，注册错误和程序错误向外抛出。

展开当前工具执行流程

增加工具：编写普通函数，指定参数模型、所需权限和路径参数名，再调用 register()。不修改 registry.py 或 Runner。

2. Model：统一请求与回复，隔离 SDK 协议

原理与接口见Model 通用教程。当前由 LLMService.invoke() 接收 ModelRequest，返回 ModelResponse 或抛出 ModelError。服务内部管理 Key、Base URL 和 client，并使用 OpenAIChatModel 适配现有 DashScope 调用。

  1. 模型契约：先读 Model 接口、请求、回复与消息类型。
  2. 模型服务：LLMService 在构造时读取配置并创建 client，invoke() 发起请求，close() 释放连接。
  3. 协议适配器：看消息编码、SDK 请求、响应解码与错误转换。
  4. 沿一次工具调用，观察回复中的文字、调用 ID、停止原因和原生续接材料如何被保存，再用于下一轮请求。

第一版支持非流式文本与函数工具，记录供应商报告的用量。每次请求只有一次网络尝试；截断、拒绝、协议错误与连接错误都明确停止。路由、熔断与降级后续迭代。

3. Runner：通过接口连接两个系统

从 main() 顺着读：接收任务 → 设置工作区和权限 → 调用 run_task() → 展示结果。工作目录 workspace 与权限 policy 作为两个参数传入。

run_task() 用提前写好的 DEFAULT_TOOLS、工作目录 workspace 和权限 policy 创建 ToolRegistry，再创建 LLMService、调用 Runner，运行后关闭模型连接。它只返回 Runner 的运行结果。Key、Base URL、鉴权和 SDK client 都由模型服务内部管理。进入 run_agent() 后，Runner 只做：

  1. 读取工具的 specs，连同消息历史提交给 model.invoke()。
  2. 保存整份 ModelResponse，检查是否正常完成。
  3. 有工具调用时提交给 tools.execute()，将 ToolResult 追加到历史，再请求模型。
  4. 没有工具调用时返回 RunResult，包含模型说明与本次回执；请求次数耗尽则停止。

黑盒交互图分别见Runner ↔ Tools与Runner ↔ Model。SDK 消息编码由 Model 适配器负责，Runner 不解释原生续接材料。

阶段 2：用 Policy 控制动作权限

1. 本轮目标：保存摘要，禁止覆盖

已有 Agent 能调用工具读写文件。本轮增加权限检查：允许保存新文件，保留已有文件。完成标准是覆盖请求被 Policy 拒绝，原文件内容未变。

Policy 通用教程讲设计原则与可选方案。本章只讲本项目选用的实现；summary.txt 是验证用的示例名，不是通用入口的固定输出。

2. 当前选择，以及选择理由

  • 动作从哪里来：工具注册时声明所需权限和路径参数名，由共享代码生成本次动作。现有文件工具能复用 read、list、write，不必为每个工具写动作描述函数。
  • 规则怎样判断：Policy 对象保存权限开关和可选的文件名单，evaluate() 用条件分支判断。当前规则少，这种实现便于沿代码阅读，暂不引入配置规则语言或独立策略服务。
  • 在哪里控制执行：ToolRegistry.execute() 统一检查，拒绝就返回，允许才调用注册的函数。普通函数只负责实际操作，新增工具复用已有权限时不改注册表或 Runner。

这是本项目的组合选择。通用原则要求拒绝能阻止实际操作，并不要求所有 Agent 都采用这些类名、注册方式或判断位置。

3. 沿当前代码走一遍

  1. main() 创建允许新建、禁止覆盖的 Policy；run_task() 将它与工作目录传给工具注册表。这是初始化配置。
  2. 写入工具注册项声明 permission="write"、path_parameter="path"。它表示需要写入权限，具体文件名来自本次调用，不代表已经获准。
  3. prepare_action() 取出已校验的路径，检查目标：不存在是 create，已有普通文件是 overwrite。它返回 ActionRequest，此时没有写文件。
  4. Policy.evaluate() 按程序配置返回 PolicyDecision。本例的覆盖请求得到 allowed=False，原因是“禁止覆盖已有文件”。
  5. ToolRegistry.execute() 返回带原调用 ID 的 policy_denied 回执，不调用 write_file()。获准时才执行；Runner 接收回执并交给下一轮模型请求。

当前契约是 evaluate(ActionRequest) → PolicyDecision。执行函数收到已校验的参数、工作目录和获准动作，不接收 Policy。替换权限判断的实现，不必改变这条交互。

4. 运行禁止覆盖实验

预期：第二次返回 policy_denied，原因是“禁止覆盖已有文件”，文件仍为“原内容”。实验源码走的工具执行路径与 Runner 相同。

阶段 5：中断后怎样安全继续

只有在需要跨进程继续时引入恢复协议。

1. 区分事实

检查点说明停在哪里，回执说明观察到什么；超时或连接断开不能证明外部动作没有发生。

2. 先做只读恢复

保存稳定的运行与动作身份，从已知边界重建状态。对有副作用的动作，先核对结果，再决定重试。

3. 注入故障

分别中断于派发前、派发后未回执、取得结果未提交、提交回执后。检查实际副作用和恢复决策。

4. 验收

区分未派发、已完成、仍运行与未知；未知动作不被无条件重试。需要不可信执行时再增加 Worker 或隔离后端。

阶段 6：按需求增加入口、扩展与编排

从稳定的单 Agent 基线选择一个需求分支。

1. 应用入口

需要 Web 时先让 CLI / HTTP 共用应用用例；执行、查询与观察分开，断开 SSE 不等于取消任务。

2. 能力扩展

方法资料可接 Skills，生命周期可接 Hooks，外部工具可接 MCP；每种扩展仍需权限、预算与回执。

3. 编排分支

1. 实现原理：提交、执行和观察分开

Web 与 CLI 的入口结构

入口、执行与观察分别组织。

同一个生成报告的请求，无论来自命令行还是浏览器，都应经过相同配置、权限和执行流程。前端不需要理解模型协议，CLI 也不应复制另一个 Agent Loop。

应用服务接收业务数据，例如会话身份和问题，而不是 HTTP Request 或 DOM 对象。存储中的 Run ID 用来关联执行、历史和进度，页面状态只是展示视图，不是执行事实源。

2. 执行服务有哪些方案

A. 请求内同步执行

接口一直等待 Runner 返回，适合 CLI 和耗时很短的调用，实现简单、错误直接。代价是请求超时与任务生命周期紧密耦合，页面断开后也难以清楚表达执行状态。

B. 进程内后台执行

接口返回任务身份，任务由进程内集合持有，查询和进度接口独立工作。它适合本地 Web MVP，代码少，也能避免模型网络等待阻塞 HTTP 事件循环。

代价是执行者与 Web 进程共同存亡，线程里的阻塞工作也不能仅靠取消异步 Task 就可靠停止。FastAPI 并发说明有助于理解异步 HTTP 处理与同步阻塞工作的区别；实际任务所有权仍由应用设计。

C. 持久队列与独立 Worker

提交先持久化任务，由 Worker 领取并运行，前端继续按身份查询。它适合长任务、服务重启和独立扩容。

新增成本包括重复投递、租约、任务状态、取消传播和外部副作用对账。队列保证受理或再次投递，并不自动保证每个工具只执行一次，参见State。

D. 外部 Agent 运行服务

Web 或 CLI 调用完整运行服务，消费其任务身份与事件。它减少自建调度，但需要明确会话、权限、历史和产物由谁管理，避免同时维护两套冲突状态。

这是部署与控制权方向的选择，不必为了拥有 Web UI 就引入它。

5. 断线、历史与重复提交

事件采用稳定身份和游标，客户端重连后补读，再按身份去重。持久历史负责重建页面，实时事件负责显示后续变化；只保存前端聊天数组，无法可靠应对刷新和跨入口读取。

用户点击发送后网络中断，可能不知道任务是否已经受理。后续可以增加客户端请求 ID，由服务做提交去重；仅仅重发 HTTP POST 可能启动第二次任务。这个提交身份与模型工具调用身份不同。

页面关闭、请求断开、用户取消和进程退出也应分别定义。取消的接口应返回受理状态，最终停止要由执行端确认；UI 不应在发出取消请求后立即伪装所有工具已经停止。

6. 本项目的演进顺序

Loop / Runner：控制一次任务怎样继续和停止

1. 实现原理：一个有边界的状态机

以生成报告为例：用户请求进入当前状态，Builder 构建输入，Model 返回读取调用，执行器读取文件，Runner 保存结果并再次调用模型。模型也可能返回不含工具调用的文字，此时返回模型说明与执行记录。

Loop：继续、停止与有界修复

通用控制模式 · 当前没有自动验收修复。

状态至少包含当前输入、模型和工具记录、已用预算、停止原因，以及检查结果。预算和取消在程序边界检查；Prompt 中的“最多执行五步”可以指导行为，程序仍需自己计数。

不要把三类控制混成一个状态：模型响应结束是供应商协议事实，Loop 结束是程序控制事实，任务验收是针对需求和产物的事实。三者可能有不同结果。

2. 控制流有哪些方案

A. 自主工具循环

程序只固定“模型 → 工具 → 模型”的骨架，模型根据实际反馈选择下一步。实现简单，适合路径未知、需要搜索和试错的任务。

它的代价是路径不稳定，可能重复探索或提前结束。需要限制 Step、工具次数、时间和费用，并在外部设置验收条件。阶段 0 的单循环采用这一基本控制方式；其他预算与验收按需求再增加。

B. 单循环内的可更新计划

增加结构化计划或 update_plan 工具，让模型维护目标、步骤和当前进度，实际动作仍在同一个循环中选择。它主要改善长任务状态和用户可见进度，不要求每个步骤单独调用一个 Agent。

收益是可以明确展示依赖和未完成工作；代价是计划可能过时，模型也可能错误勾选完成。计划状态应与实际工具回执、检查结果分开，不能用“所有 Todo 已完成”代替验收。

C. 独立规划器与执行器

规划器先生成带依赖的任务，执行器领取当前任务，反馈触发重规划。实现需要计划版本、步骤状态、结果契约和重规划条件。

它适合步骤较稳定、执行者能力不同的任务，也方便分别优化规划与执行。代价是额外调用、交接损失和过时计划；若每个小改动都重做全计划，成本可能高于自主循环。可以先尝试 B，再根据真实失败判断是否需要独立角色。

D. 显式 Graph 或业务状态机

程序定义必要节点和转移条件，例如“读资料 → Agent 生成候选 → 检查 → 用户批准 → 发布”。节点内部仍可运行自主 Loop。Graph 控制业务边界，Loop 处理节点内的不确定过程。

它适合固定审批、条件路由和持久等待；代价是状态 Schema、节点版本和恢复语义。Graph 不要求多个 Agent，也不能自动提供安全沙箱或副作用幂等。控制流与持久执行的关系见State。

方案 决策主要在哪里 适合的问题 主要代价
自主循环 模型逐步决定 路径未知的短任务 难预测动作数量
循环内计划 模型决策加结构化进度 同一目标的较长任务 计划更新与事实核验
规划器和执行器 分层决策与反馈 可分解、依赖明确的任务 额外调用和交接

这些方案可以嵌套，不是从“低级”到“高级”的产品排名。Anthropic 控制模式也区分工作流与动态 Agent；选择依据应是任务的可预测部分和实际失败。

4. 验证循环放在哪里

终止后检查最容易理解：模型给出最终说明，检查器读取产物，程序报告指定检查通过或失败。可以先实现这种终止后检查，再考虑循环内修复。

检查后自动修复在失败时生成结构化反馈，再进入执行循环。反馈应包含检查名、目标版本、实际错误和允许修复范围。修复必须继续消耗原任务的总预算，另设次数上限，禁止通过新建无限 Run 绕过限制。

过程内检查让某些动作完成后立即检查局部不变量，例如写入配置后解析 Schema。它可以更早发现问题，但局部通过不等于最终目标通过。三种检查可以组合，检查对象和时刻要记录清楚。

5. 停止与无进展检测怎样实现

建议区分普通工具失败、模型错误、预算耗尽、取消、状态损坏和验收失败。普通工具失败可以作为结果交回模型纠正；状态损坏则应由程序停止，而不是让模型猜测下一条数据库操作。

重复调用不总是错误：轮询外部任务可能连续读取同一资源。无进展判断应综合工具、规范化参数、结果摘要、外部版本和重复次数，配合等待间隔；只比较参数容易误伤正常等待。对长期等待，更合适的做法是保存等待条件并释放执行者，参见编排。

6. 本项目的演进顺序

当前由 run_agent() 控制闭环。先保持请求、调用和回执的顺序；当停止策略、用量或任务状态增长时，再提取单次运行状态与控制函数。只有需要可替换的执行策略时才引入额外抽象。

每次只增加当前需求所需的机制，用相同任务和可观察证据检查行为。

7. 动手练习与验收

在检查失败时，允许真实模型进行一次修复，保留原 Step、时间和权限边界。记录初次结果、检查证据、修复动作和最终结论，不覆盖失败轨迹。

验收时分别观察：检查通过、检查失败后修复、预算不足、工具拒绝和用户取消。未稳定触发的分支明确标为未验证。模型说“已经修好”不能覆盖检查失败；未配置检查时也不能自动报告任务通过。

模块原理与方案

Model：隔离供应商协议，保留续接语义

1. Model 是什么，为什么单独做一个模块

Model 模块负责和模型服务通信：把任务和已有对话发给模型，再把模型的回答交回来。

请求模型需要处理地址、密钥和服务要求的数据格式。如果把这些全写进 Runner，循环就会和某一家模型服务绑在一起。单独做一个模块，Runner 就可以专心决定什么时候请求模型、什么时候执行工具。

两个核心抽象

  • 统一调用接口：Runner 总用同一种方式发送请求、取得回答。本项目由 LLMService.invoke() 提供。
  • 协议适配器：把项目自己的请求和回答，转换成模型服务要求的数据格式。更换模型服务时，主要修改这一层。

密钥、服务地址和连接也由 Model 内部管理。请求回来后，如果模型要求执行工具，仍由 Runner 安排执行。

2. Runner 怎样使用 Model

以“读取 notes.txt”为例：Runner 先把任务、已有对话和可用工具告诉 Model；Model 请求远端模型，可能带回“请调用 read_file”的回答。Runner 执行后，把实际读到的内容放进下一次请求。

  • 发给模型的材料（ModelRequest）：任务和对话、可用工具说明，以及这次最多生成多少内容。
  • 模型的回答（ModelResponse）：回答文字，或者要求执行的工具调用；也可能同时有两者。
  • 请求失败（ModelError）：例如连不上服务，或回答无法按约定读取。当前 Runner 遇到这种错误会停止。

Runner 通过 LLMService.invoke() 完成一次请求。它保存整份回答，执行工具后再继续请求。

读源码时再看：回答里还保存了什么

回答还可能带有生成停止原因、Token 用量，以及下一次请求需要原样带回的供应商数据。这些数据由适配器解释，Runner 保存后继续传递。

如果回答被截断或被服务拒绝，当前循环会停止，避免执行没有生成完整的工具调用。工具参数仍由工具系统解析和检查。

展开编码、请求与解码管线

工具参数保留原始 JSON，由工具系统解析和校验。协议编码与资源授权各自在对应边界处理。

3. 协议之间有什么差异

Chat Completions通常按消息表示交互：Assistant 的工具调用列表与后面的工具结果通过 ID 关联。Responses按输出项表示文字、调用和其他协议材料；函数结果通过 call_id 关联。

阿里云函数调用说明展示应用接收调用、执行函数、追加结果并再次请求的流程。OpenAI 函数调用说明另外说明推理项与函数结果续接的要求。只抽取最终文字，会丢掉执行工具所需的信息；只重建调用，也可能丢掉其他续接项。

将“兼容 OpenAI”理解为需要验证的协议范围，而不是全部特性承诺。模型、地域、端点与模式都可能影响并行调用、思考材料和参数支持。升级时应重新执行真实契约测试。

4. 有哪些适配方案

A. 每个供应商一个原生适配器

编码器和解码器分别使用供应商 SDK 或 HTTP 协议，核心只依赖统一接口。它能保留独有能力和清楚的错误，但需要维护多个适配器。

适合学习协议、需要特殊响应项，或对用量与错误可追溯性要求高的系统。若后续直接实现 Responses 协议，可以采用这一方向。

B. 统一兼容接口或模型网关

应用统一调用某种消息协议，由服务或网关完成供应商转换。它减少接入工作，便于集中鉴权、限流和路由；代价是协议差异可能被隐藏，特有字段可能需要透传。

阶段 0 直接使用 OpenAI SDK 调用 DashScope 兼容端点，没有自建网关或适配器类。若未来加入网关，需要确认工具参数、错误码、用量、续接项和取消是否仍能正确传递。

C. 中立内部协议加能力协商

内部使用明确的消息、内容块、调用、停止原因和续接对象，再由适配器转换。另设能力信息，例如是否支持图片、原生压缩、并行调用和 Token 计数。

它利于长期演进，但设计过早会产生许多尚未验证的抽象。不要为了字段统一就删除供应商语义；不透明续接材料可以保存在适配器自己的命名空间中，核心只负责原样保存与传递。

D. 把循环交给完整 Agent SDK 或托管运行时

应用传入工具和配置，由运行时处理更多循环与会话行为。它可以减少自建代码，但接入边界已从“模型适配器”上移到“Agent 运行服务”。如果仍让本地 Runner 同时控制工具和状态，就容易形成两套相互竞争的生命周期。

这是一条独立产品方向，不是替换某个 invoke() 方法即可完成的升级。要先确定谁负责重试、历史、授权、工具执行和恢复。

6. 流式响应为什么是另一套状态机

流式接口可能逐段返回文字、工具名、参数片段和最终状态。实现时按响应项身份缓存增量，只有在调用完整并通过校验后，才允许执行。网络断开时残缺的参数不是可以执行的 JSON。

用户可见的文字流可以提前显示；可执行调用必须经过完成边界。工具进度事件与模型 Token 增量也是两种流：后续 Web 可以用 SSE 传递运行事件，这并不意味着模型已经流式生成。参见应用入口计划。

7. 错误、重试与切换模型

输入无效、权限错误和上下文超限不能原样无限重试。限流或临时故障可采用有限退避，但要记录尝试次数并消耗同一预算。流式断开后还需识别是否已经执行工具，避免整段任务重跑产生重复效果。

切换模型也不是只改名称：新模型可能有更小窗口、不同协议和不兼容续接材料。应重新编码可移植事实并重新检查预算，不把旧的加密续接项直接带给另一供应商。用量缺失报告未知，不记为零。

8. 当前实现与后续扩展

阶段 1 的 Model 第一版已实现统一请求、统一回复与 Chat Completions 适配器。当前由 LLMService 管理凭证和连接，支持文本和函数工具；认证、连接、超时与 HTTP 错误形成明确异常，原生材料限定在同一协议、端点和模型续接。

3. 有哪些实现方案

A. 全量历史：建立最直接的基线

实现时按时间顺序发送完整交互，另外附上稳定指令和工具定义。它几乎没有选择逻辑，适合短任务，也便于检查模型是否因缺少材料而失败。

收益是信息没有被有意压缩；代价是输入持续增长，且信息存在于窗口里也不保证模型会正确使用。扩大窗口可以延迟溢出，但没有消除无关内容、费用和长程约束遗漏。它是对照基线，不是生产系统永远适用的默认方案。

B. 按完整交互块裁剪：限制增长速度

给消息分块，保留近期块、当前请求和未结束调用，再从最旧的可移除块开始裁剪。一个块至少要维护模型调用与全部对应结果；不能只按最后 N 条消息切片。

它不增加摘要模型成本，行为确定、容易定位遗漏。缺点是旧约束和旧证据可能直接失去可见性。适合短对话、彼此独立的任务；持续修改同一产物时，应额外维护当前目标和重要约束。后续也可以采用更保守的方案：整个活动 Run 都不裁剪。

C. 工具输出卸载与确定性投影：先处理重复的大内容

将长日志保存在产物存储中，消息只留状态、首尾预览、引用和补读方式。对于已保存到文件的写入内容，可以在后续请求投影中移除重复的大参数；执行时的原始参数仍需保存。

这类策略不需要模型概括，通常比立即摘要更容易保持准确的路径、错误码和数值。但引用必须可以回读，文件可能被覆盖或删除，预览也可能漏掉关键错误。可以使用内容哈希、版本和读取时刻固定证据。直接截断且不给补读路径，会永久丢失可用细节。

对上面的报告任务，可以把 50 页构建日志变成“测试失败、失败项摘要、完整日志引用”，而不是把用户的“不发布”也压缩掉。分页读取工具应限制返回量，否则刚卸载的内容又会一次读回。

D. 摘要加近期原文：保存过程中的工作状态

在完整块边界选取旧前缀，调用摘要模型，保留近期原文和活动调用。重建输入时使用“任务状态 + 旧摘要 + 近期块 + 当前材料”。摘要可以包含目标、已确认约束、事实和来源、失败尝试、待办、产物引用与不确定项。

实现时把来源 ID、源范围哈希、摘要版本和生成用量由程序保存。模型只生成内容，不能自行决定哪些旧授权仍有效。连续摘要还会累积信息损失，因此关键约束和检查事实最好能从结构化状态重新生成。

同步摘要会阻塞当前请求，生命周期简单；后台摘要可提前准备，减少等待，却要处理取消和过期。如果后台根据版本 10 生成摘要，而用户已在版本 11 修改要求，就不能直接覆盖新状态。先做同步并验证效果，再考虑带版本检查的后台生成。

摘要失败时要明确选择保留原视图、采取较保守裁剪，或停止；不能悄悄用空摘要继续。摘要中的“已完成”仍是模型生成的工作说明，真正验收应读取检查器与产物证据。

E. 按需检索与渐进加载：减少一开始装入的内容

先提供目录、标题、工具名称或方法描述，任务需要时再取正文。项目文件可先用路径、关键词或 SQLite FTS；表达变化较大的知识可以尝试向量召回；混合检索结合精确匹配、语义匹配与重排。

检索适合“资料很多，但本轮只需要很少一部分”。它无法替代过程摘要：当前目标为何改变、刚才试过什么，需要从任务状态和交互中取得。检索还可能漏召回、命中旧版本或跨作用域读取；访问控制应在检索和取原文阶段都生效。

在报告任务中，先检索与报告主题相关的段落，再补读原文。将返回片段带上来源位置、版本和截断信息，最后测量证据命中率与约束召回，而不是只看输入减少多少。

F. 独立子任务 Context：避免主过程积累全部探索

把边界明确的搜索或评审交给独立执行者，只把目标、必要约束和证据要求传给它，主过程接收结果与来源引用。这样改变的是信息流拓扑，不是压缩同一段文本。

收益是大量探索过程留在子任务中；代价是额外调用、遗漏交接信息和结果核验。复制全部父历史的 fork 仍有输入成本，不能一律宣称委派节省 Token。权限、文件系统、预算和消息上下文的隔离也是不同问题，详见编排教程。

G. 供应商原生压缩：保留协议级续接状态

部分模型 API 提供压缩接口，由服务返回供后续请求使用的协议项。其内容可能是不透明状态，不能按普通摘要解析、编辑，或直接带到另一个供应商继续。

它能减少应用自己设计摘要的工作，但会增加协议和供应商耦合；保真程度仍需任务评测。跨供应商迁移要保留可移植的任务事实、原始记录与产物引用。本项目目前没有启用这类压缩，兼容 Chat Completions 也不能证明某端点支持它。

源码核对，固定提交。 agent-loop.ts 先运行 transformContext，再经 convertToLlm 转成供应商消息。这样可以分别扩展上下文选择和协议编码。

6. 同一个长任务会有什么差异

假设用户在第 1 轮要求报告使用 UTC 时间，第 10 轮读取大量日志，第 20 轮修改报告格式，然后在第 30 轮要求继续：

  • 仅裁剪可能保留第 20 轮格式，却失去第 1 轮时间要求。需要从已确认任务状态补回。
  • 仅摘要可能把“不要发布”概括成“准备发布”。需要保留来源、关键约束和独立授权检查。
  • 仅卸载能移走日志正文，但无法概括目标变更。仍需历史或任务状态。
  • 仅检索可能找到相关文档，却不知道用户刚改过格式。仍需当前要求和过程信息。
  • 组合策略可以保留已确认约束，卸载日志，摘要旧过程，按需补读原文；仍要通过实际检查确认是否有效。

这些是用于比较机制的推演，不是上述产品实测结果。同一任务应固定模型、工具、文件快照与验收条件，再比较压缩前后的输入、结果与失败。

7. 本项目按什么顺序演进

当前直接把内存消息和工具定义传给 SDK。先在输入确实增长时增加纯选择函数，再考虑预算与完整块裁剪；需要更复杂来源时才增加输入清单或构建器，不让构建输入顺便产生外部动作。

每次只增加当前需求所需的机制，用相同任务和可观察证据检查行为。

8. 动手练习与验收

先实现一个纯选择函数，输入真实记录中的完整块，输出保留、摘要和省略范围，原始记录保持不变。再接入真实模型生成摘要，使用同一组长任务比较扩展前的基线与新策略。

本章讲工具系统的核心抽象、与 Loop 的接口和内部机制；注册与调用见阶段 1，受控创建见阶段 2。

1. Tools 是什么，怎样和 Runner 配合

工具是程序实际做事的代码。例如模型想知道 notes.txt 的内容，只能提出“读取这个文件”的要求；工具才会真正打开文件，把内容或失败原因交回来。

用户不知道文件名时，模型可以先调用 list_files 查看工作目录，再决定读取哪个文件。工具系统保存每个工具的说明和实现，收到调用后按名称找到对应工具。

两个核心抽象

  • 工具定义（ToolDefinition）：把普通执行函数与名称、用途、参数模型、权限声明对应起来。模型只看到工具说明，不会取得 Python 函数。
  • 工具注册表（ToolRegistry）：保存这些定义，收到调用后按名字找到工具，检查参数、识别动作、询问 Policy，允许才执行。

工具系统与 Runner 的黑盒交互

仍然看读取文件：工具系统先告诉 Runner“有 read_file，可以传入文件路径”；模型提出读取 notes.txt 后，Runner 把这次调用交给工具系统，工具系统实际读取并交回结果。

  • 工具说明（ToolSpec）：告诉模型工具能做什么、需要哪些参数。Schema 是程序可读取的参数格式要求。
  • 调用要求（ToolCall）：例如调用 read_file，参数是路径 notes.txt。
  • 执行结果（ToolResult）：例如实际文件内容，或“文件不存在”。结果保留调用编号，Runner 才知道它对应哪次要求。

在代码中，Runner 读取 specs 取得说明，通过 execute(call) 提交调用。它不需要逐个了解工具内部的写法。增加写文件工具后，执行前的允许检查见Policy。

2. 工具粒度有哪些方案

A. 专用结构化工具

例如 read_file(path, offset, limit) 和 write_file(path, content)，每个工具有少量明确参数。实现可以准确限制路径、大小和作用，模型也更容易理解返回值。

它适合学习和明确业务边界。代价是需要维护较多工具，组合能力取决于提供的操作；工具数量增大后还要处理 Schema 占用和发现问题。

B. 通用能力工具

例如 Shell、SQL 或代码执行，一个接口可以表达很多操作。它灵活、工具表短，也方便复用现有 CLI；代价是难以从任意字符串识别真实资源和副作用，超时、进程清理和隔离也更复杂。

通用工具适合已有执行环境和资源约束的场景。不能仅通过检查命令前缀就假设获得安全边界，子进程和间接调用也会产生效果。执行隔离见Policy。

C. 高层业务工具

例如 generate_monthly_report(source_ids, template_version)，内部完成取数、生成和登记。它减少模型需要协调的步骤，并能把业务不变量放进确定性代码。

代价是复用范围窄、接口版本与业务耦合。内部如果继续调用模型或外部服务，也必须把用量、错误、部分效果和检查范围返回给上层，不能只返回一句“已完成”。

专用结构化工具 组合小动作 参数、路径和结果范围 工具与 Schema 增长
通用工具 生成命令或程序 灵活表达复杂操作 效果识别与隔离困难

Anthropic 工具设计实践讨论名称、说明和返回内容对决策的影响。它们应作为任务评测变量；“工具越少越好”和“越专用越好”都需要具体任务证据。

3. 执行放在哪里

进程内函数依赖少、延迟低，适合可信且有界的小工具；但阻塞、崩溃和主进程共享权限是明显限制。

独立 Worker 进程通过结构化协议执行，方便限制输出和强制终止。它需要进程监督和资源清理；单独启动进程并没有自动隔离主机文件和网络。

远程服务或沙箱后端通过 RPC 提交动作，返回任务身份和回执，适合更强隔离与独立扩容。它引入认证、网络故障、版本兼容和结果未知，需要与持久状态协议一起设计。

工具 API 与执行后端可以分开。例如同一个 read_file 访问本地工作区、受限容器或远程逻辑文件系统；Runner 继续使用同一 ToolCall，后端负责真实资源映射。

4. 真实实现怎样做

Deep Agents，源码核对。 FilesystemMiddleware提供模型可见文件工具，并通过后端协议访问存储；wrap_tool_call 在结果边界处理超大内容。BackendProtocol区分文件能力与执行能力。可借鉴的是将定义、结果治理和真实后端分离。

pi，源码核对。 agent-loop.ts根据执行设置和工具的串行要求选择串行或并行批次。可借鉴的是让执行策略由程序决定，不能因为模型一次返回多个调用就自动并行所有副作用。

MCP，协议文档。 架构规范把外部能力放在服务器、连接放在客户端、授权和聚合放在宿主。MCP 可以统一发现与调用，但业务幂等、效果对账和访问范围仍需应用定义，详见扩展教程。

5. 串行、并行和长任务怎样选择

互不依赖的只读操作适合受限并发；同一文件的“读 → 改 → 检查”有依赖，应保持顺序。并行写入不同路径也可能共享索引或全局状态，因此仅比较文件名不足以判断独立性。

工具元数据可以增加 effect_class、并发分组、超时和是否可查询回执。调度器据此限制并发；这些元数据必须由可信实现提供，不能直接把外部服务器自报的“只读”当成授权证明。

长任务宜返回 job_id，再通过事件或有间隔的状态查询续接。返回任务 ID 只表示已受理，不能视为产物已完成。

6. 回执、幂等与未知效果

考虑外部创建报告的调用：服务已经创建资源，但返回前网络断开。程序只知道结果未知，不能简单按失败重试。正确设计需要先保存逻辑调用身份，执行时使用稳定幂等键，随后查询回执或真实资源。

后续接入远程工具时，再增加逻辑调用编号、每次尝试编号、成功或未知状态，以及外部系统的记录。当前没有实现这套远程协议。

同一逻辑调用的重试复用幂等键；用户有意再次执行的新动作应取得新身份。仅按参数哈希全局去重会把合法重复动作误删。更完整的恢复设计见State。

7. 大结果与精确编辑

大结果应带总量、预览范围、截断标记和补读引用。Context 可以选择少发一些内容，但完整回执仍应有位置可查；模型不应把预览当成全量结果。

下一阶段的编辑工具可要求 expected_sha256 和精确旧片段，写入前重读并比较版本，发现外部修改就拒绝。它能减少旧视图覆盖新文件的问题，却不自动解决所有跨进程竞态；需要结合原子替换、锁或隔离工作区。

2. 当前实现

Tools 怎样询问 Policy

注册时用数据声明需要 read、write 或 list 权限，不传权限判断函数。比如 read + path_parameter="path" 表示“读取本次调用中 path 指定的文件”。

注册表先根据权限声明和本次参数生成动作与目标（ActionRequest），再统一调用 Policy.evaluate()。读取与搜索对应 read；写入先识别 create 或 overwrite。

Policy 返回允许或拒绝及原因（PolicyDecision）。允许才调用注册的执行函数；拒绝直接返回 policy_denied，执行函数不会运行。完整协议与黑盒图见 Policy 教程。

所有注册的工具共用这一处权限检查，执行函数不需要手动调用授权。注册与回执见阶段 1；统一权限检查见阶段 2。

3. 动手练习

count_lines 需要读取文件，因此注册时直接声明 read，并说明路径来自调用参数 path：

tools.register(
    count_lines, ReadFileArguments,
    permission="read", path_parameter="path",
)

permission 表示工具需要什么权限；path_parameter 是参数名，不是固定文件名。声明需求不等于获得授权，Policy 仍可拒绝。

完整例子见 count_lines.py。运行后先得到 3 行，再看到禁止读取的回执；不请求模型：

uv run python -m examples.count_lines

接入测试还验证它能通过 Runner 完成模型与工具往返，无需修改注册表。

Policy：把授权落实到真实动作

1. 解决什么问题，必须保证什么

用户让 Agent 保存摘要，同时希望保留已有资料。模型可能选中一个已有文件，工具也有能力改写它。程序需要在操作发生前，判断这次覆盖是否允许。这就是 Policy：按规则作权限判断。

核心是规则与决定：规则说明允许哪些动作，决定回答本次动作是否允许及原因。Policy 判断权限，不执行写入，也不评价摘要内容是否正确。

  • 根据实际动作判断：明确要做什么、操作哪个目标；“保存摘要”可能实际造成覆盖。
  • 权限来源可信：程序依据应用配置或经确认的授权作判断，模型文字和读到的资料不能自行授予权限。
  • 决定约束执行：被拒绝的操作不能发生，也不能通过另一个调用入口绕过检查；没有获得许可时不能默认为允许。
  • 执行符合许可：获准新建不能变成覆盖；允许尝试也不代表操作已经成功。

这些是设计原则。权限声明、某个类名、某个函数签名，以及检查放在哪个文件里，都是实现选择。

2. 黑盒交互：动作与目标，决定与原因

仍以保存摘要为例：工具系统识别到本次准备覆盖 summary.txt，向 Policy 提交动作与目标。Policy 回答“拒绝：禁止覆盖”；工具系统据此停止写入，并把失败交回 Runner。

  • 输入：本次要做的动作与目标，例如“覆盖 summary.txt”。
  • 输出：允许或拒绝及原因，例如“拒绝：禁止覆盖”。

Policy 负责作决定，调用与执行部分负责落实决定。检查可以接在统一执行入口或资源访问接口，但必须覆盖真实操作路径。具体 Python 契约和初始化配置见阶段 2。

3. 可选实现方案：两个不同的选择

“规则怎样判断”和“本次动作怎样取得”可以分别选择。以下是设计参考，不表示项目已经实现了所有方案。

规则怎样判断

  • 条件分支：在代码中判断动作、目标与权限开关。规则少时容易阅读；规则增多后，修改与维护成本会上升。
  • 配置规则匹配：把允许、拒绝条件写成配置，按明确顺序匹配。适合经常调整的规则；需要处理冲突、默认行为和规则版本。
  • 独立策略服务：统一服务接收动作并返回决定。适合多个入口共用组织规则；会增加服务维护、调用失败和权限数据管理的成本。

本次动作怎样取得

  • 工具或适配器提供动作描述：用函数整理实际动作与目标，适合每种工具差异较大的场景；需要维护描述逻辑，并保证与实际执行一致。
  • 注册时声明所需权限：由共享代码结合声明与调用参数生成动作。适合多个工具复用相同权限类型；新增权限类型时，需要扩展共享解析逻辑。

两种接法都可以在统一入口调用 Policy。采用哪种方式，都需要先取得准确动作，并在执行前落实拒绝决定。

4. 本项目当前选择

本项目选用注册时声明权限、共享代码生成动作、统一执行入口检查、条件分支判断规则。它便于复用当前文件工具的权限，也便于从一次调用读懂整个过程。

这是当前版本的实现，不是 Policy 的唯一设计。选择理由、源码顺序和运行命令集中在阶段 2。

5. 如何验证原则成立

既检查允许的动作能执行，也检查被拒绝的动作没有发生。验证禁止覆盖时，要确认权限判断返回拒绝、写入函数没有运行、原文件内容未变。

还需检查实际执行是否符合获准动作。例如获准新建后，目标突然出现，也不能改成覆盖。具体实验与检查见阶段 2 的禁止覆盖实验。

按需了解：审批、受限授权与执行隔离（当前未实现）

人工审批

需要人作决定时，可以暂停并展示具体动作、目标和参数。审批后执行前仍须确认动作未变、授权仍有效。它适合需要人工判断的操作，代价是等待状态、身份校验和恢复流程。

执行隔离

Policy 判断是否批准动作；沙箱限制执行代码实际能访问什么。它们是不同职责。子进程本身不保证文件或网络隔离，操作系统限制、容器或虚拟机也需要按授权范围配置，不能替代业务权限判断。

受限授权凭据

也可以由可信程序签发仅允许特定主体、动作、目标和有效期的凭据。它适合短期委托，代价是撤销、过期、并发消费与重试管理；不是给工具加一个“已批准”参数就能实现。

不可信资料与进一步阅读

资料可能诱导模型提出越权动作。提示模型忽略恶意指令有帮助，但权限仍须由程序执行检查，不能让资料自行修改规则。更多源码与设计资料见方案依据；等待与恢复涉及的状态问题见Session / State。

1. 实现原理：区分位置、事实和外部效果

生成报告时，程序可能已保存模型的写入调用，却还没执行工具；也可能文件已经创建，但回执尚未提交。两种情况看起来都“停在写入附近”，恢复动作却不同。

2. 有哪些状态方案

A. 仅内存状态

将消息、当前步骤和预算保存在进程对象中。它实现直接，适合一次性任务或可随时重做的只读操作；进程结束后无法继续，也不适合有昂贵副作用的任务。

B. 快照加执行账本

快照保存工作状态，账本按稳定逻辑身份保存动作意图、尝试和回执。启动时读取最新快照，再判断动作是尚未派发、已确认，还是效果未知。

它适合从简单循环逐步增加恢复。代价是必须明确快照提交边界和动作协议；仅保存 step_index 然后执行后续步骤，无法判断中断前动作是否已经发生。

C. 事件日志加状态投影

执行事实按顺序追加，查询状态和工作视图由投影产生；可用检查点减少每次重放的成本。它适合多个消费者、丰富审计和复杂恢复。

代价是事件版本、重放规则、投影升级和顺序管理。普通观测日志不自动等于事实源。 只有定义了提交约束、完整事件和重放语义，日志才足以支持执行恢复；当前独立脚本只打印进度，没有事件存储或恢复保证。

D. 持久工作流运行时

由运行时保存节点、等待和重试状态，应用将动作放入明确任务或节点。它适合长时间等待、审批和跨服务协调，也会引入运行时约束与工作流版本兼容。

这种运行时减少部分调度代码，却不能自动确认任意外部 API 的效果。依然需要幂等键、查询回执或人工对账。

6. 并发与版本为什么不能省略

同一会话多执行者竞争时，需要租约或锁和条件更新，避免两个 Worker 都认为自己有权继续。租约过期本身也不足以让旧 Worker 失去写能力，重要后端还需要检查执行代次或 fencing token。

事件和快照必须带 Schema 版本。升级后应验证旧记录能否读取与投影；无法解释的状态应拒绝自动执行。原始事实的重放只重建状态，不应在普通查询时再次发送外部动作。

7. 本项目的演进顺序

当前消息只在单次 run_agent() 内存中存在。需要重查任务时先记录运行和消息，需要续接会话时再定义历史投影；自动恢复是另一个需求，不从保存数据库自然推导。

每次只增加当前需求所需的机制，用相同任务和可观察证据检查行为。

8. 动手练习与验收

先给只读动作保存稳定身份，在意图保存后、工具返回后和结果提交后分别中断程序。重新启动时检查已确认结果不重复执行、未派发动作可以继续，变化的文件被明确标记为新观察。

工具仍使用真实文件，任务仍由真实模型发起；故障注入用于进程和存储边界，不替换模型。写动作在完整协议建立前不自动恢复。最后解释同一策略为什么不能直接用于创建订单或发送邮件。

1. 实现原理：写入和读取是两条管线

2. 先区分知识类型和存储方案

知识可以分成事实与偏好、经验案例、可复用方法。前两类适合保存来源和适用条件；多步骤方法也可能更适合整理成 Skill。分类帮助确定生命周期，不要求为每类部署一个数据库。

文件、SQL 和向量索引则属于另一组选择：文件方便人工编辑，SQL 方便结构化约束，向量索引方便语义召回。它们可以组合，不是知识类型，也不是固定的技术升级阶梯。

3. 有哪些实现方案

A. 用户维护的文件记忆

用短索引列出主题，正文放在 Markdown 文件中；每个 Run 只加载相关概览，再按需读取正文。写入由用户维护或由显式操作触发。

它容易审阅、版本控制和迁移，适合单用户学习系统。代价是冲突合并、作用域和删除规则需要约定；全量加载不断增长的文件，会把记忆问题转成 Context 问题。

B. 结构化条目加关键词检索

用 SQLite 保存 ID、类型、作用域、来源、版本和状态，再按关键词、项目和时间检索。正文可以在数据库或文件中，检索索引由程序维护。

它便于更正、撤销和审计，精确术语和项目名也容易命中；代价是查询与 Schema 设计，语义改写可能漏召回。这是本项目优先考虑的方案，可以先用 SQL 条件，再按需要增加 FTS。

C. 向量或混合检索

为条目生成 Embedding，按语义召回，再与关键词、时效和类型过滤组合，必要时重排。它适合知识量大、表达变化明显的检索问题。

新增成本包括模型用量、索引版本、重建和质量评测。权限过滤不能只在拿到前几条结果后做，否则既可能漏掉有权内容，也会把越权数据带入后续处理。原文、来源和条目状态仍应在正式存储中维护。

D. 自动提取与后台整理

任务结束时或压缩前，从交互提取候选，再合并、去重和确认。有的系统直接更新记忆文件，有的先保存日记或观察，再周期整理。

它减少人工维护，但可能把模型猜测写成事实、把一次性要求写成长期偏好，或在用户更正后写回旧值。应记录提取器版本和来源范围，先允许查看与拒绝候选，再逐步提高自动写入比例。

SQL 条目与关键词 需要版本、更正与隔离 行为可解释 语义召回有限

2. Skills 有哪些加载方案

A. 全量正文常驻

启动时读全部方法，将正文加入每轮输入。实现直接，适合极少、很短且固定的方法。代价是输入随方法库增长，任务无关内容和冲突也会增加。

3. Hooks 和中间件怎样实现

进程内回调

程序在 run.start、model.before、tool.before 或 tool.after 等边界调用注册函数。它类型清楚、开销低，适合可信内置逻辑；代价是共享内存和权限，阻塞会影响主执行。

进程外事件协议

通过 stdin 传事件 JSON，stdout 返回有限控制结果，stderr 写诊断日志。它便于输出限额、超时和进程终止，也需要接口版本、退出码语义与子进程清理。

不同事件应有不同能力。例如观测事件只读取元数据，工具前事件可以拒绝调用。若允许改写参数，应重新解析、校验和授权，不能先批准旧参数再执行新参数。

包裹调用的中间件

中间件接收请求和下一层处理函数，可以修改输入、重试或观察结果。嵌套通常形成“外层前处理 → 内层前处理 → 实际调用 → 内层后处理 → 外层后处理”，顺序因而是可见语义。

它适合多项横切能力组合，代价是调用链不再直观。一个重试中间件包住工具执行，可能重复副作用；一个摘要中间件的计数若早于后续工具定义注入，也可能低估请求。需要固定顺序并检查真实输入。

扩展点 适合什么 收益 主要代价
进程内回调 可信、轻量事件逻辑 简单、低延迟 共享故障和权限
进程外 Hook 外部脚本和独立超时 接口与进程可分离 协议、清理与部署
中间件 请求转换和组合控制 复用横切能力 顺序和重试语义复杂

普通观测导出失败可以按明确策略降级；用于阻止未授权动作的控制逻辑失败时应拒绝执行。Hook 返回继续，也不能扩大上层强制授权范围。

Orchestration：决定执行者怎样分工和交接

1. 实现原理：任务、执行和汇合分别有身份

报告任务可以由主 Agent 负责整体目标，将资料检索和证据检查交给不同执行者。调度层需要知道谁拥有任务、谁在运行、结果交给谁，以及最终由谁对用户负责。

多 Agent：任务、子运行与汇合

设计方案 · 当前仍是单 Agent 基线。

角色名只影响模型看到的方法和工具，程序仍需管理身份、预算、状态与权限。Context 隔离、文件修改隔离、操作系统隔离是三个不同问题。

2. 有哪些编排方案

A. Agent 作为工具

主 Agent 提交一个边界明确的子任务，子 Agent 使用独立 Context 与受限工具，返回结构化结果，主 Agent继续负责整合和回答。

实现时定义输入快照、任务要求、返回证据和错误；同步版本可以先限制深度为一层。它适合检索、分析和独立评审，代价是额外调用与交接遗漏。子 Agent 声称完成仍需核对结果。

B. Handoff 转移交互责任

当前 Agent 把这段交互交给另一专家，后者继续与用户工作，可能不返回原 Agent。它适合专业路由和明确的责任切换。

实现需要决定转交哪些历史、当前任务和授权，下一次用户输入也要路由到正确执行者。它与“主 Agent 调用助手再继续”不同，不能只用同一个子调用接口而不定义所有权。

C. 显式 Graph 与并行汇合

程序定义分类、分支、节点与合并策略；节点可以是普通函数，也可以是 Agent。独立任务可以并行执行，汇合时核对版本并处理失败。

它适合业务阶段稳定、依赖清晰的任务。代价是状态合并、节点版本和恢复；多数投票不能自动证明答案正确，评审角色也可能共享相同盲点。

D. 持续子会话与邮箱

子 Agent 保留身份和状态，后续可接收任务、澄清和更正。消息应有发送者、接收者、序号、任务归属与是否需要唤醒模型的类型。

它适合持续沟通，代价是乱序、重复、过期消息、取消和回收。普通进度通知不应必然触发新的模型请求，否则容易产生空转和互相回复的循环。

E. 共享任务板与队列

执行者领取满足依赖的任务，持有租约，提交结果后更新状态。需要任务版本、领取原子性、超时和重新分配。

它适合大量可独立处理的任务和后台扩容，代价是调度与资源冲突。它主要解决任务分配，不自动定义内容质量或 Agent 之间如何理解对方的结果。

3. 真实实现怎样分工

OpenAI Agents SDK，官方文档。 编排与 Handoff明确区分 Manager 调用 Agent 工具和转移交互责任。可以借鉴的是先定义所有权，再选择调用形式。

Deep Agents，源码核对。 subagents.py为普通子任务构建任务输入，将结果转换为主过程的工具结果；fork 另有历史继承路径。可借鉴的是显式定义输入继承与返回投影，不把所有子 Agent 都视为全新窗口或全部共享历史。

Claude Code，官方文档。 子 Agent 说明描述独立窗口、工具范围和结果返回，普通子任务与继承父历史的 fork 不同。它说明了探索过程隔离的价值，同时也提醒子任务有自己的请求成本。

AgentScope Java，固定官方文档。 子 Agent 设计区分工作区模式、同步等待和后台任务；特定同步等待超时可以转成后台继续。可借鉴的是将“等待超时”“取消执行”和“任务失败”分别定义。目录层面的 ISOLATED 也不能自行证明操作系统访问隔离。

LangGraph，官方文档。 Graph API用状态、节点和边表达工作流，并通过 reducer 定义状态更新。可借鉴的是让合并规则进入程序，而不是只把多个模型答案拼接在一起。

4. 子任务契约怎样设计

建议输入包含目标、验收要求、资料引用与版本、允许工具和预算；输出包含发现、证据位置、产物身份、实际检查和未解决问题。不要默认复制所有父历史，也不要把没有共享的关键约束留给子 Agent 猜测。

权限由程序约束为父授权和子配置的交集；子任务不能因为拥有不同角色而扩大授权。所有调用和摘要用量计入总预算，委派开始前可以预留额度，防止并行执行者各自使用完整上限。

取消需要传播并等待执行端确认。父调用超时不等于子任务已停止，HTTP 断开也不等于后台资源已释放；结果未知时保留实际状态，不能补造失败回执。

5. 共享工作区怎样处理

只读任务可以使用同一固定快照；独立写入可按资源划分，必要时加版本检查或锁。代码修改可以用独立 Git worktree，再在汇合时合并和测试。

Worktree 隔离 Git 文件修改，不限制拥有主机权限的进程访问其他目录。最终验收应在合并后的产物上运行，而不是把各分支单独通过视为整体通过。文件冲突和语义冲突需要分别处理。

6. 外部调度与长时间等待

Cron 触发周期任务，Webhook 响应外部变化，持久工作流保存等待与后续步骤。它们管理外层任务，内部仍可运行同一 Agent Loop。

长时间等待时保存外部任务 ID、条件和截止时间，再释放 Worker；事件到达后去重、检查任务版本并唤醒。调度器还应处理重叠、并发和重试。没有变化的事件不必不断调用模型，真正的状态变化才需要进入决策。

7. 本项目的演进顺序

当前保持单 Agent。先确认一次调用或单循环无法经济地解决什么问题，再为一个子任务约定输入、预算、结果和汇合；用同一任务比较收益后再增加执行者数量。

每次只增加当前需求所需的机制，用相同任务和可观察证据检查行为。

8. 动手练习与验收

增加一个只读 review_document 子 Agent 工具，使用真实模型检查固定文档快照，返回问题、证据位置和不确定项。主 Agent 检查引用再整合，子任务不再创建子任务，也没有写权限。

分别检查输入遗漏、子任务超时、结果重复和父取消；最后对同一任务集比较单 Agent 与委派版本。只有收益和新增成本都可解释，才继续增加异步通信和共享任务调度。

术语与图例

1. 核心术语

术语描述职责与数据含义，不表示阶段 0 已定义同名 Python 类。阶段 0 使用 SDK 字典消息；阶段 1 的 Runner 使用中立的消息、ModelRequest 与 ModelResponse，工具边界使用 ToolCall、ToolResult 与 ToolExecutor。阶段 2 已实现 Policy；Session、Checkpoint 与 outcome 属于后续设计概念。

  • Agent：使用模型选择动作，并根据真实反馈继续执行的系统。
  • Harness：管理模型输入、工具、状态、权限与生命周期的运行系统。
  • Framework：用于构建系统的一组抽象和组件。
  • Agent Loop：一次 Run 中反复请求模型与执行工具的控制流。
  • 外层任务循环：反复启动、唤醒或评估 Run 的机制。
  • Graph：用节点、边与状态表达的控制流。
  • Session：连续交互的会话身份。
  • Run：处理一个用户请求的过程。
  • Step：一次模型请求与该响应提出的工具批次。
  • ToolCall：模型提出的工具名称、参数和调用 ID。
  • Invocation：后续执行账本中一个稳定逻辑动作的身份。
  • Attempt：一次实际派发尝试。
  • ToolResult：程序返回的工具执行观察。
  • Transcript：按顺序保存的完整消息与工具交互。
  • Context：某次模型请求实际可见的输入视图。
  • Memory：经选择保存、供以后复用的知识。
  • Artifact：工作区或产物库中的外部交付物。
  • Event：关键运行边界的记录。
  • Checkpoint：用于定位执行位置的状态快照。
  • Receipt：执行端保存的真实执行回执。
  • Policy：根据身份、动作、资源和授权作出决策的规则。
  • Sandbox：限制实际执行环境可访问资源的隔离机制。
  • Eval：用一组任务比较系统行为与质量的过程。

下面是本项目采用的工作定义，用于讨论职责与实现。它们不代表行业已经形成统一、互斥的分层标准。

Harness 是包围模型的运行系统，负责输入组织、动作权限、状态记录、停止条件和错误处理。Agent Loop 则是其中的一段控制流，重复执行“构建输入 → 调用模型 → 执行工具 → 接收结果”。

外层任务循环负责重复启动或唤醒 Agent，例如在 CI 失败后启动诊断。它与一个 Run 内的模型循环处在不同范围，设计调度器时需要说明触发、等待和停止分别由谁负责。

Graph 用节点、边和状态转移表达控制流。节点既可以是普通函数或人工审批，也可以运行完整 Agent Loop；一个 Graph 可以只包含一个 Agent，也可以组织多个 Agent，因此 Graph 和 Loop 可以组合使用。

Framework 提供构建系统所需的组件和抽象，同一个产品也可以同时提供 Harness。理解产品时，可以分别问它提供了哪些开发组件、哪些运行约束，而不必强行把它归入单一类别。

Anthropic 的基础模式文章区分预定义工作流与由模型动态选择动作的 Agent。本文沿用这一思路，再单独讨论运行时需要补充的权限、状态和预算约束。

2. 动作被拒绝与循环结束

动作被拒绝：Policy 返回不允许，工具不执行这次操作，Runner 收到 policy_denied 回执后交给模型。

循环结束：Runner 返回 RunResult，包含模型回答与本次工具记录。模型的回答不能代替工具实际执行的回执。
