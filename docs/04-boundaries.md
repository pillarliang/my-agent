# 04. 运行边界与故障处理

## 1. 已实现

- 一个同步 Agent Loop。每次模型响应中的工具调用按顺序执行。
- 原生函数调用适配器。模型文字不作为 Shell 命令执行。
- 严格 JSON 参数校验。拒绝多余字段、重复键和非有限数字。
- 三个有界文件工具。文件内容按字符分页。
- 默认关闭写权限。开启后只允许新建文件。
- 完整旧轮次裁剪。保留当前执行链。
- SQLite Run、消息和事件记录。
- 同一会话最多一个 `running` Run。
- 历史跨进程加载。仅自动加载正常结束的 Run。
- 可选产物文字检查。
- 真实模型运行、真实集成测试与任务评测入口。
- CLI 与 Web 共用的应用服务。
- 本地 Web 聊天、工具进度、分页历史与 SSE 事件补读。

- Skills、Hooks、MCP 和插件加载。

- 账户费用硬上限、跨会话全局资源预算。

## 3. 输入与输出限制

`--max-input-bytes` 限制内部 Context 序列化后的 UTF-8 字节数，包含工具定义和保留的模型续接材料。这个值便于实施确定的本地保护，但供应商协议开销与分词规则不同，因此它不能精确表示请求正文大小或模型 Token 数，模型窗口仍可能超限。

`--max-output-tokens` 作为单次输出额度传给模型 API，部分推理模型还会把内部推理计入额度。输出不足可能表现为 Responses 的 `incomplete`，或 Chat Completions 的 `finish_reason=length`；适配器会拒绝把这些未完成响应中的调用交给工具执行。

`--max-steps` 限制模型调用次数，每次响应最多接受 8 个工具调用。默认一次 Run 最多 8 Steps，单次输出上限为 2048 Token；输入、缓存与供应商计费也会影响成本，因此这些限制还不能构成账户级费用上限。

`RunResult` 保存接口已报告的输入与输出用量；网络失败或接口缺少字段时，`usage_complete` 会为 `false`。此时已知数值为零表示没有完整用量证据，不能据此认为没有产生费用。

## 4. 时间与取消

Runner 在关键边界检查 `--max-seconds`，并将单次模型超时设为剩余时间与 30 秒中的较小值。远程模型适配器关闭 SDK 自动重试，使一次 Step 的请求次数与错误更容易观察。

这些时间限制采用协作式检查：同步文件调用和 SDK 网络操作无法由 Runner 强制抢占，HTTP 超时也不一定是整个请求的严格挂钟截止时间。被阻塞的磁盘、持续分块返回的服务或第三方扩展仍可能拖长运行；需要强制回收时，应增加独立 Worker 和进程监督。

CLI 中的 `Ctrl+C` 会由 Runner 转换为 `cancelled`，并尝试保存当前消息；Web 关闭页面只会断开观察连接，服务退出时则等待已接受的任务结束。强制终止、断电或存储故障可能阻止最终保存，而且取消不会撤销已经创建的文件，详见 [Web 退出说明](10-web-ui.md#6-刷新断线与退出)。

## 5. 本地文件边界

工具路径必须位于指定工作区中。程序拒绝绝对路径、`..`、符号链接、一组保护目录，以及 `.env` 和 `.env.*` 文件，防止这些入口绕过正常文件范围。

名称普通的文件也可能包含秘密，而真实模型会看到实际读取的片段。因此，学习时应使用专用目录，只放入允许发送给模型的材料；路径保护只能约束访问范围，无法自动识别全部敏感内容。

路径检查与实际打开之间存在竞态，恶意并发进程可能在检查后替换目录或符号链接。这是当前实现的安全边界：它不具备操作系统沙箱能力，也不适合用于执行不可信本地扩展或向多个租户开放主机目录。

`create_file` 使用独占创建，已有文件不会被覆盖；但它还没有临时文件加原子发布协议，进程崩溃仍可能留下不完整的新文件。

## 6. 数据持久化边界

数据库默认位于 `.learn-agent/state.sqlite3`，新建数据目录权限为 `0700`，数据库权限设为 `0600`。消息保存原始输入、工具参数、结果和协议续接材料，普通事件只保存元数据；数据库没有加密或完整脱敏，文件权限之外仍需考虑备份和使用范围。

SQLite 的记录顺序不等于文件效果的事务保证。例如，文件已经写入，但进程在保存 `tool.finished` 前退出，此时缺少结果记录也不能证明文件没有创建。

## 7. 崩溃后处理

当前版本不会自动恢复 `running` Run。遇到进程崩溃时，先检查执行记录与外部效果，再释放旧运行状态：

1. 从先前终端输出取得 Run ID。
2. 执行 `uv run learn-agent inspect RUN_ID`。
3. 确认原进程已退出。
4. 检查工作区内的实际文件。
5. 执行 `uv run learn-agent abandon RUN_ID`。
6. 使用同一会话提交新请求，或创建新会话。

`abandon` 会检查记录的 PID，若该 PID 仍存在就拒绝操作。由于 PID 可能被其他进程复用，这只是本地保护；遇到无法确认的情况，可以创建新会话并保留旧记录。

放弃的 Run 不会自动进入后续历史，因此新请求应说明已经核实的外部效果。直接删除 `running` 行会丢失调查线索，也不能改变已经发生的文件动作。

## 8. 会话与返回码

每个 Session ID 绑定绝对工作区与模型标识；DashScope 标识还包含端点摘要。绑定变化会返回配置错误，已有运行中的任务会返回 `session_busy`。不同会话仍可能操作同一个工作区，本版本没有跨会话资源锁。切换到 `qwen3.8-flash` 后，应新建会话，旧绑定仍保留原值。

- 退出码 `0`：命令正常结束，且配置的检查未失败；若未配置检查，仍是 `outcome=unverified`，不能据此判定业务验收通过。
- 退出码 `1`：Run 达到限制、执行失败或验证失败。
- 退出码 `2`：参数、配置、工作区或存储入口错误。

用户主结果使用 `outcome`，工具与检查证据分别放在 `tool_evidence` 和 `verification.checks`，`answer` 单独作为模型说明。业务自动化需要检查验收结论与范围，不能将循环结束或 CLI 退出码 0 直接当成业务成功。
