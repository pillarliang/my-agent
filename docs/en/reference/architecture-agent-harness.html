Architecture Reference · Current Implementation vs. Evolution Blueprint

Current Minimal Skeleton & Future Module Blueprint

This page summarizes the project's current real call chains—from the single-file minimal loop (Stage 0) to the modular architecture (Stages 1–4)—alongside the future expansion blueprint for a complete Agent Harness.

1. Stage 0: Single-File Minimal Agent Loop

  • Source location: examples/00_plain_loop.py.
  • Call chain: run_agent directly assembles messages and tool definitions and calls the model SDK → upon receiving tool calls, dispatches to read_file via execute_tool → appends the real file receipt back to the message list for the next turn until the model replies with plain text (see Stage 0 for details).

2. Stages 1–2: Modular Tools & Policy Authorization Chain

  • Wiring relationship: The application layer injects the workspace directory and Policy when creating ToolRegistry, while Runner depends only on the abstract ToolExecutor interface.
  • Execution & interception: The registry uniformly validates arguments, classifies the operation type (such as read-only, file creation, or file overwrite), and queries Policy.evaluate(); only after approval does it invoke the underlying file function, converting denials or expected failures into a structured ToolResult returned to the model (see Stage 1 and Stage 2).

3. Stage 3: Session Record Persistence & Multi-Turn History Continuation

  • State flow: Before each run, Runner loads completed historical messages for the same session from local JSONL session storage, appends the current user question before entering the loop, and persists new requests, model responses, tool receipts, and terminal status in order (see Stage 3).

4. Stage 4: Select Context Before Every Request

run_agent() calls select_context() before every model.invoke(). It omits the oldest optional turns when needed, protects required history and current messages, and preserves full JSONL records. Required-content overflow records a failure and stops. See Stage 4 for configuration and source.

5. Complete Agent Harness Reference Blueprint (Future Evolution)

Future Evolution Blueprint (not yet fully implemented): On top of the current core skeleton, Stage 4 implements budgets and trimming through select_context(). Persistent state recovery and a result checker (Checker) remain optional future work. Multiple nodes labeled Runner in the diagram represent different phases within the same loop rather than separate microservices.

For detailed module boundaries and jump links, see the Module Responsibility Panorama.
