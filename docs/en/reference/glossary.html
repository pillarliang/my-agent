Glossary & Legend

1. Core Glossary

The terms below define consistent system responsibilities and data boundaries across the tutorial (code does not need a identically named class for every term; for granularity differences across open-source projects, see the Session / Turn / Step Source Comparison Table):

  • Agent: A system that uses a model to dynamically choose actions and continues execution based on real feedback from tools.
  • Harness: The runtime system surrounding the model, responsible for managing model input, tool execution, state persistence, permission interception, and stopping conditions.
  • Framework: A set of developer components and abstract interfaces used to build Agent systems.
  • Agent Loop: The core control flow inside a single Run that repeatedly executes "build input → request model → execute tools → receive receipts".
  • Outer Task Loop: The scheduling mechanism outside a Run responsible for timer-based launches, event-driven wakeups, or evaluation triggers.
  • Graph: A workflow control structure expressed with explicit nodes, conditional edges, and state transition functions (an individual node can also run an Agent Loop inside).
  • Session: A container that groups continuous tasks across a multi-turn conversation; in this project, one Session is bound to one workspace directory.
  • Run: The complete execution process from receiving a user task until the loop terminates (by producing an answer or stopping due to limits or errors).
  • Step: A single model request together with all tool calls and returned receipts executed from that response.
  • ToolCall: The tool name, argument dictionary, and unique call ID emitted by the model to request a tool invocation.
  • Invocation: A logical tool call with domain meaning; identified by a stable ID during crash recovery or retries so the same logical action is not re-executed as a brand-new action.
  • Attempt: A single concrete execution attempt for a logical Invocation (if retries occur, one Invocation maps to multiple Attempts).
  • ToolResult (Tool Receipt): The real output, status code, or error message returned after tool execution, carrying the corresponding ToolCall ID.
  • Transcript: The complete set of raw messages and tool interactions persisted in chronological order.
  • Context (Current Model Input): The system instructions, historical messages, reference materials, and tool definitions actually sent to the model after filtering and assembly before a single model call.
  • Continuation data: Protocol-level data that a model service requires to be echoed back verbatim in subsequent requests (such as reasoning items or encrypted state), parsed by the adapter and stored/passed by the Runner.
  • Projection: A specialized view derived from the raw record (Transcript)—such as the Context view sent to the model or a session summary for a frontend—generated without mutating the raw record.
  • Idempotency: The property that repeating a request for the same logical operation does not produce duplicate side effects (for example, retrying report creation returns the initially created report instead of generating two files).
  • Memory: Curated, stable facts and user preferences retained for reuse across sessions.
  • Artifact: Concrete data entities generated or read during task execution, such as files, reports, or long logs.
  • Event: A structured record of a key execution milestone (such as initiating a model request, receiving a tool receipt, or finishing a run).
  • Checkpoint: A state snapshot saved at a well-defined execution boundary so an interrupted task can safely resume from the last confirmed step.
  • Receipt: The real operation result persisted on the execution side, used during recovery to verify whether an external action has already taken effect.
  • Policy: The rule component that evaluates whether an action is "allowed" or "denied" before execution based on operation type, target resource, and configuration.
  • Sandbox: An OS- or container-level isolation mechanism that restricts which filesystem paths, networks, and system resources a process can access.
  • Eval (Evaluation): The process of quantitatively comparing system behavior and artifact quality using a fixed task suite, initial snapshots, and verification criteria.

Commonly Confused Concepts (cf. Anthropic: Building Effective Agents):

  • Harness vs. Agent Loop: The Agent Loop is the inner "request model ↔ execute tools" control flow; the Harness is the complete runtime foundation surrounding the Loop (covering Context budgets, Policy permissions, State records, and crash recovery).
  • Graph vs. Agent Loop: The two are not mutually exclusive. A Graph defines deterministic stage transitions, while any node inside a Graph can run an autonomous Agent Loop.

2. Core State Distinction: Action Denied vs. Loop Terminated

  • Action denied (policy_denied): Policy determines that the operation is not permitted, so the underlying tool never runs at all; the Runner passes the denial receipt back to the model, letting the model decide how to explain the constraint to the user or adjust its plan.
  • Loop terminated (RunResult): The Runner stops looping and returns a RunResult containing the model's final text and the list of tool receipts from the run; note that the model verbally claiming "done" is never a substitute for a real, successful tool receipt.

3. Guide to Reading Architecture & Sequence Diagrams

  • Solid vs. dashed lines: In flowcharts, solid lines indicate primary calls or data flow, while dashed lines indicate optional extensions or policy constraints; in sequence diagrams, solid lines indicate outgoing calls or writes, while dashed lines indicate returned results.
  • Dependency direction vs. call order: Arrows in module dependency diagrams show "who depends on whose interface" and do not directly represent runtime execution order.
  • Distinguishing "currently implemented" from "future blueprint": Every diagram explicitly labels in its title or caption whether it depicts the "Stages 0–3 implemented flow" or a "future extension blueprint", so you can verify against the source code at any time.
