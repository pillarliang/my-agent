Stage 3: Sessions & Records

1. Starting Point: How Can the Program Remember Past Conversations?

By default, both model APIs and single-run CLI invocations are stateless. Consider this scenario:

  • User: "In this conversation, please call me Star."
  • Model: "Got it, Star."
  • (Exit the program and run it again)
  • User: "What did I just ask you to call me?"

If only the last sentence is sent to the model, the model has no prior context and no way of knowing what was said earlier.

To solve this problem, the system must satisfy two core requirements:

  1. Provide context to the model: Automatically include prior history messages when asking follow-up questions in the same session.
  2. Let users inspect history: Allow users to look up past conversations even after exiting and restarting the program.

Therefore, the program cannot act merely as a stateless pass-through—it must also persist conversation records and load them by session when needed.

Expected Outcomes:

  • Persistent records: After exiting and reopening the program, previous Q&A records can still be queried.
  • Automatic context continuation: When asking a follow-up question in the same session, the program automatically passes prior messages to the model.
  • Isolated sessions: Creating a new session never mixes in history messages from other sessions.
  • Zero-compute queries: Viewing history reads directly from local storage without calling the model or executing tools.

2. What Conversation Data Needs to Be Saved?

To reconstruct a conversation faithfully, we cannot save only the user's questions (otherwise we lose what the assistant answered) or only the final answer (otherwise we lose the initial constraints). At minimum, we must save the following in order:

  • User input (TextMessage): Records the raw text and role of each user prompt.
  • Full model response (ModelResponse): Contains not just the answer text, but also tool call requests, stop reasons, token usage, and protocol continuation data—it cannot be flattened into a plain text string.
  • Strict ordering: Saying "Call me Star" followed by "Call me River instead" means the opposite if reversed. Timestamps are for reference only; an incrementing sequence number is required to guarantee deterministic ordering.

What Else Must Be Saved When Tool Calls Are Involved?

When a conversation triggers tool calls, the interaction becomes multi-step:

  • User: "What files are in the current workspace?"
  • Model: Issues a list_files tool call (including tool name, arguments, and call_id).
  • (The tool runs locally and returns the actual file list or failure reason.)
  • Model: Produces the final answer based on the tool result.

To verify both "what the model intended to do" and "what the tool actually executed," we must also save the verbatim tool result (ToolResult) and correlate it with the corresponding tool call via call_id. Permission denials and execution errors are real outcomes that must be recorded as-is; a model's verbal claim of "done" can never substitute for an actual tool result. For exact data structures, see the model contracts and tool contracts.

3. How to Group Multiple Prompts and Tell Whether a Task Finished?

A flat list of messages is not enough; the system needs two boundary levels to organize records:

  • Session — Isolate distinct conversations: Mixing all questions into a single history causes old topics to pollute new ones. Assigning a unique identifier (session_id) to each continuous conversation lets follow-up prompts append to and read from the same record, while a new session starts from a blank history.
  • Turn — Mark the start and completion status of a single user task: Consider what happens if the program crashes mid-run after writing the user question to disk but before the model replies. On the next run, we must not mistake a few partial records in the file for a completed task. We therefore define the lifecycle from receiving a user prompt to producing a final answer (or stopping on error) as one Turn.

Each Turn explicitly records its start and finish status:

  • completed: The message and tool-call chain for this prompt closed normally (note: if a tool call is denied by Policy and the model reports that denial to the user in a final answer, the conversation turn itself is still complete and recorded as completed).
  • failed: An exception occurred mid-execution and aborted the turn.
  • Unfinished (has start record, no finish record): The process was interrupted mid-turn; the partial records remain on disk for inspection but are excluded from subsequent model context.

Current choice in this project: Session + user-task Turn + ordered records. This structure directly satisfies conversation isolation, message grouping, and unfinished-task detection without introducing extra Run, Step, or separate event tables.

Do other Agents use the same naming?

Not necessarily. In pi, a turn is closer to a single assistant response plus its tool results, whereas in Codex a turn is closer to a single user task. This project adopts the latter granularity. The terminology comparison across pinned source versions explains the differences; identical names do not imply identical data scopes.

4. Persistence Format: Why One JSONL File per Session?

In-memory data disappears when the process exits, so records must be written to persistent storage. This project currently maps each session to a single JSONL file (default path: .learn-agent/sessions/<session_id>.jsonl), with one JSON object per line and new records appended to the end of the file. Compared with introducing a database upfront, plain-text JSONL requires zero external dependencies and can be opened directly to inspect ordering and payloads; we can evolve to SQLite later if massive session filtering or concurrent writes become necessary.

Record Structure Inside a JSONL File

  • First-line file header (SessionHeader): Records the format version, session_id, bound workspace directory, and creation timestamp. Binding the workspace prevents accidentally resuming a session against a different directory.
  • Subsequent ordered entries (Record): Each line fixes its order via an incrementing seq, marks its owning task via turn_id, records time, and distinguishes three entry types via type:
    • turn_started: Marks the start of a user prompt.
    • message: Uses kind (user / assistant / tool_result) and value inside payload to store the full message or tool result.
    • turn_finished: Records the task completion status (completed / failed) and any failure reason.
Example of a wrapped user message entry
{
  "seq": 2,
  "turn_id": "T1",
  "type": "message",
  "time": "2026-10-25T01:00:00Z",
  "payload": {
    "kind": "user",
    "value": {"role": "user", "content": "这段对话里，请叫我星河。"}
  }
}

T1 is a shorthand label for readability; actual turn IDs are generated by the program. The session ID lives in the first-line header rather than being repeated on every line.

The system prompt, model connection, tool registry, and Policy belong to the initialization config of the current run; they are assembled dynamically on each model request and are not duplicated inside user history messages.

5. Write Timing & Exception Handling

If the program waited until the final answer to save everything at once, any mid-run error would lose the interactions that already occurred. Instead, the program appends and flushes records incrementally as execution progresses:

  1. On turn start: Immediately writes turn_started and the user input message.
  2. On model return: Writes the full ModelResponse to disk first, then checks the stop reason (even if refusal or truncation occurs, the raw response is preserved for debugging, though its tool calls will not be executed).
  3. After tool execution: Writes the actual ToolResult to disk.
  4. On turn finish: Writes completed on normal completion; if an exception is caught, writes failed along with the error message and re-raises the original exception.

Reliability and boundary constraints:

  • Single-writer exclusive lock: Each session file uses a file lock so only one writer can append at a time, preventing interleaved sequence numbers across processes.
  • Fail fast on corruption: If reading encounters an unknown format version, a gap in sequence numbers, or a truncated trailing line, it raises an explicit error rather than silently falling back to empty history.
  • Non-transactional boundary: If the process is killed abruptly (e.g., SIGKILL), it may not write a finish entry, leaving that Turn in an "unfinished" state; local file operations and log appends are also not in a single transaction, so extreme events like power loss require verifying external state during recovery.

6. Read Paths: Supporting History Queries & Multi-Turn Continuation

The saved JSONL files serve two distinct read paths:

  • History inspection for users: Listing sessions only reads the first-line header and modification time of each file without loading all messages; viewing a single session validates the version and sequence numbers and returns all records verbatim (including failed and unfinished turns) without calling the model or re-executing tools.
  • Context continuation for the model: Filters for turns in order whose status is completed and whose message chains are intact, reconstructing the message list accepted by the model. Failed or unfinished turns remain on disk for human debugging but are never mixed into subsequent model inputs; if a turn is marked completed yet lacks a paired tool result or final answer, the reader immediately reports file corruption.

Full Walkthrough: A Two-Turn Conversation ("Call Me Star")

  1. Turn 1 prompt (create session S1, start turn T1):
    • Input sent to model: [System prompt, User: "In this conversation, please call me Star."]
    • Appended to file: T1 started → User message → Assistant response → T1 completed.
  2. Exit, reopen, and ask a follow-up (specify session S1, start turn T2):
    • (System action: Locate file S1, validate version and workspace, extract messages from completed turn T1.)
    • Input sent to model: [System prompt, Turn 1 question, Turn 1 answer, Follow-up: "What did I just ask you to call me?"] (4 input items in total).
  3. Receive Turn 2 answer and finish:
    • Appended to file: T2 started → Follow-up question → Assistant Turn 2 answer → T2 completed (the history from T1 is only read when requesting the model and is never written a second time to the file).

After both turns finish, the session file contains 1 header line and 8 records (4 of which are message records). Querying session details displays all 8 records, whereas the second model request receives the 4 filtered and reconstructed context items—the on-disk record format, the query display view, and the model request input each serve their own role; you cannot dump raw file lines straight into the model.

Likewise, loading historical tool results simply places past observations back into the context without re-running tools; if the user asks about the current directory state again, the model will issue a new tool call. When history messages accumulate and approach the context window limit, we move to Stage 4: Context Management & Budgets.

7. Source Implementation: Connecting SessionLog to the Agent Loop

Session persistence, querying, and history reconstruction are encapsulated in session.py; the Loop stays focused on driving the current task and calls session methods at key lifecycle points.

Tracing a Call Against the Source Code

  1. Entry dispatch (main()): Separates queries from execution. For query flags, it calls read_session() or list_sessions() directly, prints the output, and returns; for task execution, it creates or opens the specified SessionLog and passes the workspace and Policy.
  2. Environment verification (run_task()): Verifies that the workspace bound to the session matches the current configuration, creates ToolRegistry and LLMService, calls run_agent(), and closes the model connection on exit.
  3. Load history & start turn (run_agent()): Calls session.history_turns() first to retrieve completed history blocks, then start_turn() to record the new task and prompt without loading it twice. history() still provides flattened messages; see Stage 4 for request-time budget selection.
  4. Record model responses & tool results: Each time model.invoke() returns, calls append_message() to save the full response first; if tools need to run, executes them through tools.execute() (validation, authorization, execution) and calls append_message() to save the actual tool result.
  5. Record turn conclusion (SessionLog): Once a valid final answer is obtained, calls finish_turn() to verify message-chain closure, write completed, and update the in-memory completed history; if an exception is raised mid-turn, writes failed with the reason and re-raises the exception.

When reading the source code, start with the SessionHeader / Record data structures, then read the write logic in start_turn(), append_message(), and finish_turn(), and finally see how _history() filters and reconstructs completed turns. The Session / State Module Guide compares these trade-offs against the pi and Codex codebases.

8. Running & Verification

Run the following commands from the project root (the first two call a real model and consume API tokens; configure environment variables as described in README):

uv run python -m learn_agent "这段对话里，请叫我星河。"
uv run python -m learn_agent --session <session_id_from_first_command> "我刚才让你怎么称呼我？"

Then run the local read-only query commands (no model requests, no tool execution, and no API key required):

uv run python -m learn_agent --list-sessions
uv run python -m learn_agent --show-session <same_session_id>

Run the local automated tests (using fixed local protocol responses and temporary files without calling an external model):

uv run pytest tests/test_session.py
uv run python scripts/check_docs.py

Expected Outcomes

  • Round-trip record fidelity: After writing a Q&A turn, finishing normally, and closing and reopening the session, the loaded message fields match the original content exactly.
  • Follow-up prompts include history automatically: On the second prompt in the same session, the request sent to the model contains [system, user, assistant, user] in order; creating a new session starts from an empty history without cross-contamination (see test_session.py).
  • Side-effect-free queries: Running --list-sessions and --show-session creates no model connections, calls no tools, and adds no lines to the session file.
  • Intact tool call chains: Conversations involving tool calls preserve the model's tool call requests, call_id, actual tool results, and final answer; continuing a session reuses those recorded observations without re-running old tools.
  • Clear failure and corruption boundaries: Model errors, policy denials, and unfinished turns remain queryable on disk, but failed or unfinished turns are never mixed into subsequent model context; unknown format versions, sequence gaps, or truncated lines fail fast with an explicit error.
