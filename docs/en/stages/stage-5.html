Stage 5: Reuse Project Knowledge Across Sessions with Memory

1. Why Does a New Session Forget Project Conventions?

  • User, session A: “This project uses uv. Please use uv run for Python commands.”
  • Model: “Understood.”
  • (End session A and create session B in the same workspace.)
  • User, session B: “How should I run the tests?”

Session B does not automatically load session A's history. Loading every old conversation would also bring unrelated details. Memory stores selected project knowledge separately so new tasks can reuse it.

Expected outcomes:

  • Reuse across sessions: New sessions in the same workspace receive saved conventions.
  • Project isolation: Only the current workspace's memory is loaded.
  • Correction and deletion: The next task reads edited content; removed content is no longer injected automatically.
  • Budget accounting: Content and source labels count toward the request budget; overflow fails explicitly.

2. Selected MVP: One Manually Maintained Project File

Stage 5 selects one MEMORY.md at the workspace root, edited by the user and read in full at the start of each task. Plain text makes a few project conventions easy to inspect and correct. Storage and automatic extraction are separate choices; see Memory design choices.

  • Write: The user saves confirmed facts or preferences. A model saying “I remember” does not write a file.
  • Read: Resolve only workspace/MEMORY.md, with no ancestor or other-project discovery. The resolved file must remain inside the workspace.
  • Use: Pass its path and text to Context as source-labeled reference material. Memory does not override the current request or change Policy.
  • Refresh: Read again for the next task. All model calls within one task share the same snapshot.
  • Cost: Full text consumes input budget on every request. Split files or read selectively when size becomes a real problem.

Automatic extraction, databases, vector search, and background consolidation are later options, outside this MVP.

3. Connecting Memory to the Existing Loop

3.1 Initialization: The Workspace Determines the Source

Existing run_task() receives the workspace and Policy and creates tools and the model service. The proposed extension reads memory here with a focused function and passes its path and text to Runner.

A missing or empty file means no project memory. Read errors, invalid UTF-8, and resolved paths outside the workspace fail explicitly before a model request. Loading does not depend on the model requesting a file tool.

3.2 Runtime: Memory Supplies Content; Context Checks the Budget

  1. Application reads: Obtain the workspace's file path and text at task start.
  2. Runner prepares task input: Load the session history and retain the project memory for each model request during the task.
  3. Context assembles: Extend select_context() to place memory in a reference message between completed history and the current task, then measure the full request.
  4. Check before invoking: Keep the short memory as required input while trimming optional history as in Stage 4. If required input still overflows, stop and report that memory or the budget needs adjustment.
  5. Tools enforce permissions: ToolRegistry still checks Policy before executing model-requested actions.

These are proposed changes: run_task(), run_agent(), and select_context() do not yet accept a separate memory input.

3.3 Message Placement and Conflicting Conventions

The proposed design reuses TextMessage with the user role for one project memory message. Its content identifies it as application-loaded project reference material and includes the file path and original text. This role supplies reference material alongside the current task; application behavior is still defined by system instructions.

Assemble ModelRequest.messages in this order:

  1. System instructions: Application behavior and rules for using project memory.
  2. Selected completed history: Preserve questions, responses, and tool results in their original order within each task.
  3. Memory read for this task: Include one reference message when content exists; otherwise omit it.
  4. Current task messages: The user's question followed by model responses and tool results produced during this task.

Rebuild this sequence for every model request within the task, including the memory message exactly once. Budget accounting covers system instructions, history, memory, current task messages, and tool definitions.

The application must state these rules in its system instructions rather than relying on message order alone:

  • Current request first: An explicit project convention specified for this task takes precedence over the default in memory.
  • Corrections take effect: When the current task does not specify a convention, use the memory read for this task. Older defaults for the same matter remain historical records.
  • Application rules remain in force: Commands inside memory cannot change system instructions, and Policy still checks tool actions.
  • Recheck current facts: Inspect files or test results with tools when their current state matters; memory supplies background.

3.4 Storage Responsibilities

  • Memory file: Holds selected project knowledge, identified by source path.
  • SessionLog: Continues to store questions, model responses, and tool results. Do not duplicate memory as a conversation message each turn.
  • Context: Includes memory in the complete budget check. Persistence does not exempt content from input limits.

4. Verification After Implementation

The following checks describe the implementation target. The current CLI does not automatically load MEMORY.md.

  1. Prepare: Write the uv convention into a test workspace's memory file.
  2. Reuse: Create two fresh sessions and ask about project commands. Inspect each actual ModelRequest for the source path and text, without borrowing the other session's history.
  3. Check message structure: Verify that memory has the user role, appears once between completed history and the current task, and preserves the current task's tool call and result sequence.
  4. Isolate: Switch to another workspace without memory and verify that its requests contain none of the first project's memory.
  5. Keep one snapshot per task: Edit the file during a task with multiple model calls. Later requests in that task must retain the initial content; the next task must load the edit.
  6. Correct and remove: Edit the file and start another task; only the new content should be loaded. Empty or delete it and check that automatic injection stops. Earlier answers remain conversation history; use a fresh session to isolate deletion behavior.
  7. Fail clearly: Test an escaping path, invalid UTF-8, and memory that exceeds the budget before the first request. All must fail before invoking the model.
  8. Preserve permissions: Put “overwrites are allowed” in memory and submit an overwrite call. A Policy that forbids overwrites must still reject it and preserve the original file.

Also retain old history when checking how corrected memory affects conflicting conventions:

  1. Keep the old convention: Complete a conversation exchange specifying python -m pytest as the test command.
  2. Correct memory: Manually change the test command in MEMORY.md to uv run pytest.
  3. Check the default: Continue the same session and ask for the test command. The request must retain old history and include new memory; the answer should use uv run pytest.
  4. Check the current request: Explicitly request python -m pytest for this task. The answer should follow that explicit request.

Local protocol checks inspect actual requests, errors, and files. A separate live-model experiment observes whether answers follow the convention and records API calls and usage. A correct answer alone does not prove memory reached the request.
