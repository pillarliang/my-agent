Stage 4: Context Management & Budgets

1. Starting Point: As History and Tool Results Grow, Should We Send Everything on Every Request?

After Stage 3, the program can load history across turns and call tools repeatedly within a single turn. However, as an interaction deepens, input volume expands rapidly in two places:

  • User (Turn T1): "Write an event announcement in Chinese, using UTC for all times."
  • Model: Produces a first draft.
  • (Intermediate turns T2 and T3 repeatedly tweak the title and tone, generating several obsolete drafts.)
  • User (Current Turn T4): "Refer to the past notes in the workspace, keep the earlier time rule, and condense the announcement into two sentences."
  • (Step 1 of the current turn: the model calls read_file, the tool returns a large text result, and the program prepares to send Step 2 to the model.)

When assembling the next model request, the program faces a dilemma:

  1. If it sends only the latest prompt: The model neither knows the "UTC time rule" established in Turn 1 nor receives the file content just read or the draft to revise.
  2. If it blindly concatenates all history and tool results: Obsolete drafts and bulky tool outputs repeatedly consume the model's context window, increasing latency and cost or triggering a context-window overflow error outright.

"How much history is saved on disk" and "how much content is sent in this request" are two separate questions. The core task of this stage is: before every model call, select the context required for the current step within the input budget, and clearly record which task blocks were kept or omitted.

Expected Outcomes:

  • Pass through unchanged when within budget: When total candidate input volume does not exceed the budget, retain all available history and current messages intact.
  • Trim whole turns when over budget: When input exceeds the budget, retain explicitly pinned required history (such as T1) and current-turn messages, and omit optional history starting from the oldest whole Turn—never slicing a tool call apart from its result.
  • Fail fast when required content alone exceeds the budget: If omitting all optional history still leaves the system prompt, required history, and current-turn content over budget, stop with an explicit error before calling the model rather than silently truncating required content.
  • Re-evaluate dynamically at every step inside the loop: After a tool returns a large result mid-turn, re-measure and re-select before the next model request; trimming only builds a view for the current request while leaving on-disk and in-memory records intact.

2. What Context Data Does a Single Model Request Contain?

All inputs submitted to a single model.invoke() call make up the current request context. Against the existing ModelRequest contract, it consists of four parts:

  • System prompt (SYSTEM): Application-configured global behavior rules (TextMessage("system", ...)).
  • Candidate history turns (Candidate History): The sequence of previously completed user turns. They can come from Stage 3's SessionLog or be passed directly in memory when file persistence is disabled—persistent storage is not a prerequisite for context budget management.
  • Current turn messages (Current Turn Messages): The current user prompt, plus any ModelResponse and real ToolResult items already produced during the current turn's loop.
  • Tool definitions & protocol continuation data: Even if the model does not call a tool on the current step, available tool schemas (request.tools) are sent with the request and occupy the context window; native continuation fields (ProviderContinuation) in historical responses also participate in protocol encoding.

When selecting and assembling context, every item must preserve its original role and trust boundary: an early user requirement for UTC remains a user message, and file content returned by a tool remains a ToolResult. Marking a historical turn as "required" must never promote it to a system prompt, nor can a previously approved write in history bypass the current Policy check.

3. How to Measure Input Volume and Calculate the Budget?

"Keep only the last 5 turns" cannot reliably control request size—a casual chat turn might take a dozen tokens, whereas a file-reading turn might take tens of thousands. To know whether the context fits, we need an explicit measurement basis and budget formula:

  • Measure the complete protocol-encoded request: Models process inputs in tokens. The measurement function must cover encoded message structures, role markers, tool call arguments, tool schemas (ToolSpec), and protocol continuation data, matching what OpenAIChatModel actually sends to the SDK rather than simply summing raw text character counts.
  • Deduct output reservation and safety margin: When input and output share the same model context window, the available input budget is:

    input_budget = context_window - max_output_tokens - safety_margin

    If the application or provider also specifies a separate input cap (max_input_tokens), take the smaller of the two. If measurement fails or the resulting budget is non-positive, stop with an error immediately rather than treating unknown size as 0.

Current measurement: estimate_input_tokens() shares encode_input() with the SDK adapter and counts UTF-8 bytes of the input JSON, including messages, tools, and tool control fields. This is a conservative estimate, not an exact provider token count or a guarantee against server-side overflow. The safety margin allows for template overhead and estimation error. Defaults are a configured window allowance of 32768, output reservation of 512, and margin of 1024, leaving 31232 input units. Set the window allowance for your actual model; it is not automatically detected. A model-specific InputMeter can replace the estimator.

4. Separating "Required Content" from "Removable Blocks" Before Trimming

Returning to the event announcement example: the "Chinese, UTC time" rule from Turn 1 (T1) matters more than the discarded title drafts from Turns 2 and 3 (T2, T3). "Most recent" is only a default ordering, not a synonym for "most important." Before introducing model-driven summarization, the first version divides candidate inputs into three categories:

  • Fixed required content for the current turn (Required Current): The system prompt SYSTEM, tool definitions tools, the current user prompt, and any ModelResponse and ToolResult items already produced in the current Turn (because the current turn is still in progress, its internal steps are never partially trimmed).
  • Explicitly pinned required history (Pinned / Required Turns): Completed historical turns explicitly designated by the caller via turn_id as mandatory to retain (for instance, pinning T1 containing the active UTC rule).
  • Removable history grouped by whole Turn (Optional Turns): All remaining completed historical turns.
    • Why use a completed whole Turn as the minimum trimming unit? If a model response issues two tool calls (call_1, call_2) and receives two tool results, slicing by raw message count breaks call_id pairing and causes protocol errors. In Stage 3, every completed Turn is already verified for closure ("user prompt → tool call & result chain → final answer"), so retaining or omitting an entire Turn never orphans a tool call or tool result.

5. First-Version Trimming Strategy: Omit Oldest Optional Turns as Whole Blocks

Stage 4 MVP choice in this project: deterministic whole-Turn trimming. The rule is: when within the input budget, retain all candidate content unchanged; when over budget, lock required content and omit optional turns starting from the oldest Turn, re-measuring the full candidate request after each removal until it fits the budget. Retained turns and messages strictly preserve their original chronological order.

Verifying the Trimming Process with Hand-Calculable Numbers

Suppose a unit test injects a hand-calculable measurement function with an input budget of 30 and the following candidate items:

  • Candidate items & sizes: Fixed required content (system prompt + tool definitions + current prompt) takes 8; explicitly pinned required turn T1 (with the UTC rule) takes 4; optional older turn T2 takes 12, and T3 takes 7.
  • Step 1 (initial full measurement): Total candidate volume is 8 + 4 + 12 + 7 = 31, exceeding the budget (30) by 1 unit.
  • Step 2 (skip required blocks, remove oldest optional block): T1 is pinned required history and is skipped; remove the oldest optional turn T2 (size 12). Even though we are over by only 1 unit, we never slice half the messages or tool results inside T2 just to pack the budget to 30.
  • Step 3 (re-measure full request and return): Re-measure the remaining sequence [SYSTEM, T1, T3, current prompt], yielding a total volume of 19 ≤ 30, which fits the budget. Return the selected message sequence along with a selection manifest (budget=30, used=19, kept=["T1", "T3"], dropped=["T2"]).

When connected to real protocol token counting, the selector likewise re-invokes the measurement function on the full candidate request after removing each optional Turn, rather than assuming individual block sizes always add up linearly.

6. Per-Step Re-Evaluation in the Loop, Overflow Blocking & Selection Manifest

When integrating context selection into the Runner loop, we must account for dynamic growth across multi-step tool calls within a single turn. Consider a turn T4 that calls a tool (budget still 30):

  • (Before Step 1 model request): The candidate sequence is [SYSTEM, T1(required,4), T3(optional,7), T4 prompt(8)], measuring 19 ≤ 30, so the first model request is sent normally.
  • Model (Step 1 response): Issues a read_file tool call.
  • (Tool executes and flushes to disk): read_file returns the file content result, which is appended to SessionLog.
  • (Re-evaluate before Step 2 model request): The fixed required content for the current turn now includes the Step 1 model response and tool result:
    • Case A (fits after omitting optional blocks): If the new response and result take 6, total volume becomes 19 + 6 = 25 ≤ 30 and passes directly; if they take 15, total volume becomes 34 > 30, so the selector omits the remaining optional turn T3 (saving 7), re-measures 27 ≤ 30, and sends the second model request.
    • Case B (required content alone exceeds budget; block immediately): If the tool result takes 20, even after omitting all optional history (T2, T3), [SYSTEM, T1, T4 prompt, Step 1 response & result] already reaches 32 > 30. The Context Manager refuses to truncate the current turn or required history and immediately returns a budget-overflow error before making the Step 2 model request (reporting required size 32, budget limit 30, and measurement basis); Runner marks the current Turn as failed and stops the loop.

Why return a "selection manifest" without mutating original records?

  • Clear evidence for debugging: Every context build returns the budget limit, kept turn_id list, dropped turn_id list, and final measured size. If a model answer misses a requirement, developers can check the manifest to immediately tell whether that turn was trimmed due to budget limits or was sent to the model and ignored.
  • Original history remains intact: Trimming always returns a new message tuple to construct the current ModelRequest, never mutating in-memory history lists or JSONL records in SessionLog.
When Should Offloading, Summarization, or Retrieval Be Added?
  • A tool result is too large: Store the full result separately and return a preview and reading location.
  • Early requirements keep getting trimmed: Maintain task requirements or summarize older turns.
  • Too much reference material: Retrieve relevant passages before assembling input.

Choose these techniques in Stage 6 when real bottlenecks justify them; see Context design choices. For cross-session project knowledge, see Stage 5: Memory.

7. Initialization, Runtime Flow & Source

Initialization

  • Budget: The CLI accepts window, output reservation, safety margin, optional input cap, and --pin-turn. ContextBudget validates the values at construction. run_task() passes them to Runner and closes the model connection afterward.
  • History: SessionLog.history_turns() returns completed HistoryTurn blocks with IDs. history() still returns flattened messages. Without persistent storage, pass in-memory blocks through run_agent(history=...). Both sources validate complete user/tool/answer chains.
  • Required turns: required_turn_ids pins completed historical turns. Unknown or incomplete IDs fail explicitly. CLI pins apply to the current invocation and must be specified again on subsequent runs.

Runtime flow

  1. Load history: run_agent() loads completed blocks before starting the new turn and accumulates current messages separately.
  2. Select: select_context() receives system instructions, history blocks, required IDs, current messages, tools, budget, and meter. It removes the oldest optional turn and remeasures the complete candidate request until it fits.
  3. Invoke: Runner prints the decision and passes ContextSelection.request to model.invoke(). Its output cap matches the configured reservation.
  4. Continue: Responses and tool receipts are appended in full to the current turn and session file. The next model request repeats selection with these new messages.
  5. Finish or fail: RunResult.context_decisions returns per-step decisions. Required-content overflow raises ContextOverflowError with a decision describing size, budget, unit, and kept/dropped IDs. Runner records a failed turn and propagates the error. Measurement failures also stop before any request.

Successful selection decisions are printed and returned, rather than inserted into conversation history. Overflow details are saved in the failed turn's error message.

8. Running & Verification

Local checks use temporary files and a local HTTP server without external model calls:

uv run pytest tests/test_context.py tests/test_session.py tests/test_models.py
uv run python scripts/check_docs.py

Context tests verify:

  • Whole turns: Inputs at or below budget remain intact. Optional turns are removed oldest first while pinned history and message roles remain unchanged.
  • Overflow: Oversized required content causes zero model requests. Large tool receipts can stop the next request while preserving the action's full record.
  • Protocol: Multiple calls, failure receipts, and continuation fields stay together. SDK input matches measured input, including tools, and the output cap matches its reservation.
  • Preservation: Existing JSONL bytes remain an unchanged prefix. Dropped history remains available after reopening the session.

Continue with a real model

  1. Save a requirement: Run the first command and note its session and turn IDs.
  2. Add drafts: Continue in that session to grow optional history.
  3. Pin and continue: Pin the first turn, then inspect budget, used, unit, kept, and dropped.
uv run python -m learn_agent "Write an event notice in Chinese. Express all times in UTC."
uv run python -m learn_agent --session SESSION_ID "Suggest several alternative titles and drafts."
uv run python -m learn_agent --session SESSION_ID --pin-turn TURN_ID --max-input-tokens 6000 "Keep the time rule and shorten the notice to two sentences."
uv run python -m learn_agent --show-session SESSION_ID

Replace the IDs with actual values. The 6000-unit cap is for observing trimming; whether history is dropped depends on its length. Configure --context-window, --max-output-tokens, and --safety-margin as appropriate. Required overflow fails explicitly.

Task commands consume real API usage, with at most four model requests per task by default. History queries are local. Automated tests verify program behavior and protocol; real-model adherence to Chinese, UTC, and two-sentence requirements must be checked separately.
