Stage 7: Resume Safely After Interruption

When a process is unexpectedly interrupted mid-task, "asking a new follow-up question in the session" and "resuming an unfinished task from its interruption point" are two very different things. This stage focuses on resuming interrupted tasks safely without causing duplicate side effects.

1. Starting Point: Why Saving History Alone Does Not Guarantee Safe Resumption

Consider an interruption that occurs in the middle of a tool call:

  • Model: Requests a call to write_file or an external creation API.
  • (The program has already sent the request or written the file, but crashes before appending the tool result to the log.)

At this point, the log contains only "the model requested the call" with no result. If the program blindly replays that call on restart, it will modify the file twice or create a duplicate external order. Therefore, we must distinguish two kinds of data:

  • Checkpoint: Records which step the task paused at and which steps are confirmed complete.
  • Action execution receipt (Receipt): Verifies whether an external action actually took effect—a network timeout or a missing log entry must never be treated as proof that "the action did not happen."

2. Recovery Workflow Design: From Read-Only Resumption to Side-Effect Verification

2.1 Relationship Between Existing Records and the Recovery Module

Current status: session persistence and querying are implemented, but there is no interruption recovery entry point yet. Currently, run_agent() writes a failed record on exception and stops; a future recovery mechanism builds on Stage 3 session records by adding unfinished-task detection and external state verification.

2.2 Steps to Resume an Interrupted Task

  1. Dedicated recovery entry point: Use an explicit resume command to read the progress and action records of a specific unfinished task—never conflating it with the normal "ask a follow-up question" entry point or blindly flipping the status to completed.
  2. Determine action state: Distinguish whether the pending action is "not yet dispatched," "confirmed completed," or "outcome unknown"—reuse existing receipts for completed actions, and verify actual external state whenever the outcome is unknown.
  3. Re-verify permissions and execute: If a read tool genuinely needs to run again, re-check permissions against the current Policy, execute through ToolRegistry, and record the fresh observation.
  4. Persist recovery progress: Save the verified or re-executed result before continuing the model loop. For write or external mutation actions, bind a unique idempotency key and attempt record (Attempt) to each logical invocation (Invocation).

2.3 Additional State Needed Beyond Session Records

Stage 3's record format stores only the session header, Turn start/finish markers, and complete messages. Reliable recovery additionally requires recording: recovery checkpoints (Checkpoint), logical action IDs (Invocation ID), per-attempt records (Attempt), and dispatch/confirmation states—a message log alone cannot be used as a replay script.

2.4 Scope of Recovery Exercises

Start with interruption recovery for read-only tools to verify rebuilding runtime state from confirmed steps; then extend to side-effecting write actions by verifying external state before deciding whether to retry.

3. Fault-Injection Test Scenarios

Inject interruptions at four critical points to verify how the recovery logic responds:

  1. Interrupted before action dispatch: The model has returned a tool call request, but the tool has not started running.
  2. Interrupted during execution / before return: The tool has started running or completed its underlying operation, but has not returned a result yet.
  3. Interrupted after receiving result / before flushing to disk: The tool has returned a ToolResult, but it has not been written to the session log.
  4. Interrupted after flushing result / before the next model request: The tool result is on disk, but the next model call has not been sent.

4. Expected Outcomes

  • Strict distinction among four operation states: The program accurately distinguishes "not dispatched," "completed," "still running," and "outcome unknown."
  • Zero blind retries on unknown state: For side-effecting actions whose outcome is unknown, the program checks external state first or stops for human confirmation, never retrying unconditionally.
  • No duplicate execution of confirmed steps: Steps that already have complete receipts reuse their recorded results during recovery without wasting tool or model compute.
