Stage 7: Add Entry Points, Extensions & Orchestration on Demand

Once the single-Agent core loop is running reliably, selectively add web entry points, capability extensions (Skills / Hooks / MCP), or multi-Agent orchestration based on real application needs.

1. Application Entry Points: Sharing the Execution Core Across CLI & HTTP

1.1 Current CLI Entry Point & Future Extension Points

The current entry point is the CLI function main(): it parses arguments and either calls run_task() to drive run_agent() or queries session records directly (see Stage 3).

1.2 Call Flow for Adding an HTTP Entry Point

  1. Request validation & session resolution: The HTTP endpoint receives a task description and an optional session ID, creating a new session when none is provided or verifying the workspace and permission config when resuming an existing session.
  2. Separation of execution and queries: Task submissions go through run_task() (long-running tasks can be dispatched to a background worker or queue that returns a task ID immediately), while history queries call read-only record interfaces directly without triggering the model or tools.
  3. Live progress observation: Stream or poll the progress of submitted tasks via SSE or polling; a client disconnecting from the observation stream does not cancel the background task.
  4. Attaching extensions or orchestration on demand: External tools return unified ToolResult objects through adapters; Hooks fire at fixed lifecycle points; and subagent orchestration explicitly manages parent/child task IDs, permission boundaries, and result aggregation.

1.3 State Data Needed for Extensions

When introducing an asynchronous web entry point or multi-Agent orchestration, add background task status, event cursors, cancellation flags, or parent/child task correlation fields on demand (note: serve_tutorial.py in this repository only serves the static tutorial pages locally and does not provide an Agent execution API).

1.4 Core Principles for Entry Point Design

Whether a task is submitted via CLI or Web, both entry points should reuse the same application service, permission rules, and session records, keeping task submission, read-only queries, and progress observation cleanly separated.

2. Capability Extensions: Skills, Hooks & MCP

  • Skills (workflow reuse): Package domain-specific task procedures into on-demand instruction documents so they do not bloat the always-on system prompt.
  • Hooks (lifecycle interception): Inject observability, auditing, or argument inspection logic before/after model requests or tool calls.
  • MCP (external tool integration): Connect external tool servers over a standard protocol, adapting them into internal ToolSpec and ToolResult contracts while keeping them subject to Policy and budget limits.

3. Multi-Agent Orchestration: Graphs & Subagent Delegation

  • Explicit workflows (Graph): Well suited for business processes with fixed steps, deterministic checks, or human approval gates.
  • Subagent delegation (Subagents): Delegate heavy search or independent review work to subagents with isolated context windows and restricted permissions, returning only structured conclusions and evidence citations to the main Agent.

4. Expected Outcomes

  • Consistent behavior across entry points: CLI and Web entry points share the same permission enforcement and execution logic, and queries or client reconnections never trigger duplicate execution.
  • Extensions remain governed: Connected Skills, Hooks, and MCP tools strictly obey the host program's Policy permissions and input budget limits.
  • Quantifiable orchestration gains: After introducing multi-Agent orchestration or extensions, you can compare quality, token usage, latency, and coordination overhead against the single-Agent baseline to prove the added complexity is worthwhile.
