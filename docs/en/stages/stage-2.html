Stage 2: Control Action Permissions with Policy

1. Starting Point: How to Block Dangerous Actions Before Tool Execution?

Once an Agent can write files (write_file), it introduces the risk of accidentally overwriting existing files. Consider this scenario:

  • User: "Summarize the reference notes and save the summary."
  • Model: Calls write_file(path="notes.txt", content="..."), attempting to overwrite the original notes file in the workspace.

If the tool writes to disk as soon as it receives the call, the original notes are destroyed. Therefore, the program must perform a permission check (Policy) before actually executing the tool function: allow creating new files, but forbid overwriting existing files by default.

Expected Outcomes:

  • Allow new file creation: When the target path does not exist, identify the action as create and allow the write.
  • Strictly block overwrites: When the target path already exists, identify the action as overwrite and deny it via Policy—write_file() never runs, and the original file content remains intact.
  • Feed back denial results: After blocking an action, return a policy_denied result carrying the original call_id so the model knows why it was denied and can adjust its next step.

2. Selected Approach: Permission Declarations + Centralized Registry Enforcement

  • How actions are identified: When registered, a tool declares its required permission category (such as read, list, or write) and path parameter name (path_parameter="path"). The shared function prepare_action() checks whether the target file already exists to produce a concrete ActionRequest (distinguishing create from overwrite).
  • How rules are evaluated: A Policy object stores permission flags and optional file allowlists, returning a PolicyDecision via evaluate().
  • Where execution is gated: Checked centrally at the entry of ToolRegistry.execute()—if Policy denies the action, it returns a policy_denied result immediately; only after approval does it call the actual tool function. Plain tool functions do not need to write their own permission logic.

3. Code Walkthrough: How Is an Overwrite Request Blocked?

3.1 Functions, Classes & Permission Data Objects

Policy stores rules and evaluates decisions, while PolicyEvaluator is the protocol depended on by the registry; prepare_action() and write_file() are plain functions; and ActionRequest, PolicyDecision, ToolCall, and ToolResult are data classes carrying requests, decisions, and results.

3.2 Full Call Sequence for an Overwrite Request

  1. Initialize policy (main() → run_task()): Creates a Policy instance that allows file creation but forbids overwriting, passing it along with the workspace directory into ToolRegistry.
  2. Declare tool permissions (filesystem.py): The write tool is registered with permission="write" and path_parameter="path" (declaring the required permission category does not mean the action is already approved).
  3. Identify the concrete action (prepare_action()): Inspects the validated target path on the filesystem—generating a create action if the target does not exist, or an overwrite action if it already exists (without writing to the file yet).
  4. Evaluate permission (Policy.evaluate()): Inspects the ActionRequest and returns PolicyDecision(allowed=False, reason="禁止覆盖已有文件") for an overwrite request.
  5. Block and return result (ToolRegistry.execute()): Seeing allowed=False, immediately returns a policy_denied result with the original call_id without calling write_file(), handing the result back to Runner.

3.3 Where Policy Rules and Denial Results Live

Policy flags and allowlists live in application memory; when an action is denied, policy_denied is appended as a standard ToolResult to the current run's messages list for the next model request.

4. Run the No-Overwrite Experiment

Create a file first, then request an overwrite through the real tool; does not call a model
uv run python -m examples.policy_no_overwrite

The experiment script reuses the exact same ToolRegistry.execute() path as Runner inside a temporary directory and issues two consecutive writes:

  • First call (target file does not exist): Identified as create; the write succeeds and the file content is "原内容" ("original content").
  • Second call (target file already exists): Identified as overwrite; returns policy_denied (reason: "禁止覆盖已有文件"), and reading the file again confirms its content is still "原内容".

5. Local Tests & Implementation Boundaries

Real temporary files and local SDK protocol without calling an external model
uv run pytest tests/test_policy.py tests/test_tools.py tests/test_application.py
  • Action identification & original file protection (test_policy.py): Verifies that the first write is identified as create, the second write is identified as overwrite, and the original file on disk remains untouched after denial.
  • Unified control for new tools (test_tools.py): Verifies that any newly registered plain function goes through ToolRegistry's unified permission check and never executes when denied.
Underlying safety limits of the current file-writing tool

Even after file creation is approved, the underlying implementation opens the file in exclusive creation mode (x mode): if a concurrent process creates the same file first, it returns a file_exists result instead of overwriting. Writing through symlinks is also forbidden, the parent directory must already exist, and a single write is capped at 16,000 UTF-8 bytes (currently supported on macOS / Linux).
