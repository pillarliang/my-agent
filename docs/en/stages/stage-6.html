Future Stage · Not Yet Implemented

Stage 6: Long Tasks: Offloading & Compaction

Stage 4 implemented deterministic block-level context trimming based on token budgets, and Stage 5 enabled cross-session project memory reuse. However, as single tasks grow longer and tool outputs become massive, simple block trimming drops critical initial goals, and oversized tool returns instantly blow the context window. This stage focuses on these two fatal bottlenecks, introducing tool output offloading and historical block structured compaction to allow long tasks to complete reliably.

1. Problem Origin: Two Fatal Long-Task Bottlenecks

In multi-step long tasks or complex troubleshooting scenarios, systems frequently run into two predictable execution failures:

Bottleneck 1: Massive Single Tool Output (Single-turn Context Explosion)

  • User: "Analyze access.log to find the root causes of the top 5 HTTP 500 errors."
  • Model: Calls read_file(path="access.log").
  • (Tool execution: The log file is 10MB with 200,000 lines of text)
  • (Context assembly: A single ToolResult exceeds 80,000 tokens, blowing past the budget and crashing the task)

Bottleneck 2: Goal Forgetting from Multi-Turn Block Trimming (Task Drift)

  • User: "Refactor the auth module. You must strictly preserve backwards compatibility with legacy JWT format and output a summary list of changed files."
  • (Model executes 16 consecutive turns of searching, reading, and unit testing)
  • (Stage 4 budget trimming triggers: The first 8 turns are discarded completely)
  • Model: "Refactoring complete." (Completely forgets the legacy JWT compatibility requirement and omits the changed file list)

Expected Outcomes:

  • No single-turn blowout: Regardless of tool return size, payload sent to the model never exceeds budget thresholds.
  • No lost task intent: Even across 20+ steps, the original user prompt and global acceptance criteria remain pinned and protected.
  • Inspectable details on demand: Previews and summaries include explicit disk paths and offset pointers for precise on-demand reading.
  • Quantifiable compression gain: Clear metrics demonstrating increased task completion rates and token savings compared to raw baselines.

2. Mechanism Design: Tool Output Offloading & Structured Compaction

To address the two bottlenecks, two complementary context protection mechanisms are introduced:

  • Tool Output Offloading & Head/Tail Preview:
    • When triggered: When a tool finishes execution and returns to Runner, check output volume; if it exceeds a threshold (e.g., 3,000 characters or 1KB), trigger offloading.
    • System action: Write the complete output into a disk artifact file (e.g., .learn_agent/artifacts/tool_xxx.txt).
    • Model payload: Replace the raw ToolResult with a head/tail preview (first 500 chars + last 500 chars), the artifact file path, and a pagination hint (e.g., read_file(offset=..., limit=...)).
  • Historical Block Structured Compaction:
    • When triggered: When completed historical blocks exceed the context budget watermark (e.g., 50% of total budget).
    • System action: Instead of outright dropping old turns, condense a sequence of intermediate trial-and-error steps into a concise structured summary.
    • Protected boundaries: The initial user prompt (containing core constraints) and the most recent turn are in the permanently protected zone and are never discarded.

Clear Boundaries with Stage 4 Budgets and Stage 5 Memory:

  • Stage 4 Context Budget: The ultimate safety net. Estimates token volume and trims oldest optional blocks when over limit.
  • Stage 5 Memory: Manages cross-session project conventions (workspace/MEMORY.md).
  • Stage 6 Long Tasks: Precedes Stage 4 trimming by offloading oversized outputs and compacting intermediate steps, preventing hard drops of core goals.

3. Implementation & Comparison Workflow

3.1 Existing Code Foundation & Extension Points

Current status: Output offloading and structured compaction are not yet implemented. The codebase already provides run_agent(), ToolRegistry, SessionLog, and select_context(). Long-task mechanisms plug in at two clear boundaries:

3.2 Implementation Steps

  1. Diagnose the failure root cause: Inspect Stage 3 JSONL transcripts to verify whether failures are due to single-turn output blowout (Bottleneck 1) or lost initial requirements from Stage 4 trimming (Bottleneck 2).
  2. Implement Output Offloading: Intercept oversized text in ToolRegistry, write full contents to disk artifacts, and construct preview-enabled ToolResult payloads.
  3. Implement Structured Compaction: Extract structured summaries from completed intermediate turn blocks to replace verbose message sequences.
  4. Integrate into Context Selection: In select_context(), inject pinned instructions, compacted summaries, and active turn messages before passing Stage 4 budget verification.
  5. Evaluate Against Baselines: Measure pass rates, total token consumption (including summarization calls), and wall-clock latency across complex multi-step tasks.

3.3 Storage Structure Design Essentials

Maintain lightweight metadata structures for offloaded artifacts and compaction records:

  • Offloaded artifact metadata: Session ID, Turn ID, Tool Call ID, raw byte length, and disk relative path.
  • Compacted block records: Start/end Turn index range, original estimated tokens, summary text, and tokens used for generation.

3.4 Comparison Discipline

Introduce one mechanism at a time (offloading first, then compaction). Account for auxiliary model tokens consumed by compaction to verify true net efficiency gains.

4. Expected Outcomes

  • No single-turn blowout: Massive tool returns never overflow single-turn request limits.
  • No lost task intent: Complex multi-step tasks retain original requirements and acceptance criteria without drifting.
  • Inspectable details on demand: Previews and summaries provide actionable file paths for selective drilling.
  • Quantifiable compression gain: Demonstrable improvements in multi-step task completion and token economy.
