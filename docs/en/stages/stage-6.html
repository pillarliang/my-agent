Stage 6: Choose Long-Task Mechanisms from Real Failures

Handling long tasks does not mean building summarization, retrieval, and long-term memory all at once. Instead, reproduce the bottleneck on a real task first, then introduce the specific mechanism that addresses it.

1. Establish an Evaluation Baseline

Fix the test task, input materials, and model configuration, run the baseline with the existing loop, and record four key metrics: missed task requirements, token usage, end-to-end latency, and failure causes.

2. Match the Mechanism to the Bottleneck

  • Single tool result is too large: Offload the full result to storage and keep only a head/tail preview plus a path for on-demand reading in the message.
  • History trimming drops early requirements: Explicitly maintain structured task requirements, or generate summaries for older turn blocks.
  • Too many candidate reference documents: Switch to on-demand retrieval (keyword or vector search) and load only snippets relevant to the current query.
  • Project facts or user preferences must be reused across sessions: Introduce long-term memory (Memory) with explicit provenance and scope.

3. Implementation & Comparison Workflow

3.1 Existing Code Foundation & Extension Points

Current status: summarization, retrieval, and long-term memory are not yet implemented. The existing codebase already provides run_agent(), ToolRegistry, and SessionLog; future long-task mechanisms plug in around input assembly and tool-result boundaries.

3.2 Implementation Steps After Selecting a Mechanism

  1. Diagnose the failure root cause: Inspect the session records saved in Stage 3 to confirm whether failure was caused by a single oversized tool output blowing the window, early requirements being trimmed away, or missing cross-session knowledge.
  2. Implement a single processing mechanism: For result previews, save the full output path and generate a preview when a tool returns; for history summarization or document retrieval, implement the corresponding processing function and record data provenance and version.
  3. Connect to context assembly: Load previews, summaries, or retrieved snippets during Stage 4's input selection step, verify the budget, and construct ModelRequest.
  4. Evaluate against the baseline: Compare task pass rate, token consumption (including summarization overhead), and total latency on the same task before and after introducing the mechanism, keeping it only if it proves effective.

3.3 Storage Structure Design Essentials

Add data structures only for the chosen mechanism rather than pre-creating redundant tables upfront:

  • History summaries: Record the compressed Turn range, raw content hash, summary version, and tokens consumed to generate the summary.
  • Document retrieval: Record document IDs, chunk offsets, index versions, and deletion sync status.
  • Long-term memory: Record applicable scope (user / project), source message IDs, active status, and revision versions.

3.4 Comparison Discipline

Change only one variable per experiment, preserve source and version metadata for every piece of data entering the context, and validate improvements with reproducible task outcomes.

4. Expected Outcomes

  • Explainable context provenance: You can inspect exactly which raw messages, summaries, retrieved snippets, or memory entries the model saw on a given turn.
  • Traceable and correctable errors: When a summary distorts facts or a memory entry becomes stale, you can trace it back to the original record and update or revoke it.
  • Data-backed gains: Compared against the baseline, you can quantify improvements in pass rate, token savings, and any newly added call overhead.
