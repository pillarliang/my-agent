Module Principles & Design Options

Interfaces: User Entry Points & Real-Time Communication Protocols

1. Starting Problem: Why Can't an Agent Entry Point Be a Plain Web API?

Traditional Web endpoints follow a standard request-response cycle: the client issues an HTTP POST, receives JSON within a few hundred milliseconds, and closes the connection. Applying this pattern directly to an Agent system breaks down under three engineering hurdles:

  • Hurdle 1: Long-running black box execution: An Agent frequently requires seconds or minutes to perform multi-step planning, model invocations, and tool executions. If the user must wait blindly for a single HTTP response without any intermediate signals, they often assume the UI is frozen, reload the page, or resend requests—creating costly duplicate tasks.
  • Hurdle 2: Inability to pause for human intervention (Human-in-the-loop): When an Agent encounters high-risk actions (e.g., deleting production database tables, executing write operations on critical files) or ambiguous goals, it must halt and request human authorization. A unidirectional HTTP request cannot pause mid-stream to solicit reverse user input.
  • Hurdle 3: Inability to interrupt promptly (User Abort): If a user notices that the model is hallucinating, spiraling into a loop, or making useless tool calls, they need to cancel immediately. Without a bidirectional control channel, closing the browser tab leaves the backend burning tokens and rate limits unattended.

Expected Outcomes:

  • Decoupled execution core: Whether invoked from a CLI, Web UI, IDE extension, or Slack bot, tasks share the exact same Runner, Policy rules, and toolsets; interface layers only parse inputs and translate events.
  • Transparent execution visibility: Model thoughts, token-level typing, and tool call start/finish states are streamed in real time via structured events so users always know what is happening.
  • Seamless Human-in-the-loop support: Approvals for sensitive tools, clarifications, and user cancellations integrate naturally into the running loop without tearing down the entire session.
  • Resilience across disconnects: Clients that reconnect after Wi-Fi blips or page reloads catch up on missed progress using event cursors without triggering duplicate runs.

2. Architecture Layers: Presentation, Transport, Application, and Execution Core

To share the underlying Agent logic cleanly across various interfaces, the system is separated into four layers:

  • Presentation Layer: Terminal CLI, Web frontend, or IDE extension. Only collects user input and renders structured events emitted by the server. Never place model SDK calls or permission evaluations in the presentation layer.
  • Transport Layer: CLI argument parser, HTTP route handlers, and WebSocket gateways. Handles connection lifecycles, authentication, heartbeats, and serialization (e.g., JSON-RPC or custom Event Schemas).
  • Application & Dispatcher Layer (AgentService / Task Manager): Accepts normalized domain requests (task text, session ID, approval results), locates past session records, resolves workspaces and Policy rules, and tracks background workers or tasks.
  • Execution Core (Runner Loop): The pure Agent Loop orchestration engine. Takes run_task requests, drives model invocations, dispatches tools, and logs state; communicates outward solely through lifecycle event broadcasts and abort signals.

In a multi-entry architecture, execution and query paths must remain strictly separated:

  • Run submission path: The entry point collects prompt → application service configures workspace and Policy → launches Runner loop → State persists history → transport pushes events to the client.
  • Read-only query path: The entry point requests session listings or conversation details → reads directly from persistent storage (JSONL or database) → returns raw records without invoking models or tools.
  • Layered error reporting: The presentation layer clearly differentiates between validation errors (400), controlled tool failures (returned to the model), and system crashes (500), never disguising failure as success.

Separation of Initialization and Runtime: Component dependencies (API keys, workspace paths, Policy definitions) are injected when the service starts or a task is initialized; runtime messages only convey domain payloads, and frontend UI states never serve as the authority for backend permissions.

3. Execution and Scheduling Approaches

Depending on task duration and concurrency needs, runtime execution falls into 4 common patterns (Pattern A is currently implemented; B, C, and D are extension paths):

A. One-Shot Batch Execution (Non-interactive CLI & Automated Scripts)

  • How it works: Run-to-completion invocation. The calling process blocks until Runner completes the entire loop and prints the final output.
  • Best for: CI/CD automation pipelines, cron scripts, and simple CLI commands (such as the Stages 0–5 CLI in this repository).
  • Trade-offs: Does not listen for user input during execution, making mid-run human approval impossible; wrapping this directly into a synchronous HTTP route easily triggers gateway timeouts.

B. In-Process Background Task (Local Web MVP)

  • How it works: The endpoint returns a task ID immediately and spawns an asynchronous coroutine (e.g., Python asyncio.create_task) to run the Runner, while the client monitors progress via a separate channel.
  • Best for: Single-user local Web UIs (e.g., FastAPI / Starlette) with minimal architectural footprint.
  • Trade-offs: Tasks are lost if the Web process restarts or crashes; state is isolated to a single process.

C. Persistent Queue & Dedicated Worker (Production Long Tasks & Temporal Orchestration)

  • How it works: Submitted tasks are persisted to storage or durable execution engines (such as Redis/Celery, RabbitMQ, or Temporal state machines); independent Worker processes claim tasks via long-polling, run the Runner, and notify clients upon completion.
  • Best for: Multi-user enterprise platforms, long-horizon deep research or project-summary agents, and systems requiring horizontal elasticity and automated failover.
  • Architectural Patterns:
    • Native Worker Pattern (e.g., Temporal Activity Worker): The agent exposes no HTTP API; workers poll a Task Queue directly, with the coordinator automatically handling timeouts and node failover.
    • External Service Pattern (e.g., HTTP 202 + Signal Callback): An upstream orchestrator (like Temporal) triggers the agent via HTTP; the agent immediately returns 202 Accepted, executes in background coroutines, and notifies the workflow via asynchronous Signals upon completion, paired with K8s graceful shutdown.
  • Trade-offs & limitations: Introduces distributed dependencies; requires lease heartbeats, idempotency locks, distributed cancellation routing, and side-effect reconciliation (see State and Stage 7: Recovery).

D. Externally Hosted Agent Runtime (Fully Managed Cloud Services)

  • How it works: Developers do not build a custom Runner or session database; instead, they call managed cloud Agent platforms (such as Dify API, Coze, OpenAI Assistants API, or LangGraph Cloud). The cloud orchestrator fully manages conversation history, context truncation, tool loop execution, and sandboxes, while the client merely renders incoming standard event streams.
  • Best for: Early MVPs, lightweight interfaces, and teams focusing strictly on frontend product experience without needing deep private Policy governance.
  • Trade-offs & limitations:
    • Dual-State Split-Brain: The cloud platform stores one version of conversation records, while your internal database usually wants to store another. Network hiccups easily lead to desynchronization.
    • Black-Box Inflexibility & Vendor Lock-in: Inability to customize context compaction logic or inject granular local Policy permission checks before tool dispatch, paired with higher per-run costs.

4. Choosing a Transport Protocol: Polling, SSE, or WebSocket?

How should clients receive real-time execution progress from an Agent? Three main protocols exist:

Transport Protocol Channel Characteristics Best For Trade-offs & Overhead
HTTP Polling Unidirectional pull: Client issues GET requests every 1–2 seconds to fetch incremental events Minimal read-only clients, restricted corporate networks banning websockets Fixed polling latency, high server query overhead, no smooth token-by-token streaming
POST + SSE + GET Half-duplex: POST to start, SSE (Server-Sent Events) for downstream push, GET for history Text chat and read-only progress views (e.g., standard Q&A assistants) Only supports server-to-client push; client interruptions or replies require separate HTTP calls
WebSocket Full-Duplex Full-duplex: Single persistent connection allowing bidirectional, low-latency structured frames Agent IDEs, human approvals (HITL), interactive prompts, and instant cancellations Requires handling heartbeats, connection reconnect state machines, and frame routing

Why WebSocket Excels for Human-in-the-Loop Workflows

Autonomous coding and DevOps agents are rarely passive text generators; they require frequent two-way collaboration:

  • Immediate two-way communication: A single authenticated TCP connection enables the server to stream tokens while the client sends control signals with sub-millisecond dispatch.
  • Explicit connection lifecycle: When a WebSocket disconnects, the server immediately detects the drop and decides whether to pause execution or continue running in the background.
  • Lower signaling overhead: Eliminates repetitive TCP handshakes, TLS negotiation, and header re-authentication for every user approval click.

Recommended Pattern: Adopt a hybrid pattern of "RESTful HTTP for static history queries + WebSocket for active bidirectional execution".

Switching to full-duplex WebSocket (Pattern 3) brings an architectural upgrade:

  • Single persistent session: A single WebSocket handshake multiplexes task triggers, token streams, and lifecycle steps over one persistent TCP socket.
  • Zero-friction bidirectional signaling: When the server sends an approval_required frame, the client replies immediately over the same socket with approval_response or abort_run, achieving true full-duplex collaboration (detailed in the next section).

5. Deep Dive into Full-Duplex Control: Human-in-the-Loop Flows

Over WebSocket, the system cleanly supports three essential interaction patterns:

Scenario 1: Human Approval for Sensitive Actions

When Policy identifies an action requiring explicit user consent (e.g., deleting a file, changing production config), Runner pauses and requests guidance:

  • Runner: Detects that delete_file needs authorization, emits an approval_requested event, and pauses the coroutine.
  • Server (WebSocket): Pushes frame: {"type": "approval_required", "action_id": "act_981", "tool": "delete_file", "params": {"path": "main.py"}}.
  • Client (UI): Renders a modal displaying parameters and warning dialogs.
  • User: Clicks "Reject action".
  • Client (WebSocket): Emits: {"type": "approval_response", "action_id": "act_981", "approved": false, "reason": "Keep original, make a copy instead"}.
  • Runner: Resumes coroutine with ToolResult(error="User rejected: Keep original, make a copy instead") and lets the model adapt.

Scenario 2: Mid-Run Clarifications (Ask User)

When task instructions are ambiguous, the model calls an interactive prompt tool:

  • Model: Requests ask_user(prompt="What is the database password for testing?").
  • Server (WebSocket): Broadcasts {"type": "user_input_requested", "prompt": "What is the database password for testing?"}.
  • User: Types credentials and submits.
  • Client (WebSocket): Sends {"type": "user_input_response", "answer": "secret_123"}.
  • Runner: Feeds the reply as the tool output back into the model context.

Scenario 3: User Interrupt and Safe Cancellation

When the user notices bad trajectory drift, they click "Stop":

  • Client (WebSocket): Pushes {"type": "abort_run", "run_id": "run_001"}.
  • Server: Triggers the task's asyncio.Event cancellation flag.
  • Runner: Safely winds down current steps, writes an interrupted status in the session log, and releases workspace resources.
  • Server (WebSocket): Emits {"type": "run_interrupted", "run_id": "run_001"} to unlock the frontend interface.

Why Does Claude Code Support Rich Human Interactions Despite Being a CLI?

Developers often wonder: "If terminal commands are typically batch scripts, why do tools like Claude Code, Cursor Terminal, or Aider run in the terminal yet provide real-time typewriter streaming, interactive approvals ([Y/n]), and instant Ctrl+C cancellation?"

This is because CLI applications exist in two fundamentally different forms:

  • Form 1: One-Shot Batch CLI (Traditional Scripts):
    • Runtime Profile: Run-to-completion invocation (like python -m learn_agent --task "..." in Stages 0–5). The main process blocks synchronously until the entire task finishes, ignoring terminal events in between. Ideal for CI/CD pipelines.
  • Form 2: Interactive Terminal User Interface (TUI / REPL, like Claude Code or pi):
    • Runtime Profile: A persistent, event-loop-driven application. Operating directly over OS standard streams (stdio), it achieves capabilities identical to full-duplex WebSockets:
      1. Stdout Streaming: Intercepts model delta chunks and writes ANSI escape codes directly to stdout, delivering typewriter animations, cursor repositioning, and folding progress bars.
      2. Raw Mode & Interactive stdin (Approvals): When Policy halts on high-risk tools, Runner pauses its coroutine while the terminal switches into Raw Mode to capture arrow keys, Enter, or y/n keystrokes. Upon user confirmation, stdin restores normal mode and Runner resumes.
      3. Signal Interruption (POSIX Signals): Captures SIGINT (Ctrl+C) and triggers AbortController signals to abort active network calls and child processes cleanly.

Architecture Takeaway: In robust Agent design, the frontend (whether a Web browser or a terminal TUI) is purely a presentation shell. Both rely on the same fundamental trinity: event-driven streaming + coroutine suspend/resume state machines + honest cancellation signaling. Headless architectures (like pi) even run the TUI as a client communicating with an Agent Core via stdio-based JSON-RPC frames.

6. End-to-End System Data Flow Architecture & Event Protocols

6.1 Core Distinctions: Four Different Dimensions of Event, Session, State, and Checkpoint

When designing data models, never confuse incoming step events with internal state. These four concepts occupy distinct system dimensions and serve entirely different audiences:

Concept Dimension & Nature Primary Consumer Storage & Lifecycle Core Question Answered
Event (Stream) Transport & Telemetry
Immutable transient pulses emitted at runtime		 Presentation (Web / TUI)
Tracing (e.g., Langfuse)		 In-memory ring buffer or socket stream, discardable after task finish "What micro-step just happened in the last 10 milliseconds?"
Session (Log) Human-Agent Interaction
Domain conversation & task Turns		 Humans (history review)
Model (next turn context assembly)		 Persistent storage (JSONL / DB), durable for long horizons "What did the user and agent discuss and conclude previously?"
State (Working Memory) Execution Core
Shared blackboard & variables inside a task		 Runner orchestrator
Tools & Subagents		 In-process object variables, active only during a single Run "What structured data has been accumulated right now? What are the next step dependencies?"
Checkpoint Fault-Tolerance & Recovery
Frozen physical snapshot at key milestones		 Recovery state machine
Human intervention reconciler		 Persistent disk/store, flushed before critical side-effects "If the node crashes right now, where do I safely resume without double-charging or re-writing files?"

6.2 End-to-End System Data Flow Architecture: How Data Flows Across Layers

To keep data boundaries clean and decoupled, an industrial-grade Agent harness coordinates data across five distinct architectural tiers:

The Five Stages of Data Lifecycle:

  1. Stage 1: Initialization & Context Assembly (Memory + Session → Context → State):
    • When a user sends a prompt, Context Manager reads closed past turns from Session storage and loads the pinned project memory snapshot (Memory).
    • It truncates history within strict Token budgets and initializes the active in-memory State.
  2. Stage 2: Loop Execution & Transient Event Broadcasts (State ↔ Model ↔ Policy ↔ Event):
    • Runner drives model inference. Token fragments are packaged as model_delta events to feed the frontend typewriter effect without altering persistent state.
    • Tool call proposals update in-memory State and trigger tool_call_started lifecycle events to the client.
  3. Stage 3: Crash Recovery Freezing (State → Checkpoint Flush):
    • Before executing physical actions with side effects (file modifications, external payments), the system persists step index, unique invocation_id, and State snapshots to Checkpoint storage.
    • If the node crashes, recovery logic verifies physical receipts to prevent duplicated operations.
  4. Stage 4: Full-Duplex Human Suspension & Resumption (State Pauses ↔ Event ↔ Client Approval ↔ State Resumes):
    • Upon encountering high-risk tools, Runner suspends the active coroutine and emits an approval_required event.
    • The user decides in the UI; the client sends an approval_response back over the same WebSocket, resuming the Runner.
  5. Stage 5: Turn Finalization & History Archival (State → SessionLog / S3 / Workspace):
    • When the model finishes without further tool calls, Runner seals the Turn boundary.
    • Clean inputs, final answers, and tool results append to SessionLog, releasing temporary scratchpads while preserving domain artifacts.

6.3 Tiered Event Streams and Standard Frame Formats

When designing WebSocket or SSE protocols, distinguish two tiers of events:

  • Tier 1: Model Token Streaming (Deltas): Incremental token fragments generated by the model. Used solely for typewriter rendering, without modifying state.
  • Tier 2: Harness Step / Lifecycle Events: Structured events reflecting agent milestones and tool invocations, driving UI components like folding thought boxes and progress indicators.

Recommended standard JSON frame structure:

{
  "event_id": 104,
  "run_id": "run_20261031_001",
  "session_id": "sess_default",
  "timestamp": 1793433600.123,
  "type": "tool_call_started",
  "payload": {
    "tool_call_id": "call_abc123",
    "tool_name": "search_text",
    "arguments": {"keyword": "Policy"}
  }
}
Event Type Trigger Condition Frontend Presentation & Behavior
run_started Runner validates and starts the task Lock input, show spinning indicator
model_delta Incoming model token fragment Append text in the active message bubble
thought_delta Incoming reasoning trace (Thinking) Stream into a collapsible thought accordion
tool_call_started Model requests tool execution Display tool badge and argument preview
tool_call_completed Tool execution finishes with output Update badge to success/fail, fold result preview
approval_required Policy flags high-risk tool call Display approval modal with Approve / Deny buttons
run_completed Model outputs final answer and stops Unlock input box, display summary stats
run_error Model error, budget exceeded, or crash Highlight error message, allow retry

7. Edge Cases: Reconnection, Deduplication & Honest Cancellation

A. Reconnect Catch-up with Event Cursors

Mobile lock-screens or network drops terminate WebSocket connections. Rather than restarting tasks:

  • Monotonic Server Event IDs: Every event emitted carries an incrementing event_id (e.g., 1, 2, 3...).
  • Client Cursor Tracking: The frontend stores the highest received last_event_id.
  • Resume Handshake: Upon reconnection, the client sends {"action": "resume", "run_id": "run_001", "after_event_id": 42}; the server replays all events newer than 42 before switching to live stream.
  • Deduplication: The client filters event IDs to prevent duplicate renders.

B. Idempotent Submission (Client Request ID)

To prevent double execution caused by repeated user clicks:

  • Client UUID: Each new task sends a unique client_request_id.
  • Server Lock: The server checks if the request ID is already processing; if so, it binds to the existing run_id without launching a duplicate loop.

C. Honest Cancellation Propagation

Differentiate between tab closure, disconnection, cancellation requests, and confirmed halts:

  • Real Signal Routing: Clicking "Stop" propagates cancellation tokens into the Runner rather than merely hiding the spinner in the UI.
  • Safe Completion of Atomic Actions: If a tool is currently writing a file to disk, wait for the single write call to complete cleanly before terminating the loop.
  • Truthful States: The server returns "Cancellation accepted" first, updating to run_cancelled only when the Runner safely terminates.

8. How Open-Source Systems Organize Multiple Entry Points

  • pi (Official Docs): Its RPC interface turns the core Agent into a headless server. CLI, Web, and VS Code extensions speak JSON-RPC commands and event frames, keeping permissions and tool logic unified in the core engine.
  • AgentScope Java (Official Docs): Its architecture guide separates direct synchronous execution, in-request streaming, and persistent background tasks, ensuring shared configurations across entry points.
  • OpenAI Assistants & Realtime APIs: Decouple Threads and Runs, broadcasting granular step events (e.g., thread.run.step.created) and yielding a requires_action state whenever tool approval or external results are needed.

9. Current Implementation & Unimplemented Scope

  • Implemented (as of Stage 5: Synchronous CLI + Session Queries):
    • Task submission enters Runner via run_task(), waiting synchronously for RunResult with session continuation support via --session ID.
    • Provides --list-sessions and --show-session ID for read-only queries against local JSONL logs without calling models or tools (see Stage 1 and Stage 3).
  • Not Yet Implemented (deferred to Stage 8 On-Demand Extensions): Web HTTP / WebSocket gateway, persistent background tasks, bidirectional human approval frames, cursor-based replay, and cancellation signals.

10. Expected Outcomes (Future Web & WebSocket Entry Exercise)

When connecting Web and WebSocket interfaces to the Agent, verify against these criteria:

Expected Outcomes:

  • Identical execution across interfaces: Submissions from the CLI and Web browser share the exact same Runner, tool definitions, and Policy restrictions.
  • Zero side-effects on read queries: Listing sessions or loading history only reads persisted records, never triggering model calls or tool executions.
  • Fluid full-duplex collaboration: Sensitive tool approvals and model questions pop up in the UI seamlessly; decisions immediately resume or cancel the runner.
  • Lossless catch-up on reconnect: Clients reconnecting with a cursor receive all missed step events in order, without duplicate renders.
  • Idempotent submissions: Submitting identical client request IDs rejoins the existing run rather than launching duplicate agent loops.
  • Truthful cancellation: Stopping a task cancels backend execution safely and logs the interruption; the backend never runs invisibly after cancellation.
