Module Principles & Design Options

Interfaces: Share Execution Flow Across Entry Points

1. Starting Problem: How Do Different Entry Points Share a Single Execution Core?

When a system needs to provide a Web UI or API in addition to a CLI, the most common code smell is each entry point assembling its own set of tools, permissions, and loop logic.

Expected Outcomes:

  • Separate submission, execution, and presentation: Whether a request originates from the CLI or a browser, it passes through the exact same application service configuration, permission checks, and Runner execution flow.
  • Keep entry points free of wire-protocol details: The frontend does not need to understand model SDK protocols, and the CLI does not duplicate the Agent Loop; the application service accepts plain domain parameters (such as session ID and task text).
  • Ground truth lives in persistent records: Link execution, history, and progress via stored Run IDs rather than judging task completion solely by what the frontend page displays.

2. Module Collaboration: How Are the Execution Path and Query Path Separated?

In a multi-entry architecture, "submitting a run" and "querying records" are two completely independent paths:

  • Run submission path: The entry point collects the user prompt → the application service selects the workspace directory, toolset, and Policy configuration → hands off to Runner to drive the execution loop → the State recording layer persists the actual steps and results.
  • Read-only query path: The entry point requests a session list or history details → reads saved records directly → renders them as-is, never triggering model calls or tool execution.
  • Layered error presentation: The presentation layer clearly distinguishes between "request parameters rejected," "run execution failed," and "record query failed," never disguising an empty result as a successful execution.

Separating initialization from runtime: Initialization fixes components and permission configurations; runtime only passes task input, session ID, execution results, and error details—frontend button state cannot directly dictate tool permissions.

3. Comparing Core Approaches: Where Does the Task Run, and Does the Caller Wait?

Depending on task duration and deployment topology, there are 4 common execution service approaches (Approach A is currently used; B, C, and D are optional extensions):

A. Synchronous In-Request Execution

  • How it works: The calling entry point blocks and waits until Runner returns the final result.
  • Best for: CLI tools and very short calls—simplest to implement with the most direct error reporting.
  • Trade-offs & limitations: Task runtime is bounded by a single request timeout, and intermediate state is hard to track if the connection drops.

B. In-Process Background Execution

  • How it works: The endpoint immediately returns a task ID and spawns a background task inside the current Web process to run Runner; the client queries progress and results via separate endpoints (see FastAPI Concurrency Docs).
  • Best for: Local single-node Web MVPs with minimal code, avoiding blocking the HTTP event loop during model network waits.
  • Trade-offs & limitations: Background tasks are lost if the Web process exits or restarts, and synchronous blocking operations cannot be stopped immediately just by cancelling an async Task.

C. Persistent Queue & Dedicated Worker

  • How it works: Submitted tasks are persisted to storage first, claimed and executed by separate Worker processes, and queried by the frontend via task ID.
  • Best for: Long-running tasks and systems requiring service restarts and independent horizontal scaling.
  • Trade-offs & limitations: Requires handling task leases, duplicate delivery, cancellation propagation, and external side-effect reconciliation (see State).

D. Externally Hosted Agent Runtime Service

  • How it works: The CLI or Web app calls a full external runtime service directly and receives a task ID and event stream.
  • Best for: Scenarios that want to reuse existing scheduling infrastructure.
  • Trade-offs & limitations: You must clearly define which side serves as the single source of truth for sessions, permissions, and history records to avoid maintaining two conflicting states locally and remotely.

4. How to Choose a Progress Transport Protocol?

Web Progress Push, Reconnect Catch-up & History Query (Future Design)

Transport Approach How It Works Best For Main Implementation Cost
HTTP Polling Client periodically requests task status or incremental events Low-frequency status updates, minimal clients Polling interval latency and redundant requests
POST + SSE + GET POST to submit task, one-way SSE stream, GET for history Streaming conversation display and tool step progress Requires managing long-lived connections, event cursors, and reconnect catch-up
WebSocket Full-duplex persistent message channel High-frequency bidirectional control and real-time interaction Requires custom message protocol, heartbeats, and reconnect state machine

Key Conceptual Distinctions:

  • SSE one-way event stream: The MDN SSE specification defines one-way events, event IDs, and automatic reconnection. When a Web entry point mainly receives progress, using "plain POST for submit/cancel + SSE for progress + GET for history" is usually simpler and cleaner than WebSocket.
  • Task step progress vs. token-by-token streaming: Pushing step events such as "model request started" or "tool returned" is distinct from token-level streaming output from the model; the latter also requires adapting the Model adapter.

5. How Open-Source Systems Organize Multiple Entry Points

  • AgentScope Java (Official Docs): Its architecture guide explicitly separates direct invocation, in-request streaming events, and persistent session task operations, allowing different entry points to reuse the same model, tool, and middleware configuration.
  • pi (Official Docs): Its RPC interface connects the same runtime core to different UIs (not limited to HTTP or browsers) via standardized structured commands and events.

6. Edge Cases: Reconnection, Duplicate Submission & Cancellation

  • Reconnect catch-up & deduplication: Assign a monotonically increasing or fixed ID to each event and track the read cursor on the client; after reconnecting, catch up on missed events from persistent storage first and deduplicate by event ID rather than relying solely on an in-memory frontend array for chat history.
  • Preventing duplicate submissions: If a user resends a plain POST during network jitter, a second duplicate task would launch. Support a client-supplied idempotency key (client_request_id) so the server can deduplicate submissions.
  • Expressing cancellation state honestly: Strictly distinguish between "page closed," "connection dropped," "user requested cancellation," and "execution actually stopped." A cancel endpoint should first return "cancellation request accepted" and update the final state only after the executor confirms termination; the UI must never pretend a background tool has stopped the instant the cancel button is clicked.

7. Current Implementation & Unimplemented Scope

  • Implemented (as of Stage 3: Synchronous CLI + Session Queries):
    • Task submissions enter Runner via run_task() and wait synchronously to return RunResult, supporting session continuation via --session ID.
    • Provides --list-sessions and --show-session ID for read-only queries against local JSONL session records without invoking the model or tools (see Stage 1 and Stage 3).
  • Not Yet Implemented (deferred to Stage 8 On-Demand Extensions): Web HTTP server, background tasks, persistent queues, SSE / WebSocket real-time streaming, request idempotency deduplication, and task cancellation protocol.

8. Expected Outcomes (Future Web Entry Exercise)

When adding a Web entry point later, first make the CLI and HTTP routes share the same application service, then verify against these criteria:

Expected Outcomes:

  • Consistent behavior across entry points: Submitting the same task from CLI and HTTP obeys the exact same toolset and Policy permission restrictions.
  • Zero side effects on queries and refreshes: Querying history or refreshing the browser page only reads saved records and never triggers new model requests or tool executions.
  • Catch-up progress after disconnect: After an SSE connection drops and reconnects, missing steps are filled in using the event cursor without rendering duplicate events.
  • No duplicate runs on resubmission: Submitting repeatedly with the same client request ID returns the existing task state directly without starting a second run.
  • Truthful cancellation status: After initiating cancellation or closing the frontend page, task status accurately reflects whether the backend executor has truly stopped, without fabricating success or stopped states.
