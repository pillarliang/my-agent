Context Manager: Assemble What Goes to the Model

1. Starting Problem & Design Principles: Why Does "Saving History" Not Mean "Sending Everything Every Turn"?

In multi-turn conversations or long-running tasks, historical messages and tool outputs grow rapidly. Consider this multi-step scenario:

  • User (Turn 1): "Write an event announcement in Chinese, use UTC for all timestamps, and do not overwrite the original file before the final draft is approved."
  • (Followed by multiple rounds of reading files, inspecting long logs, and revising drafts, accumulating dozens of historical messages)
  • User (Current Turn): "Follow the earlier time rule and condense the announcement into two sentences."

If the system simply concatenates every record from persistent storage and sends it to the model verbatim, two problems appear immediately:

  • Resending everything blows up the context window and dilutes key constraints: Obsolete drafts and bulky tool outputs repeatedly consume the model's context window, driving up latency and cost, triggering context-length overflow errors, or burying Turn 1's "UTC time" rule in noise.
  • Blind truncation drops constraints or breaks wire protocols: Simply slicing the "last K messages" can both drop Turn 1's core requirements and slice right between a tool call (ToolCall) and its execution receipt (ToolResult), immediately causing a model API protocol error.

Therefore, "how much history is saved in storage (State / Transcript)" and "how much content is actually sent to the model in this request (Context)" must be separated into two distinct responsibilities. The Context Manager is dedicated to filtering and assembling each request before calling the model, selecting from candidate history, current task messages, reference materials, and tool definitions within the input budget.

Data Object What It Stores Maintained By Sent in Full on Every Turn?
Execution Transcript (Transcript / SessionLog) Strictly ordered on-disk user prompts, full model responses, tool calls, and actual receipts Session & State Layer (State) No (retained in storage as the complete audit and recovery record)
Structured Task State (Task State) Current goal, confirmed constraints (e.g., UTC rule), todo items, and check statuses Application or Task State Layer Only currently active items are sent
External Artifacts (Artifacts) Workspace files, long logs, and other concrete data artifacts Filesystem & Artifact Storage Reference paths, summary previews, or relevant snippets sent on demand
Long-Term Memory (Memory) Project facts and user preferences reused across sessions Memory Module (Memory) Filtered and injected by user/project scope
Current Context (Context) System instructions, selected messages, reference snippets, and tool definitions actually sent in this request Context Manager Yes (directly forms a single ModelRequest)

Whether you use whole-block trimming, tool output offloading, or history summarization, Context Manager must uphold four baseline invariants:

  • Separate raw records from model input (read-only, side-effect-free): Filtering, trimming, or compacting only produces an "input view for the current model call" and never overwrites or deletes the complete history in session storage.
  • Keep calls and receipts strictly paired (protocol integrity): In the filtered message sequence, every ToolCall must appear paired with its corresponding ToolResult, never leaving orphaned calls or receipts.
  • Account for the full encoded payload in the budget: Budget accounting must cover system instructions, selected history, current task messages, tool schemas, and protocol continuation data (continuation), while reserving output headroom for the model's reply (max_output_tokens).
  • Preserve source roles and permission boundaries: Data entering the context from different sources must keep its original role (never elevating file contents or old messages into system instructions), and past authorizations in history never alter current Policy checks; if required content alone exceeds the budget, fail explicitly before calling the model rather than silently dropping required constraints.

2. Black-Box Interaction & Call Timing: Who Initiates, Who Decides, Who Executes?

Inside the execution loop, Context Manager plugs in as a pure decision module right before Runner calls Model.invoke() on every step, exchanging two core data structures with neighboring modules:

  • Input (candidate materials & budget config): System instructions, candidate historical blocks grouped by task, prompts/responses/receipts generated so far in the current task, available tool definitions (schemas), and the input token budget.
  • Output (current request view or overflow error): The assembled message sequence within budget plus a selection decision manifest (recording which blocks were kept, which were omitted or compacted, and the final token count); if fixed required content alone exceeds the budget, it returns an explicit unbuildable reason.

Note the call timing: context is not filtered just once when the user prompt arrives—it must be re-evaluated before every single model request inside the loop. After Step 1 calls a tool to read a file within the same task, the large returned receipt immediately increases the input size for Step 2's model request.

3. Core Mechanism Breakdown: How Open-Source Harnesses Solve Three Shared Problems

To safely turn candidate data into a single model request, every Agent Harness must solve three concrete problems in order: where to transform the view, how to account for the budget, and where to cut safely.

Problem 1: How Are Persistent Records Transformed into a Model Request View?

  • pi (Explicit three-step pipeline): Strictly separates "storage records → context messages → provider wire protocol" into three layers. buildSessionContext in session/context.ts first reconstructs the active branch's messages from the JSONL entry tree; inside streamAssistantResponse in agent-loop.ts, it first calls transformContext to filter or inject at the Agent message layer, and finally calls convertToLlm to encode into the specific provider's request format.
  • Codex (Rollout reconstruction & runtime context): RolloutRecorder appends full interactions to JSONL; on resume or request, model_context.rs (load_latest_model_context) and rollout_reconstruction.rs extract the active ResponseItem sequence based on rollback or compaction markers.
  • Deep Agents & AgentScope Java (Pre-request middleware interception): Deep Agents intercepts model calls and replaces oversized history inside wrap_model_call in summarization.py; AgentScope Java checks budgets and invokes its compactor before requests in CompactionMiddleware.java.

Problem 2: How Do We Measure Size and Decide When to Trigger Trimming or Compaction?

"Keep only the last 5 conversation turns" cannot prevent overflows—a single receipt from reading a large file can fill the entire context window. A reliable implementation must account in tokens and reserve output headroom for the model's reply:

Available Input Budget = Model Context Window (contextWindow) - Max Output Reserve (reserveTokens / max_output_tokens) - Safety Margin

  • pi (Window minus reserved tokens): shouldCompact(contextTokens, contextWindow, settings) in compaction.ts checks whether current context tokens exceed contextWindow - settings.reserveTokens, reserving space ahead of time for the current generation.
  • Deep Agents (Proportional threshold from model window): compute_summarization_defaults in summarization.py automatically sets the compaction trigger token threshold and retained tail budget based on the model's maximum context window.
  • Codex (Configurable compaction threshold): Exposes the context window and automatic compaction token threshold in its Configuration Reference.

Problem 3: Where Can We Cut Without Breaking Tool Call and Receipt Pairing?

Model protocols require every assistant ToolCall to be followed by its matching ToolResult with the same call_id. Slicing arbitrarily by message count leaves orphaned calls or half-receipts that the model API will immediately reject:

  • pi (findCutPoint avoids toolResult boundaries): compaction.ts accumulates the retained tail backward from the newest message (keepRecentTokens) and, in findCutPoint, explicitly enforces that a cut point must never start on a toolResult message—it must align with a complete interaction boundary, preserving everything after the cut point verbatim as retainedTail.
  • AgentScope Java (Paired pruning verification): ConversationCompactor.java explicitly verifies and guarantees that tool calls and tool results are retained or removed in pairs when pruning old tool outputs and compacting history.
  • This Project's Stage 4 MVP (Using a completed Turn as the minimal trimming unit): Directly reuses the closed user-task boundaries (Turn) validated in Stage 3. A completed Turn encapsulates "user prompt → all tool calls and receipts → final answer" as a whole; retaining or omitting entire Turn blocks naturally guarantees that no call_id pair is ever split apart.

4. Comparing Design Options: 7 Strategies When Content Exceeds the Budget

When candidate content exceeds the input budget, you can choose from the following strategies progressively based on your actual bottleneck (think of them as a composable toolkit rather than a checklist to build all at once in v1):

A. Full History Concatenation (Baseline Control)

  • How it works: Send all completed history and current messages in chronological order along with system instructions and tool definitions (Stage 3's current behavior).
  • Best for: Short conversations with few turns and brief tool outputs, or as a baseline for diagnosing whether a model error was caused by trimming away needed context.
  • Trade-offs & limitations: Input size grows linearly with turns and tool calls, inevitably hitting context window limits on large files or long conversations.

B. Deterministic Trimming by Complete Interaction Block (Stage 4 MVP Choice)

  • How it works: Lock system instructions, explicitly pinned required history, and current task messages, treating all other completed historical tasks (Turn) as optional blocks; when over budget, omit optional Turn blocks from oldest to newest until the budget is met.
  • Best for: Multi-turn daily Q&A, self-contained phased tasks, and the foundational budget guardrail before adding long-task mechanisms.
  • Trade-offs & limitations: Zero extra model calls, 100% deterministic behavior, and 100% verbatim fidelity inside kept blocks; however, if early requirements are neither pinned nor extracted into structured task state, very early constraints will be dropped along with old turns.

C. Large Tool Result Offloading & Preview (Offloading)

  • How it works: When a tool returns a huge file or long log, save the full content to the workspace or artifact store and keep only the execution status, head/tail preview, file path, and pagination instructions in context; in later turns, large write arguments that have already been flushed to disk can also be replaced with compact references.
  • Best for: Tasks that frequently read long documents, large source files, or build logs.
  • Trade-offs & limitations: Drastically cuts single-step volume noise without extra model calls; however, you must provide a reliable paginated read tool (truncating without a way to read the rest permanently hides middle details) and record content hashes in case the underlying file changes.

D. History Summarization + Recent Verbatim Tail (Compaction / Summarization)

  • How it works: At a safe cut point (such as findCutPoint), ask a model to condense earlier interaction blocks into a structured summary (retaining goals, confirmed constraints, key findings, failed attempts, and file references) and combine it with "recent verbatim blocks (retainedTail) + current task messages."
  • Best for: Complex long tasks that evolve the same deliverable across dozens of turns.
  • Trade-offs & limitations: Adds extra model call latency and token cost; repeated summarization can accumulate drift (e.g., dropping "UTC time" or misstating "do not overwrite yet"), so hard constraints should live in structured state and summarization must have a fallback strategy on failure.

E. On-Demand Retrieval & Progressive Disclosure (Retrieval / Progressive Disclosure)

  • How it works: Put only a brief index, document titles, or Skill summaries in the initial context, dynamically fetching relevant snippets during execution via keyword search (e.g., FTS) or vector retrieval based on the current query.
  • Best for: Projects with large reference libraries, specification docs, or many extension tools where any single turn only needs a tiny fraction.
  • Trade-offs & limitations: Only supplements external static/semi-static reference material and cannot replace the execution state of the active conversation; carries retrieval-miss risk, and both indexing and reading must obey Policy workspace boundaries.

F. Isolated Sub-agent Context Windows (Sub-agent Isolation)

  • How it works: Delegate step-heavy code searches, log investigations, or independent reviews to a sub-agent with its own isolated context window; the main Agent receives only the distilled conclusion and evidence citations (see Orchestration).
  • Best for: Sub-problems with long exploratory trails and noisy intermediate output but concise final conclusions.
  • Trade-offs & limitations: Increases multi-agent coordination and verification overhead; if the sub-agent omits critical context, the main Agent may not notice.

G. Provider-Native Server-Side Compaction (Provider-Native Compaction)

  • How it works: Call a model provider's dedicated compaction endpoint (such as OpenAI Responses API Compaction), which returns opaque compacted continuation data to pass into subsequent turns.
  • Best for: Scenarios standardized on a single model provider that want to avoid maintaining custom summarization prompts.
  • Trade-offs & limitations: Compacted payloads are opaque, cannot be partially edited, and cannot be reused across models or providers; you must still keep local raw JSONL records for auditing and model switching.

Do not confuse Prefix Caching with Context Budget Management: Keeping system instructions and leading prefixes stable lets model providers hit prefix caches, reducing repeated compute cost and time-to-first-token; however, cached tokens still count 100% toward the current request's context window limit—prefix caching never replaces input token accounting and trimming.

7. Scenario Walkthrough: How Different Strategies Behave on the Same Long Task

Returning to our opening scenario, suppose a 30-turn task goes through four key milestones:

  • Turn 1 (User): "Write an event announcement in Chinese, use UTC for all timestamps, and do not overwrite the original file before the final draft is approved."
  • Turn 10 (Tool receipt): Reads 50 pages of past event records and long logs.
  • Turn 20 (User): "Format the schedule at the end of the announcement as a three-column table."
  • Turn 30 (User): "Follow the earlier rules and finish the final announcement."

How different strategies perform in this scenario:

  • Whole-block trimming only (without pinning required blocks): Preserves Turn 20's three-column table requirement and recent tool pairs intact, but drops Turn 1's "UTC time" rule because it is the oldest block; improvement: support explicitly pinning required historical blocks (such as keeping T1) or extracting structured task constraints.
  • History summarization only: Condenses the first 20 turns into a short paragraph, but the summarizer model might drop "UTC time" or misstate "do not overwrite the original file yet" as "prepare to write to the original file" (which is why, alongside preserving key requirement text verbatim, write operations must still be gated by an independent Policy).
  • Large tool result offloading only: Eliminates the massive footprint of Turn 10's 50-page log, but cannot stop the continuous growth of the 30 conversation turns themselves.
  • External document retrieval only: Finds past event snippets by keyword, but has no idea the user verbally changed the table format in Turn 20.
  • Staged combination: First implement "budget accounting + required block protection + deterministic whole-Turn trimming" in Stage 4 to guard the context window baseline; then in Stage 6 add "large result offloading with previews" for long logs or "history summarization" for extended exploration when needed.

8. Current Project Choice & Evolution Roadmap

  • History source: SessionLog.history_turns() reconstructs complete completed turns from JSONL; in-memory history is also supported. Original records remain separate from each model input.
  • Currently implemented (Stage 4 MVP: Context Management & Budgets): We choose shared protocol encoding for offline size estimates + output reserve calculation + required content protection + deterministic oldest-first trimming by complete user task (Turn) + re-verification before every model.invoke() + returning a selection decision manifest.
    • Why this combination for v1: Reusing Stage 3's closed Turn boundaries guarantees 100% intact ToolCall and ToolResult pairing; pure functional logic consumes zero extra model tokens for summarization, behaves deterministically, and is easy to hand-verify and boundary-test locally.
  • Measurement scope: UTF-8 bytes of input JSON provide a conservative estimate, not an exact provider token count. Configure the window allowance and safety margin or replace the meter for a specific model; see Stage 4.
  • Future on-demand extensions: Large tool result offloading and paginated reading, history summarization (Compaction), on-demand retrieval (RAG), and cross-session long-term memory (Memory).

9. Expected Outcomes

Once Context Manager is wired into the loop, expected outcomes:

  • Zero damage to raw records: Regardless of how many old turns are omitted from the current request, the full original history in SessionLog files or memory remains untouched.
  • Strictly paired calls and receipts: Every tool call (ToolCall) and tool receipt (ToolResult) in the filtered input is closed in pairs, never triggering protocol pairing errors.
  • Protected required constraints: System instructions, explicitly pinned required history (such as Turn 1's UTC requirement), and the currently executing task's messages are prioritized; if required content alone exceeds the budget, the run fails explicitly before calling the model.
  • Dynamic in-loop re-verification: After a tool returns a large receipt within the same task, the next step automatically recounts and re-filters before invoking the model, preventing mid-loop window overflows.
  • Transparent, auditable selection decisions: Every build returns the budget cap, kept block list, omitted block list, and final token count, making it immediately clear whether "information was never sent to the model" or "it was sent but the model ignored it."
