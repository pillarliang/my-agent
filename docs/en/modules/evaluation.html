Module Principles · Offline Verification & Sandbox Assertions

Evaluation: Agent Benchmarks & Sandboxes

1. Starting Problem: Why "Executed Without Error" != "Task Passed"

When iterating on an Agent, the most frequent failure mode is not a crash, but silent divergence where execution terminates normally without fulfilling the goal:

  • User: "Write unit tests for the math utility function and ensure they pass."
  • Model: "I have written the unit tests in tests/test_math.py and verified that all tests pass."
  • (System action): Runner stops normally, HTTP 200, zero unhandled exceptions.
  • (Physical disk reality): Checking the generated file reveals assertions written as assert True, or the model edited the implementation function to make tests trivially pass!

This demonstrates: Runtime Observability only proves execution didn't throw errors; it cannot prove deliverables meet functional requirements.

To quantify capabilities, benchmark prompt modifications, and prevent regressions during model upgrades, a dedicated **Evaluation Module** is required.

Expected Outcomes:

  • Deterministic Artifact Assertions: Validate physical disk diffs (Git Diff) and automated test suite passes rather than trusting the model's text claim.
  • Strict Sandbox Isolation: Run evaluations in isolated temporary sandboxes that allow arbitrary file edits and roll back 100% cleanly.
  • Comparable Benchmarking: Pin task datasets, initial snapshots, and scorers to compare Pass@k across models and prompt versions.

2. Three Inherent Characteristics of Agent Evaluation

Traditional LLM evaluation focuses on static single-turn text similarity (BLEU/ROUGE or LLM judges assessing factual hallucination).

In contrast, an Agent is a stateful system interacting with physical environments, presenting three core realities:

  1. Environment State Mutations as Core Deliverables:
    • An Agent's value lies in solving physical problems (fixing bugs, updating configurations, modifying schemas).
    • Evaluation must assert whether the physical State Diff in the sandbox matches the expectation.
  2. Path Equivalence:
    • Different models or different samplings may choose distinct valid tool sequences to solve the same problem (e.g., discovering files via list_files vs. search_text).
    • Assertions must not rigidly enforce tool call order, but instead verify final environment state and invariant constraints.
  3. Mandatory Sandbox Isolation:
    • Agents execute write actions and external commands. Running batch evaluations directly on developer workstations risks contaminating repos or deleting files.
    • Tasks must execute in disposable temporary directories or lightweight Docker containers, reset after each case.

4. Evaluation Pipeline & Sandbox Closed Loop

An Agent evaluation harness operates as a four-stage closed loop: "Sandbox Setup → Autonomous Run → Multi-tiered Scoring → Reporting & Reset":

The Four Standard Pipeline Stages

  • Stage 1: Fixture & Sandbox Setup:
    • The evaluation harness loads a test case containing the task prompt, environment dependencies, and expected outcomes.
    • An isolated sandbox is seeded with initial code, configs, or reproducible bug fixtures.
  • Stage 2: Agent Autonomous Execution:
    • The Agent Runner points to the sandbox workspace, receives the task prompt, and begins its execution loop.
    • Yields two primary artifacts: Sandbox Environment State Mutations (State Diff) and the Execution Trajectory.
  • Stage 3: Multi-tiered Scorers:
    • State Diff Checkers: Run test suites (e.g., pytest), verify artifact existence, and validate file contents (100% deterministic).
    • Trajectory Efficiency Scorers: Inspect step count budget usage, detect redundant tool calls, and flag endless loop oscillations.
    • Semantic LLM-as-a-Judge: For open-ended deliverables, a judge model evaluates quality against strict scoring rubrics.
  • Stage 4: Reporting & Sandbox Reset:
    • Aggregate case metrics: Pass@1, Pass@k, average latency, and token consumption.
    • Tear down and purge the sandbox, ensuring clean state before evaluating the next test case.

6. Practical Implementation: Minimal Agent Eval Harness

test_agent_eval.py
import tempfile
import shutil
from pathlib import Path
from dataclasses import dataclass
from typing import Dict, Any, List

@dataclass
class EvalCase:
    name: str
    task_prompt: str
    fixtures: Dict[str, str]       # Initial sandbox files and contents
    expected_files: Dict[str, str] # Expected output files and required keywords
    max_steps: int = 8             # Budget limit

class AgentEvaluator:
    """Agent offline evaluation runner with isolated sandbox support."""
    def __init__(self, runner_factory):
        self.runner_factory = runner_factory

    def evaluate_case(self, case: EvalCase) -> Dict[str, Any]:
        # 1. Create a clean, isolated temporary sandbox directory
        sandbox_dir = Path(tempfile.mkdtemp(prefix="eval_sandbox_"))
        try:
            # Seed initial environment fixtures
            for rel_path, content in case.fixtures.items():
                target_file = sandbox_dir / rel_path
                target_file.parent.mkdir(parents=True, exist_ok=True)
                target_file.write_text(content, encoding="utf-8")

            # 2. Bind the Agent to the sandbox and execute
            runner = self.runner_factory(workspace=sandbox_dir)
            run_result = runner.run_task(case.task_prompt)

            # 3. Multi-tiered scoring and assertions
            report = {
                "case_name": case.name,
                "passed": True,
                "failures": [],
                "steps_taken": len(run_result.trajectory),
                "token_usage": run_result.total_tokens,
            }

            # Check A: Step budget enforcement
            if len(run_result.trajectory) > case.max_steps:
                report["passed"] = False
                report["failures"].append(f"Budget exceeded: took {len(run_result.trajectory)} steps (max: {case.max_steps})")

            # Check B: Environment state assertions (real file checks)
            for exp_path, keyword in case.expected_files.items():
                real_file = sandbox_dir / exp_path
                if not real_file.exists():
                    report["passed"] = False
                    report["failures"].append(f"Expected file was not created: {exp_path}")
                elif keyword not in real_file.read_text(encoding="utf-8"):
                    report["passed"] = False
                    report["failures"].append(f"File {exp_path} missing required keyword: '{keyword}'")

            # Check C: Trajectory loop detection
            actions = [str(step.action) for step in run_result.trajectory if step.action]
            if len(actions) != len(set(actions)):
                report["failures"].append("Trajectory warning: detected duplicate identical tool calls (looping)")

            return report

        finally:
            # 4. Clean up sandbox to ensure zero state leakage
            shutil.rmtree(sandbox_dir, ignore_errors=True)
