Quality: Observability & Evaluation

1. Starting Problem: Why Does "Loop Finished Normally" Not Equal "Task Completed Successfully"?

When the model reads a file and outputs "The report has been generated," the system faces two distinct questions:

  • Observability answers "What actually happened during execution?": Which tools were called, what arguments were passed, what receipts came back, how many tokens were consumed, and how long each step took.
  • Evaluation answers "Did the task deliverable actually meet the bar?": Does the generated report truly contain the required fields, do the cited numbers match the source text, and were all constraints respected?

Expected Outcomes:

  • Strictly separate statuses: Never conflate "tool call succeeded," "loop terminated normally," and "business deliverable passed verification" into a single status.
  • Tie observability to concrete evidence: Every trace or log entry links back to a specific Run ID, step, and actual tool receipt.
  • Reproducible, comparable evaluations: Evaluations pin task inputs, workspace snapshots, and grading criteria, clearly distinguishing "deterministic program unit tests" from "live model quality evaluations."

2. Module Collaboration: How Do Observability and Evaluation Plug into the System?

  • Observability consumes execution records read-only: Step events from Runner, token usage and errors from Model, and actual receipts from Tools are persisted by the State recording layer and then read or exported by the observability module; observability must never re-execute tools just to fill in a dashboard.
  • Evaluation is driven by a dedicated harness entry point: A test or evaluation runner pins the task and initial file snapshot, invokes the application to complete a run, and passes the final answer and actual workspace artifacts to a checker (Checker) to produce a verdict, coverage scope, and supporting evidence.
  • Feedback-driven repair requires explicit authorization: Feeding a check failure back into Runner for automatic retry/repair requires configuring an explicit retry budget and permissions; observability or checkers never automatically possess the authority to restart execution on their own.

3. Comparing Observability Approaches

Observability approaches address "how runtime execution is correlated, stored, and inspected" (they do not replace business deliverable evaluation):

A. Structured Local Events

  • How it works: Record key steps, stable IDs, and essential metadata sequentially in local JSONL files or SQLite.
  • Best for: Single-machine development debugging and replaying execution history with zero external dependencies.
  • Caveats: Execution records used for recovery must never be dropped by sampling—keep them distinct from sampleable diagnostic logs (see State).

B. Distributed Traces, Spans & Metrics (OpenTelemetry)

  • How it works: Use a Trace to connect an entire request and Spans to record parent-child relationships, start/end timestamps, and statuses across model calls, tool executions, and sub-tasks (see the OpenTelemetry Trace Specification).
  • Best for: Pinpointing latency bottlenecks and error chains across multiple services and Workers.
  • Caveats: Token usage and call counts work well as Metrics, but never put full file contents or secrets into metric labels (which causes both sensitive data leaks and high-cardinality label explosion).

C. Dedicated Agent Observability & Evaluation Platforms

  • How it works: Export call trees, prompt versions, and evaluation results through an adapter to reuse an external platform's visualization UI and dataset management.
  • Best for: Team-wide collaborative debugging and side-by-side multi-version comparisons.
  • Caveats: Evaluate data-egress compliance and vendor coupling costs; also remember that a green call trace (no runtime exceptions) in the platform UI does not mean the business deliverable passed quality checks.
Approach Best Scope Primary Benefit Primary Cost
Local structured events Single-machine learning & inspecting runs Transparent, zero external dependencies, easy to verify Limited cross-process aggregation and visualization
OpenTelemetry Cross-service & dedicated Workers Standardized distributed tracing and metric aggregation Context propagation, sampling, and semantic convention upkeep
Dedicated Agent platform Team debugging & eval dataset management No need to build custom visualization UIs Data hosting compliance and vendor coupling

4. Open-Source & Industry Observability Practices

  • OpenAI Agents SDK (Official Docs): Its observability guide builds a complete call tree around model generations, tool calls, Handoffs, and Guardrails rather than logging only the final prompt and answer.
  • AgentScope Java (Official Docs): Session Log correlates persistent execution records, user-readable history, and live event subscriptions so a refreshed page can catch up by Run ID.
  • OpenTelemetry GenAI Semantic Conventions: The original GenAI page has migrated to the dedicated semantic-conventions-genai repository; pin the semantic convention version when integrating.

5. A Three-Tier Testing & Evaluation Pyramid

  • Tier 1: Local component unit tests: Pass arguments, temporary files, and local storage directly to deterministically verify argument validation, permission interception, context trimming, and session read/write logic.
  • Tier 2: Local wire-protocol contract tests: Point the real model SDK at a local HTTP test server returning canned responses to deterministically verify tool call pairing, refusals, truncation, and network error handling (consumes zero external tokens and does not measure remote model intelligence).
  • Tier 3: End-to-end real-task evaluations: Pin a task suite, initial workspace snapshots, a live model, and result checkers, measuring pass rates, tool call trajectories, token usage, and latency across multiple runs so a single lucky run is never mistaken for long-term reliability.

6. Current Implementation & Unimplemented Scope

  • Implemented (as of Stage 3):
    • Execution records & progress: Runner prints step-by-step console progress, ModelResponse preserves model-returned token usage, and JSONL session files record complete messages and tool receipts.
    • Deterministic test suite: pytest covers Tier 1 local component unit tests and Tier 2 local HTTP wire-protocol contract tests (see Stage 3 Checks and Verification Scope).
  • Not Yet Implemented (Optional Future Extensions): OpenTelemetry Trace export, metric aggregation, external observability platform adapters, standalone artifact checkers (Checker), batch real-task evaluation suites, and evaluation-driven automatic repair retries.
