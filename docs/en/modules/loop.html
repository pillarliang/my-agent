Module Principles & Design Options

Loop / Runner: Control How a Task Continues and Stops

1. Starting Problem: How Do We Control When a Task Continues and When It Stops?

When a user submits a task that requires multiple steps, the program needs a state machine with explicit stopping conditions to drive the entire process. This is the core responsibility of Loop / Runner:

  • Construct input and invoke the model: Gather system instructions, available history, current messages, and tool definitions, then call the model interface.
  • Decide whether to continue the loop: If the model proposes tool calls, dispatch them to the tool system, save the actual receipts, and start the next model request; if the model returns a valid final answer directly, terminate the loop and return the result.
  • Enforce budget and error boundaries: Check the step limit (max_steps), model errors, or cancellation signals at every step to prevent infinite loops or continuing in a broken state.

Loop: Continuation, Stopping & Controlled Repair Flow (General control pattern · Automatic verification repair is not yet wired up)

When designing Runner, you must strictly distinguish three levels of "completion":

  • Single model request completed: The model service returned a normal response (which may still contain tool calls, meaning the task is not finished).
  • Runner loop finished normally: The model stopped calling tools and gave a final answer (representing completion of the conversational interaction loop).
  • Business deliverable passed verification: The generated report or code passed validation by an external checker (you cannot declare a deliverable qualified merely because the model claims "it is done").

2. Collaboration Boundaries with Related Modules

Runner is the scheduling hub that connects all core modules, but it only decides "when to advance to the next step," delegating specialized work to dedicated modules:

  • Load memory & assemble context (Runner ↔ Memory / State / Context): Lock an immutable project memory snapshot (Memory) from the workspace at startup, read completed history from the session module at runtime, and pass them together with tool schemas and token budget to Context Manager to assemble the active request view.
  • Invoke the model (Runner → Model): Submit ModelRequest and receive ModelResponse. If the model errors out, truncates output, or refuses to answer, Runner records the failure and stops immediately.
  • Dispatch tool calls (Runner → Tools ↔ Policy / Extensions): Pass each ToolCall to the tool system (supporting local built-in tools and external MCP tools) for validation and Policy authorization before execution. When an ordinary tool execution fails or is denied by Policy, a real ToolResult receipt is returned to the model rather than crashing the entire task.
  • Persist records & crash recovery (Runner ↔ State): User prompts, model responses, tool receipts, and task completion statuses are written to session records in real time at each step; on sudden crash or reboot, Runner loads checkpoints, verifies unclosed action states, and safely resumes execution.

3. Control Flow Options

Here we compare who decides the next step. Currently we use Approach A's autonomous tool loop; Approach B's in-loop plans, C's hierarchical planner/executor, and D's explicit workflow graphs are not yet implemented. Persistent records, context budgets, and permission checks can be combined orthogonally with any of these control flows.

A. Autonomous Tool Loop

The program only fixes the "Model → Tool → Model" skeleton, while the model chooses the next step based on actual feedback. It is simple to implement and well-suited for tasks with unknown paths that require search and trial-and-error.

Its trade-off is path instability: the model may explore repetitively or stop prematurely. You need limits on steps, tool calls, time, and cost, along with external acceptance checks. Stage 0's single loop uses this basic control pattern; additional budgets and verification are added on demand.

B. Updatable Plan Within a Single Loop

Add a structured plan or an update_plan tool so the model maintains goals, steps, and current progress while still selecting concrete actions inside the same loop. This primarily improves long-task state tracking and user-visible progress without requiring a separate Agent invocation per step.

The benefit is explicitly surfacing dependencies and remaining work; the trade-off is that plans can go stale or the model may prematurely check off items as done. Plan state must be kept separate from actual tool receipts and verification results—never treat "all Todo items checked" as a substitute for acceptance testing.

C. Separate Planner and Executor

A planner first generates tasks with dependencies, and an executor claims the current task and adjusts the plan based on execution feedback. Implementation requires plan versioning, step statuses, result schemas, and replanning triggers.

This fits tasks with relatively stable steps and differentiated executor capabilities, making it easier to optimize planning and execution independently. The trade-offs are extra model calls, information loss during handoff, and stale plans; if every minor hiccup triggers a full replan, the cost can exceed an autonomous loop. Try Approach B first, then decide whether separate roles are needed based on real failures.

D. Explicit Graph or Workflow State Machine

The program defines required nodes and transition conditions—for example, "Read docs → Agent generates candidate → Check → User approval → Publish." An autonomous Loop can still run inside individual nodes. The Graph governs business step ordering and transitions, while the Loop inside a node chooses concrete operations based on model feedback.

This fits fixed approvals, conditional routing, and checkpointed waiting; the trade-offs are maintaining state schemas, node versions, and recovery rules. A Graph does not require multiple Agents, nor does it automatically provide sandbox isolation or guarantee idempotent re-execution. For the relationship between control flow and durable execution, see State.

Approach Where Decisions Happen Best Suited For Main Trade-off
Autonomous Loop Model decides step by step Short tasks with unknown paths Hard to predict action count
In-Loop Plan Model decisions + structured progress Longer tasks toward a single goal Plan updates and fact verification
Planner & Executor Hierarchical decisions and feedback Decomposable tasks with clear dependencies Extra calls and handoff overhead
Graph Program controls transitions between key steps Fixed business workflows and approvals Maintaining state, nodes, and recovery

These approaches can be nested—they are not a product ranking from "basic" to "advanced." Anthropic's control patterns likewise distinguish workflows from dynamic Agents; your choice should be guided by how predictable the task is and what actually fails in practice.

4. How Production Systems Organize the Loop

OpenAI Agents SDK (Official Docs). The Running Agents guide exposes a core loop: invoke the current Agent's model, execute tools, and switch executors on Handoff until a final output is reached. Streaming changes how events are received and processed without altering this fundamental loop. Here "final" is still the SDK's stopping condition; applications can run additional business verification afterward.

LangChain / LangGraph (Official Docs). create_agent middleware runs inside its compiled Graph, allowing control logic to be inserted before/after model requests and tool calls; the entire Agent can also be embedded inside an outer workflow graph. This illustrates combining "model-selected actions on the inside" with "program-controlled step ordering on the outside."

AgentScope Java (Pinned Official Docs). Plan Mode explicitly separates the planning phase from the execution phase and persists mode state. A key takeaway is letting the mode govern actual tool authorization rather than merely asking the model in the prompt to "be read-only right now."

5. Where to Place the Verification Loop

Post-termination verification is the easiest to understand: after the model gives its final explanation, a checker inspects the artifacts and the program reports whether the specified checks passed or failed. Implement post-termination checks first before considering in-loop repair.

Automatic repair after verification generates structured feedback on failure and re-enters the execution loop. Feedback should include the check name, target version, actual error, and allowed repair scope. Repairs must continue consuming the original task's total budget under a separate retry cap—never bypass limits by spawning unbounded new Runs.

In-process checks immediately validate invariants after certain actions complete, such as parsing a schema right after writing a config file. They catch issues earlier, though passing a local check does not guarantee the final goal is met. All three check timings can be combined as long as the checked target and timing are clearly recorded.

6. Stopping Conditions, No-Progress Detection & Crash Resumption State Machine

A. Stop Reason Classification & No-Progress Detection

Distinguish between ordinary tool failures, model errors, budget exhaustion, cancellation, state corruption, and verification failure. Ordinary tool failures can be returned to the model as receipts for self-correction; state corruption must halt the program immediately rather than letting the model guess the next database operation.

Repeated calls are not always bugs: polling an external job naturally reads the same resource repeatedly. No-progress detection should evaluate the tool name, normalized arguments, result summary, external resource version, and repeat count together with polling intervals; comparing arguments alone easily false-positives on legitimate waiting. For long waits, it is better to persist the wait condition and release the worker (see Orchestration).

B. Runner Crash Resumption State Machine

In production long-running tasks or automated agents, processes may abort at arbitrary steps due to network drops, OOM, or host restarts. When resumed via dedicated recovery entry points, the Runner cannot naively trigger fresh model requests from scratch, but must follow a checkpoint-based controlled recovery state machine (detailed storage design in State Module: Safe Interruption Recovery):

  1. Load Checkpoint Context: Runner loads the latest checkpoint from State, retrieving unclosed tool invocation IDs.
  2. Reconcile Action Execution Status:
    • If status is completed: Directly reuse existing ToolResult without re-running the tool, assembling the next ModelRequest immediately.
    • If status is not_dispatched or read-only: Re-evaluate against the active Policy, and safely execute upon approval.
    • If status is unknown with physical side effects (e.g. file writes): Runner must block automatic advancement. Inspect disk state or idempotency receipts first; if unverifiable, pause the loop and raise an interruption exception for human-in-the-loop (HITL) review.
  3. Enforce Original Task Budget Limits: Resumed runs continue using the remaining max_steps limit and token budget, preventing infinite retries from bypassing step constraints.

7. Current Project Choice & Unimplemented Scope

  • Current project choice: Uses a single-Runner autonomous tool loop (defaulting to at most 4 model requests per task). Runner reads completed history from the same session, appends the current prompt and tool declarations to build a ModelRequest, and finishes when the model returns a non-empty answer with no tool calls; it stops immediately with an error on refusal, truncation, empty output, model error, or step exhaustion (see Stage 1 and Stage 3).
  • Not yet implemented (extend on demand): In-loop structured plans, separate planner/executor, explicit Graph state machine, dead-loop no-progress detection, automatic post-check repair, and user cancellation protocol.

8. Follow-up Exercise & Expected Outcomes

If you later introduce a "result check + bounded auto-repair" loop, run a deterministic checker after termination and, on failure, allow the model one repair attempt within the original task's remaining budget and permissions.

Expected Outcomes:

  • Shared budget without overruns: Automatic repair shares the exact same total step limit, time limit, and Policy permissions as the initial execution, never bypassing budgets by spawning unbounded sub-loops.
  • Complete failure trail preserved: The initial output, checker error evidence, repair tool calls, and final conclusion are all written to the session record in strict order.
  • Objective pass/fail determination: Final qualification is decided strictly by the checker result, never skipping or overriding verification just because the model claims "fixed."
