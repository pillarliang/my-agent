Module Principles & Design Options

Model: Adapt Model Services & Wire Protocols

1. Starting Problem: Why Isolate Model Communication into Its Own Module?

Calling a model service requires handling API keys, endpoint URLs, SDK client connections, and provider-specific message encoding formats. If those protocol details are written directly inside the main Runner loop, switching model providers or upgrading wire protocols (e.g., migrating from Chat Completions to the Responses API) forces a rewrite of the entire loop control logic.

Therefore, we isolate model communication into the Model module using two core abstractions to contain change:

  • Unified invocation service (LLMService.invoke()): Internally manages API keys, Base URLs, and SDK client lifecycles; externally exposes a single request entry point to Runner.
  • Protocol adapter (Adapter): Translates between the project's unified internal data structures (ModelRequest / ModelResponse) and a specific provider's wire format. Switching model protocols only requires swapping the adapter.

2. Black-Box Interaction: How Does Runner Call Model?

Using a tool call to read a file as an example, a single interaction round between Runner and Model flows as follows:

  • Runner → Model: Submits a ModelRequest containing system instructions, the current message chain, available tool schemas, and maximum output limits.
  • Inside Model: Encodes internal messages into the SDK request format, calls the remote model endpoint, and decodes the returned payload into a unified ModelResponse.
  • Model → Runner: Returns a ModelResponse containing answer text or a list of ToolCall objects; if a network failure, authentication error, or output truncation occurs, it raises an explicit ModelError.

Responsibility boundaries with neighboring modules:

  • Does not filter history on its own (division with Context): Model only encodes and sends the exact messages passed to it, never querying session files or trimming history behind the scenes.
  • Does not execute tools directly (division with Tools): Model only receives tool declarations (ToolSpec) and decodes model-proposed ToolCall items; actual argument validation, authorization, and execution belong to the Tools module.
  • Preserves full responses and token usage (division with State): ModelResponse retains the full stop reason, token usage, and protocol continuation data, which Runner writes to session records.
When reading source code: What else is stored inside ModelResponse?

Beyond answer text and tool calls, ModelResponse preserves the generation stop reason (stop_reason), token usage (usage), and protocol continuation data (such as model reasoning items) that must be passed back verbatim in subsequent rounds. If a response is truncated due to hitting the output token limit (length) or refused by safety policies, the loop raises an error and stops immediately to prevent executing incomplete tool arguments.

Expand the encoding, request, and decoding pipeline

Tool arguments are kept as raw JSON strings at the adapter layer and handed off to the tool system for unified parsing and validation.

On-demand reference: Protocol differences, adapter patterns, streaming & retries

3. How Do Model Wire Protocols Differ?

The Chat Completions protocol organizes interactions as a list of messages: the tool_calls array on an Assistant message pairs with subsequent tool-role messages via tool_call_id. The Responses protocol represents text, function calls, and reasoning items as Output Items, pairing function execution outputs via call_id.

See Alibaba Cloud Function Calling Docs and OpenAI Function Calling Docs: multi-turn tool calling requires not only returning function outputs, but also preserving complete call records and reasoning continuation items per provider protocol.

4. Three Design Dimensions for Model Adaptation

  • Internal message representation: Passing a single vendor's SDK objects straight through is fastest initially but locks the loop to that vendor; defining unified internal ModelRequest / ModelResponse types converted by an adapter decouples Runner from wire protocols.
  • Service connection style: Choose between native SDK adapters, OpenAI-compatible endpoints, or a unified model gateway.
  • Ownership of loop control: When a local Runner owns the loop, Model performs a single-turn request each time; switching to a hosted Agent API requires repartitioning session state and tool execution ownership.

5. Open-Source Implementation References

  • pi (agent-loop.ts): Runs transformContext first to curate context, then calls convertToLlm to encode into the provider's wire format—cleanly decoupling "context selection" from "protocol encoding."
  • Deep Agents (graph.py): Injects models and middleware at the assembly layer so vendor-specific branching never leaks into the core loop.
  • OpenAI (Agents Guide): Clearly distinguishes between low-level model APIs, the Agents SDK, and hosted runtime interfaces.

6. Additional Constraints for Streaming Responses

When streaming is enabled, the model returns text deltas and tool argument fragments in chunks. User-visible text can be rendered incrementally as chunks arrive, but tool calls must be reassembled in full by ID and pass JSON and schema validation before execution—truncated half-JSON left behind by a dropped network connection must never be passed into a tool function.

7. Error Retries & Model Switching

Invalid parameters, authentication failures, and context-length overflows are deterministic errors and must not be retried verbatim; rate limits (429) or transient network blips can be retried with backoff up to a small cap. When switching models across providers, re-encode from generic history messages and re-verify the context window budget rather than forwarding a previous vendor's proprietary encrypted continuation data to the new model.

8. Current Project Choice & Unimplemented Scope

  • Current project choice: Uses a unified internal request/response contract + LLMService connection manager + a single Chat Completions adapter (OpenAIChatModel), disables implicit SDK auto-retries, and keeps tool loop control in the local Runner (see Stage 1 and Stage 3).
  • Not yet implemented (extend on demand): Responses API adapter, streaming output, automatic backoff retries, multi-model routing, and circuit-breaker fallback.

9. Hands-on Exercise & Expected Outcomes

Read openai_chat.py and service.py, then run the model module unit tests:

uv run pytest tests/test_models.py tests/test_llm_service.py

Expected Outcomes:

  • Protocol decoupled from loop: Runner depends only on the Model protocol; adding or swapping a model adapter requires zero changes to Runner or any tool function (see test_models.py).
  • Continuation data preserved intact: Protocol continuation data, stop reasons, and token usage returned by the model are passed losslessly across multi-turn calls.
  • Controlled errors and lifecycle: Missing configuration, truncated output, model refusal, or calling a closed service raises an explicit error rather than silently swallowing exceptions (see test_llm_service.py).
