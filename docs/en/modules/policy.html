General Design Principles & Options · Current Implementation in Stage 2

Policy: Check Action Permissions Before Execution

1. Starting Problem: Why Must Permissions Be Checked Before Executing Tools?

As soon as an Agent is given tools that write files, delete files, or call external APIs, the model may propose dangerous operations due to misunderstood instructions or prompt injection from external documents. Consider this scenario:

  • User: "Summarize the reference notes and save the summary, without touching the original notes file."
  • Model: Calls write_file(path="notes.txt", content="..."), attempting to overwrite the original notes directly.
  • (System interception: Before touching the disk, Policy inspects the action, identifies it as "overwriting an existing file," and blocks execution immediately)

This is the core responsibility of the Policy module: evaluating a proposed action against security rules (Rules) to render an authorization decision (Decision) before any tool side effect occurs. Regardless of how the concrete implementation evolves, Policy must uphold four baseline invariants:

  • Judge by the actual action rather than the literal tool name: It must distinguish whether a call is "creating a new file (create)" or "overwriting an existing file (overwrite)," along with the exact target path.
  • Trust only authoritative rule sources: Decisions must rely solely on application configuration or explicit user confirmation; model-generated text or external documents read during execution can never grant permissions on their own.
  • Denials must block execution: Once Policy returns a denial, the underlying tool function must never run, following a strict "deny by default unless explicitly allowed" posture.
  • Execution must match the granted permission: If an action is approved as a "create," and the target file comes into existence right before the write occurs, the write must never silently downgrade into an "overwrite."

2. Black-Box Interaction: Action Request In, Authorization Decision Out

Using file-overwrite interception as an example, the black-box interface between the tool system and Policy exchanges just two data structures:

  • Input (ActionRequest): The specific operation and target resource to execute, e.g., ActionRequest(operation="overwrite", resource="summary.txt").
  • Output (PolicyDecision): Whether execution is allowed and the reason, e.g., PolicyDecision(allowed=False, reason="Overwriting existing files is not allowed").

Responsibility boundaries when collaborating with neighboring modules (for concrete Python code, see Stage 2):

  • Application entry point (Application): Injects permission rules and workspace configuration when initializing the tool registry.
  • Tool system (Tools): Validates arguments and identifies the actual action at runtime, calling Policy uniformly; if denied, generates a policy_denied receipt and returns it to Runner.
  • Context & State (Context / State): Context only manages model inputs, and State only records past receipts—the fact that an operation was approved in historical records never implies a new call in the current turn is automatically approved.

3. Implementation Options: How to Identify Actions & Evaluate Rules?

When implementing Policy, "how to extract an action from a tool call" and "how to evaluate rules to reach a decision" are two orthogonal design dimensions:

Dimension 1: How to Identify the Action from a Tool Call?

  • Declarative permission metadata at registration: Tools declare their required permission category (such as read / write) and path parameter name when registered, and shared registry code inspects filesystem state to build the ActionRequest automatically. Ideal when multiple tools share the same resource permission model.
  • Custom per-tool action extractor functions: Each tool supplies its own function to parse arguments and describe the action. Fits systems where resource shapes vary wildly across tools, at the cost of higher maintenance overhead.

Dimension 2: How to Evaluate Rules?

  • In-memory conditional branches: Evaluate directly in memory using configuration flags and allowlists. Simple, transparent, and ideal for early stages.
  • Declarative rule configuration: Express allow/deny conditions in config files matched by priority. Fits environments where rules change frequently, requiring conflict resolution and default fallback handling.
  • External policy service: Delegate authorization to a centralized external service. Fits enterprise-wide shared permissions across multiple applications, at the cost of network latency and high-availability requirements.

4. Current Project Choice & Unimplemented Scope

  • Current project choice: Uses registration-time permission declarations + shared action identification + centralized registry interception + in-memory conditional rule evaluation (for source walkthrough and hands-on commands, see Stage 2). By default, the CLI allows reading and creating files inside the workspace while forbidding overwriting existing files.
  • Not yet implemented (extend on demand): Declarative rule engines, interactive human-in-the-loop approval, short-lived capability tokens, and OS-level sandbox isolation.

5. Expected Outcomes

  • Permitted operations execute normally: When reading a file inside the workspace or creating a file that does not yet exist, Policy returns allowed and the operation completes.
  • Disallowed overwrites blocked with zero side effects: When attempting to overwrite an existing file, Policy returns policy_denied, the underlying write function never runs, and the original file remains untouched (see the Stage 2 overwrite-prevention experiment).
  • No downgrade under concurrent races: After an action is approved as a new file creation, if another process creates the target file before the write occurs, the underlying exclusive-create call fails immediately rather than silently turning into an overwrite.

6. Human-in-the-Loop Approval

When a human decision is required, execution can pause and present the exact action, target resource, and arguments. Right before executing an approved action, the system must still verify that the action has not changed and the approval has not expired. This fits high-stakes operations at the cost of managing wait states, identity verification, and resume flows.

7. Execution Isolation

Policy decides whether an action is approved; a sandbox restricts what executing code can actually access at the OS/container level. They serve distinct responsibilities. Spawning a subprocess alone does not guarantee filesystem or network isolation, and OS restrictions, containers, or microVMs must be configured to match the authorized scope rather than replacing domain-level Policy checks.

8. Scoped Capability Tokens

A trusted component can also mint short-lived tokens bound to a specific principal, action, target resource, and expiration time. This fits short-term delegation to workers or sub-agents, at the cost of managing revocation, expiry, concurrent use, and retries—it cannot be achieved merely by adding an approved=True parameter to a tool.

9. Untrusted Reference Material & Further Reading

External documents may contain prompt injections attempting to trick the model into proposing unauthorized actions. Instructing the model to ignore malicious instructions helps, but permissions must always be enforced programmatically—documents can never modify Policy rules. For source samples and design references, see Design Basis; for state management around waiting and resuming, see Session / State.
