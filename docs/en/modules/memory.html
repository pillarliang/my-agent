Module Principles & Design Options

Memory: Select Knowledge Retained Across Sessions

1. Starting Problem: What Information Is Worth Remembering Across Sessions?

Within a single session, Session / State preserves the complete conversation and tool transcript; however, when starting a brand-new session, we want the system to remember stable project facts and user preferences without carrying over transient errors from a previous task as permanent facts:

  • Knowledge worth retaining across sessions: E.g., "This project uses uv for dependency management" or "The user prefers data sources listed at the end of reports."
  • Transient state unsuitable as long-term memory: E.g., "A test failed a moment ago" or "Line 10 of a file has a temporary syntax error" (these are tightly bound to a specific moment and file revision and become stale as soon as code changes).

Memory: Controlled Writing, On-Demand Reading & Explicit Forgetting (Future Capability, Not Yet Implemented)

  • The write path decides "Is this worth remembering long-term?": Verifies provenance, applicable scope (user-level / project-level), and conflicts against existing entries before saving a versioned record after confirmation.
  • The read path decides "Does this apply to the current task?": Filters by user and project scope first, then retrieves relevant entries for Context Manager to assemble.
  • Lifecycle maintenance: Long-term memory must support superseding updates, expiration, and explicit deletion (forgetting); high vector similarity only indicates semantic closeness, not that an entry is still valid or authorized.

2. Module Collaboration: How Do State, Memory, and Context Divide Responsibilities?

  • Write path (State → Memory): When the user explicitly states "Always attach sources to reports from now on," or when candidate items are extracted from historical messages in State, Memory verifies the source record ID, scope, and confirmation criteria before persisting (model-extracted candidates must never be treated as established facts without verification).
  • Read path (Memory → Context Manager): When a new task starts, Memory returns candidate entries carrying provenance, version, and active status based on the current project and task cues, and Context Manager filters them within the token budget for the current turn's input.
  • Permission & error boundaries: If the model is allowed to call a tool to write memories, that call must still pass through Tools and Policy checks, and memory contents can never expand tool execution permissions; furthermore, the system must clearly distinguish between "no retrieval hits," "memory expired," and "storage query failed."

3. Decoupling Concepts: Separate "Knowledge Type" from "Storage Medium"

  • By knowledge type (governs lifecycle & reuse pattern):
    • Facts & preferences: Project environment conventions or user formatting rules; require provenance and scope tracking.
    • Episodic cases (Episodic): Past debugging successes or failure postmortems used as reference for similar future problems.
    • Reusable procedures (Procedural): Fixed multi-step workflows, which are usually better packaged as standalone Skills (see Extensions).
  • By storage & retrieval medium (governs engineering implementation; composable):
    • Markdown files: Ideal for direct human review, editing, and Git version control.
    • Relational database (SQLite): Ideal for structured metadata, versioning, scope filtering, and exact keyword search (FTS).
    • Vector index (Embeddings): Ideal for recalling semantically related candidates across large collections.

4. Comparing Core Approaches: 4 Memory Implementation Patterns

The approaches below cover storage/retrieval patterns (A–C) and write patterns (D), which can be combined on demand (none are wired up yet):

A. User-Maintained Index + Markdown Memory Files

  • How it works: List topics in a concise index file while storing full notes in Markdown files; load only the index overview on each run and read specific topic files on demand.
  • Best for: Single-user local development with a small number of memory entries that humans want to inspect and edit directly.
  • Trade-offs & limitations: Concurrent writes across sessions, scope isolation, and expiration cleanup require extra conventions; loading every file in full on every turn quickly crowds out the context window.

B. Structured SQLite Entries + Keyword Search (SQL / FTS)

  • How it works: Store entry ID, kind, scope, source references, version number, and status in relational tables, filtering by project, timestamp, and keywords (or full-text search FTS).
  • Best for: Scenarios requiring strict scope isolation, versioned updates, audit/undo trails, and exact terminology matching.
  • Trade-offs & limitations: Requires maintaining table schemas; pure keyword search may miss relevant entries when the user phrases a question with synonyms.

C. Vector or Hybrid Retrieval (Hybrid Search)

  • How it works: Generate embedding vectors for memory entries and combine scope filtering, recency filtering, keyword matching, and semantic search to recall candidates.
  • Best for: Large memory stores where the same concept may be phrased in many different ways.
  • Trade-offs & limitations: Adds embedding API calls, index rebuild overhead, and retrieval quality evaluation costs; furthermore, scope and permission filters must be applied before or during vector recall—never recall a global Top-K across projects first and filter afterward.

D. Model-Driven Extraction & Background Consolidation

  • How it works: At the end of a task or before context compaction, invoke a model to extract candidate memories from the conversation, updating the memory store after deduplication, conflict checks, and confirmation.
  • Best for: High-frequency conversation workflows where relying purely on manual human maintenance is impractical.
  • Trade-offs & limitations: Models can mistake guesses for facts or treat a one-off request as a permanent preference; record extraction versions and source IDs, start with human confirmation or easy rollback, and increase automation gradually.

File index & Markdown body Small knowledge base reviewed directly by humans Transparent, intuitive, easy to migrate Concurrent merges and scope management
SQL entries & keyword search Versioned updates, undo trails & strict isolation Precise filtering and explainable behavior Misses synonyms with different wording

5. Open-Source & Industry Implementation Comparison

  • Claude Code (Official Docs): Its memory documentation distinguishes user-maintained rule files from auto-memory; auto-memory maintains a size-bounded MEMORY.md index while reading detailed topic files on demand so users can inspect and edit them at any time.
  • Deep Agents (Source Verified): MemoryMiddleware loads memory files for a specified scope (user-level or agent-level) at startup and injects them at request time (see the official memory docs).
  • AgentScope Java (Official Docs): Its Memory design uses a two-stage flow—"append daily raw logs + periodically consolidate into long-term memory files"—and injects long-term memory into Context as reference material.
  • LangChain Store (Official Docs): Long-Term Memory Store organizes items by namespace (such as user ID and project ID) and key, supporting scoped search within a target namespace.

6. Recommended Data Schema

When implementing structured memory entries later, include scope, provenance tracking, version superseding, and confirmation status fields (design sketch; not yet created in code):

  • Program-managed metadata: id, scope, and version are generated by code, and source_ids point back to traceable session records.
  • Preventing model-forged confirmation: confirmed_by can only be populated by the application from genuine user interaction, never emitted freely by an extraction model.

7. Lifecycle Management: Updates, Forgetting & Expiration

  • Versioned updates (Supersede): When a fact or preference changes, mark the old entry's status as superseded and write a new version pointing to the old entry ID; read queries load only active entries.
  • Complete forgetting (Forget): Deleting a memory must simultaneously clean up primary storage, search indexes, and extraction watermarks. If you only delete the index entry without marking the source transcript, a background extractor may re-extract the deleted fact from old conversation history.
  • Expiration & permission boundaries: Set expiration timestamps (expires_at) on temporary facts; even if a memory entry says "the user previously approved overwriting files," it can never bypass runtime permission checks—all tool actions are still judged live by Policy.

8. Current Implementation & Unimplemented Scope

  • Implemented (as of Stage 3): Single-session JSONL persistent records and history continuation by session ID (see Stage 3).
  • Not Yet Implemented (deferred to Stage 5 On-Demand Extensions): Cross-session knowledge extraction, structured or vector memory stores, scoped retrieval, and memory update/forgetting interfaces.

9. Expected Outcomes (Future Long-Term Memory Exercise)

When integrating the Memory module in a later stage, verify it through cross-session and cross-project experiments.

Expected Outcomes:

  • Accurate cross-session reuse: A project preference saved in Session A automatically takes effect with source citations when starting Session B in the same project.
  • Strict cross-project isolation: Switching to another project workspace never leaks memory entries belonging to the previous project.
  • Superseded values stop taking effect: After a user updates a preference, new sessions inject only the latest version and never surface the superseded rule.
  • Forgotten entries stay forgotten: After executing a forget operation, both the primary entry and index are cleared, and subsequent auto-extraction does not resurrect it from old transcripts.
  • Permission boundaries remain intact: No memory content can enable write permissions that are disallowed by Policy.
