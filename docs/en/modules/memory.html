Memory: Select Knowledge Retained Across Sessions

1. What Should a New Session Know?

  • User, session A: “This project uses uv. Use uv run for Python commands.”
  • Model: “Understood.”
  • (End session A and create session B.)
  • User, session B: “How do I run the tests?”

Without earlier messages, the new session lacks that convention. Memory stores selected reusable knowledge separately and supplies it to later tasks. It does not change model parameters or load every conversation.

  • Keep: Confirmed project facts, lasting preferences, and verified lessons, e.g., “This project uses uv”.
  • Recheck: Test results, temporary errors, and specific line contents change as code evolves and cannot be treated as permanent facts; re-verify their latest state when referencing or debugging.

2. How Session, Memory, and Context Cooperate

  • Session records what happened: Questions, responses, and tool results for inspection or continuation.
  • Memory stores what is worth reusing: Selected facts or preferences with their source and applicable project or user.
  • Context constructs the current input: Combine the question, selected history, and applicable memory within the full request budget.

A task that uses memory can be divided into the following steps:

  1. Application chooses scope: Identify allowed sources from the workspace or user configuration.
  2. Memory supplies content: Return text and sources, optionally finding relevant entries when there are many.
  3. Context checks input: Count memory together with other content before sending.
  4. Model uses the reference: Proposed tool calls still go through Tools and Policy.

Users can maintain memory directly, or an extraction process can propose content from Session. Automatic history scanning is optional. Separate model candidates from confirmed facts. Text claiming permission cannot replace Policy checks.

No memory and a failed read are fundamentally different results. The former allows execution to proceed normally, while the latter must be handled explicitly according to application policy. Never write try...except Exception: return None to silently mask failures as absent memory:

  • No memory (expected clean absence): The file does not exist (catching FileNotFoundError) or contains only whitespace. The loader returns None, and execution proceeds normally without injecting reference messages.
  • Failed read (unexpected system error): The file exists but access is denied (PermissionError), encoding is corrupted (UnicodeDecodeError), a symlink escapes the workspace, or the path is a directory. Silently swallowing these errors causes project rules to vanish without notice. Handle them explicitly:
    • Fail-fast mode (used in this project): Raise the exception immediately before sending the first model request, stopping the task until the corrupted file or permission is fixed.
    • Tolerant warning mode (e.g., pi): If memory is purely advisory, log an explicit warning to the console or telemetry and flag the run as degraded, rather than pretending nothing went wrong.

3. Storage Media & Data Structures: From Plain Text to Multi-Dimensional Namespaces

Designing Memory begins with two structural decisions: what is worth storing and what data structures and storage media to use:

  • What to Store (Core Principle): Only keep reusable project facts and conventions (such as package managers or style rules) and verified troubleshooting lessons (symptoms, root causes, and fixes). Transient error logs, single lines of code, or ephemeral test runs should be re-inspected via tools on demand, not preserved as enduring memory; fixed multi-step execution workflows belong in a Skill.

Ordered from simplest to most feature-complete, four common storage formats and data structures prevail:

A. A Single Markdown File (e.g., <workspace>/MEMORY.md, CLAUDE.md)

Stored directly at the project workspace root (scoped to the current project) or in a user configuration directory (e.g., ~/.agent/MEMORY.md). Plain text is human-readable, easy to inspect or edit by hand, and trackable via Git for PR reviews. Ideal when a project has a compact set of core conventions.

B. An Index File Plus Topic Markdown Files (e.g., MEMORY.md + memories/*.md)

The main index keeps concise summaries and directory links, while detailed module notes or troubleshooting guides live in dedicated topic files. Useful when knowledge splits naturally by domain and a single file grows unwieldy.

C. Structured Tables & Hierarchical Namespaces (e.g., SQLite memories, LangGraph BaseStore)

Every memory is persisted as a structured record with metadata. Essential for multi-tenant platforms, multi-project isolation, programmatic concurrent access, and audit trails. A robust structured entry typically carries:

  • Source: The originating session ID, user task, or reference document URL for traceability.
  • Scope: Explicit boundaries (global user, team/org, or specific workspace) used as strict query filters.
  • Status: Active (active), replaced (superseded), or deleted (deleted) to prevent pulling obsolete rules.
  • Confirmation: Distinguishes user-verified facts from model-proposed candidates; unconfirmed model guesses must never act as hard constraints.

D. Vector Indexes & Hybrid Retrieval Stores (e.g., SQLite FTS + Embeddings)

Layers full-text inverted indexes and semantic embedding vectors on top of structured entries. Helpful when entries number in the thousands and phrasing diverges from stored text, at the cost of embedding computation, chunking, and retrieval tuning.

4. Core Mechanisms: Write Pipelines (Maintenance & Extraction) and Read Pipelines (Retrieval & Injection)

With data structures defined, an Agent must establish two operational pipelines: how knowledge is written and preserved (Write Pipeline) and how knowledge enters model context (Read Pipeline). Note that storage media and read/write execution actors are orthogonal choices.

4.1 Write Pipeline: How Is Knowledge Persisted?

Writing memory can be human-driven, model-driven, or automated in the background. Across Markdown and databases alike, writes follow three main channels:

  • Channel A: Direct Manual Editing & CLI Commands (Most Reliable, Zero Hallucination): When a user confirms a lasting convention, they edit MEMORY.md directly or execute /memory in the CLI. Note: A model verbally agreeing “Understood, I'll remember that” in chat only appends to SessionLog—it never silently modifies the physical memory file.
  • Channel B: In-Conversation Tool Calls by the Model (Instant, Governed by Policy): When a user instructs “remember this constraint”, the model emits a memory_write tool call, which persists only after passing Policy checks or explicit user consent.
  • Channel C: Post-Session Offline Reflection (Automated, Requires Denoising): After a task or session completes, a background reflection task scans SessionLog, extracts reusable facts, and writes them in batches without blocking active user interaction. Guardrails must prevent saving model hallucinations or transient errors as facts.
  • Unified Persistence Governance Gate: All channels must pass three checks before disk write: Scope Binding (restrict to project/user ID), Denoising (strip transient errors), and Conflict Replacement (mark superseded versions and record trace metadata).

4.2 Read Pipeline: How Does Knowledge Enter Model Input?

Saved knowledge must be assembled into model prompts at the appropriate moment to take effect. Three primary retrieval channels exist:

  • Channel 1: Full Load at Task Start (Default for Short Files, Zero Tool Overhead, Non-RAG): At the start of run_task(), the harness reads MEMORY.md in full, and Context Manager injects it as reference messages. It requires no preliminary tool calls from the model, though every request incurs token usage for the memory text. Best suited for short project rules under dozens of lines.
  • Channel 2: Dynamic Per-Request Retrieval (Classic Passive Pre-retrieval RAG, Best for Large Stores):
    • Technical Essence: Standard Retrieval-Augmented Generation (Pre-retrieval RAG) applied to agent memory.
    • Execution Mechanism: Before assembling each request, the outer framework filters by tenant/project scope, runs keyword search (FTS/BM25) or vector similarity (Embedding Top-K) against the user query, and injects only the most relevant memory snippets into the prompt.
    • Interaction Characteristic: Passive for the model, zero tool round-trips. The system quietly handles retrieval before calling the model, ideal for large multi-tenant knowledge bases with independent rule items.
  • Channel 3: On-Demand Tool Query by the Model (Progressive Disclosure + Agentic RAG, Best for Large Topic Docs):
    • Technical Essence: Combines Progressive Disclosure information architecture with Tool-Based Retrieval (Agentic RAG).
    • Execution Mechanism:
      • Tier 1 (Lightweight Table of Contents): The initial prompt injects only a compact topic outline or index (e.g. available rule modules), consuming minimal tokens so the model knows what knowledge exists.
      • Tier 2 (On-Demand Retrieval via Tools): When the model encounters domain-specific questions mid-run, it autonomously invokes read_memory(topic) for targeted reading, or formulates precise search queries for search_memory(query) to trigger underlying full-text or vector recall.
    • Interaction Characteristic: Active model-driven exploration, multi-hop capable. The model decides when, where, and what to search, refining queries when initial hits are insufficient. Ideal for complex architectural guides and extensive documentation.

4.3 Three Core Engineering Rules for Read/Write Harmony

  • Rule 1: Lock an Immutable Snapshot Within a Task: If memory files shift mid-run, Step 1 and Step 2 will observe conflicting rules, causing hallucination. Edits take effect on the next task; the active task remains pinned to its startup snapshot.
  • Rule 2: Enforce a Three-Tier Conflict Resolution Precedence: When rules collide, do not leave it to model chance. System instructions must declare: Current explicit user request > Currently loaded Memory default > Outdated default in past session history.
  • Rule 3: Stopping Injection vs. Rewriting History: Deleting a memory means stopping automatic injection into future tasks. It does not—and must not—rewrite or erase past exchanges recorded in SessionLog.

5. Memory Architectures Across Mainstream Agents: A Comprehensive Comparison

Different Agent systems adopt starkly different Memory architectures based on their operational environment, interaction goals, and memory lifecycles. Below is a systematic breakdown of five representative architectural paradigms grounded in pinned open-source code and official engineering mechanisms:

5.1 Paradigm 1: File Conventions & Hierarchical Directory Discovery (pi / Claude Code / Cursor)

This is the predominant and most lightweight approach for coding agents. Its core principle is: store knowledge directly in plain-text files without external databases, relying on OS directory tree hierarchies for rule inheritance and automatic discovery.

  • Storage Medium and Multi-Tier Scopes:
    • Global User-Level: Kept in the user home directory (e.g., ~/.claude/CLAUDE.md or ~/.pi/agent/), capturing universal developer preferences across all projects (e.g., “answer in concise style”, “use TypeScript strict mode by default”).
    • Project Repository-Level: Kept at the workspace root (e.g., CLAUDE.md, AGENT.md, .cursorrules), defining project-wide build commands, test workflows, and architectural boundaries.
    • Subdirectory & Path-Level: Kept in module folders (e.g., .claude/rules/*.md or .cursor/rules/*.mdc), activated dynamically via glob matching only when touching corresponding files.
  • Discovery and Loading Mechanics (pi Source Analysis):

    In pi, DefaultResourceLoader in resource-loader.ts recursively scans parent directories:

    1. Upward Discovery: Starting from cwd up through parent folders, combined with the global agentDir, it collects all context files into { path, content } pairs, logging warnings on read errors without crashing.
    2. System Prompt Construction: In system-prompt.ts, buildSystemPrompt() formats collected files into a dedicated projectContext section inside the system prompt.
  • Engineering Practice (Claude Code):

    Claude Code uses CLAUDE.md files and provides a /memory command to view and edit active memory in place. Newer versions also support prompting users to save verified conventions into project memory subdirectories (.claude/) upon detecting recurring project patterns.

  • Trade-Offs and Ideal Product Fit:
    • Best-Fit Products: Local developer tools and personal workspace agents (e.g., Claude Code, Cursor, CLI coding assistants, local document/research workflows) that run on persistent user machines where rules naturally live inside Git repositories.
    • Strengths: Highly transparent, zero external database dependencies, and natively trackable via Git for diffs, commits, and PR reviews.
    • Costs & Limitations: Lacks semantic retrieval. As files expand, injecting full text into system instructions consumes significant input token budget.

5.2 Paradigm 2: Middleware Interception & Virtual File Storage Decoupling (Deep Agents)

When running an agent on a personal computer (e.g., Cursor or Claude Code), the local disk is persistent, making it natural to read ~/.claude/CLAUDE.md. In stateless cloud-native containers, however, local scratch disks are destroyed after each run and follow-up requests may land on different nodes, so the runtime cannot rely on local files.

Deep Agents solves this with one core idea: disguise underlying storage as virtual Markdown files so the model reads and edits it with ordinary file tools, while middleware injects it into the system prompt at startup.

  • Where Data Actually Lives ("Files" Are an Illusion Decided by backend):

    To the model, memory always looks like a path plus Markdown text (by convention AGENTS.md, e.g., /memories/AGENTS.md). What write_file("/memories/AGENTS.md", ...) physically writes to depends entirely on the mounted backend:

    Mounted Backend Where Does Data Physically Live? Survives a New Session?
    StateBackend (Default) No disk file and no database—just a Python dict inside the current thread state (state["files"]) No (cleared on a new thread_id; single-session scratchpad only, not cross-session memory)
    FilesystemBackend A real AGENTS.md file on the host's local disk Yes (assuming the agent stays on the same persistent host)
    StoreBackend A key-value record inside a remote database (LangGraph BaseStore, e.g., Postgres / SQLite) Yes (shared across sessions and stateless containers)
    CompositeBackend (Path Router) Routes by prefix: e.g., /memories/ goes to persistent StoreBackend, everything else goes to ephemeral StateBackend Yes for /memories/; No for other paths
  • How It Reads, Layers, and Overwrites Memory:

    Deep Agents defines MemoryMiddleware in memory.py, sharing the same backend with standard file tools:

    1. Explicit Ordered Sources: Pass an ordered sources list at startup (e.g., global first, project/tenant later); later files appear later in the prompt and refine or override earlier defaults.
    2. Pre-Execution Fetch (before_agent): In before_agent(state), if memory is not yet in state, it fetches all sources via backend.read() into memory_contents.
    3. Request Injection (modify_request): In modify_request(request, state), it appends formatted memory text into SystemMessage.
    4. Overwriting via File Tools: Rather than inventing a dedicated update_memory() tool, the model calls standard write_file / edit_file on /memories/AGENTS.md. The router persists the change to StoreBackend, and the updated memory takes effect when the next session/thread starts.
  • Candid Assessment and Key Problems:
    • Realistic Verdict: No ideal standalone product fit—not recommended as a target architecture. It is a framework convenience compromise to reuse models' edit_file habits across local and cloud runtimes. Local tools are far cleaner with Paradigm 1; serious multi-tenant cloud products are far cleaner with Paradigm 4 or 5.
    • Core Problems (Where the Abstraction Leaks):
      • Worst of Both Worlds (Fake Filesystem on a Database): Loses real filesystem tooling (Git diffs, PR reviews, editors) while also forfeiting database strengths (schema validation, atomic field updates, TTL, concurrency locks—concurrent edit_file calls easily conflict or fail to match).
      • Hidden Routing Overhead: The same write_file call may mutate an in-memory dict, local disk, or Postgres depending on backend/prefix. Debugging is opaque, and models rely solely on prompt reminders to tell persistent paths from ephemeral ones.
      • Blurred Security Boundary: Sharing write tools between workspace files and system memory requires extra path-prefix policies to prevent accidental edits or prompt-injection tampering.
      • Fragmented Control Flow: Lifecycle middleware scatters prompt assembly across hooks, making final prompts harder to trace; sources must also be pre-configured instead of auto-discovered.

5.3 Paradigm 3: OS-Style Hierarchical Memory & Self-Management (MemGPT / Letta)

For perpetual, unbounded interactions, MemGPT (now Letta) borrows OS hierarchical storage—treating the context window as RAM and persistent databases as disk, while letting the model decide when to write and retrieve.

  • Where Each Tier Lives (All Backed by Persistent DBs—No Volatile "Cache"):

    In Letta, all tiers persist in a database (SQLite locally; PostgreSQL + pgvector in production), separated by purpose and query method:

    Archival Storage Vector DB (e.g., Postgres + pgvector) Externally ingested raw document chunks + model-written long-term notes Model calls archival_memory_search for semantic retrieval

    Core rule: no auto-sync exists between Recall and Archival; all data flows through Working Context.

  • Trade-Offs and Ideal Product Fit:
    • Best-Fit Products: Persona-driven, perpetual companions (AI companions, game NPCs, 1-on-1 tutors). Rarely copied in serious enterprise/productivity tools because autonomous self-editing is unpredictable.
    • Strengths: Breaks context limits for long-horizon persona evolution.
    • Costs: Heavily dependent on model judgment; risks polluting Core Memory with noise/hallucinations or adding latency via spurious searches.

5.4 Paradigm 4: Multi-Tenant Namespace & Semantic Key-Value Store (LangGraph Long-Term Memory)

In enterprise settings serving thousands of users across organizational units, multi-tenant isolation, permission scoping, and hybrid retrieval are critical. LangGraph's Long-Term Memory architecture provides a robust implementation.

  • Core Abstraction and Data Model (BaseStore):

    LangGraph introduces a cross-session BaseStore (backed by Postgres, Redis, etc.) using hierarchical (namespace, key, value) tuples:

    • Namespace Scoping: Namespaces route access cleanly:
      • User profile: ("users", user_id, "profile")
      • Team conventions: ("orgs", org_id, "teams", team_id, "rules")
      • Project documents: ("projects", project_id, "docs")
    • Hybrid Key-Value & Vector Search: Supports exact lookups via store.get(namespace, key) and semantic Top-K searches via store.search(namespace, query="...", limit=K) with vector embeddings.
  • Dual-Lane Writing Pipeline:
    • Online Lane (In-Loop Tool): Agents call memory-write tools during execution for immediate, user-requested updates.
    • Offline Lane (Background Reflection Node): After a conversation finishes, a background reflection node scans the session log, extracts verified facts, resolves preference conflicts, and batches updates into the store without increasing user wait time.
  • Trade-Offs and Ideal Product Fit:
    • Best-Fit Products: Enterprise SaaS and B2B multi-tenant business agents (customer support ticketing, CRM sales assistants, internal engineering/ops knowledge platforms) serving thousands of users and orgs with strict tenant isolation and hybrid exact + semantic queries.
    • Strengths: Precise multi-tenant boundaries, enterprise-grade access control, and hybrid key/vector retrieval.
    • Costs & Limitations: Heavy infrastructure requirements (databases, embedding pipelines, asynchronous worker orchestration).

5.5 Paradigm 5: Event-Driven Fact Extraction & User-Auditable Profiles (ChatGPT / Codex / AgentScope Java)

To remove configuration friction for non-technical users, consumer-facing assistants use automatic model-driven fact extraction paired with a visible user management dashboard.

Conceptually, this paradigm is equivalent to extracting only the human (user profile/preferences) half of Paradigm 3's Core Memory: dropping autonomous persona edits and model-driven search tools in favor of silent system management plus a user-controlled dashboard.

  • Two Key Refinements Over Paradigm 3:
    • Discrete Fact Items Instead of One Free-Text Block: Each preference is stored with its own ID so the UI can list every saved fact and let non-technical users delete individual items with one click.
    • Silent Pre-Injection Instead of Agentic Search Tools: The backend filters and injects relevant facts before calling the model, keeping latency low and behavior predictable without extra tool turns.
  • Mechanisms and Workflow:
    1. Implicit Extraction & Event Emission: When a user states an enduring preference (e.g., “I use macOS and prefer Python 3.12”), the model emits a structured Memory Update Event.
    2. UI Feedback & Management Dashboard: The UI displays a notification (e.g., “Saved to memory”). Users can inspect all saved fact items in settings, edit them, or delete stale entries.
    3. Selective Context Injection (Assembling Input on Demand):

      Over time, a user may accumulate dozens or hundreds of facts (e.g., “owns a cat”, “prefers concise code”, “uses Python 3.12”). Dumping all facts into every request wastes token budget and distracts the model. The system applies selective filtering and compact injection:

      • Filtering Strategy (Relevance vs. Full Bundle):
        • When many facts exist (Relevance Retrieval): For coding prompts, semantic search pulls only programming-related preferences; pet/lifestyle facts are ignored (the exact pattern of Channel 2 Pre-retrieval RAG).
        • When few facts exist (All Active Facts): If a user has only a handful of facts, all active and un-superseded items are bundled directly.

6. Project Choice: One Manually Maintained File

Stages 0–5 implement session persistence, continuation, context budgets, and project memory. Stage 5 uses a user-edited MEMORY.md at the workspace root, read at task start, with source and text counted in the budget and one snapshot per task.

A few project conventions can be checked directly without first solving extraction accuracy or retrieval quality. See Stage 5 integration for initialization, source entry points, and runtime behavior; file loading is in memory.py.

7. Expected Outcomes

  • Cross-session reuse: A new session receives project knowledge without all previous conversation history.
  • Clear scope and source: Identify which project's material was read.
  • Effective corrections: New tasks no longer load old content from memory after edits or deletion.
  • Budgets and permissions: Count memory in input; keep tool execution under Policy.
