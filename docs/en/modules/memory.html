Memory: Select Knowledge Retained Across Sessions

1. What Should a New Session Know?

  • User, session A: “This project uses uv. Use uv run for Python commands.”
  • Model: “Understood.”
  • (End session A and create session B.)
  • User, session B: “How do I run the tests?”

Without earlier messages, the new session lacks that convention. Memory stores selected reusable knowledge separately and supplies it to later tasks. It does not change model parameters or load every conversation.

  • Keep: Confirmed project facts, lasting preferences, and verified lessons.
  • Recheck: Test results, temporary errors, and current file contents. These observations can become outdated.

2. How Session, Memory, and Context Cooperate

  • Session records what happened: Questions, responses, and tool results for inspection or continuation.
  • Memory stores what is worth reusing: Selected facts or preferences with their source and applicable project or user.
  • Context constructs the current input: Combine the question, selected history, and applicable memory within the full request budget.
  1. Application chooses scope: Identify allowed sources from the workspace or user configuration.
  2. Memory supplies content: Return text and sources, optionally finding relevant entries when there are many.
  3. Context checks input: Count memory together with other content before sending.
  4. Model uses the reference: Proposed tool calls still go through Tools and Policy.

Users can maintain memory directly, or an extraction process can propose content from Session. Automatic history scanning is optional. Separate model candidates from confirmed facts. Text claiming permission cannot replace Policy checks.

No memory and a failed read are different results. Handle failures explicitly according to the application contract.

3. Where Is Memory Stored? (Four Common Storage Locations)

Designing Memory starts with two questions: what is worth storing and where it lives:

  • What to store: Only keep reusable project facts and preferences (such as dependency tools or coding conventions) and verified troubleshooting lessons (symptoms, root causes, and fixes). Once a procedure becomes a fixed, repeatable workflow, package it as a Skill instead.

Ordered from simplest to most complex, Memory is commonly stored in four places:

A. A Single Project or Global Markdown File (e.g., <workspace>/MEMORY.md, AGENTS.md)

Stored directly at the project workspace root (scoped to the current project) or in a user config directory such as ~/.agent/MEMORY.md (scoped across the user's projects). Plain text is easy to inspect, edit by hand, and track in Git—ideal when you have a concise set of core project conventions.

B. An Index File Plus Topic Markdown Files (e.g., MEMORY.md + memories/*.md)

The main file holds a short directory and one-line summaries, while detailed module notes or troubleshooting records live in separate topic files. Useful when knowledge splits naturally by topic and a single file would grow too large.

C. A Structured Database Table (e.g., a SQLite memories Table)

Each memory is stored as a row with fields such as id, scope, content, source, status, and updated_at. Useful when you need exact filtering by project or status, correction audit trails, or concurrent programmatic writes.

D. A Vector Index or Hybrid Retrieval Store (e.g., SQLite FTS + Embeddings)

Adds full-text and semantic vector indexes on top of structured entries. Useful when entries are numerous and user phrasing varies widely from the stored text, at the cost of embedding generation, index maintenance, and retrieval evaluation.

4. When and How Does CRUD Happen?

Once the storage location is chosen, you must define when each Create, Read, Update, and Delete (CRUD) operation happens and who executes it. Note that where memory is stored and who writes it (manual edit vs. model tool vs. background extraction) are independent choices:

Create: When Is Memory Added, and Who Writes It?

  • Option 1: User edits the file manually (simplest and most reliable): When the user confirms a lasting convention (e.g., “use uv run in this project”), they write it into MEMORY.md. Note that the model saying “Understood, I'll remember” in chat only appends to SessionLog—it does not modify MEMORY.md.
  • Option 2: Model calls a memory tool during conversation: When the user says “remember this rule”, the model proposes a memory_write or file-write tool call, which is persisted after passing Policy checks or user confirmation.
  • Option 3: Background extraction after a session or turn ends: A background job scans SessionLog and extracts reusable facts into the memory store. This saves manual upkeep but requires safeguards against storing unverified model guesses or duplicate entries.

Read / Query: When Is Memory Read, and How Does It Enter the Request?

  • Option 1: Load the full file at task start (best for short files): At the start of run_task(), the application reads workspace/MEMORY.md in full and passes it to Context as a source-labeled reference message inside ModelRequest. It is predictable and does not rely on the model calling a file tool first, though every request pays the full token cost.
  • Option 2: Query by keyword or vector before each request (best for DB / vector stores): Before assembling Context, filter by project scope and retrieve the Top-K entries matching the current user prompt, injecting only the matched items.
  • Option 3: On-demand tool reads by the model (best for index + topic files): Inject only the short index at task start; when the model needs details on a specific topic, it calls a read or search tool on demand.

Update: How Are Conventions Corrected, and Which Source Wins on Conflict?

  • File-based approach: Edit the text in MEMORY.md directly. To keep multi-step tasks consistent mid-run, lock the snapshot read at task start for all steps in the current task; edits take effect on the next task.
  • Database / index approach: Update the entry by id and refresh search indexes, or mark the old entry superseded and insert a new version to preserve history.
  • Conflict resolution priority: When old conversation history (SessionLog) still mentions an outdated convention while the newly read Memory has been updated, system instructions must enforce a clear priority order: Current explicit user request > Currently loaded Memory > Outdated default in conversation history.

Delete / Forget: When Is Memory Removed, and What Is the Boundary?

  • File-based approach: Delete the outdated lines or remove/empty MEMORY.md; starting with the next task, that content is no longer injected.
  • Database + automatic extraction approach: Mark the entry deleted, remove it from search indexes, and prevent background extractors from re-extracting the same fact from old SessionLog files.
  • Boundary of deletion: Deleting Memory stops automatic injection in future tasks, but it does not rewrite or erase past Q&A exchanges already recorded in old SessionLog files.

5. Source Comparison: pi and Deep Agents

Both provide persistent project background from files. pi calls these project context files; Deep Agents uses MemoryMiddleware. This comparison concerns how files reach model input, without implying automatic extraction or a structured memory database.

pi: Discover Context Files by Directory

  1. Configuration and data: The resource loader uses cwd and agentDir, collecting global and ancestor sources as path/content pairs.
  2. Input construction: buildSystemPrompt() takes loaded files and places paths and text in project context within the system prompt.
  3. Read failures: The directory loader logs a warning on read errors. An application can instead choose to fail explicitly.

Pinned references, commit 9d2ec7f: discovery and reading, input construction.

Deep Agents: Configure Explicit Sources

  1. Configuration and data: MemoryMiddleware takes backend and sources, keeping path-keyed memory_contents.
  2. Runtime: before_agent() downloads sources if memory is absent from state. By default, model-call wrappers use modify_request() to append formatted memory to the system message.
  3. Failures and refresh: Missing files are skipped; other download errors raise. Existing memory state prevents reloading in this hook, so visibility of edits depends on state refresh.

Pinned references, commit 97f856d: constructor, loading, request modification.

Tutorial interpretation: Discovery supports inherited conventions but requires clear scope and ordering. Explicit sources give direct control but require configuration and refresh management. In both cases, saving a file is insufficient until its contents reach model input.

6. When Do Structured Entries Help?

A short manual file can use its path as the source and its workspace as the scope. Add entry structures when per-item queries, corrections, or automatic consolidation require them.

Metadata for extraction and structured storage
  • Source: Original session, task, or document location.
  • Scope: Applicable user or project, enforced when querying.
  • Status: Active, replaced, or deleted content.
  • Confirmation: Distinguish user-provided facts from model candidates; a model cannot confirm on the user's behalf.

Add version links when retaining correction history and expiry when facts have a known lifetime. These fields serve particular behaviors, rather than defining a universal memory schema.

7. Three Core Boundaries in Correction and Forgetting

Whether using files or a database, handling corrections and deletions requires keeping three core boundaries clear:

  • Lock an immutable snapshot within a single task: If memory files shift mid-task, Step 1 and Step 2 will see conflicting project rules, triggering confusion or hallucination. Edits must take effect on the next task, keeping the current task pinned to its initial snapshot.
  • Enforce a three-tier conflict resolution priority: When old and new conventions collide, do not rely on luck. System instructions must define the precedence: Current explicit user request > Currently loaded Memory default > Outdated default in conversation history.
  • Distinguish stopping injection from rewriting history: Deleting a memory simply means stopping automatic injection into future tasks. It does not—and should not—alter or erase past Q&A records already saved in SessionLog.

8. Project Choice: One Manually Maintained File

Stages 0–4 implement session persistence, continuation, and context budgets. Memory is not implemented. Stage 5 selects a user-edited MEMORY.md at the workspace root, read at task start, with source and text counted in the budget and one snapshot per task.

A few project conventions can be checked directly without first solving extraction accuracy or retrieval quality. See Stage 5 integration for initialization, source entry points, and proposed runtime behavior.

9. Expected Outcomes

  • Cross-session reuse: A new session receives project knowledge without all previous conversation history.
  • Clear scope and source: Identify which project's material was read.
  • Effective corrections: New tasks no longer load old content from memory after edits or deletion.
  • Budgets and permissions: Count memory in input; keep tool execution under Policy.
